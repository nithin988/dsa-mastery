Chapter 2 of 9The ShopKart story

One server is not enough

One server has a ceiling. A load balancer lets many servers share the work, survive a crash and be updated without anyone noticing, and it starts with one idea: customers see one address.

about 15 minutes4 steps4 real experiments3 interview questions

1Launch day, 12:05The story

ShopKart launches at noon with an email to 200,000 subscribers. The founders did their napkin sums in chapter 1: about 35 requests a second on a normal day, and one server that can answer about 100 a second. They feel safe with the single server they bought.

At 12:05 the traffic peaks at 260 requests a second, two and a half times what the server can answer. Its CPU sits at 100%, requests queue up, pages that took 80 milliseconds now time out, and visitors see an error page. A founder refreshes the site on a phone and watches it fail, on the one day that matters most.

By 12:30 they add a load balancer and three more servers. The same traffic now spreads across four machines, each handling about 65 requests a second, and the errors stop. That afternoon they also learn that a balancer is useful for more than speed: it hides a dead server, and it lets you update servers one at a time.

2The idea: one address, many serversThe idea

A load balancer is a front door. It receives every request at one address and hands each one to a healthy server behind it, so capacity can grow by adding machines and one failure does not take the shop down.

This is called horizontal scaling: more machines, not a bigger machine. It works best when the servers are stateless, meaning any server can answer any request. Real systems use balancers like nginx and HAProxy (software you run yourself) or a cloud load balancer, and often put them at several layers.

3How it works, step by stepHow it works

  1. Put one front door in front of many servers

    Customers talk to one address. A load balancer receives every request and passes it to one of several identical servers behind it. Adding capacity then means adding a server, not buying a bigger one.

  2. Choose who gets the next request

    Round robin hands requests out in turn: A, B, C, A, B, C. Least connections gives the next request to the server with the fewest requests in progress, which copes better when some requests are slower. Hashing sends the same user to the same server each time.

  3. Check that servers are healthy

    The balancer probes every server every fraction of a second. A server that fails a couple of probes is taken out of the rotation, and put back once it passes again. Customers never see the dead server.

  4. Keep the servers interchangeable

    If a server remembers your login or cart in its own memory, the balancer must always send you back to it. Instead keep that state in a shared store (a cache or the database), so any server can handle any request, and a server can disappear without anyone noticing.

1Round robin: who answers nine requests?

A real nginx reverse proxy in front of the three backends. upstream app { ... } lists the servers and proxy_pass http://app sends every request to that group. nginx -t checks the configuration before it is used (always do this). The clients talk to one address, port 8180, and the requests rotate over the three servers in order: round robin, nginx's default.

2A slow server: round robin versus least connections

The experiment that shows why the algorithm matters. Backend C is deliberately slow (0.5 s per request); the others answer instantly. Sixty requests arrive, twelve at a time. Round robin blindly gives C a third of them. Least connections notices that C always has requests stuck in progress and sends it far fewer, so the fast servers do most of the work and the whole batch finishes sooner.

3Kill a server and watch the health check

Active health checks with real HAProxy. HAProxy probes every server every 300 ms (check inter 300ms), marks one DOWN after 2 failures (fall 2) and UP after 2 successes (rise 2), and publishes the state on its stats page, read here as CSV. Within about a second of B being stopped it is DOWN and requests flow only to A and C. When B returns it passes two probes and rejoins automatically. The status column is the 18th field of the stats CSV.

4Reload the balancer's settings with no failed requests

A zero-downtime change. While 120 requests are flowing, the configuration is changed to take server B out of rotation (down) and nginx is told to reload (kill -HUP). New worker processes start with the new configuration; the old workers finish their in-flight requests and exit. Result: no request failed, and from then on only A and C answer. This is how you drain a server before updating it.

5How it breaks in productionFailure modes

The balancer is a single point of failure

One balancer in front of many servers just moves the weak spot. Run two, and share one address between them or use a cloud balancer that is already redundant.

Not enough spare capacity

ShopKart's four servers handle 260 requests a second at about 65 each. If one dies, the other three take 87 each, close to their limit of 100. Plan for one more server than you need.

A shallow health check

A check that only asks "does the port answer?" passes while the application cannot reach its database. Make the check test what the server really needs.

Even by count is not even by load

Round robin gave 20, 20, 20 even with a slow server C, so every third customer waited. Least connections gave C only 3 of 60. Pick the algorithm that fits how uneven your requests are.

Sticky sessions and hot servers

Sending each user to the same server fixes memory-based logins, but a few busy users can overload one server while others sit idle. Prefer shared state and keep stickiness as a last resort.

Deploys that drop requests

Restarting a server that is still serving traffic breaks requests in flight. Take it out of rotation, let it finish, update it, check it, put it back. The reload test above lost none of 120 requests.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A basic question reported by candidates at many companies, not official.

"You have three web servers behind one address. Describe how requests get distributed and what happens when one dies."

A basic but revealing question. They want to hear the components, the decision, the failure behaviour and the cost, not just "add a load balancer".

Ask first

  • Is the application stateless? If sessions live in each server's memory, any server cannot answer any request, and the balancer must keep a user on the same server (sticky sessions) or the state must move to a shared store.
  • HTTP traffic, or something else (a database, a game server)? HTTP suggests a layer 7 proxy; arbitrary TCP suggests layer 4.
  • Do we need to survive a whole data centre failing? That adds DNS or global balancing across regions on top of the local balancer.

How to think about it

  1. Say what the balancer is and why we want it.One address for clients, capacity by spreading load, availability by routing around failures, flexibility by changing servers behind it.
  2. Choose the layer.For a web application a layer 7 reverse proxy (nginx, HAProxy, a cloud application load balancer) gives TLS termination, path routing and header handling. For raw TCP or maximum throughput, layer 4.
  3. Choose the algorithm and justify it.Round robin when requests cost about the same; least connections when they vary; hashing when a user or key should stick to a server (cache locality). Start simple.
  4. Describe failure detection.Health checks: active ones probe each server every second or so and mark it down after a few failures; passive ones notice failed requests. The balancer stops sending to a down server and retries idempotent requests on another.
  5. Remove the single point of failure.The balancer is now critical, so run at least two behind a shared address (virtual IP) or use a managed service that is redundant for you.
  6. Close with deployment and operations.Remove a server from rotation (drain) before updating it, so in-flight requests finish; add capacity by adding servers; watch per-server error rates and latency.

How to say it

A model answer, about two minutes aloud

"Clients connect to one address that belongs to a load balancer. I would use a layer 7 reverse proxy because this is HTTP: it terminates TLS, can route by path, and forwards each request to one of the three servers using round robin to start, or least connections if request times vary a lot. The servers must be stateless, with sessions and data in shared storage, so any server can serve any request.

The balancer health-checks the servers, for example every second, and marks one down after two or three failures; from then on traffic only goes to the healthy ones, and idempotent requests that fail on a dying server are retried on another. That means one server dying costs a few seconds of reduced capacity and, at worst, a handful of failed requests, not an outage.

The balancer itself must not be a single point of failure, so I would run two sharing a virtual IP or use a managed load balancer, and for deploys I would drain a server before updating it. I would monitor per-backend error rate and latency to spot an uneven or unhealthy server early."

Likely follow-ups

What if the three servers have different capacities?

Use weighted balancing (give the big server a larger weight) or least connections, which adapts on its own.

Why not just use DNS with three addresses?

DNS cannot see health, clients and resolvers cache the answer for the TTL (so a dead server keeps receiving traffic), and the spread is crude. DNS is good for picking a region, not for fine-grained balancing.

Does the load balancer add latency?

Yes, a little: an extra hop and some processing, typically well under a millisecond inside a data centre. It usually saves time overall through connection reuse and by avoiding overloaded servers.

Common slips

  • Saying "a load balancer" without a layer, an algorithm or a failure story.
  • Forgetting that the balancer is itself a single point of failure.
  • Ignoring statelessness: sticky sessions hide a design problem.
A common follow-up when you say "I would add a load balancer": reported by candidates, not official.

"Round robin, least connections or consistent hashing: how do you choose?"

They give you three scenarios: stateless API with uniform requests, an image-resizing service with very uneven request times, and a cache cluster keyed by user. Which algorithm for each, and why?

Ask first

  • How much do request costs vary? That is the whole question for round robin versus least connections.
  • Do we need the same key to reach the same server? Caches and session affinity are the reasons to hash.
  • How often do servers join and leave? Frequent changes make consistent hashing worth its complexity.

How to think about it

  1. Start with the simplest that fits.Uniform, stateless requests: round robin (or weighted if servers differ). Simple and predictable.
  2. Look for variance.The image resizer has requests from 20 ms to 5 s: round robin will pile heavy ones onto unlucky servers; least connections spreads by actual load. Mention you would verify with per-server latency percentiles.
  3. Look for locality.A cache cluster keyed by user wants the same user on the same node so hits are possible: hash by user ID.
  4. Show you know the catch of hashing.With plain modulo, changing N moves almost every key and empties the caches; consistent hashing with virtual nodes limits movement to about 1/N and spreads load evenly.
  5. Mention hot keys.Hashing can overload one server if one key (a celebrity user) is hot: cache that key at the edge, split it, or fall back to load-aware balancing.
  6. Say how you would know it works.Per-server request rate, connections and latency; the spread should be even in load, not just in count.

How to say it

A model answer, about two minutes aloud

"For the stateless API with uniform requests I would use round robin, weighted if the servers differ in size: it is simple and the load is even. For the image resizer, where request times vary enormously, round robin would give some servers a run of heavy jobs, so I would use least connections, which adapts to how busy each server really is. For the cache cluster keyed by user, I want the same user to hit the same node, so I would hash on the user ID.

The catch with simple hashing is that when a node is added or removed, hash mod N remaps almost every key and the caches go cold, so I would use consistent hashing with virtual nodes, which moves only about one over N of the keys and keeps the load even. A hot key can still overload one node, so I would watch per-node load and cache or replicate very hot keys.

In all cases I would confirm with per-server request counts, connections and latency percentiles, because even by count is not the same as even by load."

Likely follow-ups

What are virtual nodes?

Each physical server appears at many positions on the ring (for example 100). This evens out the share each server gets and, when a server leaves, spreads its keys across all the others instead of dumping them on one neighbour.

How would you drain a server using these algorithms?

Set its weight to zero or mark it down so no new requests arrive, wait for in-flight requests to finish, then stop it.

What is power of two choices?

Pick two servers at random and send the request to the one with fewer connections. It gets most of the benefit of least connections with far less coordination, which matters in large distributed balancers.

Common slips

  • Choosing hashing for "fairness": it gives stickiness, not even load.
  • Describing round robin as perfectly balanced without mentioning uneven request cost.
An operational question often reported for senior roles: reported by candidates, not official.

"How do you deploy a new version of a service behind a load balancer with zero downtime?"

Walk through a rolling deployment, including what could go wrong at each step.

Ask first

  • How many servers, and is there headroom to take one out? Rolling deploys reduce capacity by one server at a time; with three servers that is a third, which must be affordable.
  • Do requests last long (uploads, websockets)? Long-lived connections need a longer drain time or a way to move clients.
  • Is the new version backward compatible with the database and with the old version running alongside? During a rolling deploy both versions serve traffic at once.

How to think about it

  1. State the principle.Never stop a server that is still receiving traffic: take it out of rotation first, let it finish, change it, verify it, put it back.
  2. Step through it.1) Mark server 1 as draining: no new requests. 2) Wait until its active connections reach zero or a timeout (for example 30 s). 3) Stop it, deploy the new version, start it. 4) Wait for the health check to pass (and ideally a warm-up request). 5) Return it to rotation. 6) Watch error rate and latency for that server compared with the old ones. 7) Repeat for the next server.
  3. Name what can go wrong.Capacity dip if too many are out at once; a new version that passes the health check but misbehaves (so use a canary: one server or 1-5 percent of traffic first, with automatic rollback on error rate); incompatible database changes (use expand and contract migrations); cache warm-up making the first requests slow.
  4. Mention alternatives.Blue-green: a full second environment, switch the balancer to it, instant rollback by switching back. Canary releases through weighted balancing.
  5. Mention the proxy's own configuration changes.Reload rather than restart (graceful), and validate with nginx -t first.

How to say it

A model answer, about two minutes aloud

"I would do a rolling deployment, one server at a time. First I take server one out of rotation so it gets no new requests, then wait for its in-flight requests to finish, up to a timeout. Then I deploy and start the new version, wait until the health check passes, and put it back. I watch that server's error rate and latency against the others before moving on to the next. The principle is never to stop a server that is still receiving traffic.

What can go wrong is a dip in capacity if I take out too many at once, a new version that passes the health check but is actually broken, and database changes that are not compatible with the old version, which is still running alongside during the rollout. So I make migrations backward compatible, start with a canary on a small share of traffic with automatic rollback if the error rate rises, and keep headroom.

Blue-green deployment is an alternative: stand up a complete new environment and switch the balancer over, which gives instant rollback at the cost of double capacity for a while."

Likely follow-ups

What is connection draining?

Telling the balancer to stop assigning new requests to a server while letting existing connections complete, usually with a timeout after which remaining connections are closed.

How do you roll back?

Rolling: redeploy the previous version the same way, so keep the old artifact. Blue-green: point the balancer back at the old environment. Both depend on the database changes being compatible with both versions.

A health check passes but users see errors. Why?

The check is too shallow (it tests that the port answers, not that the application can reach its dependencies), or the problem only shows under real traffic. Use deeper checks and judge canaries by real error rates.

Common slips

  • Restarting servers in place with no draining.
  • Deploying to all servers at once.
  • Not mentioning database compatibility during the overlap.

8Remember thisRecap

The page in 6 lines

  • A load balancer gives customers one address and spreads requests over many identical servers.
  • More servers (horizontal scaling) is how you grow, but only if servers are stateless.
  • Round robin is even by count; least connections is even by load when requests differ.
  • Health checks take a dead server out of rotation within a second or so, so customers see no errors.
  • Reload or drain before you change anything: a graceful reload dropped none of 120 requests.
  • The balancer itself needs a spare, and the servers need one spare server of capacity.

Check yourself

What does a load balancer give you besides speed?

Resilience (a dead server is skipped) and safe deploys (take servers out one at a time).

When is least connections better than round robin?

When requests take very different times, so equal counts would not mean equal load.

Why keep servers stateless?

Any server can answer any request, so servers can be added, removed or fail without losing users' logins or carts.
