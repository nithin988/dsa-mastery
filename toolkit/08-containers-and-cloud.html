Boxes inside boxes

A container is an ordinary program with a private view of the machine and a ceiling on what it may use. Learn how that works, how to build small fast images, and how to give each box only the permissions it needs.

about 20 minutes4 steps4 real experiments3 interview questions

1Sunday, 1:48 a.m.The story

ShopKart has just added photo uploads, and Priya wrote a small program, the resizer, that shrinks each photo. It works perfectly on her laptop. On the shop's one server it needs a different version of an image library from the one the checkout code uses, so you install both side by side, carefully, and tell nobody. "It works on my machine" is now true on two machines.

At 1:48 a.m. the pager goes off: checkout is down. The memory dial is at 100%. A customer uploaded a huge photo, the resizer kept asking for more memory, and Linux, to keep the machine alive, stopped the largest program it could find. That was checkout, not the resizer. Your own program killed the thing that earns money.

By morning the fix is clear: give each program its own box, with its own files and a memory ceiling, so a runaway stops alone. That box is a container. Two more rules make containers safe in the cloud: build the package so that rebuilds are quick, and give every box only the permissions it needs. This chapter covers all three.

2The idea: a private view and a ceilingThe idea

A container is not a tiny computer. It is an ordinary process that the Linux kernel has given a private view (its own process list, hostname, network and files) and a ceiling (a limit on memory and CPU).

Because containers share the machine's kernel, they start in a fraction of a second and cost almost nothing to run. The price is weaker isolation than a virtual machine, which carries a whole kernel of its own. That trade is why containers suit your own services, and why the permissions you give them matter so much.

3How it works, step by stepHow it works

  1. A private view and a ceiling

    A namespace gives a process its own view of one thing: its own list of processes, its own hostname, its own network. Inside, the first process is number 1 and the machine seems to be its own. Limits cap what a process may use. In the recorded run a process that asked for 400 MB under a 150 MB ceiling got an error, and nothing else was harmed.

  2. An image is stacked layers

    An image is the finished package your container starts from. It is a stack of read only layers, each named by a hash of its contents, so the same contents always get the same name. Two images on the same base store that base only once.

  3. Order the build for the cache

    A build step is reused only if it and every step before it are unchanged. Put slow steps that rarely change (installing dependencies) first, and the code you edit all day last. Then a one line change rebuilds one cheap step instead of a 60 second install.

  4. Give each box only the permissions it needs

    In the cloud, IAM (identity and access management) says who may do what to which resource. The safe rule is default deny: nothing is allowed unless a policy allows it, and an explicit deny always beats an allow.

1A box and a ceiling, built in four commands

The building blocks of a container, as an ordinary user. In a new PID namespace the shell is process 1 and the process list shows only its own children: a container's "private machine". A new UTS namespace lets it set its own hostname without changing the host's. A new network namespace starts with only a loopback interface: no connectivity until something is wired in. And a memory limit turns a 400 MB allocation into a MemoryError instead of exhausting the host. Docker automates exactly these steps, adds an image filesystem, and applies cgroup limits.

2Layers named by their contents, and shared

Layers are just archives named by their hash. The base layer has one hash no matter which image uses it, so both images point at the same layer and the machine stores and downloads it once. Rebuilding the base from identical files reproduces the same hash (the tar options fix timestamps and owners so the archive is deterministic), which is what makes the cache and registry work: identical content means identical identity.

3The same code change, in a good and a bad build order

Why instruction order decides build time. With the good order, the dependencies are installed in a layer that depends only on requirements.txt, so changing one line of source rebuilds only the last copy step and reuses the 60-second install from the cache. With the bad order, copying the whole source tree first means any source change invalidates that layer and everything after it, so the slow install runs again on every build. The same rule applies to any layered build cache: put what changes least first.

Show the command and the full explanation
python3 - <<'EOF'
import hashlib
def build(steps, cache):
    """steps: list of (instruction, content_hash). A step is reused only if it and every step before it are unchanged."""
    ran, parent = [], ''
    for instr, content in steps:
        key = hashlib.sha256((parent + instr + content).encode()).hexdigest()[:8]
        if key in cache: ran.append('cached  ' + instr)
        else: ran.append('REBUILD ' + instr); cache.add(key)
        parent = key
    return ran
good = lambda src, deps: [('FROM base-os', ''), ('COPY requirements.txt', deps), ('RUN install dependencies (60 s)', deps), ('COPY src/', src)]
bad = lambda src, deps: [('FROM base-os', ''), ('COPY . (source and requirements)', src + deps), ('RUN install dependencies (60 s)', src + deps)]
for name, f in (('good order: dependencies first, source last', good), ('bad order: copy everything first', bad)):
    cache = set(); build(f('src-v1', 'deps-v1'), cache)
    print(name)
    r = build(f('src-v2', 'deps-v1'), cache)
    print('  after changing one line of source:'); [print('     ', x) for x in r]
    print('  slow steps rebuilt:', sum('60 s' in x and x.startswith('REBUILD') for x in r))
EOF

4Default deny, step by step

The two rules that explain most IAM behaviour. A request is allowed only if some statement allows that action on that resource; if nothing matches it is denied by default (writing to the images bucket, deleting an upload, querying a database the role was never given). Reading an image is allowed, but reading under the private/ prefix is blocked by an explicit deny, which beats the allow that would otherwise cover it. Real policy languages add conditions and principals, but the evaluation order is the same.

Show the command and the full explanation
python3 - <<'EOF'
from fnmatch import fnmatch
POLICY = [
    {'effect': 'Allow', 'action': 'storage:Get*', 'resource': 'bucket/shop-images/*'},
    {'effect': 'Allow', 'action': 'storage:Put*', 'resource': 'bucket/shop-uploads/*'},
    {'effect': 'Deny',  'action': 'storage:*',    'resource': 'bucket/shop-images/private/*'},
]
def allowed(action, resource):
    matches = [s for s in POLICY if fnmatch(action, s['action']) and fnmatch(resource, s['resource'])]
    if any(s['effect'] == 'Deny' for s in matches): return 'DENY (an explicit deny always wins)'
    if any(s['effect'] == 'Allow' for s in matches): return 'allow'
    return 'DENY (nothing allows it: denied by default)'
for a, r in (('storage:GetObject', 'bucket/shop-images/logo.png'),
             ('storage:GetObject', 'bucket/shop-images/private/passport.jpg'),
             ('storage:PutObject', 'bucket/shop-uploads/new.jpg'),
             ('storage:PutObject', 'bucket/shop-images/logo.png'),
             ('storage:DeleteObject', 'bucket/shop-uploads/new.jpg'),
             ('database:Query', 'db/orders')):
    print('%-22s %-42s -> %s' % (a, r, allowed(a, r)))
EOF

5How it breaks in productionFailure modes

No memory limit

One leak takes the whole machine, and the kernel picks its own victim, which may be the wrong program. Fix: set a memory and CPU limit on every container, and alert well before the ceiling.

Huge, slow images

Everything copied in, nothing ordered: the image is large and every build repeats the slow steps. Fix: a small base, only runtime files in the final image, dependencies first and source last.

Secrets baked into a layer

A password copied into an early layer stays in the image history even if a later step deletes the file, because layers are only ever added. Fix: pass secrets in when the container starts, never copy them in.

Running as root inside

By default the process may run as the root user inside the box, and a mistake or a bug can then reach further than it should. Fix: run as an ordinary user and drop the extra capabilities.

A policy that allows everything

A policy with action * on resource * works today and is the quickest way to leak customer data tomorrow. Fix: start from nothing, add one allow per real need, and review it against the access logs.

A moving base tag

FROM base:latest builds a different image next month from the same recipe. Fix: pin a version, or better a digest, and rebuild on purpose.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A very common basics question: reported by candidates, not official.

"What is a container, and how is it different from a virtual machine?"

A foundation question for any backend or platform role. They want the kernel mechanisms, not a marketing definition.

Ask first

  • Is the interviewer after the definition, or the security and performance trade-offs? Give the mechanism first, then the trade-offs.

How to think about it

  1. Define it by mechanism.A container is a process with namespaces (isolated views of processes, network, mounts, hostnames, users), cgroup limits on resources, and an image as its root filesystem.
  2. Contrast with a VM.A VM runs a full guest OS with its own kernel on virtual hardware via a hypervisor; a container shares the host kernel.
  3. State the consequences.Containers start fast, use less memory and pack densely; isolation is weaker, so a kernel vulnerability or a privileged container can affect the host.
  4. Mention hardening.Run as a non-root user, drop capabilities, read-only root filesystem, seccomp profiles, and for stronger isolation sandboxed runtimes or micro-VMs.
  5. Link to orchestration.Kubernetes schedules containers onto machines, restarts them, and wires networking and storage.

How to say it

A model answer, about two minutes aloud

"A container is an ordinary Linux process that the kernel gives a private view of the system: its own process tree, hostname, network and mounts through namespaces, a ceiling on memory and CPU through cgroups, and a root filesystem from an image. It does not run its own operating system: all containers share the host's kernel.

A virtual machine runs a complete guest OS with its own kernel on virtual hardware, so it isolates more strongly but is heavier and slower to start. Containers start in milliseconds and pack densely, at the cost of weaker isolation, so I run them unprivileged, drop capabilities and use seccomp, and use sandboxed runtimes where I need stronger separation."

Likely follow-ups

What are cgroups?

Kernel control groups that limit and account for a set of processes' CPU, memory, I/O and process count.

Can a container run a different kernel?

No: it shares the host kernel (a Linux container needs a Linux kernel; on other systems a hidden VM supplies one).

Why is running as root in a container risky?

Root inside may map to root on the host if isolation is weak, and a kernel or runtime bug can become a host compromise.

Common slips

  • Saying a container is a lightweight VM.
  • Not mentioning the shared kernel.
  • Ignoring security hardening.
A common practical prompt: reported by candidates, not official.

"Our container image is 2 GB and every build takes 10 minutes. How do you fix it?"

A practical platform question. They want layers, cache order, image size and multi-stage builds.

Ask first

  • What is in the image, how is it built, and how often does the source change? Usually: a fat base, build tools left in, dependencies reinstalled on every change.

How to think about it

  1. Explain layers and the cache.Each step is a cached layer; a change invalidates that step and everything after it.
  2. Fix the order.Base image, then system packages, then copy the dependency manifest and install, then copy the source: source changes rebuild only the last layer.
  3. Shrink the image.Minimal base (slim or distroless), multi-stage build so compilers and build caches stay in the build stage, remove package caches in the same step that creates them, a .dockerignore for junk.
  4. Speed up CI.Reuse a remote build cache between runs, build in parallel, pin dependency versions so the cache is stable.
  5. Check security and reproducibility.Pin base image digests, scan images, avoid secrets in layers (they stay in history).
  6. Measure.Image size, pull time, build time before and after, and layers by size.

How to say it

A model answer, about two minutes aloud

"I would look at the layers. An image is a stack of cached layers and a change invalidates its step and everything after, so I would reorder the build: install dependencies from the manifest first, copy the source last, so a code change rebuilds only the final layer.

For size I would use a minimal base, a multi-stage build so compilers and caches stay out of the final image, remove package caches in the same step that creates them, and add a dockerignore. In CI I would reuse a remote build cache between runs. I would also pin the base image digest and check that no secret is baked into a layer, since layers keep history. Then I would measure image size, pull time and build time before and after."

Likely follow-ups

What is a multi-stage build?

A Dockerfile with several stages: build in a fat stage, copy only the artefacts into a small final stage.

Why can a secret in an early layer be a problem even if you delete it later?

Layers are immutable and kept: the file remains in the earlier layer's archive.

What does the writable container layer do?

It holds the container's changes on top of the read-only image layers; it disappears when the container is removed.

Common slips

  • Copying the whole source before installing dependencies.
  • Leaving build tools and caches in the final image.
  • Baking credentials into layers.
A common cloud security prompt: reported by candidates, not official.

"How would you give a service access to one storage bucket and nothing else?"

A cloud basics and security question. They want roles, least privilege and the evaluation rules.

Ask first

  • Read or write? Which prefix? Does it run in the cloud or outside? Scope the action and the resource as tightly as possible.

How to think about it

  1. Use a role, not a key.Attach an identity (role) to the workload so it receives short-lived credentials; no long-lived access keys in config.
  2. Write the narrowest allow.Only the needed actions (get and list, or put) on only that bucket or prefix.
  3. Add explicit denies for risks.For example deny access to a sensitive prefix, or deny any request not using TLS.
  4. Remember the defaults.Everything not allowed is denied; an explicit deny overrides allows.
  5. Review.Use access analysis tools and logs to remove unused permissions; rotate credentials where keys are unavoidable; alert on unusual access.
  6. Say why.A leaked or compromised service should only be able to touch one bucket.

How to say it

A model answer, about two minutes aloud

"I would give the service a role with short-lived credentials rather than a long-lived key, and attach a policy that allows only the specific actions it needs, for example get and list, on that one bucket or prefix. Everything else is denied by default, and I would add an explicit deny for anything sensitive, since an explicit deny always overrides an allow.

Then I would use access analysis and audit logs to remove permissions that are never used, alert on unusual access, and make sure the bucket itself is not public. The point is that if this service is ever compromised, the damage is limited to that one bucket."

Likely follow-ups

What is the difference between a role and a user?

A role is an identity assumed temporarily by a service or person, with short-lived credentials; a user is a long-lived identity with its own credentials.

Why are public storage buckets so often in breach stories?

Defaults or mistakes grant public read; block public access at the account level and audit it.

How do zones relate to resilience?

Spread replicas across zones so the loss of a data centre leaves the service running.

Common slips

  • Using one broad administrator key for convenience.
  • Wildcard actions and resources.
  • Keys committed to repositories.

8Remember thisRecap

The page in 6 lines

  • A container is an ordinary process with a private view (namespaces) and a ceiling (limits).
  • Containers share the host kernel, so they start fast and isolate less than a virtual machine.
  • An image is a stack of read only layers named by a hash of their contents; shared layers are stored once.
  • A build step is cached only if it and everything before it is unchanged: slow and stable steps first.
  • Cloud permissions are default deny: nothing works until a policy allows it, and an explicit deny wins.
  • Give every service its own role with the smallest set of allows that makes it work.

Check yourself

What is a container, and how is it different from a virtual machine?

A container is a process with its own view and limits, sharing the host kernel. A virtual machine runs a full operating system with its own kernel, so it isolates more and costs more.

Why does the order of lines in a build file change the build time?

A step is reused only if it and every earlier step are unchanged. Put slow, rarely changing steps first and your source code last.

What does default deny mean for a cloud role?

Everything is refused unless a policy explicitly allows it, and an explicit deny beats any allow, so you grant the minimum and add more only when something needs it.
