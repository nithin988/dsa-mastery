What is the machine doing?

Up is not the same as healthy. Learn the five checks, processes, memory, disk, permissions and services, that tell you what a Linux machine is really doing.

about 20 minutes4 steps4 real experiments3 interview questions

1Checkout fails, but the server is upThe story

It is 2:51 a.m. on a Tuesday and the pager says checkout errors are at 38 percent. You log in to the web server. It answers ping, the web port is open, and uptime says it has been running for 41 days. By every simple test, the machine is fine.

It is not fine. Over the next quarter of an hour you find three things. The checkout process was killed at 2:44 for using too much memory. A log file has grown to 20 GB and the disk is full. And Dana, the developer on call, deleted the log, but the disk is still full.

Nobody on the team could say what the machine was actually doing, only that it was "up". A healthy machine passes five checks: the right processes are running, there is enough memory, there is room on the disk, programs are permitted to do their job, and services restart themselves. This chapter teaches those five, in the order you run them.

2The idea: five checks, in orderThe idea

A machine can be up and still broken. Health is not one number: it is five small questions, and the answer to each one is a command you can run in seconds.

You do not need to memorise hundreds of commands. Ask the five questions in order and write down what you see. Most real incidents turn out to be one of them: a process that died, memory that ran out, a disk that filled, a file nobody may write, or a service that nobody restarts.

3How it works, step by stepHow it works

  1. Processes: who is running, and how to stop one politely

    A process is a running program. You can ask it to stop with a signal: kill sends SIGTERM (number 15), which a program can catch to save its work and exit. kill -9 sends SIGKILL, which cannot be caught, so there is no clean up.

  2. Memory: read available, not free

    Linux fills spare memory with a file cache to speed up disk reads, so the free column looks small on a healthy machine. Look at available: memory that programs could still get. If it truly runs out, the kernel's OOM killer (out of memory) picks a process and sends it SIGKILL.

  3. Disk: space, inodes, and files that are deleted but still open

    A disk can be full of bytes (df -h) or full of inodes, the records that name each file (df -i). A third trap: if you delete a file that a running process still has open, the space is not freed until that process closes it or restarts. lsof +L1 lists those files.

  4. Permissions and services: who may do what, and who restarts it

    ls -l shows three sets of rights, read, write, execute, for the owner, the group and everyone else. A program can only do what the user it runs as may do. On modern Linux, systemd starts services, runs them as a chosen user, and restarts them if they crash (Restart=on-failure).

4See it for realReal experiments

Every output below was recorded from a real run on Debian Linux as an ordinary user. Read it line by line.

Four experiments, each recorded from a real Debian Linux machine. First, what a killed process leaves behind. Then how to read the memory numbers, a deleted file that is still using space, and what a permission error looks like.

1What does exit code 137 mean?

The shell starts a sleep, kills it with kill -9 (SIGKILL), and prints its exit code. Exit codes above 128 mean "stopped by a signal": subtract 128 to get the signal. The OOM killer uses the same signal, so 137 in a restart loop is a strong hint that memory ran out.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
exit code: 137

exit code: 137A process killed by kill -9 reports 137, which is 128 plus the signal number 9.

( sleep 5 & pid=$!; sleep 0.3; kill -9 $pid; wait $pid 2>/dev/null; echo "exit code: $?" ) 2>/dev/null

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

2How do I read free -m?

free -m prints memory in megabytes. This lab machine is almost idle, so the numbers are calm. On a busy server free shrinks as the cache grows, and that is normal; available is the honest number.

3A deleted file that still takes space

The command opens a file, writes to it, then deletes it while it is still open. The kernel keeps the data until the last holder lets go. This is why df can stay at 100 percent after you delete a huge log.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
/proc/4839/fd/4 -> /home/learner/deep/held.log (deleted)
bash 4w 0
Read it line by line
In the outputWhat it means
(deleted)The name is gone, but the process still holds the file open, so its space is not freed.
bash 4w 0Command bash holds file descriptor 4 open for writing, and the file has 0 names left (the link count). lsof +L1 finds exactly these.
Show the command and the full explanation
cd ~/deep && exec 4>held.log && echo data >&4 && rm held.log; ls -l /proc/$$/fd/4 | awk '{print $9, $10, $11, $12}'; lsof +L1 2>/dev/null | grep held.log | head -1 | awk '{print $1, $4, $8}'; exec 4>&-

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

4What a permission error looks like

The command removes the execute right from a script and runs it. Linux answers Permission denied. This message is about rights, not about the file being missing, so check ls -l and the user the program runs as.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
bash: bin/hello.sh: Permission denied
Read it line by line
In the outputWhat it means
Permission deniedThe script exists, but the execute bit was removed, so the kernel refuses to run it. The fix is chmod +x, not chmod 777.
Show the command and the full explanation

5How it breaks in productionFailure modes

Free memory looks tiny

Linux uses spare memory as a file cache, so free is small on a healthy server. Read available, and look at swap activity, before you panic.

The OOM killer

When memory truly runs out, the kernel kills a process and the service may restart in a loop, exit code 137. Confirm with dmesg | grep -i "killed process", then find the cause: a leak, a limit set too high, or too many workers.

Deleted but still open

You delete a 20 GB log and df shows no change, because the process still has it open. Restart or reload the process, or truncate the file instead of deleting it.

Out of inodes

The disk shows free space but new files fail. Millions of tiny files used every inode (df -i). Delete or archive the small files, and stop the thing that creates them.

Zombie processes

A zombie has finished but its parent never collected its exit status, so it shows as Z or <defunct>. You cannot kill a zombie; fix or restart the parent.

Running everything as root

It makes errors disappear for a day. Then files owned by root break the next run as a normal user. Run services as their own user with the least rights they need.

6Where this is written downPrimary docs

Linux man pages

The signal(7) manual page describes each signal, which ones can be caught, and states that SIGKILL and SIGSTOP cannot be caught, blocked or ignored.

signal(7), Linux manual page
Linux man pages

The proc_meminfo(5) manual page describes the MemAvailable field as an estimate of how much memory is available for starting new applications without swapping.

proc_meminfo(5), Linux manual page
systemd

The systemd.service manual describes the Restart= setting that tells systemd when to restart a service that exits or crashes.

systemd.service(5), freedesktop.org

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A frequent Linux question: reported by candidates, not official.

You deleted a 20 GB log file but `df` shows no space freed. Why, and how do you fix it?

Amazon-style: expect "how do you make sure this never pages anyone again?" (alerts on disk growth, log rotation); reported by candidates, not official.

How to say it

A model answer, about two minutes aloud

A process still has the file open. The name is gone but the inode and data stay until the last handle closes.

Confirm with lsof +L1 (or ls -l /proc/PID/fd | grep deleted).

Fix: restart the process, or truncate through the open handle (: > /proc/PID/fd/N), and next time truncate instead of deleting or use logrotate with copytruncate or a reload signal.

Likely follow-ups

• What if df is full but du totals are small?

• What if df -i is 100%?

Common slips

  • Deleting more files.
A frequent question for operations roles: reported by candidates, not official.

Free memory on a server shows 2%. Is that a problem?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

Not necessarily: Linux uses spare RAM for the page cache, so "free" is usually small on a healthy busy machine.

Look at available, swap usage and swap in/out rates, and whether the OOM killer has run (dmesg, journal).

A problem looks like: available near zero, heavy swapping, rising latency or OOM kills.

Likely follow-ups

• How would you find which process is leaking?

• What is thrashing?

Common slips

  • Alerting or panicking on the free column.
Often asked in container and on-call interviews: reported by candidates, not official.

Explain SIGTERM versus SIGKILL. What does exit code 137 mean?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

SIGTERM (15) is a polite request that a process can catch to clean up. SIGKILL (9) cannot be caught or ignored; the kernel removes the process immediately.

Shutdown order: TERM, wait, then KILL.

Exit codes after a signal are 128 plus the number: 143 for TERM, 137 for KILL. In containers 137 is most often the OOM killer or a failed graceful shutdown.

Likely follow-ups

• What does Kubernetes do when a pod is deleted?

• Which signals can never be caught?

Common slips

  • Saying 137 always means out of memory.

8Remember thisRecap

The page in 6 lines

  • Up is not healthy: run five checks, processes, memory, disk, permissions and services.
  • SIGTERM asks a process to stop and can be caught; SIGKILL cannot be caught, and exit code 137 means it was SIGKILLed.
  • Read available in free, not free: the kernel uses spare memory as cache.
  • A full disk can mean no space (df -h), no inodes (df -i), or deleted files still held open (lsof +L1).
  • Permission denied is about rights and the running user: read ls -l, do not reach for chmod 777.
  • systemd starts, supervises and restarts services; systemctl status and journalctl tell you why one stopped.

Check yourself

A process exits with code 137. What happened?

It received signal 9 (128 plus 9), SIGKILL. A common cause is the OOM killer, so check dmesg and memory.

You deleted a big log but df did not change. Why?

A running process still holds the file open. Restart or reload it, or truncate the file instead of deleting it.

Why does free show almost no free memory on a healthy server?

The kernel uses spare memory as a file cache and gives it back when needed. Read the available column.
