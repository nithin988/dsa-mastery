Chapter 4 of 9The ShopKart story

Where the data lives

Three bad days, one lesson: a database is not a box of files. Indexes make finding fast, transactions make sharing safe, and the log makes saving permanent.

about 20 minutes4 steps4 real experiments3 interview questions

1Three bad days in one weekThe story

ShopKart has a balancer, four servers and a cache. The pages are fast again, then the data starts to bite. On Monday a customer complains that "my orders" takes 8 seconds. The query asks for one customer's orders, but the database reads every order the shop has ever taken, a few million rows, and throws almost all of them away.

On Tuesday the last pair of limited-edition trainers sells twice. Two customers pressed Buy within the same second. Each request read "stock: 1", each decided it was fine, and each wrote "stock: 0". Both customers got a confirmation email, and one of them will be disappointed.

On Friday there is a power cut and the server restarts. Three orders that customers had already paid for are missing: the early version confirmed an order before it was safely on disk. These are three different bugs with one root cause. The next sections show the three tools that fix them.

2The idea: a database makes three promisesThe idea

A relational database stores data in tables and promises three things: it finds rows fast (indexes), it keeps many users from corrupting each other's work (transactions), and it never loses what it said it saved (the write-ahead log).

Together the last two are part of the famous ACID guarantees: a transaction is all or nothing (atomic), leaves the data valid (consistent), does not trip over other users (isolated) and survives a crash (durable). PostgreSQL does all of this, and the experiments below use real PostgreSQL.

3How it works, step by stepHow it works

  1. Keep data in tables and ask with SQL

    A relational database stores data as tables of rows (orders, customers, stock). You ask questions in SQL, and the database decides how to find the answer. It also protects the data with rules, so a bad row is rejected instead of saved.

  2. Add an index so it does not read everything

    Without an index, finding one customer's orders means reading every row. An index is a sorted list of customer ids that points to the rows, like the index of a book. The database jumps straight there.

  3. Let the database referee two buyers

    Two buyers each read "1 left", then each write "0 left": both are told yes. This is a lost update. Fix it by letting the database do the subtraction in one statement, or by locking the row so the second buyer waits for the first.

  4. Write to a log before you say yes

    Before changing the table, the database appends the change to the write-ahead log on disk. Only then does it say "committed". If the server dies, it replays the log on restart, so every committed order is still there.

2A lost update, and two ways to fix it

The classic bug, reproduced. Two clients each read 100, wait (as real code does while it computes), then write. The result is 70 or 50, not 20: one withdrawal vanished and nothing reported an error. Making the update a single atomic statement fixes it (20), and so does locking the row you read with FOR UPDATE: the second client waits for the first to finish, then reads the new value and gets 20.

3Kill the server and see committed rows survive

Durability, tested by violence. After rows are committed the server process is killed with kill -9: no chance to shut down cleanly. On restart PostgreSQL finds the data files behind the log, replays the write-ahead log, and reports that it was not properly shut down and recovered automatically. All 6,000 committed rows are there. (We turned fsync off for speed, which is safe against a killed process because the operating system still holds the written data; it would not be safe against power loss, which is why production keeps fsync on.)

4Why a table grows when you update it

Bloat, measured. Every full-table update writes a new version of every row, so the table roughly doubles after the first update and grows again after the second. After a plain VACUUM the dead space becomes reusable, so a third update does not grow the file. VACUUM FULL rewrites the table to its minimal size but needs an exclusive lock, so it is a maintenance-window tool. The practical lesson: keep autovacuum healthy and avoid long transactions that stop it from cleaning.

5How it breaks in productionFailure modes

A missing index

A page that should take milliseconds takes seconds, and gets worse as the table grows. Fix: read the query plan, look for a full table scan, and add an index on the column you filter by.

Too many indexes

Every index is extra work on every write and extra disk space. In the practice database an index on one integer column took about an eighth of the table's size. Add indexes for the queries you really run.

Read, think, then write

Reading a value in your code, changing it, and writing it back lets two users overwrite each other. Fix: one atomic statement, a row lock, or a unique constraint that makes the second attempt fail.

Deadlocks

Two transactions each hold a lock the other needs, and both wait forever. The database notices and cancels one. Fix: lock rows in the same order everywhere, and keep transactions short.

Bloat from old versions

An update writes a new version of the row and keeps the old one for readers who still need it. In the experiment, 100,000 rows grew from 14 MB to 27 MB to 40 MB with no cleanup. Let vacuum run, and watch dead rows.

Too many connections

Each connection to the database costs memory, and four servers each opening many connections add up quickly. Fix: use a connection pool so a few connections are shared by many requests.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

The most reported database question: reported by candidates, not official.

"This query is slow. How do you find out why, and what do you do?"

The most common database question in interviews and on call. They want a method, not a guess.

Ask first

  • How slow, how often, and how big is the table? A 2 s query run once a day is different from a 50 ms query run 5,000 times a second.
  • Is it slow always, or only sometimes? Always slow suggests a missing index; sometimes slow suggests locks, a bad plan after a statistics change, or load.

How to think about it

  1. Get the actual query and its plan.EXPLAIN (ANALYZE, BUFFERS) on the real query with real parameter values. Look for a Seq Scan on a big table, a large gap between estimated and actual rows, a Sort spilling to disk, or nested loops over many rows.
  2. Diagnose from the plan.Seq Scan with many rows removed means a missing or unusable index. Wrong estimates mean stale statistics (ANALYZE) or correlated columns. A Sort over a huge set means an index could deliver the order.
  3. Choose the index to fit the query.Equality columns first, then range or sort; consider a covering index (include) if the query reads few columns; check functions in the WHERE clause (lower(email)) need a matching expression index.
  4. Weigh the cost.Each index slows writes and uses memory. Measure on a copy with production-like data; create indexes without blocking writers (create index concurrently).
  5. Verify and monitor.Re-run EXPLAIN ANALYZE, compare latency percentiles before and after, and watch that write throughput did not suffer.

How to say it

A model answer, about two minutes aloud

"First I get the real query with real parameters and run EXPLAIN ANALYZE. I look for a sequential scan on a large table, estimates far from actual rows, or a sort that spills. A Seq Scan with almost all rows removed means a missing or unusable index; bad estimates mean I should refresh statistics.

I design the index around the query: equality columns first, then the range or sort column, and I check things like a function applied to a column that would stop the index being used. I weigh the write cost and the space, build it concurrently so writers are not blocked, and then re-run the plan and compare latency percentiles before and after. If a single index is not enough I look at the query itself: select fewer columns, paginate with a keyset instead of a big offset, or cache the result."

Likely follow-ups

Why might the planner ignore your index?

The query uses a function or type cast on the column, the table is small, the condition matches most rows (a scan is cheaper), or statistics are stale.

What is a covering index?

An index that contains every column the query needs (include (...)), so PostgreSQL answers from the index alone without visiting the table.

What are the downsides of OFFSET pagination?

The database still reads and discards all skipped rows, so deep pages get slower; keyset pagination (where id > last_seen order by id limit n) stays fast.

Common slips

  • Adding an index without looking at the plan.
  • Indexing every column "just in case".
  • Forgetting that a function on a column prevents the plain index from being used.
A staple of tickets, hotels and inventory design questions: reported by candidates, not official.

"Two users try to book the last seat at the same moment. How do you make sure only one succeeds?"

A staple of design interviews (tickets, rooms, inventory). They want you to name the race and give at least two concrete fixes with trade-offs.

Ask first

  • One database or several? Is the inventory in a single row or many? A single primary database makes row locks and constraints enough; sharded or multi-service inventory needs more.
  • What happens on conflict: wait, fail or retry? Failing fast with a clear message is usually better for the second buyer than waiting.

How to think about it

  1. Name the race.Both read seats_left = 1, both decide to sell, both decrement: oversell. It is a read-modify-write race.
  2. Fix 1: atomic conditional update.update seats set left = left - 1 where event = 7 and left > 0, then check how many rows were updated: zero means sold out. The database serialises the two updates; no explicit lock or retry loop.
  3. Fix 2: row lock.begin; select ... for update; check; update; commit; The second transaction waits, then sees the new value. Simple but holds the lock while your code runs: keep the transaction short.
  4. Fix 3: optimistic version check or a unique constraint.For individual seats, a unique constraint on (event, seat) makes the second insert fail: the database enforces it, so it holds under any concurrency.
  5. Handle the edges.Retries after serialization failures or deadlocks; a reservation with a short expiry (hold the seat for 10 minutes) with a job to release expired holds; idempotency keys so a retried request does not book twice.
  6. Mention scale.A hot single row (the last seat of a famous concert) is serialised on its lock: that is correct but limits throughput; queue the requests or shard by event.

How to say it

A model answer, about two minutes aloud

"The race is read-modify-write: both requests see one seat left and both sell it. I would let the database make the decision atomically. The simplest way is a conditional update, update seats set left = left - 1 where event_id = 7 and left > 0, then check the number of rows changed: if it is zero, the seat is gone. For individual seats a unique constraint on event and seat does the same job and cannot be bypassed.

Alternatively I would take a row lock with SELECT FOR UPDATE in a short transaction. I would keep transactions short, retry on deadlock or serialization errors, hold a seat with an expiry during payment, and use an idempotency key so a retried request does not book twice. For a very hot event all buyers serialise on one row, which is correct but limits throughput, so I would queue requests or partition by event."

Likely follow-ups

What if the inventory is in a different service from the database that records the order?

You cannot use one transaction. Reserve first (with an expiry), then confirm after payment, and compensate on failure: a saga with idempotent steps (later modules).

Optimistic or pessimistic locking?

Optimistic works well when conflicts are rare (retry on the rare conflict, no waiting); pessimistic when conflicts are frequent or retries are costly.

Why not just use serializable isolation everywhere?

It is correct but aborts some transactions under contention, which you must retry, and costs throughput; use it where the invariant is complex, not by default.

Common slips

  • Checking availability in the application and then updating separately.
  • Holding a row lock during a slow external call such as payment.
  • Forgetting what happens on a retry: a double booking.
A common depth question on durability: reported by candidates, not official.

"What happens inside PostgreSQL when I update a row and commit? What if the server crashes right after the commit?"

They are testing whether you understand durability beyond the word, and whether you know why databases need maintenance.

Ask first

  • Is it okay to describe PostgreSQL specifically? Yes: the ideas (log first, snapshots) are shared by most systems; mention where they differ.

How to think about it

  1. Walk the write path.The transaction finds the row, writes a new row version (MVCC), appends a log record to the WAL buffer, and at commit flushes the WAL to disk. Only then is the client told the commit succeeded. Data pages stay in memory and are written later by a background process (checkpointing).
  2. Answer the crash question.Data files may be stale, but the log has the commit. On restart PostgreSQL replays the log from the last checkpoint, so the committed update is present; uncommitted changes are discarded.
  3. Mention what makes it real.The guarantee depends on fsync being honest all the way down (disk caches, battery-backed controllers, cloud disks) and on synchronous_commit.
  4. Connect to replication.Replicas stream the same WAL. Synchronous replication waits for a replica to confirm before acknowledging commit: durable against losing the primary at the cost of latency; asynchronous is faster but can lose the last commits on failover.
  5. Mention the maintenance cost of MVCC.Old versions need vacuum; long transactions block cleanup and cause bloat, so monitor transaction age and autovacuum.

How to say it

A model answer, about two minutes aloud

"The update creates a new version of the row, since PostgreSQL never overwrites in place, and appends a record to the write-ahead log. At commit the log is flushed to disk and only then is the client told it succeeded; the data pages themselves are written later in the background. If the server crashes right after the commit, the data files may be behind but the log has the change, so on restart PostgreSQL replays the log and the committed update is there, while uncommitted work is discarded.

That durability depends on fsync being honest through the whole storage stack. Replicas work by streaming and replaying the same log; synchronous replication waits for a replica's confirmation before commit returns, so a failover cannot lose it, at the price of latency. The cost of keeping old versions is vacuum: dead rows must be cleaned, and long-running transactions prevent that, so I would monitor transaction age and bloat."

Likely follow-ups

What is a checkpoint?

A point where all dirty data pages up to a log position are flushed to the data files, so recovery only has to replay the log after it.

How can a replica be behind the primary?

It replays the log asynchronously: network delay or heavy replay can make it lag, so reads from a replica may be stale (read-your-writes needs care).

What is the risk of synchronous_commit = off?

A crash can lose the last few commits (up to a short window) but not corrupt the database: a latency-for-durability trade.

Common slips

  • Saying the data is written to the table first.
  • Not mentioning that durability depends on the disk honouring flushes.
  • Forgetting the maintenance cost of MVCC.

8Remember thisRecap

The page in 6 lines

  • A database makes three promises: fast lookups, safe sharing and no lost commits.
  • An index lets a query jump to its rows; without one the database scans the whole table.
  • Reading, changing and writing back in your code loses updates; do the change inside the database.
  • Fixes for the last item: one atomic update, a row lock (SELECT FOR UPDATE), or a unique constraint.
  • The write-ahead log is written first, so committed data survives a crash; it is replayed on restart.
  • Updates keep old versions until vacuum cleans them: watch table size and dead rows.

Check yourself

What does an index trade for faster reads?

Extra disk space and slower writes, because every write must update the index too.

How do you stop two buyers getting the last item?

Make the check and the update one atomic step: update stock = stock - 1 where stock > 0, or lock the row first.

Why does a committed row survive a power cut?

The change was written to the write-ahead log on disk before the database said committed, and the log is replayed on restart.
