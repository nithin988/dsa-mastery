Design a URL shortener

The classic warm-up: small enough to finish in 45 minutes, deep enough to show whether you reason from numbers or just draw boxes.

about 25 minutes2 real experimentsThe most common first design question

1A link that will not fitThe question

A marketing team at ShopKart wants to put a product link in a text message. The link is 300 characters of tracking parameters. The message limit is 160. They ask engineering for something like bit.ly: paste a long link, get a short one, and when anyone opens the short link they land on the long one.

It sounds trivial, and the first version is: a table with two columns, a counter, a redirect. The interesting parts appear when you ask what happens at scale. What if two servers hand out the same code at the same moment? What if one link goes viral and gets a million clicks an hour? What if you need to count the clicks without slowing down the redirect?

The interviewer says: Design a URL shortener like bit.ly. Walk me through it.

What they are looking for: The canonical warm-up. A strong answer has structure and numbers: requirements, estimates, API, data model, architecture, deep dives, failure.

2What to ask before drawing anythingRequirements

Two minutes of questions is what separates a design from a guess. Write the answers on the board.

  • Do we need custom aliases, expiry, analytics, private links? What scale? Assume: 100 million new URLs a month, 100:1 read to write, 5-year retention, custom aliases optional, click analytics wanted, redirects must be fast.
  • What availability do we need for redirects versus creation? Redirects: very high (99.99%); creation can be a little less strict.

Functional: create a short code for a long URL; redirect from the code; optional custom alias and expiry; click statistics. Non-functional: redirects are fast and almost never down (they sit inside links people already shared); codes never collide; creating a link can be a little slower.

1Capacity, code length and storage

The numbers an interviewer wants to hear in the first five minutes. At 100 million new URLs a month the system sees only about 40 writes per second and 4,000 redirects per second (peaks ten times higher): small by large-system standards, which is why the design is a cache plus a simple store, not a heroic distributed database. Six base62 characters give 56.8 billion codes, nearly 50 years of supply at that rate; seven give effectively forever. A counter encoded in base62 yields short codes with no collisions at all.

4A first design that worksArchitecture

  1. Create: a short code for a long URL

    The API validates the URL, takes a unique number from an ID generator, turns it into a base62 string (the code) and stores code -> long URL. The write path is short and cheap.

  2. Redirect: the hot path

    The redirect service looks in the cache by code. On a hit it returns 302 with the long URL at once. On a miss it reads the store, fills the cache, and returns. Nothing else happens on this path.

  3. Counters in ranges, so no server is a bottleneck

    Each app server leases a block of numbers (for example a million) from a tiny coordination service and hands them out locally. No call per request, no collisions, and if the coordinator is down servers keep going until their block runs out.

  4. Click analytics happen later

    The redirect publishes a click event to a queue and returns immediately. A separate consumer aggregates counts by code and day. Analytics can lag by minutes; the redirect cannot.

5The hard part: codes that never collide, and a redirect that stays fastThe hard part

Every interview has one part where the answer is not obvious. Spend your time here.

There are two real decisions. How to make codes: hashing the long URL and keeping a few characters sounds simple but collides much earlier than people expect (the birthday paradox), so you must detect and retry. A counter encoded in base62 never collides; scramble it if codes must not be guessable. How to redirect: 301 is cached by browsers (less load, but you lose later clicks and cannot change the target); 302 reaches you every time, so you can count and edit. Pick from the requirements, and say which.

1Hashing collides sooner than you expect; counters never do

Why "just hash the URL" is a trap. Hashing 100,000 URLs into five characters (916 million possible codes, so the space is 99.99 percent empty) still produces a handful of collisions, as the birthday formula predicts: n²/2m. A fuller code space needs constant retries: the database's primary key constraint is the safety net that makes retrying correct, because two requests can never insert the same code. A counter encoded in base62 has no collisions at all, which is why most real designs use one (often allocating ranges of numbers to each application server so no central bottleneck exists), scrambling the order if codes must not be guessable.

cd ~/warm && python3 - <<'EOF'
import hashlib, random, sqlite3, time
chars = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ'
def b62(n, width):
    s = ''
    for _ in range(width): n, r = divmod(n, 62); s += chars[r]
    return s
# 1. truncated hashes: the birthday paradox in action (5-character codes: 916 million possibilities, only 100,000 URLs)
N, W = 100_000, 5
seen, collisions = {}, 0
for i in range(N):
    url = 'https://example.com/page/%d' % i
    code = b62(int(hashlib.sha256(url.encode()).hexdigest(), 16), W)
    if code in seen: collisions += 1
    seen[code] = url
expected = N * N / (2 * 62 ** W)
print('hashing %d URLs into %d-character codes (%s possible): %d collisions (the birthday estimate predicts about %.1f)' % (N, W, '{:,}'.format(62 ** W), collisions, expected))
print('even a tiny fraction of the space in use produces collisions: you must detect and retry, or avoid hashing.')
# 2. a fuller space: 4-character random codes with 300,000 already stored; each insert may need retries
db = sqlite3.connect(':memory:'); db.execute('create table urls(code text primary key, url text)')
rng = random.Random(1); t = time.perf_counter(); retries = 0
for i in range(300_000):
    while True:
        code = ''.join(rng.choice(chars) for _ in range(4))
        try: db.execute('insert into urls values (?, ?)', (code, 'u%d' % i)); break
        except sqlite3.IntegrityError: retries += 1                        # the database enforces uniqueness: retry with a new code
print('inserting 300,000 random 4-character codes (14.8 million possible): %d retries needed (%.1f%% of inserts) in %.1f s' % (retries, 100 * retries / 300_000, time.perf_counter() - t))
# 3. counters never collide
db.execute('create table c(code text primary key)'); n = 0
for i in range(300_000): db.execute('insert into c values (?)', (b62(i + 1, 4),)); n += 1
print('300,000 counter-based 4-character codes: %d inserts, 0 retries, zero collisions by construction' % n)
EOF

2301 or 302: what the browser remembers

The redirect decision, in two responses. A 302 goes back to the shortener on every click, so every click can be counted and the destination can be changed later. A 301 carries Cache-Control: max-age=31536000: browsers and proxies remember it for a year, which removes load from your servers but means later clicks are invisible to your analytics and the link can never be repointed. Choose by the requirement: analytics or editable links need 302; pure, immutable shortening can use 301 (or a short max-age).

import http.server, socketserver
class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        kind = 301 if self.path.startswith('/p/') else 302                   # /p/ permanent, otherwise temporary
        self.send_response(kind); self.send_header('Location', 'https://example.org/very/long/target?utm=1')
        if kind == 301: self.send_header('Cache-Control', 'max-age=31536000')
        self.send_header('Content-Length', '0'); self.end_headers()
    do_HEAD = do_GET                                                         # curl -I sends HEAD
    def log_message(self, *a): pass

socketserver.TCPServer(('127.0.0.1', 8330), H).serve_forever()

6Scale, failure and trade-offsDeep dive

Reads at 400,000 per second

More cache replicas with consistent hashing, a CDN or edge in front for the redirect with a short TTL, read replicas of the store.

The coordinator is down

Servers keep using their leased range. Lease generously and alert early; a range of a million lasts hours.

A viral link (hot key)

One key, huge traffic. Replicate the entry across cache nodes or keep it in each app server's memory for a few seconds.

Abuse

Rate limit creation, scan targets for malware and phishing, support takedown, and make private links unguessable.

Consistency

A creator must be able to open their new link immediately: read your own write from the primary for a few seconds.

7Say it in two minutesThe answer

The most reported cross-company question: reported by candidates, not official.

"Design a URL shortener like bit.ly. Walk me through it."

The canonical warm-up. A strong answer has structure and numbers: requirements, estimates, API, data model, architecture, deep dives, failure.

How to say it

A model answer, about two minutes aloud

"Let me start with numbers. At 100 million new URLs a month that is about 40 writes per second and, at 100 to 1, about 4,000 redirects per second with peaks ten times that, and roughly 3 terabytes over five years: small, read-heavy and key-value. The API is POST to create a short URL and GET on the code, which returns a 302 so I can count clicks and change targets.

For codes I use seven base62 characters from a counter: 3.5 trillion values and no collisions, whereas hashing and truncating collides early by the birthday paradox. Each app server leases a range of numbers from a small coordination service so there is no central call per request, and I scramble the order if codes must not be guessable. The data is one key-value row per code, sharded by hash of the code. Redirects check a Redis cache first, with a hit ratio above 95 percent, so the store sees a few hundred reads a second; clicks are published to a queue and aggregated asynchronously so analytics never slows the redirect. Everything is replicated across zones; if the range service is down, servers keep using their leased range. I would add rate limits, abuse checks, expiry and a takedown path."

Likely follow-ups

How would you prevent guessable or enumerable codes?

Apply a reversible permutation (a block cipher over the counter) before base62-encoding, or use random codes with collision retry; add rate limits on lookups.

What happens when the same long URL is submitted twice?

Either create a new code each time (simple, allows per-user analytics) or deduplicate by hash of the URL per user; state the choice.

How do you scale reads to 400,000 per second?

More cache replicas, consistent hashing across cache nodes, CDN or edge caching of the 302 with a short TTL, and replicas of the store.

Common slips

  • No numbers at all.
  • Hashing and truncating without discussing collisions.
  • Counting clicks synchronously on the redirect path.

8Remember thisRecap

The page in 6 lines

  • Estimate first: ~40 writes/s, ~4,000 reads/s, ~3 TB over five years. It is a small, read-heavy, key-value system.
  • Codes: 7 base62 characters from a counter with leased ranges. Hashing collides early; counters do not.
  • Redirect path = cache, then store, then 302. Nothing else runs on it.
  • Analytics go through a queue so counting never slows the redirect.
  • 301 saves load but hides clicks and freezes the target; 302 is the safer default.
  • Say the failure story: coordinator down, hot link, abuse, new-link consistency.

Check yourself

How many characters does a 7-character base62 code give?

62^7, about 3.5 trillion codes.

Why not just hash the URL?

Truncated hashes collide long before the space is full (birthday paradox), so you need retry logic; counters avoid it.

Why publish clicks to a queue instead of counting in the redirect?

Counting on the redirect path adds latency and a failure mode to the hottest request.
