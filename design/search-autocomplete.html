Design search and autocomplete

Start with autocomplete, which is a data structure question. Then show how the full search behind it works, because they use two different tools.

about 35 minutes2 real experimentsReported for search focused companies

1The search box that waitsThe question

ShopKart's search box works like a form: type a whole word, press Enter, wait for results. Support notices the pattern. People type 'camra', get nothing, and leave. A competitor shows suggestions after the first two letters, and customers prefer it.

The team builds suggestions fast: on every keystroke, scan the log of past queries for ones that start with the typed text and sort by popularity. It works for the team of five testing it. On launch day thousands of customers type at once, each typing ten keys a query, and the scan turns into the busiest thing in the system.

The interviewer says: Design search autocomplete (typeahead) for a search box with 100 million daily users.

What they are looking for: A classic that tests data structure choice, the offline/online split and latency thinking.

2What to ask before drawing anythingRequirements

Two minutes of questions is what separates a design from a guess. Write the answers on the board.

  • How many suggestions, how fresh must they be, personalised or global, languages, and the latency budget? Assume top 5, refreshed hourly (trending faster), global with light personalisation, under 100 ms end to end.

Functional: as the user types, show the top five matching popular queries; then, on submit, return ranked product results. Non-functional: suggestions in under 100 ms end to end, ideally a few milliseconds on the server; fresh within about an hour, with trending faster; results can be a little stale; unsafe queries never appear.

1Scanning versus a trie with stored suggestions

Why the work is done in advance. The trie is built once from the query log, keeping only the top five queries at every node. A keystroke is then a walk down two or three characters and a read of a short list: no scanning, no sorting. The experiment checks that the answers are identical to scanning the entire log, and measures the gap: the trie lookup takes microseconds against milliseconds for the scan, and the gap grows with the size of the log. In production the build runs as a periodic batch job over the aggregated log and the result is swapped into memory atomically.

python3 - <<'EOF'
import random, time
rng = random.Random(6)
syll = ['ca', 'mer', 'ra', 'cam', 'pus', 'cat', 'ch', 'cap', 'tain', 'ca', 'lo', 'ri', 'es', 'sho', 'pe', 'ph', 'one', 'lap', 'top', 'pri', 'ce']
queries = {}
for _ in range(60000):                                           # a query log: 60,000 distinct queries with a skewed popularity
    q = ''.join(rng.choice(syll) for _ in range(rng.randint(2, 4)))
    queries[q] = queries.get(q, 0) + int(1000 / (1 + rng.random() * 400)) + 1
K = 5
class Node:
    __slots__ = ('kids', 'top')
    def __init__(self): self.kids, self.top = {}, []
root = Node()
t0 = time.perf_counter()
for q, c in queries.items():
    n = root
    for ch in q:
        n = n.kids.setdefault(ch, Node())
        n.top.append((c, q))
        if len(n.top) > 4 * K: n.top.sort(reverse=True); del n.top[K:]          # keep only the best few at each node
def finish(n):
    n.top.sort(reverse=True); del n.top[K:]
    for kid in n.kids.values(): finish(kid)
finish(root)
build_ms = (time.perf_counter() - t0) * 1000
def suggest_trie(prefix):
    n = root
    for ch in prefix:
        n = n.kids.get(ch)
        if n is None: return []
    return [q for c, q in n.top]
def suggest_scan(prefix): return [q for c, q in sorted(((c, q) for q, c in queries.items() if q.startswith(prefix)), reverse=True)[:K]]
print('built a trie over %d queries in %.0f ms (done offline, not per request)' % (len(queries), build_ms))
for p in ('ca', 'cam', 'camp'):
    print('prefix %-5r top %d: %s' % (p, K, suggest_trie(p)))
print('same answers as scanning the whole log: %s' % all(suggest_trie(p) == suggest_scan(p) for p in ('c', 'ca', 'cam', 'camp', 'ph', 'lap')))
N = 2000
t = time.perf_counter()
for _ in range(N): suggest_scan('cam')
scan = (time.perf_counter() - t) / N * 1000
t = time.perf_counter()
for _ in range(N): suggest_trie('cam')
trie = (time.perf_counter() - t) / N * 1000
print('per keystroke: scanning the log %.2f ms, trie lookup %.4f ms (%.0f times faster)' % (scan, trie, scan / trie))
EOF

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

4A first design that worksArchitecture

  1. Count queries offline

    Search events go into a log. A batch job counts how often each query was searched, gives recent searches more weight, and removes unsafe or banned queries. Nothing here runs per keystroke.

  2. A trie that already knows the answer

    A trie is a tree where each step down is one more letter. At every node we store the top five queries below it, worked out ahead of time. Typing 'cam' means walking three steps and reading a ready made list.

  3. Publish the whole trie as a snapshot

    The builder writes a new immutable trie and the suggestion servers load it into memory, then switch over in one step. If a build fails, servers keep serving the last good snapshot.

  4. The client does half the work

    The page waits for a short pause before asking, cancels the request when the next key arrives, and remembers answers it already got for a prefix. That cuts requests a lot before any server is involved.

5The hard part: fresh, fast, and then real searchThe hard part

Every interview has one part where the answer is not obvious. Spend your time here.

Autocomplete is fast because the thinking was done earlier. The cost is freshness: the trie reflects the last build. Fix that by blending in a small, fast-updating trending list, and say the trade-off aloud.

Full search is a different tool. An inverted index maps each word to the products that contain it, so a query reads only a few short lists instead of every product. Results are then ranked, commonly with a score called BM25 that rewards rare words and does not let one word repeated many times dominate. The experiments below build both ideas by hand and compare them with a real full text engine.

1Build an inverted index and rank results by hand

A search engine in forty lines. Each document is analysed and added to the inverted index: for each stemmed term, which documents contain it and how often. A query is analysed the same way, the short postings lists are intersected (documents containing every term) and the survivors are scored by term frequency weighted by how rare the term is across the collection, so a match on a rare word beats a match on a common one. Nothing scans the documents at query time: the work depends on the lists, which is why this scales to billions of documents once the index is sharded.

import math, re
from collections import defaultdict
docs = {1: 'Red running shoes for trail running', 2: 'Blue running shorts, lightweight', 3: 'Red cotton shorts', 4: 'Leather office shoes, black', 5: 'Running socks for trail and road'}
STOP = {'for', 'and', 'the', 'a'}
def analyse(text):
    out = []
    for w in re.findall(r'[a-z]+', text.lower()):
        if w in STOP: continue
        for suf in ('ing', 's'):                       # a toy stemmer: running -> runn... good enough to show the idea
            if w.endswith(suf) and len(w) > len(suf) + 2: w = w[:-len(suf)]; break
        out.append(w)
    return out
index = defaultdict(lambda: defaultdict(int))          # term -> {doc id: term frequency}
for i, text in docs.items():
    for t in analyse(text): index[t][i] += 1
print('inverted index (term -> {document: count}):')
for t in sorted(index): print('  %-10s %s' % (t, dict(index[t])))
def search(query):
    terms = analyse(query)
    postings = [set(index[t]) for t in terms]
    hits = set.intersection(*postings) if postings else set()
    N = len(docs)
    def score(i): return sum(index[t][i] * math.log(1 + N / len(index[t])) for t in terms)       # TF x IDF
    return sorted(((round(score(i), 2), i, docs[i]) for i in hits), reverse=True)
for q in ('red shorts', 'running shoes', 'trail'):
    print('\nquery %r analysed to %s' % (q, analyse(q)))
    for s, i, d in search(q): print('   score %.2f  doc %d: %s' % (s, i, d))
EOF

2A real full text index against scanning every row

The same idea in a real engine you already have. SQLite's FTS5 builds an inverted index and ranks with BM25. The needle (saffron, present in one document of 100,001) is found by the LIKE scan only after reading everything, while the index answers in a fraction of a millisecond; the gap grows with the corpus. Multi-term queries return ranked results, and the Porter stemmer makes run match running. Elasticsearch, OpenSearch and Solr are distributed, feature-rich versions of exactly this structure (built on Lucene).

6Scale, failure and trade-offsDeep dive

Memory grows

Keep only queries above a minimum count and trim the lists. Shard by the first letters of the prefix if one machine cannot hold it.

Typos

Add edit distance or phonetic matching as a second step, so 'camra' still suggests 'camera'.

Unsafe suggestions

Filter in the builder and also support a quick block list applied at serving time.

The index is stale

For full search, publish product changes to a queue and update the index within seconds. Rebuild into a new index and switch an alias when the schema changes.

A shard of the search index is down

Run each shard with replicas, and return partial results rather than none if a whole shard is missing.

7Say it in two minutesThe answer

A classic data structure and design question: reported by candidates, not official.

"Design search autocomplete (typeahead) for a search box with 100 million daily users."

A classic that tests data structure choice, the offline/online split and latency thinking.

How to say it

A model answer, about two minutes aloud

"That is about five billion requests a day, roughly 60,000 a second and 200,000 at peak, each needing an answer in a few milliseconds, so it must be served from memory. I would use a trie with the top five suggestions precomputed at every node, so a keystroke is a walk down the prefix and a read, independent of the number of queries.

The expensive work is offline: queries are logged to a stream, counts are aggregated with recency decay in hourly batches plus a streaming path for trending, unsafe or removed queries are filtered, and a new trie snapshot is built and swapped in atomically on stateless suggestion servers, sharded by prefix range and replicated, with an edge cache for short prefixes. The client debounces keystrokes, caches by prefix and cancels stale requests. If the builder fails we keep serving the last snapshot. I would add light personalisation and typo tolerance on top."

Likely follow-ups

Trie or hash table of prefixes?

A hash table from prefix to top K is simpler and fast but uses more memory for long prefixes; a trie shares prefixes; either way the top K is precomputed.

How do you handle trending queries?

A streaming aggregation over a short window boosts rising queries and merges them with the batch top K.

How would you shard the trie?

By prefix range (a-f, g-m, ...), balanced by traffic rather than letters, with the first characters cached at the edge.

Common slips

  • Computing rankings per keystroke.
  • No offline pipeline.
  • Ignoring client-side debouncing.

8Remember thisRecap

The page in 6 lines

  • Autocomplete is about 60,000 requests a second, so every answer comes from memory.
  • A trie stores the top five suggestions at each node, computed ahead of time.
  • Build offline from query logs, publish as an immutable snapshot, keep the last good one.
  • Debounce, cancel and cache on the client to cut requests.
  • Full search uses an inverted index: word to documents, then ranking such as BM25.
  • Keep the search index separate from the database and feed it with events.

Check yourself

Why store top suggestions at every trie node?

So a lookup is just a walk down the prefix and a read, with no scanning and no sorting.

What is an inverted index?

A map from each word to the documents containing it, so a query reads a few lists instead of every document.

How do you keep suggestions fresh?

Rebuild the snapshot regularly and blend in a small trending list that updates faster.
