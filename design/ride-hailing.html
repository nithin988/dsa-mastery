Design ride hailing and nearby search

Mostly a write problem in disguise: a million moving points, and a search that must only look in the right few cells.

about 30 minutes1 real experimentsA frequent location based design question

1Where is the nearest driver?The question

ShopKart starts same day delivery in one city with a few hundred couriers on bikes. The first version stores each courier's last position in a database table and, for each order, computes the distance to every courier. With 300 couriers nobody notices. A year later the fleet is 100,000 and the dispatch screen takes a full minute to offer a job.

Two things grew at once. Couriers send their position every few seconds, which is a stream of writes that never stops. And every order needs a search for who is closest. This is the same shape as ride hailing: how do you find the nearest moving things quickly?

The interviewer says: Design the matching of riders to the nearest drivers for a ride-hailing service.

What they are looking for: The geospatial design question (and the first half of the Uber problem). They want the index, the update path, the search, scale and failure.

2What to ask before drawing anythingRequirements

Two minutes of questions is what separates a design from a guess. Write the answers on the board.

  • How many drivers and riders, location update frequency, and what does "nearest" mean (distance, ETA, availability)? Assume 1 million active drivers updating every 4 seconds, 100,000 ride requests a minute at peak; ETA matters more than straight-line distance.

Functional: drivers report location; a rider requests a ride; the system finds nearby available drivers, offers the ride, and tracks the trip. Non-functional: a match in a few seconds, the system tolerates losing a server without losing the trip, and one driver is never matched to two riders.

3The numbers that shape the designEstimates

QuantityEstimate and what it tells you
Location updates1 million active drivers each ping every 4 seconds: 1,000,000 / 4 = 250,000 updates per second. These writes dominate.
Searches100,000 ride requests per minute at peak is about 1,700 searches per second. Much less than the updates.
Data sizeOnly the latest position matters: id, latitude, longitude, time, say 50 bytes each. A million drivers is 50 MB. It fits in the memory of one machine; the trouble is the update rate, not the size.
Cell sizeIn the recorded experiment, geohash precision 6 gives cells about 0.61 km by 0.97 km, and precision 7 about 0.15 km by 0.12 km. Choose a cell about the size of the search radius.
Why an indexThe recorded brute force search over 100,000 drivers took 56.8 ms and the cell index with neighbours took 2.20 ms, examining 1,789 candidates instead of 100,000.

1Geohash cells against brute force, measured

A geohash index built from scratch and checked against the truth. The encoder reproduces the well-known reference value, and the table shows how each extra character shrinks the cell (about a kilometre at six characters). With 100,000 drivers, brute force computes 100,000 distances; the index looks only at the rider's cell and its eight neighbours (a few hundred candidates), then filters by exact distance. The experiment also shows the boundary problem: searching only the rider's own cell misses drivers who are close but just across a cell edge, while the nine-cell search returns exactly the brute-force answer. (Timings depend on the machine; the candidate counts and the correctness comparison do not.)

import math, random, time
from collections import defaultdict
B32 = '0123456789bcdefghjkmnpqrstuvwxyz'
def encode(lat, lon, precision):
    lat_r, lon_r, bits, even, h, ch = [-90.0, 90.0], [-180.0, 180.0], 0, True, '', 0
    while len(h) < precision:
        rng, val = (lon_r, lon) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        if val >= mid: ch = (ch << 1) | 1; rng[0] = mid
        else: ch <<= 1; rng[1] = mid
        even = not even; bits += 1
        if bits == 5: h += B32[ch]; bits = 0; ch = 0
    return h
def decode_center(h):
    lat_r, lon_r, even = [-90.0, 90.0], [-180.0, 180.0], True
    for c in h:
        v = B32.index(c)
        for b in range(4, -1, -1):
            rng = lon_r if even else lat_r; mid = (rng[0] + rng[1]) / 2
            if (v >> b) & 1: rng[0] = mid
            else: rng[1] = mid
            even = not even
    return (lat_r[0] + lat_r[1]) / 2, (lon_r[0] + lon_r[1]) / 2, (lat_r[1] - lat_r[0]), (lon_r[1] - lon_r[0])
def haversine(a, b):
    la1, lo1, la2, lo2 = map(math.radians, (a[0], a[1], b[0], b[1])); d = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 6371.0 * 2 * math.asin(math.sqrt(d))
print('known value: encode(57.64911, 10.40744, 11) = %s   (the Wikipedia example is u4pruydqqvj)' % encode(57.64911, 10.40744, 11))
print('precision  cell height x width at this latitude')
for p in (4, 5, 6, 7):
    lat, lon, dh, dw = decode_center(encode(37.77, -122.42, p)); print('   %d       %6.2f km x %6.2f km' % (p, dh * 111.2, dw * 111.2 * math.cos(math.radians(lat))))
rng = random.Random(2)
pts = [(37.70 + rng.random() * 0.15, -122.52 + rng.random() * 0.20) for _ in range(100000)]       # 100,000 drivers over a city
P = 6
cells = defaultdict(list)
for i, p in enumerate(pts): cells[encode(p[0], p[1], P)].append(i)
def neighbours(h):
    lat, lon, dh, dw = decode_center(h)
    return {encode(lat + a * dh, lon + b * dw, P) for a in (-1, 0, 1) for b in (-1, 0, 1)}
def near_index(q, radius_km, cell_set):
    cand = [i for c in cell_set for i in cells.get(c, ())]
    return sorted((i for i in cand if haversine(q, pts[i]) <= radius_km), key=lambda i: haversine(q, pts[i]))
def near_scan(q, radius_km): return sorted((i for i in range(len(pts)) if haversine(q, pts[i]) <= radius_km), key=lambda i: haversine(q, pts[i]))
q = (37.7749, -122.4194); R = 0.5
t = time.perf_counter(); truth = near_scan(q, R); scan_ms = (time.perf_counter() - t) * 1000
t = time.perf_counter(); same = near_index(q, R, {encode(q[0], q[1], P)}); one_ms = (time.perf_counter() - t) * 1000
t = time.perf_counter(); nine = near_index(q, R, neighbours(encode(q[0], q[1], P))); nine_ms = (time.perf_counter() - t) * 1000
print()
print('drivers within %.1f km of the rider: brute force finds %d in %.1f ms' % (R, len(truth), scan_ms))
print('  index, own cell only:           finds %d in %.2f ms   <- misses %d nearby drivers across the cell boundary' % (len(same), one_ms, len(truth) - len(same)))
print('  index, cell + 8 neighbours:     finds %d in %.2f ms   same answer as brute force: %s' % (len(nine), nine_ms, nine == truth))
print('  candidates examined: %d instead of %d' % (sum(len(cells.get(c, ())) for c in neighbours(encode(q[0], q[1], P))), len(pts)))

4A first design that worksArchitecture

  1. Divide the map into cells

    A geohash turns a latitude and longitude into a short string. Nearby places share the same beginning, so a string prefix is a cell. Each driver belongs to exactly one cell at a time. Other systems use S2 or H3 cells for the same idea.

  2. Keep the index in memory

    Store drivers in a map from cell to set of drivers. An update just rewrites the position, and moves the driver to a new set only when the cell changes. Entries expire if pings stop, so a lost phone disappears by itself.

  3. Search the cell and its neighbours

    The rider's own cell is not enough, because a driver 50 metres away may sit across the line. Search the rider's cell plus the eight around it, then widen in rings until you have enough candidates. The recorded run shows the own cell alone missed 162 of 290 nearby drivers.

  4. Rank the few, then offer with a lock

    Straight line distance is a guess. Ask a routing service for the arrival time of only the best 10 or so candidates. Offer the ride to the best one with a short lease on that driver, so no other rider can be given the same driver while the offer is open.

5The hard part: the boundary problem and the update stormThe hard part

Every interview has one part where the answer is not obvious. Spend your time here.

The boundary problem is that cells cut the world into hard lines. Nearness does not respect lines, so you must always search the neighbouring cells as well. The second hard part is the write rate: 250,000 updates per second. Shard the index by cell id so a search touches a few shards and each shard handles a share of the writes. Splitting a crowded cell into smaller cells (an airport, a stadium) handles hotspots.

Because the index holds only the latest position and is rebuilt from the stream, it is soft state. If a shard dies, its drivers reappear on their next ping a few seconds later. That makes the design simple to run: trips and payments live in a durable database, locations live in memory.

1The same idea in Redis: a geohash sorted set

The same idea as a database feature. Redis stores drivers as a sorted set whose score is a geohash integer, so GEOSEARCH can find members within a radius by scanning a few score ranges (the cell and its neighbours) and filtering by exact distance, returning them sorted with distances. A driver that moves is a single GEOADD on the same key: this is why in-memory geo indexes are the usual choice for moving objects, while static places go in PostGIS or a database index.

6Scale, failure and trade-offsDeep dive

Hot cell at an airport

Hundreds of drivers in a small cell. Split the cell into finer ones when it holds too many, and cap how many candidates one search reads.

A geo shard dies

Its drivers reappear on the next ping. Search a wider radius for a few seconds and replicate shards for faster recovery.

Update storm

A network blip makes every phone resend at once. Use the queue as a buffer, drop stale updates (only the newest position matters) and apply backpressure.

Two riders, one driver

Take a lease on the driver before offering. Release it on decline or timeout, then move to the next candidate.

Moving across shards

A driver crossing a shard boundary is written to the new shard and removed from the old. A short double listing is harmless because the lease decides who gets the ride.

3. How to say it

A model answer, about two minutes aloud

"The load is mostly writes: a million drivers pinging every four seconds is about 250,000 location updates per second, while ride requests are around 1,700 searches per second. I would keep the latest position of each driver in an in-memory geospatial index keyed by cell, using geohash, S2 or H3 cells sized to the search radius. An update only changes the cell membership when the driver crosses a cell boundary, and entries expire if pings stop, so the index is soft state that rebuilds itself within seconds after a failure.

The index is sharded by cell so a query touches few shards, with finer splitting for hot cells. To match a rider I query their cell and its neighbours, expanding rings until there are enough candidates, filter by availability and distance, and rank the best few by ETA from a routing service rather than computing ETA for every driver. The offer uses a lease on the driver so two riders are not matched to the same one, falling back to the next candidate on a decline or timeout. Updates flow through a queue, and trips and payments live in durable stores."

4. Likely follow-ups

Geohash, quadtree, S2 or H3?

Geohash is simple and works with any sorted index; quadtrees adapt to density; S2 and H3 give uniform cell neighbours on a sphere (H3 hexagons make ring searches simple); the choice matters less than getting the boundary and update path right.

How do you avoid matching one driver to two riders?

A short lease or atomic compare-and-set on the driver's state (available to offered) so only one offer can exist at a time.

How do you handle a stadium emptying?

A hot cell: split into finer cells dynamically, shard it separately, and batch updates; apply backpressure on the pings.

Common slips

  • Computing distances to all drivers.
  • Ignoring the cell boundary problem.
  • Treating the location index as a durable store instead of soft state.

8Remember thisRecap

The page in 6 lines

  • It is write heavy: 250,000 location updates per second against about 1,700 searches.
  • Keep only the latest position, in memory, keyed by cell. Entries expire if pings stop.
  • Search the rider's cell and its eight neighbours: 290 found, same as brute force, 2.20 ms against 56.8 ms.
  • The own cell alone missed 162 nearby drivers: the boundary problem.
  • Rank only the top few by arrival time, then offer with a lease on the driver.
  • Locations are soft state rebuilt from the stream; trips and payments are durable.

Check yourself

What is the boundary problem?

A nearby driver may sit in the next cell, so searching one cell misses them; search the neighbours too.

Why is the index in memory and not a database?

The data is tiny but the update rate is huge, and only the latest position matters.

How do you stop two riders getting one driver?

Take a short lease on the driver before making the offer.
