Chapter 9 of 9The ShopKart story

Keep it safe

Security is not a feature you add at the end: it is a handful of habits on every request. Learn the few that stop most real breaches.

about 18 minutes4 steps3 real experiments3 interview questions

1Invoice 1002 belongs to someone elseThe story

ShopKart lets customers download invoices at addresses like /invoices/1001. On a Thursday morning a customer, Ben, spots the number in the web address. Out of curiosity he changes it to 1002. An invoice opens: someone else's name, address and what they bought.

He emails support, politely, and attaches a screenshot. The engineer who reads it checks the code in five minutes. The server confirms that the request has a valid login, then loads the invoice with that number. It never asks whose invoice it is. Anyone logged in could read all of them by counting upwards.

No password was cracked and no server was hacked. The feature simply forgot one question. Most serious breaches look like this: a missing check, not a clever exploit. This chapter is the short list of checks to build in from the start, and how to explain them.

2The idea: ask three questions, and expect each layer to failThe idea

Security for a system designer means three questions on every request (who are you, may you do this, is this input safe) plus layers around them, so that when one layer fails the next still holds. This is called defence in depth.

Everything here is defensive. You are not learning to attack: you are learning which mistakes real breaches share, so you can design them out. Start with the cheap, high-impact habits: check ownership on every object, hash passwords properly, use TLS everywhere, use parameterised queries and keep secrets out of code.

3How it works, step by stepHow it works

  1. Check the owner, not only the login

    Authentication asks who you are. Authorisation asks what you may touch. The invoice bug is an IDOR (insecure direct object reference): the server trusts an id from the client. Put the owner in the query, so another customer's invoice is simply not found.

  2. Prove who you are, and store passwords safely

    Never store passwords. Store a salted, slow hash (Argon2id, scrypt or bcrypt): the salt makes equal passwords look different, and the slowness makes guessing expensive. After login, hand out a short-lived token. A signed JWT carries claims, but it is only encoded, not secret.

  3. Encrypt the wire, and treat input as hostile

    TLS encrypts traffic and, if the client checks the certificate and name, proves the server is the real one. mTLS makes both sides show certificates, so internal services know who is calling. Pass user input to the database as parameters, never glued into the SQL text.

  4. Keep secrets out of code, and encrypt in layers

    Keys and passwords belong in a secrets manager, not in the repository: git remembers every old commit. With envelope encryption, a random data key encrypts the data and a master key encrypts that data key, so rotating the master key re-wraps one small key, not all the data.

1The invoice bug (IDOR) and its one-line fix

The most common serious web flaw, in twelve lines. The vulnerable handler returns whatever order id it is given, so ben simply asks for 1001 and reads ana's order; enumerating ids reveals everyone's. The fixed handler is scoped by the caller's verified identity and answers not found for both a missing order and someone else's (so it does not even confirm that the id exists). Unguessable ids would make enumeration harder, but they are defence in depth, never the control: the control is the ownership check, applied in one central place so no endpoint can forget it.

2How fast weak password storage falls

Three experiments in one. With unsalted SHA-256 the attacker hashes a list of likely passwords once (a few hundredths of a second for 20,000) and then looks up every stolen hash: four of the five users fall instantly; only the long, unique password survives. Next, without salts two users with the same password have identical hashes, a free hint to the attacker; with salts they differ. Finally scrypt makes each guess cost tens of milliseconds and a lot of memory, so even this tiny dictionary would take minutes per stolen hash, and real attackers' lists have billions of entries. (Attackers use GPUs that are far faster than this CPU core; the principle, making each guess expensive, is why password hashes are slow on purpose.)

same = {u: hashlib.sha256(b'welcome77').hexdigest() for u in ('x', 'y')}
print('two users with the same password, no salt: hashes equal? %s' % (same['x'] == same['y']))
salted = {u: (s, hashlib.sha256(s + b'welcome77').hexdigest()) for u, s in (('x', os.urandom(8)), ('y', os.urandom(8)))}
print('two users with the same password, salted:  hashes equal? %s' % (salted['x'][1] == salted['y'][1]))
# 3. a slow, memory-hard hash (scrypt), per-user salt
salt = os.urandom(16)

3A token built, and the checks that must not be skipped

The anatomy of a JWT and of the mistakes made with it. The payload is plain base64: anyone can read it, so no secrets in tokens. A correct verifier checks the signature with the expected algorithm, then expiry and audience, and rejects the tampered role, the expired token and the token meant for another service. The famous alg: none attack works against a verifier that believes the algorithm named inside the untrusted token: it accepts an unsigned token that claims to be an administrator. The fix is one line: the server decides which algorithm and key to use.

cd ~/sec && python3 - <<'EOF'
import base64, hashlib, hmac, json
SECRET = b'server-side-secret'
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b'=').decode()
unb64 = lambda s: base64.urlsafe_b64decode(s + '=' * (-len(s) % 4))
def make(claims, alg='HS256'):
    h = b64(json.dumps({'alg': alg, 'typ': 'JWT'}, separators=(',', ':')).encode()); p = b64(json.dumps(claims, separators=(',', ':')).encode())
    sig = b64(hmac.new(SECRET, ('%s.%s' % (h, p)).encode(), hashlib.sha256).digest()) if alg == 'HS256' else ''
    return '%s.%s.%s' % (h, p, sig)
def verify_good(token, now):
    h, p, s = token.split('.')
    if json.loads(unb64(h))['alg'] != 'HS256': return 'REJECT: algorithm is not the one we expect'
    if not hmac.compare_digest(s, b64(hmac.new(SECRET, ('%s.%s' % (h, p)).encode(), hashlib.sha256).digest())): return 'REJECT: bad signature'
    c = json.loads(unb64(p))
    if c['exp'] < now: return 'REJECT: expired'
    if c.get('aud') != 'orders-api': return 'REJECT: wrong audience'
    return 'ACCEPT as %s (role %s)' % (c['sub'], c['role'])
def verify_naive(token, now):                      # a typical bug: trusts the alg field in the token itself
    h, p, s = token.split('.')
    if json.loads(unb64(h))['alg'] == 'none': return 'ACCEPT as %s (role %s)  <- no signature checked' % (json.loads(unb64(p))['sub'], json.loads(unb64(p))['role'])
    return verify_good(token, now)
now = 1_800_000_000
good = make({'sub': 'ben', 'role': 'user', 'aud': 'orders-api', 'exp': now + 600})
print('payload is only encoded, not encrypted:', json.loads(unb64(good.split('.')[1])))
print('1. genuine token:                  ', verify_good(good, now))
h, p, s = good.split('.'); forged_payload = b64(json.dumps({'sub': 'ben', 'role': 'admin', 'aud': 'orders-api', 'exp': now + 600}, separators=(',', ':')).encode())
print('2. role changed to admin, old sig: ', verify_good('%s.%s.%s' % (h, forged_payload, s), now))
print('3. expired token:                  ', verify_good(make({'sub': 'ben', 'role': 'user', 'aud': 'orders-api', 'exp': now - 1}), now))
print('4. token for another service:      ', verify_good(make({'sub': 'ben', 'role': 'user', 'aud': 'billing-api', 'exp': now + 600}), now))
none = make({'sub': 'mallory', 'role': 'admin', 'aud': 'orders-api', 'exp': now + 600}, alg='none')
print('5. alg=none token, naive verifier: ', verify_naive(none, now))
print('6. alg=none token, correct verifier:', verify_good(none, now))

5How it breaks in productionFailure modes

Trusting the id in the address

Any endpoint that takes an object id must check that the caller may access that object. Fix: scope every query by owner or tenant, and return the same "not found" for missing and forbidden. Random ids help a little but are not the fix.

Fast, unsalted password hashes

In the recorded run an unsalted SHA-256 table of 20,000 guesses was built in 0.024 s and cracked 4 of 5 users. Fix: a salted slow hash (one scrypt check took 144 ms), plus multi-factor authentication for important accounts.

Tokens accepted without full checks

A token must be verified for signature, expiry, audience and the expected algorithm. In the recorded run a naive verifier accepted an unsigned token as an admin. Fix: pin the algorithm, keep expiry short, never put secrets in the payload.

Switching certificate checks off

Using curl -k or disabling verification "just to make it work" accepts any server. Fix: trust your own certificate authority properly, use mTLS between services, and alert well before certificates expire.

User input glued into queries or pages

Joining text into SQL lets input change the query (injection); printing it raw into a page can run script (XSS). Fix: parameterised queries, and encode output for the place it lands.

Secrets in the repository

Deleting a key from the latest commit leaves it in history. Fix: use a secrets manager, scan history, and if a real key leaks, rotate it at once.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A common security prompt: reported by candidates at large tech companies, not official.

"Users can read other users' invoices by changing the id in the URL. What went wrong, and how do you prevent this whole class of bug?"

The most common real vulnerability, framed as an incident. They want the cause, the fix, and a systemic prevention.

1. Ask first

  • Is the id a sequential integer, and where does the code check ownership? Sequential ids make enumeration trivial, but the root cause is a missing ownership check.

2. How to think about it

  1. Name it.Broken object-level authorisation (IDOR/BOLA): the endpoint authenticates the user but does not authorise access to the specific invoice.
  2. Fix this endpoint.Query with the caller's identity from the verified session or token: where id = :id and owner_id = :caller; return 404 for both missing and not-yours.
  3. Prevent the class.Make the safe path the default: a data-access layer or repository that requires the caller context and always adds the tenant and owner filter; row-level security in the database as a second barrier; policy checks centralised in middleware or a policy engine rather than per-endpoint code.
  4. Defence in depth.Unguessable ids (UUIDs) so enumeration is hard; rate limits and anomaly alerts on id scanning; separate roles for support access with audit trails.
  5. Test for it.Automated authorisation tests that, for every endpoint, call it as user A with user B's object ids and expect 403/404; run in CI; include in code review checklists and periodic penetration tests.
  6. Respond.Check logs for past exploitation, notify per policy, fix and verify; add detection.
  7. Broader.Same pattern at tenant level in a multi-tenant system: the tenant id comes only from the token.

3. How to say it

A model answer, about two minutes aloud

"This is broken object-level authorisation: the endpoint checks that the caller is logged in but not that the invoice is theirs. I would fix this endpoint by scoping the query by the caller's verified identity, where id = :id and owner_id = :caller, returning not found for both missing and not-yours so it does not leak existence.

To prevent the class I would make the safe way the default: a data-access layer that requires the caller context and always applies the owner or tenant filter, row-level security in the database as a second barrier, and centralised policy checks. Unguessable ids and rate limits on id scanning add depth. Then I would add automated tests that call every endpoint as one user with another user's object ids and expect a refusal, run them in CI, check the logs for past exploitation, and add detection for enumeration."

4. Likely follow-ups

Why return 404 instead of 403?

403 confirms that the object exists; 404 for both cases leaks nothing. Choose by whether existence is sensitive.

What is row-level security?

A database feature that automatically applies a policy to every query on a table (for example tenant_id = current_setting('app.tenant')), so even a buggy query cannot see other tenants' rows.

RBAC or ABAC?

RBAC assigns permissions to roles (simple, coarse); ABAC decides from attributes of user, object and context (flexible, more complex); many systems use RBAC plus ownership or tenant checks.

Common slips

  • Hiding the id (UUIDs) as the only fix.
  • Checking permissions in the UI only.
  • Fixing one endpoint without a systemic prevention.
A frequent question about leaks and passwords: reported by candidates, not official.

"How should we store user passwords, and how do we make a database leak survivable?"

The most basic security design question, used to see whether you know why and not just which function.

1. Ask first

  • What is the threat: a stolen database backup, SQL injection, a rogue employee? Do we have users with high privilege? All three; assume the hash table will leak one day.

2. How to think about it

  1. State the principle.Store a verifier, not the password. Assume the table leaks, and make the stolen data as useless as possible.
  2. Choose the function.Argon2id (or scrypt, or bcrypt): slow and memory-hard, with a per-user random salt, parameters tuned to roughly 100 ms per hash on your hardware, stored with the hash so they can be upgraded.
  3. Explain why not SHA-256, MD5 or encryption.Fast hashes allow billions of guesses per second; unsalted hashes allow precomputation and expose duplicates; encryption is reversible, so the key becomes the single point of failure.
  4. Add defences around it.Rate limiting and lockout per account and per source, breached-password checks, a pepper kept outside the database (an HSM or secret manager) as defence in depth, constant-time comparison.
  5. Add a second factor.TOTP or passkeys; recovery codes; protect the reset flow as strongly as login.
  6. Plan for upgrades.Rehash on login when parameters improve; force resets after a breach; log and alert on credential stuffing patterns.
  7. Reduce the problem.Prefer delegating login to an identity provider or passkeys so you store fewer secrets at all.

3. How to say it

A model answer, about two minutes aloud

"I store a verifier, not the password, and I assume the table will leak. I use Argon2id, or scrypt or bcrypt, with a random salt per user and parameters tuned so one hash takes about a hundred milliseconds, recorded with the hash so I can raise them later. SHA-256 or MD5 would let an attacker try billions of guesses a second, unsalted hashes allow precomputed tables and reveal duplicate passwords, and encryption is reversible so the key becomes the single point of failure.

Around that I add rate limiting and lockout per account and per source, a check against known breached passwords, a pepper held outside the database in a secret manager, and constant-time comparison. I add a second factor, TOTP or passkeys, with a recovery flow no weaker than login, rehash on login when parameters improve, and alert on credential stuffing patterns. Better still, I delegate authentication to an identity provider so I store fewer secrets."

4. Likely follow-ups

What is a pepper?

A secret value mixed into every password hash and kept outside the database (secret manager or HSM), so a stolen table alone is not enough to crack hashes.

What is credential stuffing?

Attackers try username and password pairs leaked from other sites; defences are rate limiting, breached-password checks, MFA and bot detection.

Why are passkeys better?

They use public-key cryptography bound to the site's origin: nothing secret is stored on the server, nothing can be phished or reused elsewhere.

Common slips

  • "I would hash with SHA-256 and a salt."
  • Encrypting passwords instead of hashing them.
  • No plan for rate limiting or a second factor.
A senior prompt on tokens and multi-tenant APIs: reported by candidates, not official.

"Design authentication and authorisation for a multi-tenant SaaS API used by a web app, a mobile app and partner integrations."

A synthesis question. They want identity, tokens, scopes, tenant isolation and revocation in one coherent design.

1. Ask first

  • Which user types and integrations exist, and what must a leaked token be able to do? Users in the web and mobile apps, machine clients for partners; blast radius should be small.

2. How to think about it

  1. Delegate identity.Use an identity provider (OIDC): login, MFA, social and enterprise SSO (SAML/OIDC), password hashing, account recovery. Do not build it.
  2. Web and mobile.OAuth 2.0 authorisation code flow with PKCE; short-lived access tokens (about 5 to 15 minutes) and rotating refresh tokens; web apps use HttpOnly Secure SameSite cookies or a backend-for-frontend holding the tokens.
  3. Partners and machines.OAuth client credentials with scoped tokens, or API keys that are hashed at rest, scoped, rotatable and rate limited; mTLS for high-trust integrations.
  4. Verification at the API.A gateway or middleware validates signature (keys from the provider's JWKS endpoint, cached and rotated), expiry, issuer, audience and scopes; services trust only validated claims.
  5. Tenant isolation.The tenant id comes from the verified token, never from a request parameter; every query is scoped by tenant; automated tests that try cross-tenant access; row-level security as a second barrier.
  6. Revocation and incident response.Short lifetimes, refresh-token revocation, a denylist of token ids for emergencies, key rotation, audit logs of authentication and authorisation decisions.
  7. Say what you will not do.No secrets in JWTs, no long-lived access tokens, no custom crypto, no trust in client-supplied roles.

3. How to say it

A model answer, about two minutes aloud

"I would not build identity: I would use an OpenID Connect provider for login, MFA, SSO and recovery. The web and mobile apps use the authorisation code flow with PKCE and get short-lived access tokens of a few minutes plus rotating refresh tokens, with web tokens held in HttpOnly cookies or by a backend-for-frontend. Partners use client credentials with scoped tokens, or hashed, scoped, rotatable API keys, and mTLS where trust must be high.

The API gateway validates every token: signature with the expected algorithm and keys from the provider's JWKS, expiry, issuer, audience and scopes. The tenant id comes only from the verified token and every query is scoped by it, with row-level security as a second barrier and automated cross-tenant tests. For revocation I rely on short lifetimes, refresh-token revocation and an emergency denylist, with key rotation and audit logs. I would never put secrets in tokens or trust client-supplied roles."

4. Likely follow-ups

Why short-lived access tokens?

They cannot be revoked individually without a lookup, so a short lifetime bounds how long a stolen token is useful.

Where should a browser app keep tokens?

Not in localStorage (reachable by injected scripts); use HttpOnly Secure SameSite cookies or have a backend hold the tokens and give the browser a session cookie.

What is PKCE for?

It binds the authorisation code to the client that asked for it, so an intercepted code cannot be exchanged by someone else (essential for mobile and single-page apps).

Common slips

  • Putting the role in a client-controlled field or unverified token.
  • Long-lived access tokens with no revocation plan.
  • Rolling your own login.

8Remember thisRecap

The page in 6 lines

  • Authentication is who you are; authorisation is what you may touch. Check both on every request.
  • An IDOR is a missing ownership check: scope every query by owner or tenant.
  • Store a salted, slow hash of each password, never the password; add multi-factor for important accounts.
  • A JWT is signed, not secret: verify signature, expiry, audience and algorithm, and keep it short-lived.
  • Use TLS everywhere, mTLS between services, parameterised queries, and never turn verification off.
  • Keep secrets out of git, encrypt data with a wrapped data key, and rotate on any leak.

Check yourself

Why not just use random invoice ids?

Random ids make guessing hard, but the real fix is the ownership check; ids leak through logs, links and emails.

What does a salt do?

It makes equal passwords hash differently and forces an attacker to attack each hash on its own.

Why does envelope encryption help rotation?

Rotating the master key re-wraps only the small data key, so the large data is not re-encrypted.
