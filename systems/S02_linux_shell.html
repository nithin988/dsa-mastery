Module S02 of 29Foundations

Linux shell fluency

The shell is the fastest way to talk to a server. This module takes you from "where am I?" to pipelines, permissions and job control, with every command explained line by line and run for real.

6 lessons3 labs3 animations8 interview questionsabout 4 to 5 hours

Why this matters

A real situation

It is 2 a.m. The web server has stopped answering and the alert says the disk is full. You have a terminal and nothing else. Someone asks: which directory is eating the space, which log file is the biggest, can we clear it without breaking anything, and how do we know it worked?

An engineer who is fluent in the shell answers in a minute: look around, find the big files, read the end of the log, fix it, check. Everyone else is stuck. Interviews test exactly this: find the largest files, count the errors in a log, explain what a pipeline does, say what happens when you run a command. They also test something quieter: how calm and methodical you are when something is broken.

After this module you can
  • Move around the filesystem with absolute and relative paths without getting lost.
  • Read, create, copy, move and delete files, and know which of those actions cannot be undone.
  • Find any file or text on a machine with find, grep and friends.
  • Join small programs into pipelines and redirect output and errors on purpose.
  • Read and fix file permissions, and explain why chmod 777 is a bad fix.
  • Run, pause, stop and recover long-running jobs, and read exit codes.

Before you start

No Linux experience is needed. You need a terminal on Linux, macOS or Windows with WSL. Git Bash on Windows works for the first lessons but lacks some tools.

Everything on this page that says Real output was produced by running the command in a real Debian system. Your numbers (dates, sizes, usernames) may differ slightly; the shape of the output is what matters.

Your practice shell

The practice area is a small folder called ~/workshop full of safe files. Create it with one script. The script only ever creates or replaces ~/workshop, and it refuses to run if you already have a folder of that name that it did not create.

curl -fsSLO https://nithin988.github.io/dsa-mastery/systems/labs/linux/workshop.sh then bash workshop.sh. Read the script first if you like: less workshop.sh. No Linux machine? See the Docker option in the first lab.

The lessons

1

Where am I? The filesystem and paths

Must know
Situation

You open a terminal on a server and the cursor is blinking. You are somewhere, but where? Every command you type is interpreted relative to that place.

You will learn
  • What the current directory is and how to see it
  • Absolute and relative paths, ., .. and ~
  • How to list files, including hidden ones, and what each column means
Mental model

Linux has one tree of directories that starts at a single root, written /. There are no drive letters. Everything, including your documents, programs and even devices, hangs off that tree.

The shell always has a current directory. A path that starts with / is absolute: it says how to get there from the root and works from anywhere. A path that does not start with / is relative: it starts from the current directory. Most "No such file or directory" errors are a relative path used from the wrong place.

Everyday analogy: A path is like a postal address. An absolute path is the full address with country and city. A relative path is "two doors down from here", which only works if you are standing in the right street.

Traps to avoid

2

Reading, creating and removing files

Must know
Situation

A deploy failed and you need to read the end of a log, make a safe copy of a config before editing it, and clean up a scratch directory.

You will learn
  • View files: cat, head, tail, less, wc, file
  • Create, copy, move and rename: mkdir, touch, cp, mv
  • Delete: rm, rmdir, and why there is no undo
Mental model

In Linux almost everything is a file, and most files are plain text. Small programs read and write them: cat prints a whole file, head the first lines, tail the last lines (the end of a log is usually what you want), less lets you scroll a long file.

mv both moves and renames (renaming is just moving to a new name in the same place). cp makes a copy. rm deletes immediately: there is no recycle bin. The only safety net is your habit of checking before you press Enter.

Everyday analogy: rm is like shredding a paper instead of putting it in the bin. ls and echo first, then rm: look at exactly what the shell will hand to the command before it can hurt anything.

Traps to avoid
  • rm -rf deletes a directory and everything in it with no confirmation. Before running it, run the same command with ls instead and read what you would delete.
  • mv and cp silently overwrite an existing destination. Add -i to be asked first.

Finding things: find, grep and getting help

Must know
Situation

A teammate says "the setting is in some config file on that machine". You do not know where. You have two questions: which file, and which line in it.

You will learn
  • find locates files by name, type, size and age
  • grep locates text inside files
  • How to read built-in help when you do not remember a flag
Mental model

find walks a directory tree and prints the paths that match your conditions. grep reads lines of text and prints the ones that match a pattern. Together they answer "which file?" and "which line?".

You will never remember every flag. Professionals rely on three sources: command --help (quick summary), man command (the full manual), and the shell itself telling you what a name is with type.

Everyday analogy: find is asking the librarian to bring every book with a red cover. grep is opening each book and reading only the lines that contain a word.

4

Pipes, redirection and the three streams

Must know
Situation

The access log has thousands of lines. You do not need to read it: you need to know which pages fail with HTTP 500 and how often. One line of shell does it.

You will learn
  • stdin, stdout and stderr, and how to redirect each
  • Pipes: connecting programs
  • The classic trap: reading and writing the same file in one command
Mental model

Every program starts with three streams open. stdin (0) is where it reads input, stdout (1) is where normal output goes, and stderr (2) is where error messages go. By default stdin is your keyboard and the other two are your screen.

Redirection changes where a stream goes: > sends stdout to a file (replacing it), >> appends, 2> sends only errors, < reads input from a file. A pipe | connects the stdout of one program straight to the stdin of the next. That is the Unix idea: tiny programs, each doing one job, joined into something bigger.

Everyday analogy: Think of plumbing: a pipe joins one tap's output to the next machine's input. Redirection is putting a bucket under the pipe instead of letting the water run down the drain.

A trap everyone falls into once 
cp data/names.txt scratch/n.txt; sort -r scratch/n.txt > scratch/n.txt; wc -c scratch/n.txt

We try to sort a file back into itself. The shell opens (and empties) scratch/n.txt for the > before sort even starts reading, so sort reads an empty file. The result is 0 bytes: the data is gone. Always write to a different file, or use sort -o file file or sponge.

Real output · Debian GNU/Linux 13 (trixie), ordinary user

Traps to avoid
  • > file truncates the file immediately, even if the command then fails. command < file > file and sort file > file destroy the input.
  • 2>&1 must come after > file: cmd 2>&1 > file sends errors to the screen and only stdout to the file.
  • A pipe only carries stdout. Errors still go to the screen unless you add 2>&1 before the pipe.
5

Permissions and users

Must know
Situation

A deploy script says "Permission denied", and a teammate suggests chmod 777 on the whole folder to "make it work". You should be able to say why that is a bad idea and what the right fix is.

You will learn
  • Read the nine characters in ls -l and the numeric form (755, 644, 600)
  • Change permissions with chmod
  • What the execute bit means on files and directories
Mental model

Every file has an owner, a group and three sets of permission bits: what the owner may do, what the group may do, and what everyone else may do. Each set is made of read (r), write (w) and execute (x).

The kernel checks these bits on every access. For a file, x means "may run it as a program". For a directory, r means "may list the names" and x means "may enter it and reach things inside". Numbers are just shorthand: r = 4, w = 2, x = 1, added together per group, so rwxr-xr-- is 7, 5, 4 and the mode is 754.

Everyday analogy: Think of a building: the owner has all the keys, the group (the team) has a key card for some rooms, and everyone else only gets into the lobby. chmod 777 hands a master key to every visitor.

Running things as an administrator

sudo runs one command with administrator (root) rights after asking for your password. Use it only for the exact command that needs it. Habitually working as root is how people delete the wrong thing, which is why many systems log every sudo use.

Illustrative output · will differ on your machine
[sudo] password for learner:
Traps to avoid
  • chmod 777 makes a file or directory writable by every user and every program on the machine. It hides the real problem (wrong owner, missing x) and creates a security hole. Fix the owner or the specific bit instead.
  • chmod -R on a directory changes everything under it, including files that should stay private.
  • A directory without x cannot be entered even if you can read its name: this explains many confusing "Permission denied" messages.
6

Variables, exit codes and job control

Good to know
Situation

You started a long backup in your terminal and now need the terminal back, or the network dropped and you are not sure the command finished. You need to know how to run things in the background and how to tell success from failure.

You will learn
  • Shell variables, export and the PATH
  • Exit codes and &&, ||
  • Background jobs, Ctrl-C, Ctrl-Z, kill, and surviving a closed terminal
Mental model

A shell variable is a named piece of text: NAME=value sets it and $NAME reads it. A variable is only visible to programs you start if you export it. The most important one is PATH: the ordered list of directories the shell searches when you type a program name.

Every command ends with an exit code: 0 is success, non-zero is failure (the number says why). && runs the next command only if the first succeeded, and || only if it failed. Scripts, CI systems and monitoring all rely on exit codes, not on how the output looks.

Everyday analogy: Exit codes are the thumbs-up or thumbs-down a coworker gives when they finish a task. You can read the message they wrote (the output), but automation only looks at the thumb.

Variables and exit codes 
GREETING=hello; echo "$GREETING world"

Set a variable and read it back with $. No spaces around =.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
hello world
export COLOUR=blue; bash -c 'echo "child sees: $COLOUR"'

export makes the variable visible to programs started from here. The inner bash -c is a child process, and it can see COLOUR. Without export it would print an empty value.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
child sees: blue
true; echo "true gives $?"; false; echo "false gives $?"

true and false are tiny programs that only return an exit code. $? is the exit code of the previous command.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
true gives 0
false gives 1
mkdir -p scratch2 && echo "created"

&&: run the second command only if the first succeeded.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
created
cd /nonexistent 2>/dev/null || echo "could not change directory"

||: run the second command only if the first failed. We silenced the error message with 2>/dev/null.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
could not change directory
echo "$PATH"

The directories searched for programs, separated by colons, left to right. If two directories hold a program of the same name, the first one wins. This is how a wrong version of a tool ends up running.

Illustrative output · will differ on your machine
/usr/local/bin:/usr/bin:/bin:/usr/local/games
Jobs and signals

Job control works in an interactive terminal, so these are shown as illustrations rather than recorded runs.

sleep 300 &

A trailing & starts the command in the background. The shell prints a job number and the process id and gives the prompt back.

Illustrative output · will differ on your machine
[1] 4821
jobs

List background jobs.

Illustrative output · will differ on your machine
[1]+  Running                 sleep 300 &
kill %1

kill sends a signal; by default SIGTERM, a polite "please stop". %1 refers to job 1. If a process ignores it, kill -9 (SIGKILL) cannot be ignored, but it gives the program no chance to clean up.

Illustrative output · will differ on your machine
[1]+  Terminated              sleep 300
nohup ./backup.sh > backup.log 2>&1 &

nohup makes the command ignore the hangup signal sent when your terminal closes, so it keeps running after you disconnect. For serious long-running work use tmux or a service manager.

Illustrative output · will differ on your machine
[1] 4902
Traps to avoid
  • Ctrl-C stops (interrupts) the foreground command. Ctrl-Z only suspends it; it is still in memory until you fg (resume in front) or bg (resume behind) or kill it.
  • kill -9 should be the last resort. It skips cleanup, so locks, temporary files and half-written data can remain.
  • A script that ignores exit codes will happily carry on after a failure. That is how a failed cd leads to deleting the wrong directory.

Real-life cases

Real-life case

The command that ran on the wrong server

In January 2017 an engineer at GitLab was fixing a broken database replica. Tired and late at night, they ran a command to wipe a data directory, believing they were on the replica. They were on the primary. They noticed within a second or two, but about 300 GB of production data was already gone.

Recovery was made worse by something unrelated to the typo: several of the backup mechanisms were not working, and the failures had gone unnoticed. GitLab published a detailed, blameless postmortem and even streamed the recovery publicly.

What to take from it: Destructive commands deserve a pause to confirm which machine and which directory you are on (check the prompt, hostname and pwd). The postmortem's larger lesson: backups you have never restored are a hope, not a safety net.

Read the original public write-up

Real-life case

An empty variable in an rm -rf

In January 2015 a user reported that launching Steam on Linux deleted a large amount of their files after they had moved Steam's folder. Commenters on the public issue pointed at a line in Steam's start-up script of the form rm -rf "$STEAMROOT/"*, and discussed how an empty variable would turn that into a deletion starting at the filesystem root.

Be careful with the facts: the user's account and the commenters' theory are what the issue records; Valve's own explanation is not on that page. The pattern, however, is real and well known.

What to take from it: In scripts, never run a recursive delete on a path built from a variable that might be empty. Use set -u (error on unset variables), check the value first, and quote the variable. This is why careful engineers write rm -rf -- "${DIR:?}/"*.

Interview corner

Shell questions are asked in two ways: directly ("how would you find...") and through scenarios ("a disk is full, what do you do?"). Say the commands out loud and explain what each does.

Explain the difference between an absolute and a relative path. When does it matter?
Shape of a strong answer
  • Absolute starts at the root / and means the same thing everywhere. Relative starts from the current directory.
  • It matters in scripts and cron jobs: their current directory is often not what you expect, so absolute paths are safer.
  • Mention . .. and ~ as shortcuts.
Follow-ups to expect
  • What does cd - do?
  • Why does a cron job fail with a relative path that works in your terminal?
Common mistakes
  • Treating ~ as a magic path that works in every context (it is expanded by the shell, so not inside quotes or some programs).
What are stdin, stdout and stderr? How do you save only the errors of a command to a file?
Shape of a strong answer
  • Three streams every process has: input (0), normal output (1), error output (2).
  • command 2> errors.txt sends only stderr. command > out.txt 2>&1 sends both to one file.
  • Say why they are separate: so you can pipe real results while errors still reach a human.
Follow-ups to expect
  • What does 2>&1 > file do differently from > file 2>&1?
  • How do you throw errors away?
Common mistakes
  • Writing 2>&1 before the file redirection and expecting both to land in the file.
You run sort data.txt > data.txt and the file is empty. Why?
Shape of a strong answer
  • The shell processes the redirection first: it opens and truncates data.txt before sort starts.
  • sort therefore reads an empty file and writes an empty file.
  • Fixes: write to a temporary file then mv it back, or sort -o data.txt data.txt.
Follow-ups to expect
  • How would you edit a file in place safely?
Common mistakes
  • Blaming sort; the trap is in how the shell handles redirection.
A disk is 100% full. How do you find what is using the space?
Shape of a strong answer
  • df -h to see which filesystem is full.
  • du -sh /path/* | sort -rh | head to find the biggest directories, then repeat one level down.
  • find / -xdev -type f -size +500M for single huge files.
  • Check deleted-but-open files (lsof +L1) and inodes (df -i) if numbers do not add up.
  • Fix, then verify with df -h, and say how you would prevent it (log rotation, alerts).
Follow-ups to expect
  • Free space did not change after deleting a big log, why?
Common mistakes
  • Deleting things before knowing what they are.
  • Forgetting inode exhaustion.

Company angle: Amazon-style interviews often turn this into "how would you operate it": which alarm should have fired earlier, and how would you stop it recurring? Google SRE-style rounds expect a hypothesis-driven order (reported by candidates, not official).

What does chmod 755 mean? Why is chmod 777 discouraged?
Shape of a strong answer
  • Owner rwx (7), group r-x (5), others r-x (5): everyone may run or read, only the owner may change.
  • 777 lets any user or process write, which hides the real fix (owner or execute bit) and is a security hole.
Follow-ups to expect
  • What do the execute and read bits mean on a directory?
  • What are setuid and the sticky bit (briefly)?
Common mistakes
  • Saying x on a directory means "run"; it means "may enter".
You type ls and it works, but ./script.sh says "Permission denied". What happened and how do you fix it?
Shape of a strong answer
  • ls is found via PATH. A path with a slash runs the file directly, which needs the execute bit.
  • ls -l script.sh shows no x; fix with chmod +x script.sh.
  • Alternative: bash script.sh runs it as an argument to bash, which only needs read permission.
Follow-ups to expect
  • What if the filesystem is mounted noexec?
Common mistakes
  • Using sudo to "fix" it.
How do you keep a command running after you close your SSH session? How do you stop it?
Shape of a strong answer
  • nohup cmd & (ignores hangup), or run inside tmux or screen and detach, or make it a systemd service for anything permanent.
  • Stop with kill PID (SIGTERM first), then kill -9 only if it ignores that.
  • Find the PID with pgrep -f name or ps aux | grep name.
Follow-ups to expect
  • What is the difference between SIGTERM and SIGKILL?
Common mistakes
  • Reaching for kill -9 first.
What happens when you type ls -l and press Enter, at the level of the shell and the system?
Shape of a strong answer
  • The shell reads the line, splits it into words and expands variables and wildcards.
  • It looks for ls: a builtin? an alias? otherwise it searches the directories in PATH.
  • It starts a child process (fork) that runs the program (exec) with the arguments.
  • ls reads the directory through system calls, formats the result, and writes it to stdout; the shell waits and then shows the prompt, remembering the exit code.
Follow-ups to expect
  • Hard link vs symbolic link?
  • What is a system call?
Common mistakes
  • Skipping the PATH lookup and the child process.

Company angle: Reported by candidates as a Google SRE-style question that probes Unix internals; the next module goes deeper. Treat as a likely probe, not a guaranteed question.

Self-test

Answer in your head first, then open the question.

What is the difference between cd work and cd /work?

cd work is relative: it goes into a work directory inside the current one. cd /work is absolute: it goes to a work directory directly under the root.

Why does find . -name *.log sometimes behave strangely and how do you fix it?

The shell expands *.log against the current directory before find runs. Quote the pattern: find . -name "*.log".

What is the exit code of a successful command, and how do you read it?

0. Read it with $? immediately after the command.

What does cmd 2>&1 | tee out.txt do?

Sends stderr to stdout, then pipes the combined stream into tee, which shows it on screen and saves it in out.txt.

What permissions does mode 640 give?

Owner read and write, group read, others nothing.

Why can you not enter a directory that you can list?

Entering a directory needs the execute bit; listing only needs read. Without x you cannot reach anything inside.

Why does rm not ask for confirmation, and what is the safe habit?

Unix assumes you mean what you type; there is no recycle bin. Run ls with the same arguments first, use rm -i, or move files to a temporary folder before deleting.

What is the difference between && and ;?

; always runs the next command. && runs it only if the previous one succeeded.
