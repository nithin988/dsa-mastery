Chapter 3 of 9The ShopKart story

Make it fast

Why a tiny amount of memory in front of the database is the cheapest speed-up in system design, and why it is also the source of the most confusing bugs.

about 15 minutes4 steps3 real experiments3 interview questions

1Black Friday, 9:02 a.m.The story

ShopKart is two years old and doing fine. Every product page makes six database queries: the product, its photos, the price, stock, reviews and related items. With a few hundred visitors an hour nobody cares.

Then Black Friday starts. At 9:02 the pager goes off: the site is crawling, then failing. The web servers are bored (CPU 15%). The database is at 96% and its queue is growing. Pages that took 80 milliseconds now take eight seconds, and customers are leaving.

The senior engineer looks at the query log and sees something odd: the same six queries, over and over, for the same forty popular products. The database is working very hard to give the same answers it gave a second ago. The fix is not a bigger database. It is a place to remember answers.

2The idea: remember the answerThe idea

A cache is a small, fast place that remembers answers you already worked out, so the next person who asks does not make the slow system do the work again.

It works because real traffic is lopsided: a few items get most of the requests. Remembering only the hottest 5 to 20 percent of items can answer 70 to 90 percent of requests. Caches exist at every level (browser, CDN, web server, Redis, the database's own memory), and a request stops at the first level that has the answer.

3How it works, step by stepHow it works

  1. Look in the cache first

    Every question has a key, such as product:42. The web server asks the cache for that key before anything else. Memory is about a hundred times faster than disk.

  2. On a miss, ask the database, then remember the answer

    If the key is not there (never asked, expired, or pushed out), read the database once, save the answer in the cache, and return it. This is called cache-aside, and it is the pattern most real systems use.

  3. Decide how long to remember

    A cached answer can go stale. Give every entry a time to live (TTL) as a safety net, and delete the entry whenever you change the data, so the next read refills it with the new value. When memory is full, the cache throws away the least recently used entries.

  4. Protect the database from the crowd

    When a very popular entry expires, thousands of requests miss together and all ask the database at once: a stampede. Let one request rebuild it while the others wait, spread the expiry times with a little random jitter, and cache "not found" for missing keys.

4See it for realReal experiments

Three experiments, each a few lines of code you can run and change. First: what does a cache actually save? Then: why stale data appears, and the fix. Then: what a stampede looks like, and how one lock stops it.

1What does a cache actually save?

The whole idea in one experiment. A pretend database call takes 50 ms. Twenty identical lookups cost a full second without a cache. With a cache, the first lookup is a miss (50 ms, and the answer is stored) and the other nineteen are hits that take a fraction of a millisecond. Redis itself counts hits and misses, which is the number you watch in production.

20 lookups with a cache:        60 ms  (3.0 ms each)
Redis counted: 19 hits, 1 miss, hit ratio 95%

. ~/cache/rig.sh; redisup; cd ~/cache; cat > slow.py <<'EOF'
import sys, time
sys.path.insert(0, '.')
from rc import R, stat
r = R()
def slow_lookup(key):
    time.sleep(0.05)                       # pretend this is a database query that takes 50 ms
    return 'value-for-' + key
def cached_lookup(key):
    v = r.cmd('GET', key)
    if v is None:                          # miss: do the slow thing once, remember the answer
        v = slow_lookup(key)
        r.cmd('SET', key, v, 'EX', 60)
    return v
r.cmd('CONFIG', 'RESETSTAT')
t = time.perf_counter()
for _ in range(20): slow_lookup('item:1')
without = (time.perf_counter() - t) * 1000
t = time.perf_counter()
for _ in range(20): cached_lookup('item:1')
with_cache = (time.perf_counter() - t) * 1000
hits, misses = stat(r, 'keyspace_hits'), stat(r, 'keyspace_misses')
print('20 lookups without a cache: %6.0f ms  (%.1f ms each)' % (without, without / 20))
print('20 lookups with a cache:    %6.0f ms  (%.1f ms each)' % (with_cache, with_cache / 20))
print('Redis counted: %d hits, %d miss, hit ratio %d%%' % (hits, misses, 100 * hits / (hits + misses)))
EOF
python3 slow.py; redisdown

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

2Why stale data appears, and the fix

Cache-aside and its staleness problem, in a few lines. The first read is a miss (one database read), the second a hit (no database read). Then the database changes and nobody tells the cache: the next read returns the old value. Deleting the key on write fixes it (the next read reloads the new value). Write-through also gives a fresh value without any extra database read, because the cache was updated together with the database.

after delete-on-write:             Asha (plan v2)
after write-through:               Asha (plan v3)    (database reads: 2, no extra read needed)

import sys
sys.path.insert(0, '.')
from rc import R
r = R(); r.cmd('FLUSHALL')
db = {'user:1': 'Asha (plan v1)'}; db_reads = [0]
def db_read(k):
    db_reads[0] += 1; return db[k]
def get(k):                                          # cache-aside read
    v = r.cmd('GET', k)
    if v is None:
        v = db_read(k); r.cmd('SET', k, v, 'EX', 300)
    return v
print('read 1:', get('user:1'), '   (database reads so far: %d)' % db_reads[0])
print('read 2:', get('user:1'), '   (database reads so far: %d)' % db_reads[0])
db['user:1'] = 'Asha (plan v2)'                      # the database changes; nobody tells the cache
print('after an update, no invalidation: ', get('user:1'), '   <- STALE')
r.cmd('DEL', 'user:1')                               # invalidate on write
print('after delete-on-write:            ', get('user:1'))
db['user:1'] = 'Asha (plan v3)'; r.cmd('SET', 'user:1', 'Asha (plan v3)', 'EX', 300)   # write-through
print('after write-through:              ', get('user:1'), '   (database reads: %d, no extra read needed)' % db_reads[0])

3A stampede, and how one lock stops it

Forty requests ask for the same expired key at once. Without protection, nearly all of them miss and each runs the 300 ms query: forty database calls for one answer. With the lock, one caller wins SET ... NX and rebuilds the entry while the other thirty-nine poll the cache and return as soon as it appears: one database call. Same latency for users, one fortieth of the load for the database.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
no protection  40 simultaneous requests -> 40 expensive database calls, finished in  336 ms
with a lock    40 simultaneous requests ->  1 expensive database calls, finished in  342 ms

Show the command and the full explanation
. ~/cache/rig.sh; redisup; cd ~/cache; cat > stampede.py <<'EOF'
import sys, threading, time
sys.path.insert(0, '.')
from rc import R
calls = [0]; guard = threading.Lock()
def expensive():
    with guard: calls[0] += 1
    time.sleep(0.3)                                  # an expensive query: 300 ms
    return 'page'
def naive(r):
    if r.cmd('GET', 'page') is None:
        r.cmd('SET', 'page', expensive(), 'EX', 60)
def guarded(r):
    if r.cmd('GET', 'page') is not None: return
    if r.cmd('SET', 'page:lock', '1', 'NX', 'PX', 5000):         # only ONE caller wins the lock
        r.cmd('SET', 'page', expensive(), 'EX', 60); r.cmd('DEL', 'page:lock')
    else:                                                        # everybody else waits for the winner
        for _ in range(100):
            time.sleep(0.02)
            if r.cmd('GET', 'page') is not None: return
def run(fn):
    R().cmd('FLUSHALL'); calls[0] = 0
    ts = [threading.Thread(target=fn, args=(R(),)) for _ in range(40)]
    t = time.perf_counter(); [x.start() for x in ts]; [x.join() for x in ts]
    return calls[0], (time.perf_counter() - t) * 1000
for name, fn in (('no protection', naive), ('with a lock', guarded)):
    n, ms = run(fn)
    print('%-14s 40 simultaneous requests -> %2d expensive database calls, finished in %4.0f ms' % (name, n, ms))
EOF
python3 stampede.py; redisdown

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

5How it breaks in productionFailure modes

Stale data

The database changed and the cache still holds the old answer. Fix: delete the entry on every write, and keep a TTL as a safety net. Never cache what must be exactly current (balances, checkout stock).

Stampede

A hot entry expires and a thousand requests rebuild it together. Fix: one request rebuilds under a lock, TTLs get random jitter, the hottest keys refresh ahead of expiry.

Missing keys

Requests for things that do not exist always miss and always reach the database (a bug or an attack). Fix: cache "not found" for a short time, validate input.

Cold start

After a restart the cache is empty and the database takes the full load. Fix: warm it before taking traffic, restart nodes gradually, and rate limit as a backstop.

Too small

Memory fills, hot entries are evicted, and the hit ratio falls from 95% to 60%: the database load jumps eight-fold. Fix: size from the hot set, watch evictions and hit ratio.

6How real companies do itReal companies

Facebook

The paper on scaling memcache describes a lease mechanism: when a popular key is invalidated, only one client gets permission to refill it, which prevents a thundering herd and also stops stale values being written back.

Scaling Memcache at Facebook (NSDI 2013)
Netflix

Netflix has written about EVCache, a distributed in-memory cache built on memcached and replicated across zones, used so that most reads never reach the persistent stores.

Netflix Tech Blog: Caching for a Global Netflix
Everyone

Browsers and CDNs apply the same idea to web content: Cache-Control, ETag and 304 Not Modified let copies near the user be reused safely.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. Companies are not published official lists; these are the shapes of question candidates report.

A common system design prompt: reported by candidates at large tech companies, not official.

"Walk me through adding caching to a slow product page, end to end."

The capstone question for this chapter. They want a structured plan that uses what you know: measure, choose levels, patterns, sizing, failure handling, verification.

Ask first

  • What is the traffic, the page's content mix, and how fresh must prices and stock be? Prices tolerate a minute; stock at checkout must be exact.

How to think about it

  1. Measure first.Profile the page: which queries are slow, how many times each runs, and what fraction of requests ask for the same products (skew).
  2. Split by volatility.Product description and images: change rarely, cacheable for hours, CDN. Price: changes sometimes, tolerates a minute, cache with short TTL and invalidate on change. Stock level at checkout: not cached. Personalisation: separate, private.
  3. Choose levels.CDN for images and the shared part of the HTML; Redis for the assembled product data and expensive queries; database untouched except on a miss.
  4. Pick patterns and settings.Cache-aside with TTLs by data type, delete on write, jittered TTLs, a lock for rebuilds of the hottest products, negative caching for unknown IDs.
  5. Size it.Hot set of products times value size times measured overhead, plus headroom, sharded with replicas; use the hit-ratio curve to choose a target such as 90 percent rather than 99.
  6. Plan for failure and cold start.If Redis is down the page must still work (slower): timeouts on cache calls, fall back to the database with a rate limit. Warm the cache before a big sale.
  7. Verify with numbers.Before and after: database queries per second, page p50 and p99, hit ratio, evictions; run a load test including an expiry event.

How to say it

A model answer, about two minutes aloud

"I would start by measuring: which queries make the page slow, how often each runs, and how skewed the traffic is across products. Then I split the page by how it changes. Images and descriptions are static enough for the CDN with fingerprinted URLs. The assembled product data goes in Redis with cache-aside, a TTL by data type, and delete-on-write so edits show up quickly. Price tolerates a minute of staleness, stock at checkout is read from the database and never cached, and personalisation is loaded separately and kept private.

To protect the database I would add jitter to TTLs, a lock so only one request rebuilds a hot product, and negative caching for unknown IDs. I would size Redis from the hot set times the measured per-key memory with headroom, sharded with replicas, aiming for something like a 90 percent hit ratio since the curve flattens after that. If Redis fails, the page must still work, with timeouts on cache calls and a rate-limited fallback to the database. I would verify with before and after numbers: database queries per second, p50 and p99 latency, hit ratio and evictions, including a load test through a key expiry."

Likely follow-ups

How do you know the cache is not serving wrong prices?

Bound staleness with TTL and delete-on-write, sample cache against the database in a background check and alert on divergence, and make price changes publish an invalidation event.

The page is still slow on a cache hit. Why?

The time may not be in the data fetch: rendering, serialisation, large payloads, many sequential cache calls (batch them with MGET or pipelining), or other services. Profile before adding more caching.

How would you prepare for a flash sale?

Pre-warm the cache for sale items, raise TTLs for the duration, add replicas, rehearse a cold-cache scenario with the database protected by rate limits, and watch hit ratio and eviction live.

Common slips

  • Starting with Redis before measuring anything.
  • Caching stock or balances that must be exact.
  • Not saying what happens when the cache fails.
A frequent follow-up to "I would add a cache": reported by candidates, not official.

"What is a cache stampede, and how would you prevent it?"

A favourite follow-up after you say "I would add a cache". It tests whether you have thought about what happens at the moment a cache entry disappears.

Ask first

  • Which keys are hot, and how expensive is a rebuild? A stampede matters for hot keys with expensive rebuilds; a cheap query barely notices.

How to think about it

  1. Describe the failure precisely.A hot key expires or is evicted. Many concurrent requests miss, and each independently recomputes the value from the database. The database sees a burst of identical expensive queries exactly when load is highest, and can slow or fail, which makes the rebuild even slower and more requests pile up.
  2. Give the family of fixes.(1) Single flight: only one request rebuilds; others wait or reuse. (2) Serve stale while revalidating: keep the old value a little longer and refresh in the background. (3) Jittered TTLs so entries do not expire together. (4) Refresh ahead for the hottest keys. (5) Never let a cache expire on its own for the very hottest data: update it from the writer.
  3. Explain the lock approach concretely.SET lock NX PX 5000 gives the lock to exactly one caller and expires by itself if that caller dies; the winner recomputes, stores the value and deletes the lock; losers poll the cache briefly or return stale data.
  4. Mention the related problems.Cold start after a restart is a stampede on every key; penetration (missing keys) bypasses the cache entirely; hot keys overload one node.
  5. Say how you would test it.Load test with an expiring key and watch database queries per second: it should not spike.

How to say it

A model answer, about two minutes aloud

"A stampede is what happens when a very popular cache entry expires or is evicted: many concurrent requests all miss at once and each recomputes the same value from the database, so the database gets a burst of identical expensive queries just when traffic is highest, and may slow down or fail.

To prevent it I would make only one request rebuild the entry. In Redis that is a lock with SET NX and an expiry: the winner recomputes and refills the cache, and the others briefly wait for the cache to be filled or serve the previous value. I would also add random jitter to TTLs so entries do not all expire together, and refresh the very hottest keys before they expire. After a restart the whole cache is cold, which is a stampede on every key, so I would warm it or bring nodes back gradually. And I would load test an expiring hot key to see the database stays flat."

Likely follow-ups

What is stale-while-revalidate?

Serving the old value past its expiry while a background request fetches a new one: users never wait for a rebuild, at the cost of slightly older data.

What if the lock holder crashes?

The lock has an expiry (PX), so after that time another request can take it; choose it longer than a normal rebuild and shorter than your tolerance for a stall.

How does a Bloom filter help penetration?

It answers "definitely not present" cheaply for IDs that cannot exist, so invalid lookups are rejected before they reach the cache or the database; it may say "maybe present" wrongly but never the reverse.

Common slips

  • Only describing the problem without a concrete fix.
  • A lock without an expiry: one crash blocks the key forever.
  • Forgetting cold starts and missing keys, which are cousins of the same problem.
A frequent probing question about consistency: reported by candidates, not official.

"How do you keep a cache and a database consistent?"

One of the most common caching questions. The honest answer is that you cannot make them perfectly consistent for free, so you choose how stale is acceptable and how to bound it.

Ask first

  • How stale can this data be, and what happens if a user sees an old value? A profile picture can be minutes stale; a stock count at checkout cannot.
  • Read to write ratio, and how often is the same key written? Rarely-written data suits invalidation; constantly changing data may not suit caching at all.
  • Is there one writer path or many (several services update the same table)? Every writer must invalidate, which is easy to forget; a central write path is much safer.

How to think about it

  1. State the baseline.Cache-aside with a TTL and delete-on-write. The database is the source of truth; the cache is a disposable copy.
  2. Explain the order of operations.Write to the database, then delete the cache key. If you delete first, a concurrent read can reload the old value before the write lands and keep it for a whole TTL.
  3. Name the remaining race.A reader that missed before the write can still store its old value after your delete. This is rare and bounded by the TTL, which is why you always set one.
  4. Offer stronger options and their prices.Write-through gives fresh reads but ties writes to cache availability. Versioned keys (user:7:v12) avoid races. Event-driven invalidation publishes a change event that all caches consume (CDC), at the cost of infrastructure. For must-be-correct data, skip the cache or read from the primary database.
  5. Say what you monitor.Hit ratio, and sampled comparisons between cache and database to detect divergence.

How to say it

A model answer, about two minutes aloud

"I treat the database as the source of truth and the cache as a disposable copy. For reads I use cache-aside with a TTL. For writes I update the database first and then delete the cache key, so the next read reloads the fresh value. The order matters: if I deleted first, a concurrent read could reload the old value and keep it for the whole TTL.

There is still a small race, where a reader that missed before the write stores its old value after my delete, so every entry has a TTL that bounds staleness. If the business cannot tolerate that for some data, I would use write-through, versioned keys, or event-driven invalidation from a change stream, or I would not cache it and read from the primary instead. And I would monitor the hit ratio and compare samples of cache and database to catch divergence."

Likely follow-ups

Why delete rather than update the cache on a write?

Two concurrent writers can update the database in one order and the cache in the other, leaving the cache with the older value. Deleting lets the next read load whatever is currently in the database.

What is write-behind and when is it acceptable?

The cache acknowledges the write and the database is updated later in batches. It makes writes fast and cheap but can lose the last writes if the cache fails; it fits counters, metrics or view counts, not orders or payments.

What happens if the cache delete fails after the database write?

The cache keeps a stale value until the TTL. Retry the delete (from a queue if necessary), keep TTLs short for important data, and treat the TTL as the guaranteed bound.

Common slips

  • Updating the cache before the database.
  • Saying the cache and database are always consistent.
  • No TTL: one missed invalidation then lives forever.

8Remember thisRecap

The page in 6 lines

  • A cache remembers answers so the slow system does not repeat work; traffic is lopsided, so a small cache helps a lot.
  • Cache-aside: look in the cache, on a miss read the database and fill the cache.
  • Staleness is bounded by a TTL and fixed by deleting the entry on every write.
  • Hit ratio is the number to watch: 95% means the database sees one request in twenty.
  • The hard problems are stampedes, missing keys, cold starts and eviction thrash: each has a one-line fix.
  • Never cache what must be exactly current, and always say what happens when the cache fails.

Check yourself

What does a 95% hit ratio mean for the database?

It sees 5 requests for every 100: a twenty-fold reduction in load.

How do you keep a cache from serving stale data?

Delete the entry whenever the data changes, and give every entry a TTL as a safety net.

What is a cache stampede and the simplest fix?

Many requests rebuild an expired hot entry together; let one rebuild under a lock while the others wait.
