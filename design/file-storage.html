Design file storage and sync

Two stores in one: a tiny database that must never be wrong, and a giant blob store that must never lose a byte.

about 30 minutes2 real experimentsA common storage design question

1The one typo that cost a gigabyteThe question

ShopKart's designers share large product catalogues, some of them a gigabyte. The team first builds sync the obvious way: when a file changes, upload the new file. A designer fixes a typo on the train, and her phone spends the whole commute uploading one gigabyte over a poor connection. Worse, a colleague edited the same file the same hour, and one of the two edits vanishes.

So the question is a real one. How do you build something like Dropbox or Google Drive, where only the changed part travels, a dropped connection resumes, many devices stay in step, and nothing is ever lost?

The interviewer says: Design a photo and video storage service like Google Photos or S3. How are files stored, kept durable and served?

What they are looking for: A storage design question. They want upload paths, metadata, durability, cost and serving.

2What to ask before drawing anythingRequirements

Two minutes of questions is what separates a design from a guess. Write the answers on the board.

  • Object sizes, total volume, read to write ratio, durability and availability targets? Assume 2 billion photos a day... scaled down: 500 million uploads a day averaging 3 MB (1.5 PB/day), videos larger; eleven nines durability, 99.99% availability.

Functional: upload, download, edit files from several devices; devices sync automatically; share files; keep version history. Non-functional: never lose data (durability above all), upload only what changed, resume after a dropped connection, and show a consistent view of each folder.

3The numbers that shape the designEstimates

QuantityEstimate and what it tells you
Users and storage (assumption)100 million users with 2 GB each on average is 200 PB of logical data. These inputs are assumptions chosen for the arithmetic.
Replication versus erasure codingThree full copies would need 600 PB. A 10+4 erasure code uses 1.4 times the space: 280 PB. The recorded experiment shows the idea with 4+1 fragments at 1.25 times, and rebuilds a lost fragment.
Change rate (assumption)If each user changes files twice a day, that is 200 million syncs a day, about 2,300 per second. Most are small edits, so chunk level sync saves most of the bytes.
Chunk size (assumption)At 4 MB chunks, a 1 GB file is 256 chunks. A one typo edit changes 1 chunk, so about 4 MB travels instead of 1 GB.
Metadata versus dataMetadata (names, folders, chunk lists) is tiny, a few hundred bytes per file, but every operation touches it. Data is huge and touched rarely. Keep them in different systems.

1Chunks, hashes and erasure coding, measured

Two storage ideas in one experiment. Chunking with hashes: a 40 KB file and a copy with four changed bytes share every chunk but one, so storing the second version costs one chunk (and uploading it only needs the chunks the store lacks). This is the basis of deduplication and delta uploads in cloud storage. Erasure coding, in its simplest form: four data fragments plus one XOR parity fragment; when one fragment is lost the others and the parity reconstruct it exactly, for 1.25 times the space instead of the 3 times that replication would need for the same single-failure protection. Production systems use Reed-Solomon codes that survive several simultaneous losses.

mkdir -p ~/spec && cd ~/spec && python3 - <<'EOF'
import hashlib, os, random
rng = random.Random(8)
# Two "files" that differ by one small edit in the middle; store them as fixed-size chunks addressed by hash.
base = bytes(rng.getrandbits(8) for _ in range(40 * 1024))                       # a 40 KB file
edited = base[:20000] + b'EDIT' + base[20004:]                                   # the same file with 4 bytes changed
def chunks(data, size=4096): return [data[i:i + size] for i in range(0, len(data), size)]
store = {}
def put(data):
    keys = []
    for c in chunks(data):
        h = hashlib.sha256(c).hexdigest(); store.setdefault(h, c); keys.append(h)    # identical chunks are stored once
    return keys
v1 = put(base); v2 = put(edited)
print('file v1: %d chunks; file v2: %d chunks; distinct chunks actually stored: %d (instead of %d)' % (len(v1), len(v2), len(store), len(v1) + len(v2)))
print('uploading v2 after v1 needs only the chunks the store does not already have: %d of %d' % (len(set(v2) - set(v1)), len(v2)))
# Erasure coding with a single XOR parity fragment (the simplest case of the idea): any ONE of k+1 fragments can be lost.
k = 4; frags = [base[i * 10240:(i + 1) * 10240] for i in range(k)]
parity = bytes(a ^ b ^ c ^ d for a, b, c, d in zip(*frags))
print()
print('erasure coding (4 data fragments + 1 XOR parity = 1.25x the space):')
lost = 2; survivors = [f for i, f in enumerate(frags) if i != lost]
rebuilt = bytes(a ^ b ^ c ^ p for a, b, c, p in zip(*survivors, parity))
print('  fragment %d is lost (a failed disk); rebuilt from the other fragments and the parity: identical to the original = %s' % (lost, rebuilt == frags[lost]))
print('  replication would need 3x the space for the same single-failure protection; real systems use Reed-Solomon codes such as 10+4 (1.4x, any 4 losses).')
EOF

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

4A first design that worksArchitecture

  1. Cut files into chunks and name them by hash

    The client splits the file into chunks and computes a hash (a short fingerprint) of each one. The chunk's hash is its name, so identical chunks have identical names. Upload then asks: which of these names do you not have yet?

  2. Upload with a resume point

    The client uploads chunks in parts. If the link drops, it asks the server how many bytes arrived and continues from there. A final commit call swaps the file's chunk list in one atomic step, so nobody sees half a file.

  3. Metadata keeps the order of events

    The metadata database stores each file's current chunk list and a version number. Every change also gets a place in a per-user change log. This log is what other devices read to learn what happened.

  4. Other devices pull the changes

    A device keeps a long poll or a push channel open. When the log has news, it fetches the changed file entries, then downloads only the chunks it does not already have. If two edits clash, keep both and mark one as a conflicted copy.

5The hard part: never lose data, and keep devices consistentThe hard part

Every interview has one part where the answer is not obvious. Spend your time here.

Durability comes from the blocks. Erasure coding splits a chunk into fragments plus parity pieces spread over disks and zones. Any few can fail and the chunk is rebuilt. A background scrubber reads blocks and checks the hashes, because disks rot quietly. Deduplication falls out for free: a chunk with a known hash is never stored twice (be careful across users, since it can reveal that someone else already has a file).

Consistency comes from the metadata. The chunk list and the change log must be strongly consistent, so keep them in a sharded relational database or a consensus based store, shard by user, and commit each change in one transaction. The classic mistake is to put file bytes and file records in the same system: one needs cheap scale, the other needs strict correctness.

1Resume after a drop, then a ranged read

Resumable uploads and ranged reads with real HTTP. The file goes up in parts; after the connection "drops" the client asks the server how many bytes it has (HEAD), then sends only the remainder starting at that offset: no need to start over a multi-gigabyte upload, and the final checksum proves the object is intact. A Range request fetches just ten bytes from the middle, which is how video players seek and how downloads resume. Real object stores add parallel parts, a part list to assemble, a final commit and signed URLs, but the protocol idea is exactly this.

# A tiny blob server with resumable uploads: PUT with a Content-Range appends a part; HEAD tells the client how much has arrived.
import http.server, os, socketserver
os.makedirs('/tmp/blobs', exist_ok=True)
class H(http.server.BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def path_(self): return '/tmp/blobs/' + self.path.strip('/').replace('/', '_')
    def do_HEAD(self):
        p = self.path_(); size = os.path.getsize(p) if os.path.exists(p) else 0
        self.send_response(200); self.send_header('X-Received-Bytes', str(size)); self.send_header('Content-Length', '0'); self.end_headers()
    def do_PUT(self):
        n = int(self.headers['Content-Length']); start = int(self.headers.get('Content-Range', 'bytes 0-').split()[1].split('-')[0])
        p = self.path_(); have = os.path.getsize(p) if os.path.exists(p) else 0
        if start != have:                                                          # the client must continue exactly where the server stopped
            self.send_response(409); self.send_header('X-Received-Bytes', str(have)); self.send_header('Content-Length', '0'); self.end_headers(); return
        open(p, 'ab').write(self.rfile.read(n)); self.send_response(200); self.send_header('Content-Length', '0'); self.end_headers()
    def do_GET(self):
        p = self.path_(); rng = self.headers.get('Range'); data = open(p, 'rb').read()
        if rng: a, b = rng.split('=')[1].split('-'); data = data[int(a):int(b) + 1]; self.send_response(206)
        else: self.send_response(200)
        self.send_header('Content-Length', str(len(data))); self.end_headers(); self.wfile.write(data)
socketserver.TCPServer.allow_reuse_address = True
socketserver.TCPServer(('127.0.0.1', 8340), H).serve_forever()
EOF

2Content addressing saves space, measured

Three mechanisms in one run. Content addressing stores each distinct blob once: because almost half the pastes in this data set repeat popular contents, a large share of the bytes is never written twice. The expiry sweep deletes thousands of expired metadata rows in one indexed range delete (an index on expires_at is what avoids a full scan) and then removes only blobs that no remaining paste references. And a cache holding a small fraction of the pastes serves most reads, because popularity is heavily skewed. Together they answer the usual follow-ups: how do you save storage, how do you expire at scale, and how do you serve reads cheaply.

mkdir -p ~/warm && cd ~/warm && python3 - <<'EOF'
import hashlib, os, random, shutil, sqlite3, time
from collections import OrderedDict
rng = random.Random(4)
shutil.rmtree('blobs', ignore_errors=True); os.makedirs('blobs')
db = sqlite3.connect(':memory:')
db.execute('create table pastes(id integer primary key, hash text, size int, expires_at int)')
db.execute('create index pastes_exp on pastes(expires_at)')                    # makes the expiry sweep cheap
templates = ['error log line %d: connection refused\n' % i * 40 for i in range(300)]       # 300 distinct popular contents (logs, templates)
def new_content(i): return rng.choice(templates) if rng.random() < 0.45 else 'unique paste number %d: %s\n' % (i, 'x' * rng.randint(200, 3000))
now = 1_000_000; stored_bytes = logical_bytes = 0
for i in range(5000):
    data = new_content(i).encode(); h = hashlib.sha256(data).hexdigest(); logical_bytes += len(data)
    path = 'blobs/' + h[:2] + '_' + h[2:]
    if not os.path.exists(path): open(path, 'wb').write(data); stored_bytes += len(data)                 # store the blob only once
    db.execute('insert into pastes(hash, size, expires_at) values (?, ?, ?)', (h, len(data), now + rng.choice([60, 600, 3600, 86400])))
print('5000 pastes: %.1f MB submitted, %.1f MB actually stored (%.0f%% saved by content addressing)' % (logical_bytes / 1e6, stored_bytes / 1e6, 100 * (1 - stored_bytes / logical_bytes)))
# expiry sweep 10 minutes later: delete expired metadata in one indexed range delete, then blobs nobody references
later = now + 601
t = time.perf_counter(); n = db.execute('delete from pastes where expires_at < ?', (later,)).rowcount; el = (time.perf_counter() - t) * 1000
refs = {r[0] for r in db.execute('select distinct hash from pastes')}
removed = 0
for f in os.listdir('blobs'):
    h = f.replace('_', '')
    if h not in refs: os.remove('blobs/' + f); removed += 1
print('sweep: %d expired pastes deleted in %.1f ms (using the expiry index); %d orphan blobs removed, %d blobs kept (still referenced)' % (n, el, removed, len(os.listdir('blobs'))))
# a cache in front of reads: popularity is very skewed
ids = list(range(1, 3001)); weights = [1 / (i + 1) for i in range(len(ids))]
reqs = rng.choices(ids, weights, k=100000)
def hit_ratio(cap):
    c, hits = OrderedDict(), 0
    for k in reqs:
        if k in c: hits += 1; c.move_to_end(k)
        else:
            if len(c) >= cap: c.popitem(last=False)
            c[k] = 1
    return 100 * hits / len(reqs)
print('read cache: holding the hottest 5%% of pastes gives a %.0f%% hit ratio; 20%% gives %.0f%%' % (hit_ratio(150), hit_ratio(600)))
EOF

6Scale, failure and trade-offsDeep dive

Hot shared folder

Thousands of people edit one shared folder, and one metadata shard takes all the writes. Batch change log appends and cache read views; as a last resort split by sub folder.

A zone or disk dies

Erasure coding across zones rebuilds lost fragments. Budget repair bandwidth so rebuilding does not starve normal traffic.

A bug uploads garbage

Hashes are verified on upload and again on read. Versioning means a bad write can be rolled back to the previous chunk list.

Orphan chunks

Deleted files leave unreferenced chunks. A garbage collector counts references, waits a safe delay, then deletes.

Privacy and deduplication

Cross user deduplication can leak whether a file exists. Dedupe inside an account, or require proof the client holds the file before linking it.

3. How to say it

A model answer, about two minutes aloud

"Photos are large immutable blobs, so I would use an object store and keep metadata in a separate database. At 500 million uploads a day that is about 6,000 uploads a second and 1.5 petabytes a day, so cost and durability dominate. Clients get a presigned URL or a multipart upload id from the API after auth and quota checks and upload parts directly to the store, resumable; a completion call verifies size and hash and makes the object visible. Thumbnails, transcoding and scanning run asynchronously from a queue.

The store separates a sharded metadata service from the data nodes and places data across zones with erasure coding such as ten plus four for durability at about 1.4 times the space, with SSD for recent objects and a cold tier for old ones through lifecycle rules, and scrubbing to repair silent corruption. Reads go through a CDN with cached renditions and ranged requests for video. Albums, owners and labels live in a separate database. The costs are storage and egress, so tiering, compression and CDN hit ratio are the levers."

4. Likely follow-ups

Replication or erasure coding?

Replication for hot, small or latency-sensitive data (simple, fast repair); erasure coding for large, cold data where space dominates, accepting slower reads on failure and costlier repair.

How do you avoid sending large uploads through your servers?

Presigned URLs (or signed upload policies) let clients write directly to the store; your API only authorises and records metadata.

How do you handle deletion and privacy?

Soft delete in metadata, then asynchronous hard deletion with a grace period; reference counting if deduplicated; verify deletion across replicas and backups.

Common slips

  • Storing photos in the relational database.
  • Routing all bytes through the application servers.
  • No story for durability beyond "we have backups".

8Remember thisRecap

The page in 6 lines

  • Two systems: small strongly consistent metadata, huge immutable blocks.
  • Cut files into chunks named by hash: only new chunks are uploaded (1 of 10 in the recorded run).
  • Resumable upload: ask how many bytes arrived, then continue from there.
  • Erasure coding gives durability at 1.4 times the space (10+4) instead of 3 times.
  • A per user change log tells other devices what to pull.
  • Conflicts keep both copies; deleted chunks are removed by a careful garbage collector.

Check yourself

Why name chunks by their hash?

Identical content has an identical name, so duplicates are never stored or uploaded twice and corruption is easy to detect.

Why not three full copies?

That costs 3 times the space; erasure coding such as 10+4 survives more failures for 1.4 times.

How does a second device learn about a change?

It reads the per user change log, then downloads only the chunks it lacks.
