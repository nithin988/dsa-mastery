Chapter 1 of 9The ShopKart story

Think in numbers

Before you draw a single box, work out how big the thing will get. A few multiplications turn a guess into a plan, and they are the most useful skill in a design interview.

about 15 minutes4 steps4 real experiments3 interview questions

1Three weeks before launchThe story

ShopKart is two founders and a laptop. Launch is in three weeks. An advisor looks at the plan and asks one simple question: "How many servers do you need for launch?" There is a long silence. One founder says, "One big one, I think?" Nobody knows if that is right.

The advisor takes a napkin. "How many people will visit in a day?" The founders hope for 100,000. "How many clicks each?" About 30. So 100,000 times 30 is 3 million requests a day. A day has 86,400 seconds, so that is 35 requests a second on average, and the busiest hour is roughly three times that: about 104 a second. If one server handles about 100 a second and you keep it 60% busy, you need two.

The whole thing took two minutes, and it changed the conversation from opinion to numbers. But ShopKart still buys the single cheap server, because "35 a second sounds small". The napkin used an ordinary day. Launch day will not be ordinary, and chapter 2 shows what that costs.

2The idea: estimate first, then designThe idea

A back-of-envelope estimate is quick arithmetic with rounded numbers that tells you the size of a problem, so you pick the right kind of design.

The result decides the design. 35 requests a second is a tiny system: one or two servers and one database. 35,000 a second is a different world, with many servers, caches and copies of the data. Interviews follow the same path: requirements, numbers, data, a first design, a deep dive, then trade-offs. Always state assumptions and trade-offs out loud, because that is the part the other person is grading.

3How it works, step by stepHow it works

  1. Start with what it must do, how well, and how big

    Write three short lists: what the system does (browse, buy, pay), how well (fast, always up, never loses an order), and how big (users, requests, data). Most bad designs answer a question nobody asked.

  2. Know a few numbers by heart

    Memory is fast, the network is slower, and crossing an ocean is slower still: the gaps are a thousand times or more. Knowing these gaps tells you why caches, copies near users and fewer network calls exist.

  3. Turn users into load and servers

    Requests per day divided by 86,400 seconds gives requests per second. Multiply by about 3 for the busiest hour, then divide by what one server can do (and keep it about 60% busy so there is room to spare).

  4. Estimate storage, and say the trade-off

    Rows per day times bytes per row times days gives storage. Then state the choice you made and what it costs: "One database is simple and cheap now, but I will need a copy for safety." Naming the price of a choice is what makes it a design.

4See it for realReal experiments

Every output below was recorded from a real run on Debian Linux as an ordinary user. Read it line by line.

Four short experiments. First: how much slower is each kind of access, measured on a real machine. Then: the same arithmetic as the napkin, on a bigger system of 40 million users, to see load, storage and servers come out of simple multiplication.

1How different are memory, disk and network speeds?

Three measurements on your own machine: a dictionary lookup (memory), reading a cached 4 KB file (page cache) and a round trip over the loopback network. Python adds its own overhead, so read the ratios, not the digits. A real network hop between machines is slower again.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
memory lookup            96 ns
file read, 4 KB       6720 ns
local TCP round trip  69140 ns
Show the command and the full explanation
mkdir -p ~/dsg && cd ~/dsg && cat > lat.py <<'EOF'
import time, socket, threading, os
def t(f, n):
    s = time.perf_counter()
    for _ in range(n):
        f()
    return (time.perf_counter() - s) / n * 1e9
d = {i: i for i in range(1000)}
print('memory lookup      %8.0f ns' % t(lambda: d[500], 200000))
open('x.bin', 'wb').write(os.urandom(4096))
def rd():
    with open('x.bin', 'rb') as f:
        f.read()
print('file read, 4 KB   %8.0f ns' % t(rd, 20000))
srv = socket.socket(); srv.bind(('127.0.0.1', 0)); srv.listen()
port = srv.getsockname()[1]
def echo():
    c, _ = srv.accept()
    while True:
        b = c.recv(64)
        if not b:
            break
        c.sendall(b)
threading.Thread(target=echo, daemon=True).start()
cl = socket.create_connection(('127.0.0.1', port))
def rt():
    cl.sendall(b'x'); cl.recv(64)
print('local TCP round trip %6.0f ns' % t(rt, 20000))
EOF
python3 lat.py

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

40 million daily users each sending 25 messages: about 11,600 messages per second on average and about 35,000 at the peak. Shell arithmetic is enough for estimates.

Storage: one billion messages a day at 150 bytes each is 150 GB a day, about 55 TB a year. Python is handy once numbers get large.

4From peak load to a number of servers

Servers: one machine handles 2,000 requests per second, but we plan for 60% utilisation so a failure or spike does not topple the rest. 34,722 divided by 1,200 usable requests per second, rounded up, is 29 servers.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
servers: 29
Show the command and the full explanation
python3 -c "import math; peak=34722; per_server=2000; util=0.6; print('servers:', math.ceil(peak/(per_server*util)))"

5How it breaks in productionFailure modes

Using the average, not the peak

35 requests a second is the daily average, but real traffic arrives in waves. Size for the busiest hour (about 3 times the average) and for special events such as a launch or a sale.

Hiding the assumptions

"We need 29 servers" means nothing without "I assumed 2,000 requests a second per server and 60% busy". Say each assumption so the other person can fix it.

False precision

11,574 requests a second and "about 10,000" lead to the same design. Round early and keep the arithmetic easy to follow.

Planning only for today

Systems that are right today are wrong in a year. Leave room for 3 to 10 times growth, and say which part will break first.

No trade-off named

Every choice has a price: cheaper but slower, simpler but less safe. A design with no stated price sounds like a design nobody has thought about.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

The shape of estimation question candidates report at many large companies (chat, feed, storage): reported by candidates, not official.

"Estimate the load and storage for a chat app with 40 million daily users."

Give me requests per second, storage per year and a rough number of servers. Talk me through the arithmetic.

1. Ask first

  • What counts as a request: a message sent, or any call to the server? Pick one and say it. For this estimate, one message sent equals one request.
  • How many messages does a user send a day, and how big is a message? Assume 25 messages a day and about 150 bytes each. Say these are assumptions.
  • How long do we keep messages, and is there a launch or peak event? Assume we keep them for years; peak hour is about 3 times the average.

2. How to think about it

  1. Messages a day.40 million users times 25 messages is 1 billion messages a day.
  2. Requests per second.1 billion divided by 86,400 is about 11,574 a second on average, and about 34,722 at peak (3 times).
  3. Storage.1 billion messages times 150 bytes times 365 days is about 54.8 TB a year, before copies and indexes.
  4. Servers.If one server handles 2,000 requests a second and we keep it 60% busy, that is 1,200 each, so 34,722 divided by 1,200 is about 29 servers.
  5. Sanity check and trade-off.29 servers and 55 TB a year is big but ordinary: it needs many servers and data spread over several databases, but not an exotic design.

3. How to say it

A model answer, about two minutes aloud

"Let me state my assumptions: 40 million daily users, 25 messages each, about 150 bytes a message. That is 1 billion messages a day. Divided by 86,400 seconds, it is about 11,500 messages a second on average, and about 35,000 at the busiest hour if I use a factor of three.

For storage, 1 billion messages times 150 bytes is 150 GB a day, about 55 TB a year before replicas. If a server handles 2,000 requests a second and I keep it 60% busy, I need about 29 servers at peak. So this needs many servers and the data split across machines, which I would plan for from the start. I would double check the 150 byte assumption first, because storage scales directly with it."

4. Likely follow-ups

Why multiply by 3 for the peak?

Traffic is not flat: evenings and events are busier than the daily average. 3 is a common rule of thumb; use your own data if you have it.

What would change if messages included photos?

Storage jumps by orders of magnitude, since a photo is hundreds of KB against 150 bytes of text. Photos would go to cheap object storage and a CDN, not the main database.

How do you know your estimate is reasonable?

Compare with known systems, check the units, and see whether the answer changes your design. If 10 times more or less would give the same design, the estimate is good enough.

Common slips

  • Starting to draw boxes before knowing the size.
  • Giving numbers with no assumptions behind them.
  • Using the daily average instead of the peak.
  • Mixing up bits and bytes, or MB and GB.
A very common opening move in system design interviews: reported by candidates, not official.

"Design a photo sharing app." (A vague question: where do you begin?)

I have given you one line on purpose. Show me how you would start, before any design.

1. Ask first

  • Who are the users and what are the main actions? Upload a photo, see a feed, follow people. Say which three you will cover and which you leave out.
  • What matters most: speed, never losing a photo, or cost? Ask. Usually: never lose a photo, fast feed, cost second. This guides every later choice.
  • How big: users, uploads a day, photo size? If they do not say, offer an assumption and do the arithmetic.

2. How to think about it

  1. Do not draw yet.Spend the first minutes on requirements: what it does, how well, how big.
  2. Estimate.For example 10 million daily users, 1 upload each at 2 MB is 20 TB a day: that tells you photos need object storage and a CDN, not the main database.
  3. Name the first design and the likely trouble spot.Upload service, object storage, metadata database, feed. The trouble is storage cost and feed speed.
  4. Flag trade-offs as you go.Fast uploads versus checking each photo, for example. Say which you chose and what it costs.

3. How to say it

A model answer, about two minutes aloud

"I would start with requirements, not boxes. For this app I would cover uploading a photo, following people and viewing a feed, and leave comments and messages out for now. The quality that matters most is never losing a photo, then a fast feed.

Then a quick estimate: if 10 million people upload one 2 MB photo a day, that is about 20 TB a day, so photos go to cheap object storage behind a CDN, and only small records go in the database. With that size in mind I can draw the upload path and the feed, and I will say the price of each choice as I go."

4. Likely follow-ups

Why ask questions before designing?

The right design depends on size and priorities. A design for 1,000 users is wrong for 100 million and costs time to build.

What if the interviewer will not give numbers?

Offer your own, say they are assumptions, and ask if they are close enough. That shows the skill.

Common slips

  • Jumping straight to databases and load balancers.
  • Asking too many questions and never designing.
  • Never saying what the numbers imply for the design.
A behavioural style follow-up reported by candidates, not official.

"What trade-off did you make there, and why?"

You picked an option. Tell me what you gave up. They are testing whether you know every choice has a price.

1. Ask first

  • Which choice are they asking about? Name it clearly first: for example one database instead of many, or a cache instead of fresh reads.
  • What does the product need most? The trade-off only makes sense against a goal: speed, safety, cost or simplicity.

2. How to think about it

  1. Say what you chose and what you gain.For example: one database is simple and cheap to run.
  2. Say what you give up.It is a single point of failure and has a ceiling on size and writes.
  3. Say when you would change your mind.When writes pass what one machine handles, or when downtime costs more than the extra copy.

3. How to say it

A model answer, about two minutes aloud

"I chose a single database with one copy for backup. The gain is that it is simple, cheap and easy to reason about. The price is that it is a single point of failure, with a ceiling on how much it can handle.

At today's size, about a hundred requests a second and a few gigabytes, that price is fine. I would change my mind when traffic or data grows a lot, or when an hour of downtime costs more than running a second copy."

4. Likely follow-ups

How would you know when to change?

Watch numbers: database CPU, write rate, storage, and the time to recover from a failure. Set a threshold in advance.

Is there ever a choice with no trade-off?

Rarely. If you cannot find the price, you have not looked closely enough.

Common slips

  • Presenting a choice as obviously best.
  • Listing downsides but never saying when they matter.
  • Not tying the trade-off to the goals of the product.

8Remember thisRecap

The page in 6 lines

  • Estimate before you design: the size of the problem decides the shape of the solution.
  • Requirements come first: what it does, how well, how big.
  • Know the gaps: memory, the network in one data centre and across an ocean differ by orders of magnitude.
  • Users per day times actions, divided by 86,400, gives the average per second; multiply by about 3 for the peak.
  • Storage is rows times bytes times days; divide peak load by one server's share (at about 60% busy) for servers.
  • State assumptions and the price of each choice out loud.

Check yourself

How many requests a second is 3 million requests a day?

About 35 (3,000,000 divided by 86,400).

Why design for the peak and not the average?

Traffic comes in waves and events; a system sized for the average fails exactly when the most customers arrive.

Why keep a server only about 60% busy?

It leaves room for spikes, failures and slow requests; at 100% busy, queues build and everything gets slow.
