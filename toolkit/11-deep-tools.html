When the usual tools are not enough

Four tools that look inside one process or one connection when the metrics and the logs have nothing left to say.

about 15 minutes4 steps4 real experiments3 interview questions

13:12 a.m., and everything is greenThe story

The pager says orders are not being confirmed. Customers pay, then stare at a spinner. Mira, the engineer on call with you, opens every dashboard: CPU 1%, memory fine, disk fine, no errors. The worker process that confirms orders, order-sync, is running.

But the queue of orders waiting has grown from nothing to 1,400 in forty minutes, and the worker has not written a log line since 2:31. A busy process shows up as CPU. A crashed one shows up in the logs. This one is neither: it is waiting for something that never arrives.

The usual tools have run out, so you look at the process itself. One command shows the single call it is stuck in. Another shows who is on the other end: a connection to the payment gateway, opened with no timeout. A restart drains the queue by 3:34. A timeout in the code, shipped the next morning, makes sure it cannot happen again.

2The idea: ask the process, not the dashboardThe idea

Metrics and logs are what the program chose to tell you. Deep tools ask the machine what is really happening: which calls a process makes, what it holds open, what crosses the wire and where it died.

These tools work on any language, because every program talks to the machine the same way, through system calls and sockets. Start with the first 60 seconds checklist from the performance chapter. Reach for these only when it points at one process or one connection and still gives no reason.

3How it works, step by stepHow it works

  1. strace: what is the process asking the kernel for?

    A program cannot touch a file, a socket or a clock by itself: it asks the kernel through a system call such as openat or read. strace prints each call and its result, so a hung process shows its last call with no result, and a failing one shows the error code.

  2. lsof: what does it hold open, and who owns the port?

    On Linux a file, a socket and a pipe are all file descriptors, small numbers each process holds. lsof lists them for any process, or tells you which process listens on a port. It also finds a deleted file that a process still holds, which keeps the disk full.

  3. tcpdump: are the packets really arriving?

    tcpdump prints the packets that cross a network interface. Always give it a filter such as tcp port 8084. A healthy conversation starts with the handshake flags S, S., ., then data. A lone S repeated means nobody answered.

  4. Core dump and gdb: read a crash after the fact

    When a native program crashes it can leave a core file, a snapshot of its memory. gdb loads the program and the core and prints the backtrace: the chain of function calls that led to the crash, with the bad value in the top frame.

2Find a deleted file that is still using space

We keep a file open on descriptor 4, then delete it. The name is gone, but /proc/PID/fd/4 still points to it and is marked (deleted), and lsof +L1 finds it (link count 0). Its space stays used until descriptor 4 is closed.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
/proc/4839/fd/4 -> /home/learner/deep/held.log (deleted)
bash 4w 0

5How it breaks in productionFailure modes

strace slows the process

The strace manual notes that a traced process runs more slowly than a normal one. On a busy production service that can turn a small problem into an outage. Fix: trace one process briefly, filter with -e, or use strace -c for a summary.

A capture with no filter

tcpdump on a busy interface prints thousands of lines a second, fills disks and records data you should not keep. Fix: always filter by host and port, limit with -c, and keep captures private and short.

Encrypted traffic

On HTTPS the packets show who talked and when, but not what was said. Fix: use the capture to prove the connection and its timing, and read the content in the application logs or with a test client.

No permission, or no symbols

Attaching to another user's process needs root, and a binary built without debug information gives a backtrace of bare addresses. Fix: run as the right user, and keep the symbol files for every release.

Core dumps fill the disk

A core file holds the process memory: it can be large and it can contain passwords. Fix: set a size limit, store cores in a protected folder, and clean them out.

Looking at frame zero only

The top frame shows where it crashed, but the cause is often a caller that passed a bad value. Fix: read the whole backtrace, and print the arguments of each frame.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A common senior systems question: reported by candidates at large tech companies, not official.

A process hangs and uses no CPU. How do you find out why?

Reported by candidates as a common senior systems question at large tech companies; not official.

How to say it

A model answer, about two minutes aloud

It is blocked, not busy. Run it under strace -f or attach with strace -p, and read the last line: the call without a result is what it waits for.

Map descriptors to files or sockets with ls -l /proc/PID/fd or lsof -p PID.

Typical causes: waiting on a pipe, a lock or a network peer.

Likely follow-ups

• What if you cannot attach to the process?

• What does state D mean?

Common slips

  • Restarting without looking.
Reported by candidates as a classic Linux question, not official.

`df` says the disk is 100% full but `du` adds up to far less. Why, and what do you do?

A classic Linux operations question: reported by candidates, not official.

How to say it

A model answer, about two minutes aloud

A deleted file is still held open by a process, so its blocks are not freed.

Find it with lsof +L1 (or /proc/PID/fd links marked deleted).

Free the space by restarting the process, or truncate the file through /proc/PID/fd/N if a restart is not possible.

Likely follow-ups

• Why does Linux behave this way?

Common slips

  • Deleting more files.
Reported by candidates for roles that run native code, not official.

A native program crashed in production and left a core file. What do you do?

A question for roles that run native code: reported by candidates, not official.

How to say it

A model answer, about two minutes aloud

Load it with gdb ./prog core (using the same binary, ideally with symbols) and run bt for the backtrace.

Inspect arguments and locals at the failing frame to find the bad value, then fix and add a regression test.

Make sure core dumps are enabled, stored safely and limited in size.

Likely follow-ups

• What if the binary has no symbols?

Common slips

  • Looking only at frame #0 and ignoring the caller.

8Remember thisRecap

The page in 6 lines

  • When metrics and logs are silent, look at the process itself.
  • strace shows the calls a process makes; the last call with no result is what it waits for.
  • lsof shows what a process holds open, who owns a port, and deleted files that still use space.
  • tcpdump with a filter proves whether packets arrive: S, S., then data is healthy.
  • A core file plus gdb bt shows the chain of calls to a crash; read the callers, not only frame 0.
  • Every deep tool has a cost: trace briefly, filter captures, protect core files.

Check yourself

A process uses no CPU and does nothing. Which tool first?

strace -p PID (or strace -f on a new run): the last call without a result is what it waits for.

df says full but du is small. What do you check?

lsof +L1 for a deleted file that a process still holds open.

What does a repeated lone S in tcpdump mean?

The client keeps sending connection requests and nobody replies: the packets are lost or the server is not answering.
