Scaling data: replication, partitioning, sharding and NoSQL

One database server has limits: reads, writes, size, and the risk of being a single point of failure. This module takes them one at a time with real systems: a PostgreSQL primary and a streaming replica (watch lag, promote, cause a split brain on purpose), a partitioned table with pruning, real shard routing and resharding, key-value, document and log-structured stores, and finally how to choose and size a store and defend it in an interview.

6 lessons2 labs0 animations6 interview questionsabout 9 to 11 hours

Why this matters

A real situation

After caching and indexing, the database is usually the next wall. Each way past it (replicas, partitions, shards, a different store) fixes one limit and creates new problems, and the interview skill is knowing which limit you are at, which tool answers it and what it costs.

These are the topics where confident but wrong answers are most common: replicas do not scale writes, synchronous replication can stop your writes, sharding by the wrong key creates a hot shard, and "use NoSQL, it scales" is not an argument.

Everything here is run for real, so the words (lag, split brain, pruning, resharding, compaction) become things you have watched happen.

After this module you can
  • Build a real primary and replica, measure replication lag and explain read-your-writes problems and their fixes.
  • Compare asynchronous and synchronous replication, promote a replica, and explain split brain, fencing and recovery objectives.
  • Partition a table by range, read a pruned plan, and retire data by dropping a partition.
  • Route data to shards, explain scatter-gather, resharding with mod N versus consistent hashing, and hot shards.
  • Explain key-value, document and wide-column (LSM) stores and what each gives up.
  • Choose a store from access patterns and consistency needs, size it with back-of-envelope arithmetic and state the assumptions.
  • Answer scaling-data interview questions with a ladder of options, numbers and trade-offs.

1

Replication: copies for reads and for survival

Must know
Situation

One database server answers 90 percent reads and the CPU is at 85 percent. Adding a second copy that serves the reads sounds easy. It is, until a customer places an order, refreshes the page and the order is not there.

You will learn
  • How a replica is built and kept up to date (the log stream)
  • Why replicas are read-only and what that gives you
  • Replication lag and read-your-writes
  • Setting up a real replica and watching it work
Mental model

Replication keeps one or more copies of a database on other machines. In PostgreSQL (and most databases) the primary accepts writes and ships its write-ahead log to replicas, which replay it and stay read-only. This gives you read scaling (send reads to replicas), availability (a replica can be promoted if the primary dies) and a place to run slow reports and backups without disturbing production. It does not scale writes: every write still happens on the primary and on every replica.

The default is asynchronous replication: the primary acknowledges a commit as soon as its own log is safe, before replicas have applied it. So a replica is always slightly behind (replication lag): usually milliseconds, but seconds or minutes under load or network trouble. Consequences you must design for: a user can write and then read stale data from a replica (read-your-writes violated), and two reads from two replicas can disagree. Common fixes: read your own recent writes from the primary, pin a session to one replica, or send reads to a replica only when its lag is below a threshold.

Everyday analogy: A newspaper with regional print shops: the head office (primary) sends each edition's content to the shops (replicas) by courier. Readers near a shop get it quickly, but for a short while the shop still prints yesterday's edition.

The picture
How it works, step by step
  1. Clone the primarypg_basebackup copies the primary's data files to a new directory and writes a recovery configuration that points back at the primary.
  2. The replica streams the logIt connects to the primary and receives the write-ahead log continuously, replaying each record.
  3. Reads work, writes are refusedThe replica is in recovery mode: queries are allowed, writes fail with a read-only error.
  4. Lag is the gapBetween commit on the primary and replay on the replica there is a delay. You can see it in pg_stat_replication.
  5. Design around the gapRoute reads that must be fresh to the primary, and everything else to replicas.
Build a real replica and watch lag 
mkdir -p ~/rep && cd ~/rep && cat > rig.sh <<'EOF'
# A private PostgreSQL primary (port 5551) and a streaming replica cloned from it (port 5552). Sockets in ~/rep.
export PG=$(ls -d /usr/lib/postgresql/*/bin | head -1); export PATH=$PG:$PATH
export R=$HOME/rep PGUSER=learner
pq() { psql -X -q -h $R -p 5551 -d postgres "$@"; }       # talk to the primary
rq() { psql -X -q -h $R -p 5552 -d postgres "$@"; }       # talk to the replica
priup() { [ -d $R/primary ] || initdb -D $R/primary -A trust -U learner >/dev/null
          pg_ctl -D $R/primary -o "-p 5551 -k $R -c listen_addresses='' -c fsync=off $*" -l $R/primary.log -w start >/dev/null; }
repup() { priup "$1"; rm -rf $R/replica
          pg_basebackup -h $R -p 5551 -D $R/replica -R -X stream >/dev/null 2>&1
          pg_ctl -D $R/replica -o "-p 5552 -k $R -c listen_addresses='' -c fsync=off $2" -l $R/replica.log -w start >/dev/null; }
repdown() { pg_ctl -D $R/replica -m fast stop >/dev/null 2>&1; pg_ctl -D $R/primary -m fast stop >/dev/null 2>&1; }
EOF
. ./rig.sh; echo "rig ready in $R: rig.sh gives priup, repup, repdown, pq (primary) and rq (replica)"

Interview in practice

"We added read replicas and users now report missing data right after they save. What is happening and how do you fix it?"

The question: A realistic production symptom. They want you to name replication lag and offer more than one fix with trade-offs.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How are reads routed today? How long is the lag? Blind round-robin to replicas is the usual cause; lag of tens of milliseconds is enough to hit it.
2. Think it through (the reasoning, step by step)
  1. Name the cause. Asynchronous replication: the write commits on the primary and is acknowledged before replicas apply it. A read sent to a replica a few milliseconds later does not see the write.
  2. Fix 1: read your own writes from the primary. After a user writes, send that user's reads to the primary for a short window (or until the replica passes the write's log position). Simple; the primary carries a bit more read load.
  3. Fix 2: session stickiness or lag-aware routing. Pin a session to one replica (monotonic reads), or only use replicas whose lag is below a threshold; remove lagging replicas from rotation automatically.
  4. Fix 3: synchronous or remote_apply replication for critical reads. Make commit wait for the replica; correct but slower writes and a new availability dependency.
  5. Mention what replicas do not fix. Write capacity, and total storage per node. For those you partition or shard.
  6. Monitor. Alert on replication lag in seconds and bytes, and on replicas leaving the streaming state.
3. A strong answer, said out loud

"This is replication lag. Replication is asynchronous, so a commit is acknowledged by the primary before replicas apply it, and a read routed to a replica a few milliseconds later does not see the write.

The usual fix is read-your-writes: after a user writes, route their reads to the primary for a short window, or until the replica has replayed past that write. Alternatively I pin each session to one replica and route only to replicas whose lag is below a threshold, removing lagging ones automatically. For a few critical paths I could use synchronous replication, accepting slower writes and a dependency on the replica. I would also monitor lag and remember that replicas scale reads, not writes: for writes I would partition or shard."

4. Follow-ups you should expect
What is monotonic reads?

A guarantee that one user never sees data go backwards: reading from a newer replica then an older one would; pinning a session to one replica avoids it.

How do you measure lag?

On the primary, pg_stat_replication (replay_lag and byte difference between sent and replayed log positions); on the replica, the time since the last replayed transaction.

Why not make all replication synchronous?

Every commit waits for the slowest synchronous replica and stops entirely if it fails: it trades availability and latency for freshness.

Common slips
  • Saying "add more replicas" without addressing consistency.
  • Forgetting that replicas do not scale writes.
  • No lag monitoring or automatic removal.
Quick check

Answer in your head first, then open it.

What does a read replica scale: reads, writes, or both?

Reads only; every write still happens on the primary and every replica.

What is replication lag?

The delay between a commit on the primary and its replay on a replica.

How can you avoid showing a user stale data after they write?

Read their own recent writes from the primary, or use a replica that has replayed past the write.

Traps to avoid (3)
  • Round-robin reads to replicas for all queries, including ones that follow a write.
  • Ignoring replicas that fall far behind: they serve very stale data and may never catch up.
  • Believing replicas make the system write-scalable.

Failover, synchronous replication and split brain

Must know
Situation

The primary dies at 3 a.m. Promoting a replica takes one command. The hard questions are: did the replica have the last transactions, and what happens when the old primary wakes up and still believes it is in charge?

You will learn
  • Synchronous versus asynchronous commit and what each risks
  • Promoting a replica
  • Split brain and fencing
  • Why automatic failover needs a consensus system
Mental model

With asynchronous replication a failover can lose the last few committed transactions (the primary acknowledged them, the replica never received them): the recovery point is not zero. With synchronous replication a commit waits until at least one replica confirms it has the log, so nothing acknowledged is lost, at the price of higher write latency and a new availability risk: if the synchronous replica is unreachable, commits wait (or you must reconfigure and accept the risk).

Failover means promoting a replica to primary and sending clients to it. The dangerous failure is split brain: the old primary was only unreachable, not dead, and now there are two writable nodes with different data. Prevent it with fencing: make sure the old primary is shut down or cut off (power, network or a storage lock) before the new one accepts writes. Deciding "the primary is really gone" correctly is a distributed consensus problem, so production setups use a tool (Patroni with etcd or Consul, or a managed service) rather than a script, and they test the failover regularly.

Everyday analogy: Two pilots, one aircraft: if the captain becomes unresponsive the co-pilot takes the controls. If the captain was only briefly distracted and both fly, the plane is in danger. The cockpit procedure is the fencing.

The picture
How it works, step by step
  1. Decide how much loss you can acceptZero loss needs synchronous replication; accepting a few seconds of loss allows asynchronous.
  2. Detect failure with careA missed heartbeat could be a network blip. Wait long enough, ask more than one observer, ideally a quorum.
  3. Fence the old primaryStop it for certain (or cut its network or storage) so it cannot accept writes.
  4. Promote the best replicaChoose the one with the most replayed log; promote it; it becomes writable.
  5. Redirect clients and rebuildSwitch the address or proxy to the new primary, and re-create a replica from it. The old primary must be rebuilt, not simply restarted.

The price of synchronous replication, shown. With a replica attached the commit succeeds and pg_stat_replication says sync. When the replica is stopped, the next commit does not complete: timeout gives up after 3 seconds with status 124, and the server's session sits in the SyncRep wait. Nothing was lost, but writes are blocked until a replica is back or an operator removes the requirement. That is the trade: zero data loss, a new way for writes to stop.

Split brain, made on purpose. After the primary is stopped, the replica is promoted and becomes writable (pg_is_in_recovery is f). Interview in practice

"Design the failover for a primary database. What can go wrong?"

The question: A reliability-flavoured database question. They want: detection, promotion, data loss, split brain and testing.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How much data can we afford to lose, and how long can we be unavailable? These are the recovery point and recovery time objectives: they decide synchronous or asynchronous, and manual or automatic failover.
2. Think it through (the reasoning, step by step)
  1. Set the targets. RPO zero means synchronous replication to at least one replica (in another zone); RPO of a few seconds allows asynchronous. RTO of seconds needs automation; minutes allow a runbook.
  2. Detection. Health checks from several vantage points with a timeout that tolerates blips; decisions through a consensus store (etcd, Consul) so exactly one node holds the leader lock.
  3. Promotion and fencing. Pick the replica with the most log; fence the old primary (STONITH, network or storage fencing, lease expiry) before promoting.
  4. Client redirection. A virtual IP, DNS with a short TTL, or a proxy/pooler that follows the leader; clients retry idempotent operations.
  5. Aftermath. Rebuild the old primary as a replica; reconcile any lost transactions if you can read them from its log; post-incident review.
  6. Test it. Practise failover regularly in production-like environments (game days); an untested failover is a hope, not a design.
3. A strong answer, said out loud

"First the objectives: how much data can we lose and for how long can we be down. Zero loss means synchronous replication to at least one replica in another zone, at the cost of write latency and the risk that writes stop if that replica is unreachable; a few seconds of loss allows asynchronous.

For the failover itself I would not write a script: I would use a tool such as Patroni with etcd, where a leader lock held by exactly one node decides who is primary. On failure it fences the old primary, promotes the replica with the most log, and a proxy or virtual IP sends clients to the new primary, with clients retrying idempotent requests. The main risk is split brain, which fencing prevents. Afterwards the old primary is rebuilt as a replica. And I would rehearse the failover regularly, because an untested failover usually fails the first time it is needed."

4. Follow-ups you should expect
What is STONITH?

Shoot The Other Node In The Head: forcibly power off or isolate the suspected-dead node so it cannot keep writing.

Why do you need an odd number of voters?

A majority quorum (2 of 3, 3 of 5) lets one side of a partition continue and the other stop; an even split can deadlock or split.

What is the difference between RPO and RTO?

Recovery point objective: how much data you can lose. Recovery time objective: how long you can be down.

Common slips
  • Promoting without fencing the old primary.
  • Claiming zero data loss with asynchronous replication.
  • Never rehearsing the failover.
Quick check

Answer in your head first, then open it.

What is the risk of asynchronous replication during failover?

The replica may not have the last committed transactions, so they are lost.

What is the risk of synchronous replication?

Commits wait for the replica: slower writes, and writes stop if it is unreachable.

What is split brain and how is it prevented?

Two writable primaries with different data; prevent with fencing and a consensus-based leader election.

Traps to avoid (3)
  • Automatic failover on a single missed heartbeat: a network blip becomes an outage and possibly split brain.
  • Restarting the old primary instead of rebuilding it.
  • Treating a replica in the same rack or zone as a disaster-recovery copy.

Partitioning: splitting a big table inside one database

Good to know
Situation

The events table has two billion rows. Queries almost always ask for the last week, yet every query pays for the whole table's indexes, and deleting data older than a year takes hours and bloats everything. Partitioning splits the table by a key so most queries touch one small piece.

You will learn
  • Range, list and hash partitioning
  • Partition pruning in a real plan
  • Dropping old data in an instant
  • Partitioning versus sharding
Mental model

Partitioning splits one logical table into several physical partitions inside the same database, by a key: a date range (most common for events and logs), a list of values (country), or a hash (even spread). Queries and writes still address the one logical table; the database routes rows to the right partition, and when a query's where clause includes the partition key it prunes the partitions that cannot match, so it reads only the relevant ones. Indexes are per partition, so they are small and fit in memory.

The best part is data lifecycle: removing a month of data becomes drop table events_2025_01, which is instant and does not leave bloat, instead of a huge delete followed by vacuum. Partitioning does not add machines: it is a single-node tool that makes big tables manageable. When one machine is no longer enough, the same idea is applied across machines: sharding, the next lesson.

Everyday analogy: A filing cabinet with one drawer per month: finding last week's papers means opening one drawer, and shredding last year's means emptying a drawer instead of picking pages out of one giant pile.

The picture
How it works, step by step
  1. Pick the key your queries filter onFor time-series data it is almost always the timestamp: most queries want recent data.
  2. Define partitionsOne per month or day for ranges, created ahead of time by a job.
  3. Insert as usualRows are routed to the right partition automatically.
  4. Query with the keywhere created_at >= ... lets the planner prune partitions: the plan lists only the ones it will read.
  5. Retire old data by dropping partitionsInstant, no bloat; detach first if you want to archive it.
Pruning and instant deletion, on real data 
. ~/rep/rig.sh; priup
pq <<'EOF'
create table events(id bigserial, at timestamptz not null, kind text) partition by range (at);
create table events_2026_08 partition of events for values from ('2026-08-01') to ('2026-09-01');
create table events_2026_09 partition of events for values from ('2026-09-01') to ('2026-10-01');
create table events_2026_10 partition of events for values from ('2026-10-01') to ('2026-11-01');
insert into events(at, kind) select timestamptz '2026-08-01' + make_interval(secs => random() * 91 * 86400), 'click' from generate_series(1, 300000);
analyze events;
EOF

4

Sharding: splitting the data across machines

Must know
Situation

Indexes are right, caches are warm, replicas absorb the reads, and the primary is still at 90 percent CPU on writes with a disk that will be full in four months. One machine cannot hold or write this much. The only remaining move is to split the data across machines.

You will learn
  • What sharding is and how a shard key routes data
  • Single-key lookups versus queries without the key
  • Resharding: why mod N is painful and consistent hashing helps
  • Hot shards and what makes a good shard key
Mental model

Sharding (horizontal partitioning across machines) splits a data set into shards, each stored on its own database server, chosen by a shard key: shard = hash(key) mod N, or a lookup table, or a key range. Writes and data now scale with the number of machines. The price is paid everywhere else: a query that includes the shard key goes to one shard, but a query that does not must ask every shard and merge the answers (scatter-gather); a transaction or join that spans shards is no longer a plain database operation; and changing the number of shards moves data.

Choosing the shard key is the most important decision: it must appear in your hot queries, have many distinct values and spread load evenly. Sharding by tenant makes each customer's data local (great for joins within a tenant) but one giant tenant becomes a hot shard; sharding by a high-cardinality id spreads load but scatters related rows. Resharding with plain hash mod N moves almost every key when N changes; consistent hashing (a ring with virtual nodes) or a directory of many small logical shards mapped to machines moves only about 1/N of the data. Shard late: it is expensive to build and to undo.

Everyday analogy: A library that outgrows its building and splits into branches by the first letter of the author. Looking up a known author goes to one branch. Asking "every book about sailing" means phoning all branches. Adding a branch means moving books, and if one author is enormously popular, that branch is overwhelmed.

The picture
How it works, step by step
  1. Pick a shard keyIt appears in the queries that matter, is high-cardinality, and spreads load.
  2. Route by hashThe application (or a router) computes hash(key) mod N and talks to that shard only.
  3. Single-key operations stay cheapA lookup or write by the key touches one shard, and a transaction inside one shard keeps full ACID.
  4. Everything else costs moreNo key means ask all shards and merge; cross-shard changes need sagas or two-phase commit.
  5. Plan for growthUse many logical shards mapped onto fewer machines, or consistent hashing, so adding machines moves little data.

A lookup table from key (or key range) to shard that you can change, giving flexibility at the cost of an extra component to keep consistent and fast.

Avoid it by choosing the key so related data is together; otherwise two-phase commit (blocking, rarely used at scale) or a saga with compensations and idempotent steps.

Dual write or change data capture into the shards, backfill, verify counts and checksums, read from shards for a small percentage, then switch writes, keeping the ability to roll back.

NoSQL: key-value, document and log-structured stores

Must know
Situation

Someone says "just use MongoDB" or "use Cassandra, it scales". What do these systems actually change, what do they give up, and which of their ideas could you run in a relational database anyway?

You will learn
  • The four families and what each is for
  • Key-value: speed and simplicity, and what it cannot query
  • Documents: flexible shapes, and indexing inside them
  • How a log-structured (LSM) store makes writes fast
Mental model

"NoSQL" is a label for several different designs: key-value (Redis, DynamoDB: get and put by key, very fast, no queries by value), document (MongoDB, or jsonb in PostgreSQL: self-contained JSON documents with flexible shapes and indexes on fields), wide-column (Cassandra, HBase: rows grouped by a partition key, sorted within it, built for huge write rates) and graph (relationships as first-class data). What they usually trade away: joins, multi-row transactions and ad hoc queries. What they buy: simple horizontal scaling by key, flexible schemas and (often) very high write throughput.

Many scale-out stores use a log-structured merge tree (LSM): writes go to an in-memory sorted table (plus a log for safety) and are flushed to immutable sorted files; reads check memory then the files from newest to oldest; compaction merges files in the background. Writes are sequential and cheap; reads may touch several files, and compaction costs disk and CPU (write amplification). A relational B-tree updates pages in place instead. Neither is better: LSM favours write-heavy loads, B-trees favour read-heavy ones and range queries with in-place updates.

Everyday analogy: A relational database is a well-organised filing cabinet with cross-references. A key-value store is a coat check: ticket in, coat out, nothing else. A document store is a folder per case with whatever papers belong in it. An LSM store is a stack of dated notebooks: you always append to the newest one and periodically merge old notebooks.

The picture
How it works, step by step
  1. Start from the access patternGet by key? Flexible nested records? Huge ingest of time-ordered events? Relationships?
  2. Key-value for lookups by idSessions, caches, counters, carts: one key, one value, microsecond reads.
  3. Documents for variable recordsProduct catalogues and profiles where each record has a different shape and is read as a whole.
  4. LSM for write-heavy streamsMessages, metrics and events: append fast, read by partition key and time.
  5. Check what you loseJoins, constraints, transactions across records, ad hoc queries: where do they go in your design?

# A toy LSM tree: memtable + immutable sorted runs + compaction. Real stores do exactly this, with files and a log.
class LSM:
    def __init__(self, limit=4):
        self.mem, self.runs, self.limit, self.flushes = {}, [], limit, 0
    def put(self, k, v):
        self.mem[k] = v                                      # a write only touches memory (plus a log in real life)
        if len(self.mem) >= self.limit:
            self.runs.insert(0, dict(sorted(self.mem.items())))   # flush: a new immutable sorted run, newest first
            self.mem, self.flushes = {}, self.flushes + 1
    def get(self, k):
        if k in self.mem: return self.mem[k], 0
        for n, run in enumerate(self.runs, 1):               # newest to oldest
            if k in run: return run[k], n
        return None, len(self.runs)
    def compact(self):
        merged = {}
        for run in reversed(self.runs): merged.update(run)   # newer values win; old versions disappear
        self.runs = [dict(sorted(merged.items()))]
db = LSM()
for i in range(20): db.put('key%02d' % (i % 10), 'v%d' % i)  # 20 writes over 10 keys: every key is written twice
print('after 20 writes: %d runs on disk, %d keys in memory' % (len(db.runs), len(db.mem)))
print('read key00 (oldest data): value %s after checking %d place(s)' % db.get('key00'))
print('read key09 (newest data): value %s after checking %d place(s)' % db.get('key09'))
db.compact()
print('after compaction: %d run(s); read key00: value %s after checking %d place(s)' % ((len(db.runs),) + db.get('key00')))
EOF

An LSM tree you can read end to end (about 20 lines of Python). Writes only touch memory until the memtable is full, then it is flushed as a new immutable sorted run: fast and sequential. Reads must look in memory and then in every run from newest to oldest, so old data can cost several lookups (read amplification). Compaction merges the runs, keeps the newest value of each key and discards the old versions, so afterwards a read checks one place. Real systems add a write-ahead log, Bloom filters (to skip runs that cannot contain the key) and levelled compaction, but this is the mechanism.

Interview in practice

"When would you choose a NoSQL database over PostgreSQL? Give me a concrete case."

The question: A favourite opinion question. A good answer avoids tribal claims and reasons from access patterns, scale and consistency needs.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What are the access patterns and the scale? What consistency does the data need? These decide everything: money needs transactions, a feed timeline needs cheap writes.
2. Think it through (the reasoning, step by step)
  1. Start with the default. A relational database is the right default: flexible queries, transactions, constraints, mature tooling. Most systems never outgrow a well-tuned primary with replicas and a cache.
  2. Name the real reasons to leave. A write rate or data size beyond one machine with a natural partition key; a simple access pattern (by key) at huge scale; very flexible or deeply nested records; multi-region active-active writes; a specialised model (graph, time series, search).
  3. Give a concrete example. Chat messages: billions per day, always read by conversation and time: a wide-column store partitioned by conversation id with time-sorted rows (an LSM design) fits. Sessions and carts: key-value with TTL. Product catalogue with variable attributes: documents. Orders and payments: relational.
  4. State the costs. Give up joins and multi-record transactions, design tables per query, handle consistency and denormalisation in the application, and operate a new system.
  5. Hybrid is normal. Orders in PostgreSQL, sessions in Redis, messages in Cassandra, search in an index, with events keeping them in sync.
3. A strong answer, said out loud

"My default is a relational database: it gives flexible queries, transactions and constraints, and a tuned primary with replicas and a cache carries most systems a long way. I would choose NoSQL for a specific reason: a write rate or data size beyond one machine with a natural partition key, a simple access pattern at huge scale, very variable records, or a specialised model such as graph or time series.

For example chat messages: billions a day, always read by conversation in time order, so a wide-column store partitioned by conversation id with time-sorted rows fits, and its log-structured design makes the writes cheap. Sessions and carts suit a key-value store with expiry. But I would keep orders and payments relational, because they need transactions. The cost of NoSQL is losing joins and multi-record transactions and designing storage around each query, so most real systems are hybrids."

4. Follow-ups you should expect
Why are writes fast in an LSM store?

They append to memory and a log, then flush sorted files sequentially, never updating in place; compaction is deferred to the background.

What is a Bloom filter doing in an LSM store?

It tells quickly that a run definitely does not contain a key, so most runs are skipped on reads.

Is jsonb in PostgreSQL a replacement for a document database?

For moderate scale, often yes: flexible shapes with indexes and transactions. At very large scale or with built-in sharding needs, a dedicated store may be better.

Common slips
  • Choosing NoSQL because "it scales" without naming the access pattern.
  • Ignoring the loss of transactions and joins.
  • Forgetting that mixing stores is normal.

It can only look things up by key; there are no efficient queries by value without your own index.

Choosing a data store and sizing it: the decision you defend in an interview

Must know
Situation

Every design interview has the moment: "what database would you use, and how many machines?" This lesson turns the previous ones into a repeatable way to decide and to size.

You will learn

  • Back-of-envelope sizing of storage and nodes
  • Consistency choices and what you tell the interviewer
  • Combining stores in one design
Mental model

Decide from four questions: (1) What are the access patterns (by key, by range, by search, by relationship, analytical)? (2) What consistency and transactions does the data need (money, inventory: strong; feeds, counters: eventual is fine)? (3) What is the scale (data size, writes per second, reads per second, growth)? (4) What are the availability and latency needs (regions, failover)? Default to a relational database unless an answer clearly rules it out, and say why.

Then size it: data size = records x record size x replication factor x growth (plus index overhead, often 30 to 100 percent); write capacity = peak writes per second divided by what one node sustains (often a few thousand simple writes per second per node for a relational primary, tens of thousands for an LSM store); read capacity = replicas and caches. The number of shards is the larger of what size and write rate require, plus headroom (target 50 to 60 percent utilisation) and the replication factor on top. The goal is not a precise figure but a defensible one and a clear statement of which assumption dominates.

Everyday analogy: Choosing a vehicle: a car for most trips (relational), a freight truck for huge simple loads (wide-column), a courier bike for tiny instant lookups (key-value). You decide from the load, the distance and the road, then count how many you need and add spares.

How it works, step by step
  1. Write down the access patternsList the five most important queries and writes with their rates.
  2. Mark the consistency needsWhich data must be exact (balances, stock) and which can lag (counts, feeds).
  3. Estimate size and ratesRecords x bytes x replicas x growth; peak writes and reads per second.
  4. Pick the store per data setRelational by default; another store only for a named reason.
  5. Add nodes, replicas and headroomShards from size and writes, replicas from reads and availability, 50 to 60 percent target utilisation.
A sizing calculator you can reuse 
python3 - <<'EOF'
# Back-of-envelope sizing: how many database nodes does this workload need?
import math
def plan(name, records, bytes_each, growth_years, write_qps, read_qps, node_disk_gb, node_write_qps, node_read_qps, replicas=3):
    raw_gb = records * bytes_each / 1e9
    stored_gb = raw_gb * 1.5 * (1 + growth_years)             # 50% for indexes and overhead, plus growth
    shards_size = math.ceil(stored_gb / (node_disk_gb * 0.6))   # keep disks at 60%
    shards_write = math.ceil(write_qps / (node_write_qps * 0.6))
    shards = max(shards_size, shards_write)
    reads_per_shard = read_qps / shards
    replicas_for_reads = max(1, math.ceil(reads_per_shard / (node_read_qps * 0.6)))
    print('%s' % name)
    print('  data now %.0f GB, planned %.0f GB (indexes + %d years growth)' % (raw_gb, stored_gb, growth_years))
    print('  shards needed: %d by size, %d by writes -> %d shards' % (shards_size, shards_write, shards))
    print('  copies per shard: %d (the larger of %d for availability and %d for reads)' % (max(replicas, replicas_for_reads), replicas, replicas_for_reads))
    print('  total nodes: %d' % (shards * max(replicas, replicas_for_reads)))
plan('Orders: 200M orders of 1 KB, 300 writes/s, 6000 reads/s, relational nodes (2 TB disk, 3000 w/s, 20000 r/s)',
     200e6, 1000, 2, 300, 6000, 2000, 3000, 20000)
plan('Chat messages: 30B messages of 300 B, 120000 writes/s, 150000 reads/s, LSM nodes (4 TB disk, 30000 w/s, 30000 r/s)',
     30e9, 300, 2, 120000, 150000, 4000, 30000, 30000)
EOF

The same arithmetic with two very different workloads. Orders are modest: the data fits comfortably on one node, writes are far below one node's limit, so one primary plus replicas is enough, and the reasoning is about availability rather than scale. Chat messages are enormous in both size and write rate, so the data and write throughput each require many nodes, which is exactly where a partitioned LSM-style store earns its place. The numbers are assumptions and should be stated as such; what matters is that the decision follows the numbers, not fashion.

Interview in practice

"Design the storage for a chat application with 500 million users. What databases and how many machines?"

The question: The decision-and-sizing question. They want separate stores per data type with reasons, numbers, and a consistency story.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How many messages per day, how long are they kept, and what are the read patterns? Say it explicitly: for example 40 billion messages a day, retained for years, read as recent history of one conversation.
2. Think it through (the reasoning, step by step)
  1. Split the data by access pattern. Messages: append-heavy, read by conversation in time order. User accounts and relationships: moderate, relational. Presence and typing: ephemeral key-value. Media: blob storage, with only metadata in a database. Search: a separate index.
  2. Choose stores. Messages: wide-column/LSM store partitioned by conversation id (partition key) with time-ordered rows, so the latest N messages of a chat is one partition read. Accounts: relational with replicas. Presence: Redis. Media: object storage and a CDN.
  3. Size the messages. 40 billion per day is about 460,000 writes per second on average, perhaps 1 million at peak; at 300 bytes that is 12 TB per day, and with 3 replicas and retention of years, petabytes. Nodes: peak writes over about 30,000 per node gives roughly 40 nodes for writes; the data volume dominates and needs thousands of nodes with tiered storage and retention policies.
  4. Consistency and ordering. Within a conversation, messages must be ordered: assign ids per conversation (or time-based ids) and sort by them; eventual consistency across replicas is acceptable, but a user must see their own message immediately (read your writes).
  5. Failure and hot spots. Replication across zones with quorum writes; a hot group chat becomes a hot partition: cap fan-out, split very large conversations into time buckets.
  6. Say the assumptions. State the assumptions and how the design changes if they are wrong.
3. A strong answer, said out loud

"I would split by access pattern. Messages are append-heavy and read as the latest page of one conversation, so a wide-column LSM store partitioned by conversation id with time-ordered rows fits: the common read is one partition. Accounts and relationships go in a relational database with replicas, presence in Redis with expiry, media in object storage with a CDN, and search in a separate index fed from events.

For size: say 40 billion messages a day is about half a million writes a second on average and several hundred terabytes a day of raw data with replication, so message storage is a large partitioned cluster with retention and tiering, while the relational part is small. Ordering is per conversation using time-based ids, replication across zones with quorum writes, and the user always reads their own message. A very hot group conversation becomes a hot partition, so I would bucket by time and limit fan-out. I would state these numbers as assumptions and show how the design changes if they are off."

4. Follow-ups you should expect
Why not PostgreSQL for the messages?

At this write rate and size one primary is far beyond its limits; sharding PostgreSQL yourself is possible but a store built for partitioned append-heavy data does it natively.

How do you paginate message history?

Keyset by message id or time within the conversation partition: where conv = ? and id < last_seen order by id desc limit 50.

How do you delete data for compliance?

Design deletion in: time-bucketed partitions expire cheaply; per-user deletion needs a mapping and tombstones, and compaction eventually removes the data.

Common slips
  • Naming one database for everything.
  • Giving no numbers, or numbers with no assumptions stated.
  • Forgetting ordering and read-your-writes.

Do read replicas scale writes?

No: every write still happens on the primary and is replayed on every replica.

What is replication lag?

The delay between a commit on the primary and its replay on a replica.

How do you avoid stale reads right after a write?

Read the user's own recent writes from the primary or from a replica that has replayed past the write.

What does synchronous replication risk?

Commits wait for the replica, so they are slower and stop if it is unreachable.

What is split brain and how is it prevented?

Two writable primaries with different data; fencing and a leader lock held by one node.

What does partition pruning need from the query?

A condition on the partition key.

Why is dropping a partition better than deleting rows?

Instant and leaves no dead rows.

The value hashed (or ranged) to decide which shard holds a row.

Why does a query without the shard key cost more?

It must ask every shard and merge the answers.

About three quarters.

One shard receiving a disproportionate share of load, usually from a skewed shard key.

No efficient queries by value without your own index.

Study plan

  1. Hours 1 to 2: replication: build the rig, watch lag, then change the delay and explain every output.
  2. Hours 3 to 4: failover: run the synchronous and split brain demos; then the replica-lag-read lab.
  3. Hours 5 to 6: partitioning: add a fourth partition and a default partition; time the delete and the drop.
  4. Hours 7 to 8: sharding: change N and the key; then the shard-key-choice lab.
  5. Hour 9: NoSQL: add a second field to the toy LSM tree and count the runs a read touches.
  6. Hours 10 and 11: choosing and sizing: change the assumptions in the calculator; then say each interview scenario aloud for two minutes, timed, and compare with the written answer.
