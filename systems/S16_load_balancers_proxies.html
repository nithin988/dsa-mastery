Load balancers, proxies and gateways

Every service that runs on more than one server has a front door: something that accepts the clients' requests and decides which server handles each one. This module opens that door. You will run real nginx and HAProxy in front of real backends, watch the algorithms spread (and fail to spread) traffic, kill servers and see the balancer route around them, terminate TLS, route by path, rate limit, cache, and then learn how to answer the interview questions with reasoning, not slogans.

6 lessons2 labs1 animations7 interview questionsabout 9 to 11 hours

Why this matters

A real situation

One server handles 500 requests per second. Traffic is about to grow tenfold. You cannot buy a server ten times faster, but you can run ten servers, and then you immediately need something that gives clients one address, spreads requests sensibly, stops sending traffic to a server that has died, and lets you deploy without downtime. That something is the load balancer.

It is also the place where many production problems hide: an uneven spread that overloads one server, a health check that sends traffic to a broken node, a deploy that drops requests, a client IP that has vanished behind a proxy. Engineers who understand the balancer from the inside diagnose these in minutes.

In interviews a load balancer appears in almost every design. The weak answer says "add a load balancer". The strong answer says which algorithm and why, how failures are detected, where TLS ends, how the balancer itself stays up, and what it costs.

After this module you can
  • Explain what a load balancer does and where it sits, and the difference between DNS, layer 4 and layer 7 balancing.
  • Compare round robin, weighted, least connections and consistent hashing, and show the effect of each on real traffic.
  • Configure nginx and HAProxy as reverse proxies and read their behaviour from real output.
  • Explain health checks (passive and active), failure detection time, retries and zero-downtime deploys, and demonstrate them.
  • Terminate TLS at the proxy, pass client identity through headers, and route by path.
  • Use proxies for rate limiting, compression and caching, and explain what an API gateway adds.
  • Make the balancer itself highly available and spread traffic across regions.
  • Answer load-balancing interview questions with a clear approach and numbers.

Why a front door: one address, many servers

Must know
Situation

Your site now runs on three identical servers. Customers type one name. Something must receive every request and hand it to one of the three, and keep working when one of them is switched off.

You will learn
  • What a load balancer is and what it must do
  • Three places to balance: DNS, layer 4, layer 7
  • Your first real balancer, running
Mental model

A load balancer is a program (or a device, or a cloud service) that accepts connections on one address and forwards each request to one of several backend servers. It exists for three reasons: capacity (spread work so no server is overloaded), availability (stop sending traffic to a server that is down) and flexibility (add, remove or replace servers without clients noticing). It only works if the servers are interchangeable: any of them can answer any request, which is why web servers are kept stateless and shared data lives in a database or cache behind them.

You can balance at three levels. DNS balancing returns several addresses for one name; it is simple and global but slow to change (caches) and it cannot see server health. Layer 4 balancing forwards TCP connections by address and port without reading the data: very fast, protocol-agnostic. Layer 7 balancing reads the HTTP request itself, so it can route by path or header, terminate TLS, cache and rewrite, at the cost of more work per request. Real systems often stack them: DNS to pick a region, a layer 4 balancer to spread connections, layer 7 proxies to route requests.

Everyday analogy: A restaurant host: guests see one entrance and one person; the host seats them at whichever waiter is free, skips a waiter who has gone home, and lets the kitchen add tables without telling the guests.

The picture
How it works, step by step
  1. The client asks DNS for the site's addressThe name resolves to the balancer's address (or a set of balancer addresses), never to an individual backend. Clients cannot tell how many servers exist.
  2. The connection reaches the balancerIt accepts the TCP connection. A layer 7 balancer also finishes the TLS handshake here (TLS termination) and reads the HTTP request.
  3. The balancer picks a backendUsing its algorithm (round robin, least connections, hash...) and its knowledge of which servers are healthy, it chooses one.
  4. It forwards the request, usually on a connection it already has openProxies keep pools of connections to their backends, so the client's request does not pay a new TCP handshake to the server.
  5. The response travels back through the balancerThe client sees one answer from one address. The balancer may compress it, cache it, or log it on the way.
  6. Failure and change happen behind the scenesA server crashes, a new one starts, a deploy replaces everything: the balancer's list of backends changes, the clients' experience does not.

Interview in practice

"You have three web servers behind one address. Describe how requests get distributed and what happens when one dies."

The question: A basic but revealing question. They want to hear the components, the decision, the failure behaviour and the cost, not just "add a load balancer".

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • Is the application stateless? If sessions live in each server's memory, any server cannot answer any request, and the balancer must keep a user on the same server (sticky sessions) or the state must move to a shared store.
  • HTTP traffic, or something else (a database, a game server)? HTTP suggests a layer 7 proxy; arbitrary TCP suggests layer 4.
  • Do we need to survive a whole data centre failing? That adds DNS or global balancing across regions on top of the local balancer.
2. Think it through (the reasoning, step by step)
  1. Say what the balancer is and why we want it. One address for clients, capacity by spreading load, availability by routing around failures, flexibility by changing servers behind it.
  2. Choose the layer. For a web application a layer 7 reverse proxy (nginx, HAProxy, a cloud application load balancer) gives TLS termination, path routing and header handling. For raw TCP or maximum throughput, layer 4.
  3. Choose the algorithm and justify it. Round robin when requests cost about the same; least connections when they vary; hashing when a user or key should stick to a server (cache locality). Start simple.
  4. Describe failure detection. Health checks: active ones probe each server every second or so and mark it down after a few failures; passive ones notice failed requests. The balancer stops sending to a down server and retries idempotent requests on another.
  5. Remove the single point of failure. The balancer is now critical, so run at least two behind a shared address (virtual IP) or use a managed service that is redundant for you.
  6. Close with deployment and operations. Remove a server from rotation (drain) before updating it, so in-flight requests finish; add capacity by adding servers; watch per-server error rates and latency.
3. A strong answer, said out loud

"Clients connect to one address that belongs to a load balancer. I would use a layer 7 reverse proxy because this is HTTP: it terminates TLS, can route by path, and forwards each request to one of the three servers using round robin to start, or least connections if request times vary a lot. The servers must be stateless, with sessions and data in shared storage, so any server can serve any request.

The balancer health-checks the servers, for example every second, and marks one down after two or three failures; from then on traffic only goes to the healthy ones, and idempotent requests that fail on a dying server are retried on another. That means one server dying costs a few seconds of reduced capacity and, at worst, a handful of failed requests, not an outage.

The balancer itself must not be a single point of failure, so I would run two sharing a virtual IP or use a managed load balancer, and for deploys I would drain a server before updating it. I would monitor per-backend error rate and latency to spot an uneven or unhealthy server early."

4. Follow-ups you should expect
What if the three servers have different capacities?

Use weighted balancing (give the big server a larger weight) or least connections, which adapts on its own.

Why not just use DNS with three addresses?

DNS cannot see health, clients and resolvers cache the answer for the TTL (so a dead server keeps receiving traffic), and the spread is crude. DNS is good for picking a region, not for fine-grained balancing.

Does the load balancer add latency?

Yes, a little: an extra hop and some processing, typically well under a millisecond inside a data centre. It usually saves time overall through connection reuse and by avoiding overloaded servers.

Common slips
  • Saying "a load balancer" without a layer, an algorithm or a failure story.
  • Forgetting that the balancer is itself a single point of failure.
  • Ignoring statelessness: sticky sessions hide a design problem.
Quick check

Answer in your head first, then open it.

Name the three reasons to put a load balancer in front of servers.

Capacity (spread load), availability (route around failures) and flexibility (change servers without clients noticing).

What is the difference between layer 4 and layer 7 balancing?

Layer 4 forwards TCP connections by address and port without reading the data; layer 7 reads the HTTP request and can route by path or header, terminate TLS and cache.

Why must backends be interchangeable?

So any server can answer any request; this is why state is kept in shared stores rather than in a server's memory.

Traps to avoid (3)
  • Putting a balancer in front of servers that keep user state in memory: requests for the same user then hit servers that do not know them.
  • Forgetting that the balancer itself needs redundancy.
  • Running nginx -s reload or starting with a config you have not checked with nginx -t.

Algorithms: how the next server is chosen

Must know
Situation

Round robin sounds fair. But what if one server is slow, or bigger than the others, or if the same user must reach the same server? The algorithm decides whether the load is truly balanced.

You will learn
  • Round robin and weighted round robin
  • Least connections and why slow servers need it
  • Hashing for stickiness, and consistent hashing
  • What you measure to know it works
Mental model

Round robin rotates through the servers: simple and fair when requests cost about the same and the servers are equal. Weighted round robin gives bigger servers a larger share. Least connections sends each request to the server with the fewest requests in progress: it adapts automatically when some requests are slow or some servers are slower, because slow servers accumulate open requests and so receive fewer new ones. Hashing (by client IP, a header or a cookie) maps the same key to the same server, which keeps caches warm and sessions together. Plain hash mod N reshuffles almost every key when N changes; consistent hashing places servers on a ring so that only about 1/N of the keys move when a server is added or removed.

The test of an algorithm is not how it looks but what it does under uneven load. With equal, quick requests all of these look the same. Add one slow backend or a mix of heavy and light requests, and round robin keeps feeding the slow server its share while least connections steers around it.

Everyday analogy: Supermarket queues: round robin is sending each new customer to the next till in turn; least connections is joining the shortest queue; hashing is always going to the till your surname points at, so the same person always meets the same cashier.

How it works, step by step
  1. Round robinKeep a pointer into the list; each request advances it by one. No state, no measurement. Even only if requests are alike.
  2. WeightedServers with weight 3 receive three requests for every one that a weight 1 server receives. Use it when capacities differ, or to send a small share to a new version.
  3. Least connectionsTrack how many requests each server is working on right now and pick the smallest. Needs a counter per server; adapts to slowness without any configuration.
  4. Hash by keyCompute a hash of (client IP | user ID | URL) and map it to a server. The same key always lands on the same server while the server set is unchanged.
  5. Consistent hashingPlace each server at many points on a circle. A key goes to the next server clockwise. Adding or removing a server only affects the keys on the arc next to it.

Interview in practice

"Round robin, least connections or consistent hashing: how do you choose?"

The question: They give you three scenarios: stateless API with uniform requests, an image-resizing service with very uneven request times, and a cache cluster keyed by user. Which algorithm for each, and why?

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How much do request costs vary? That is the whole question for round robin versus least connections.
  • Do we need the same key to reach the same server? Caches and session affinity are the reasons to hash.
  • How often do servers join and leave? Frequent changes make consistent hashing worth its complexity.
2. Think it through (the reasoning, step by step)
  1. Start with the simplest that fits. Uniform, stateless requests: round robin (or weighted if servers differ). Simple and predictable.
  2. Look for variance. The image resizer has requests from 20 ms to 5 s: round robin will pile heavy ones onto unlucky servers; least connections spreads by actual load. Mention you would verify with per-server latency percentiles.
  3. Look for locality. A cache cluster keyed by user wants the same user on the same node so hits are possible: hash by user ID.
  4. Show you know the catch of hashing. With plain modulo, changing N moves almost every key and empties the caches; consistent hashing with virtual nodes limits movement to about 1/N and spreads load evenly.
  5. Mention hot keys. Hashing can overload one server if one key (a celebrity user) is hot: cache that key at the edge, split it, or fall back to load-aware balancing.
  6. Say how you would know it works. Per-server request rate, connections and latency; the spread should be even in load, not just in count.
3. A strong answer, said out loud

"For the stateless API with uniform requests I would use round robin, weighted if the servers differ in size: it is simple and the load is even. For the image resizer, where request times vary enormously, round robin would give some servers a run of heavy jobs, so I would use least connections, which adapts to how busy each server really is. For the cache cluster keyed by user, I want the same user to hit the same node, so I would hash on the user ID.

The catch with simple hashing is that when a node is added or removed, hash mod N remaps almost every key and the caches go cold, so I would use consistent hashing with virtual nodes, which moves only about one over N of the keys and keeps the load even. A hot key can still overload one node, so I would watch per-node load and cache or replicate very hot keys.

In all cases I would confirm with per-server request counts, connections and latency percentiles, because even by count is not the same as even by load."

4. Follow-ups you should expect
What are virtual nodes?

Each physical server appears at many positions on the ring (for example 100). This evens out the share each server gets and, when a server leaves, spreads its keys across all the others instead of dumping them on one neighbour.

How would you drain a server using these algorithms?

Set its weight to zero or mark it down so no new requests arrive, wait for in-flight requests to finish, then stop it.

What is power of two choices?

Pick two servers at random and send the request to the one with fewer connections. It gets most of the benefit of least connections with far less coordination, which matters in large distributed balancers.

Common slips
  • Choosing hashing for "fairness": it gives stickiness, not even load.
  • Describing round robin as perfectly balanced without mentioning uneven request cost.
Quick check

Answer in your head first, then open it.

Why does least connections cope with a slow backend and round robin does not?

A slow backend keeps its requests open longer, so its connection count stays high and it receives fewer new requests; round robin keeps giving it an equal share.

What does consistent hashing improve over hash mod N?

When a server is added or removed only about 1/N of the keys move, instead of nearly all of them.

What would you use to send 5 percent of traffic to a new version?

Weighted balancing: give the new server a small weight.

Traps to avoid (3)
  • Equal by count is not equal by load: measure CPU, concurrency and latency per server.

Health checks, failures and zero-downtime deploys

Must know
Situation

A server crashes at 03:00. Does the balancer keep sending it a third of the traffic, or notice and route around it? And when you deploy, can you replace servers without a single failed request?

You will learn
  • Passive and active health checks
  • How fast failure is detected, and what clients see meanwhile
  • Retries and their danger
  • Draining and zero-downtime reloads
Mental model

Balancers detect failure in two ways. Passive checks watch real traffic: if a request to a server fails or times out, count it, and after a few failures stop using that server for a while (nginx max_fails and fail_timeout). Active checks send their own probe (a request to /health) every second or so and mark a server DOWN after several failures in a row and UP again after several successes (HAProxy check inter 1s fall 2 rise 3). Detection is never instant: between the failure and the detection some requests go to the dead server. Good balancers retry such requests on another server, which is safe only for idempotent requests (GET, not a payment POST).

A health check must test what matters: a probe that only checks that the port is open will keep a server in rotation when its application is deadlocked or its database is unreachable. And a check that is too sensitive makes servers flap in and out. For deploys, drain the server first: stop sending it new requests, let in-flight ones finish, then update it. A proxy reload should switch configuration without dropping connections.

Everyday analogy: A host who sees a waiter drop their tray stops seating guests in that section (passive); a host who walks the floor every minute asking "all fine?" (active) finds problems before guests do. Before a waiter goes on break, the host stops seating them and lets them finish current tables (draining).

The picture
How it works, step by step
  1. Probe: the balancer checks each server on a timerEvery inter milliseconds it sends a small request to each backend and records success or failure.
  2. Fail: consecutive failures cross the thresholdAfter fall failures in a row the server is marked DOWN. The delay is about fall x inter, so a 1 s interval and fall 3 means up to ~3 seconds of exposure.
  3. Route around: traffic only goes to UP serversRequests in flight to the dead server fail or time out; the balancer may retry idempotent ones elsewhere.
  4. Recover: successes bring it backAfter rise successful probes the server rejoins. The rise threshold stops a flapping server from re-entering too eagerly.
  5. Deploy: drain, update, returnMark the server out of rotation, wait for connections to finish, update it, wait for it to pass health checks, then restore it, one server at a time.

"How do you deploy a new version of a service behind a load balancer with zero downtime?"

The question: Walk through a rolling deployment, including what could go wrong at each step.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How many servers, and is there headroom to take one out? Rolling deploys reduce capacity by one server at a time; with three servers that is a third, which must be affordable.
  • Do requests last long (uploads, websockets)? Long-lived connections need a longer drain time or a way to move clients.
  • Is the new version backward compatible with the database and with the old version running alongside? During a rolling deploy both versions serve traffic at once.
2. Think it through (the reasoning, step by step)
  1. State the principle. Never stop a server that is still receiving traffic: take it out of rotation first, let it finish, change it, verify it, put it back.
  2. Step through it. 1) Mark server 1 as draining: no new requests. 2) Wait until its active connections reach zero or a timeout (for example 30 s). 3) Stop it, deploy the new version, start it. 4) Wait for the health check to pass (and ideally a warm-up request). 5) Return it to rotation. 6) Watch error rate and latency for that server compared with the old ones. 7) Repeat for the next server.
  3. Name what can go wrong. Capacity dip if too many are out at once; a new version that passes the health check but misbehaves (so use a canary: one server or 1-5 percent of traffic first, with automatic rollback on error rate); incompatible database changes (use expand and contract migrations); cache warm-up making the first requests slow.
  4. Mention alternatives. Blue-green: a full second environment, switch the balancer to it, instant rollback by switching back. Canary releases through weighted balancing.
  5. Mention the proxy's own configuration changes. Reload rather than restart (graceful), and validate with nginx -t first.
3. A strong answer, said out loud

"I would do a rolling deployment, one server at a time. First I take server one out of rotation so it gets no new requests, then wait for its in-flight requests to finish, up to a timeout. Then I deploy and start the new version, wait until the health check passes, and put it back. I watch that server's error rate and latency against the others before moving on to the next. The principle is never to stop a server that is still receiving traffic.

What can go wrong is a dip in capacity if I take out too many at once, a new version that passes the health check but is actually broken, and database changes that are not compatible with the old version, which is still running alongside during the rollout. So I make migrations backward compatible, start with a canary on a small share of traffic with automatic rollback if the error rate rises, and keep headroom.

Blue-green deployment is an alternative: stand up a complete new environment and switch the balancer over, which gives instant rollback at the cost of double capacity for a while."

4. Follow-ups you should expect
What is connection draining?

Telling the balancer to stop assigning new requests to a server while letting existing connections complete, usually with a timeout after which remaining connections are closed.

How do you roll back?

Rolling: redeploy the previous version the same way, so keep the old artifact. Blue-green: point the balancer back at the old environment. Both depend on the database changes being compatible with both versions.

A health check passes but users see errors. Why?

The check is too shallow (it tests that the port answers, not that the application can reach its dependencies), or the problem only shows under real traffic. Use deeper checks and judge canaries by real error rates.

Common slips
  • Restarting servers in place with no draining.
  • Deploying to all servers at once.
  • Not mentioning database compatibility during the overlap.

Layer 4 versus layer 7, and terminating TLS

Must know
Situation

Some traffic is HTTP and could be routed by path; some is raw TCP (databases, game servers); and all of it may need TLS. Where should the balancer look at the traffic, and where should encryption end?

You will learn
  • What a layer 4 balancer can and cannot do
  • What a layer 7 proxy adds
  • TLS termination and passing the client's identity
Mental model

A layer 4 balancer sees only addresses, ports and bytes: it picks a backend when the TCP connection opens and then shuffles bytes in both directions without understanding them. It is fast, works for any protocol, and cannot route by URL or read headers. A layer 7 proxy terminates the client's connection, reads the HTTP request, and opens (or reuses) its own connection to the backend. That lets it route by path or host, add or rewrite headers, terminate TLS, compress, cache, rate limit and authenticate, for more CPU per request.

TLS termination means the proxy does the TLS handshake and decryption, then talks plain HTTP (or re-encrypts) to the backends: certificates live in one place and backends stay simple. Because backends then see the proxy as the client, the proxy adds X-Forwarded-For (the real client address) and X-Forwarded-Proto (whether the original connection was HTTPS) so applications can still know who called and how. Only trust those headers when they come from your own proxy, since clients can forge them.

Everyday analogy: Layer 4 is a mail room that forwards sealed envelopes by the address on the outside; layer 7 is a receptionist who opens the letter, reads it and sends it to the right department, and may add a note saying who it came from.

How it works, step by step
  1. A client opens a TCP connection to the proxyFor layer 4 the balancer picks a backend now and joins the two connections: the backend does the TLS and HTTP itself and sees the balancer's address as the peer.
  2. Layer 7: TLS is finished at the proxyThe proxy presents the certificate, decrypts, and reads the plain HTTP request.
  3. The proxy decides by what it readsPath (/api to one pool, / to another), host name, headers, cookies. This is content-based routing.
  4. It adds identity headers and forwardsX-Forwarded-For: <client ip> and X-Forwarded-Proto: https, so the backend can still log the real client and build correct links.
  5. The response returns the same wayThe proxy re-encrypts it for the client.

"What is the difference between a layer 4 and a layer 7 load balancer, and which would you choose?"

The question: A standard question. A good answer is a decision, not two definitions.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What protocol is the traffic? HTTP and gRPC suit layer 7. Databases, MQTT, game traffic or anything non-HTTP suits layer 4.
  • Do we need routing by path or host, header manipulation, or TLS termination? Any of these requires layer 7.
  • What is the throughput and latency requirement? At extreme throughput layer 4 is cheaper per connection.
2. Think it through (the reasoning, step by step)
  1. Define each by what it sees. Layer 4: addresses, ports and bytes; picks a backend per connection. Layer 7: parses HTTP; picks a backend per request.
  2. Compare capabilities. Layer 7 gives content routing, TLS termination, header rewriting, caching, compression, rate limiting and per-request retries and metrics. Layer 4 gives speed, simplicity, protocol independence, and passes TLS through untouched (end-to-end encryption).
  3. Compare cost. Layer 7 costs more CPU and adds a little latency because it terminates and re-creates connections. Layer 4 is lighter.
  4. Choose by requirement. A web application with path routing and TLS termination: layer 7. A TCP service or very high connection rate: layer 4. Large systems use both: a layer 4 fleet at the edge spreading connections across layer 7 proxies.
  5. Mention the identity problem. With layer 7 you get the client address in X-Forwarded-For; with layer 4 you need the PROXY protocol or direct server return.
3. A strong answer, said out loud

"A layer 4 balancer works on TCP connections: it sees addresses and ports, picks a backend when the connection opens and forwards bytes without understanding them. It is fast, protocol-independent, and can pass TLS straight through. A layer 7 balancer is an HTTP proxy: it terminates the connection, reads each request, and can route by path, host or header, terminate TLS, rewrite headers, compress, cache and rate limit, at the price of more CPU and a bit more latency.

For a typical web application I would choose layer 7, because I want path-based routing and TLS termination in one place. For a non-HTTP protocol or a very high connection rate I would choose layer 4. At large scale you often see both: layer 4 spreading connections over a fleet of layer 7 proxies. With layer 7 the backend gets the real client IP from X-Forwarded-For, which it should trust only from the proxy; with layer 4 I would use something like the PROXY protocol."

4. Follow-ups you should expect
Where should TLS terminate?

Usually at the layer 7 proxy or CDN edge so certificates are managed in one place and backends stay simple. Re-encrypt to the backends (or use mutual TLS) when the internal network is not trusted or compliance requires encryption everywhere.

What is direct server return?

A layer 4 technique where backends reply straight to the client instead of through the balancer, so the balancer only handles the small request direction. It needs special network setup.

How would you load balance gRPC?

gRPC uses long-lived HTTP/2 connections with many requests multiplexed on them, so a layer 4 balancer would pin all requests of a client to one backend. Use a layer 7 balancer that understands HTTP/2 (per-request balancing) or client-side balancing.

  • Defining the layers by number only, with no examples.
  • Forgetting that TLS termination needs the proxy to hold the private key.
  • Trusting X-Forwarded-For from the open internet.

What a proxy does besides balancing: rate limits, compression, caching, gateways

Must know
Situation

Because every request already passes through the proxy, it is the natural place to do work you do not want in every application: stop abusive clients, shrink responses, answer repeated requests from memory, check credentials.

Mental model

A reverse proxy sees all traffic, so cross-cutting features belong there. Rate limiting rejects clients that exceed a rate (HTTP 429 Too Many Requests), protecting backends from overload and abuse; nginx implements a leaky-bucket with limit_req (a steady rate plus an allowed burst). Compression (gzip, brotli) shrinks text responses several times, saving bandwidth and time. Caching (proxy_cache) stores backend responses and answers repeats from memory or disk, so a popular page is generated once and served thousands of times; the proxy reports HIT or MISS. An API gateway is a layer 7 proxy specialised for APIs: it adds authentication, per-client quotas, request validation, routing to many services, request IDs, and metrics at one choke point.

Everyday analogy: The front desk of an office does more than point people to rooms: it checks IDs, turns away someone who keeps coming back every few seconds, hands out copies of the brochure from a stack instead of asking the printing department each time.

How it works, step by step
  1. Identify the clientBy IP, API key, user ID or token. The key you choose decides who shares a quota.
  2. Apply policy before the backendCheck the rate limit, authenticate, validate. Rejected requests cost the backend nothing.
  3. Try the cacheIf the response is cached and fresh, answer immediately; otherwise forward and store the result for next time.
  4. Shape the responseCompress it, add security headers, strip internal ones.
  5. Record itLog the request ID, status and timing: the proxy is the best place for uniform access logs and metrics.

Interview in practice

"What does an API gateway do, and how is it different from a load balancer?"

The question: Many candidates blur the two. Draw the line, then say when you would add a gateway.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How many services sit behind it, and who are the clients (browsers, mobile apps, partners)? Many services and external clients are the main reasons to add a gateway.
2. Think it through (the reasoning, step by step)
  1. Start from the load balancer. It spreads traffic across identical instances of one service and keeps unhealthy ones out of rotation.
  2. Describe the gateway as a smarter, API-aware front door. It is a layer 7 proxy in front of many different services: routing by path or host to the right service, authentication and authorisation, rate limits and quotas per client, request and response transformation, API keys, logging and metrics, sometimes caching.
  3. Show where they overlap and combine. A gateway usually load balances to the instances of each service (or sits in front of per-service load balancers). In practice products (nginx, Envoy, Kong, cloud API gateways) do both.
  4. Name the costs. An extra hop and a critical shared component: it must be highly available and must not become a bottleneck or a place where business logic accumulates.
  5. Give the decision rule. One service, many identical instances: a load balancer is enough. Many services behind one public API, with shared concerns (auth, limits): add a gateway.
3. A strong answer, said out loud

"A load balancer spreads requests across identical instances of one service and removes unhealthy ones. An API gateway is a layer 7 front door for many services: it routes by path or host to the right service, handles authentication, rate limits and quotas per client, can transform requests, and gives you one place for logging and metrics. In practice the gateway also load balances across instances of each service, so the two features live in the same proxy.

I would add a gateway when there are many services behind one public API and common concerns I do not want to implement in each of them. The costs are an extra hop and a critical component that has to be highly available, and the discipline to keep business logic out of it."

A gateway-like service tailored to one client type (mobile, web) that aggregates calls to several backends and shapes the responses for that client.

At the gateway for coarse checks (is the token valid, which client is this), with services still enforcing fine-grained authorisation for their own data.

How do you rate limit across several gateway instances?

Share the counters in a fast store (for example Redis) or give each instance a share of the quota and accept some inaccuracy.

Making the balancer itself reliable, and spreading across regions

Must know
Situation

You made the servers redundant, but every request still goes through one balancer. If it dies, everything is down. And what about a whole data centre failing, or users on another continent?

You will learn
  • Redundant balancers and a shared address
  • DNS and global load balancing
  • Where the single points of failure hide
Mental model

A single balancer is a single point of failure, so balancers come in groups. Two common ways: an active-passive pair that share a virtual IP: the active one holds the address and the standby watches it (with a protocol such as VRRP, implemented by keepalived); if the active one stops answering, the standby takes the address within seconds and clients keep using the same IP. Or many active balancers behind DNS round robin (several A records) or anycast routing, where the same IP is announced from several places and the network delivers each client to the nearest one. Cloud load balancers hide all of this: they are redundant across zones for you.

To survive the loss of a region and to serve users nearby, add global load balancing: DNS that answers with the address of the closest or healthiest region (GeoDNS, latency-based routing, health-checked failover), or anycast. DNS-based failover is bounded by the TTL (clients and resolvers keep the old answer) and by clients that ignore it, so critical failover keeps the TTL short and combines DNS with application-level retries.

Everyday analogy: A building with two front doors and a receptionist who is always replaced by a colleague if they step out: visitors keep using the same street address.

The picture
How it works, step by step
  1. Give clients a stable addressA virtual IP (or a DNS name resolving to several balancers) that does not belong to one machine.
  2. Elect or assign who serves itIn an active-passive pair the master holds the virtual IP and announces it; the backup listens for those announcements.
  3. Detect failureIf the backup stops hearing the master (a few missed announcements, typically 1 to 3 seconds), it assumes the address.
  4. Keep configuration and state in syncBoth balancers need the same backend list and settings; connection state may or may not be shared, so existing connections can break at failover.
  5. Add regions on topGlobal balancing sends users to a healthy region; each region has its own redundant balancers and servers.

Interview in practice

"How would you design the load balancing for a global service that must survive a data-centre failure?"

The question: A bigger question that tests whether you can layer the pieces: DNS, regional balancers, health checks and failover behaviour.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • Where are the users, and what latency matters? Users on several continents mean serving from nearby regions.
  • Is the data replicated across regions, and is it strongly consistent? Failover is only possible if the data a region needs is there; consistency choices follow the distributed systems module.
  • What recovery time do we need? Seconds need active-active and short TTLs; minutes can allow DNS failover.
2. Think it through (the reasoning, step by step)
  1. Layer the problem. Global (which region?), regional (which balancer?), local (which server?). Each level has its own mechanism and failure handling.
  2. Global level. GeoDNS or latency-based DNS returns the address of the nearest healthy region, with health checks removing a failed region and a short TTL (such as 30 to 60 s). Anycast is an alternative that avoids DNS caching.
  3. Regional level. In each region a pair or fleet of balancers across availability zones (or a managed cloud balancer), each health-checking its servers.
  4. Failure behaviour. Region fails: health checks stop answering for it, DNS drops it, clients move to the next region within about a TTL; clients and gateways retry on connection errors to cover the gap.
  5. Name the hard parts. Capacity: the surviving regions must absorb the extra load (plan N+1 across regions). Data: replication lag and conflicts. Testing: run game days to prove the failover works.
  6. Mention costs. Active-active is expensive and complex; many services use active-passive for the data layer and active-active only for stateless tiers.
3. A strong answer, said out loud

"I would layer it. At the global level, a health-checked DNS service with latency-based routing returns the address of the nearest healthy region and uses a short TTL, so when a region fails it is dropped within a minute or so; anycast is an alternative. Inside each region, redundant load balancers across availability zones, or a managed one, distribute to servers that they health-check, and the balancers have no single point of failure because they share a virtual IP or sit behind several addresses.

When a region fails, its health checks fail, DNS stops returning it, and clients move to another region; clients and gateways retry on connection errors to cover the TTL window. The hard parts are capacity, because the remaining regions must be able to carry the extra traffic, and data, because the user's data must be available there, which brings in replication lag and consistency. I would rehearse the failover regularly, since an untested failover tends to fail."

4. Follow-ups you should expect
DNS TTLs are often ignored. How do you cope?

Combine DNS with client-side retries across several addresses, keep an anycast or global load balancer layer in front for critical traffic, and design clients to try the next address on failure.

What is the difference between anycast and GeoDNS?

GeoDNS answers DNS queries with different addresses by location; anycast announces the same address from many places and the network routes each client to the nearest one, with no DNS TTL involved.

How many balancers are enough?

At least two in different failure domains, sized so that losing one still leaves enough capacity.

Common slips
  • Saying "multi-region" without the data story.
  • Relying on DNS TTLs for instant failover.
  • Forgetting capacity on the surviving regions.
Quick check

Answer in your head first, then open it.

How does an active-passive pair of balancers keep one address?

They share a virtual IP: the master announces and holds it, and the standby takes it over when the announcements stop.

Why is DNS failover slower than local health-check failover?

Resolvers and clients cache answers for the TTL, and some ignore it.

Name two places where a single point of failure can hide in a balanced design.

The balancer itself, and shared dependencies such as the database or DNS provider.

Traps to avoid (3)
  • A pair of balancers on the same rack, switch or power feed: they fail together. Spread them across failure domains.
  • Configuration drift between balancers: the standby takes over with an out-of-date backend list.
  • A failover plan never rehearsed: practise it.

Which algorithm adapts to a slow backend, and why?

Least connections: the slow server keeps connections open so it gets fewer new ones.

What does consistent hashing improve over hash mod N?

Only about 1/N of keys move when servers change.

What is the detection delay of an active health check with inter 1s and fall 3?

About 3 seconds.

Why retry only idempotent requests?

The failed attempt may have succeeded; repeating a non-idempotent request could duplicate its effect.

What is connection draining?

Stop sending new requests to a server and let in-flight ones finish before stopping it.

What headers carry the client's identity through a reverse proxy?

X-Forwarded-For and X-Forwarded-Proto.

What status code does rate limiting return?

429 Too Many Requests.

What does an API gateway add beyond a balancer?

Routing by API, authentication, per-client limits and central logging and metrics.

Why is DNS failover slower than health-check failover?

Caches keep the old answer for the TTL, and some clients ignore it.

How is an active-passive balancer pair given one address?

A virtual IP that the standby takes over when the master's announcements stop.
