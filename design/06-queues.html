Chapter 6 of 9The ShopKart story

Do not make people wait

How to stop making customers wait for slow work: put it behind a queue, and then learn the rules that keep a queue honest (repeats, lost events, retries and overflow).

about 18 minutes4 steps5 real experiments3 interview questions

1Launch day, 11:00 a.m.The story

ShopKart's marketing team sends the big launch email at 11:00. Signup has always worked the same way: save the account (0.3 seconds), send a welcome email through a mail provider (1.5 seconds), then resize the profile photo into three sizes (2.2 seconds). Total: four seconds, with the customer staring at a spinner.

Four seconds was fine at ten signups an hour. But the web tier has 20 workers, and each one is stuck for four seconds per signup, so the shop can finish only 5 signups a second (20 workers divided by 4 seconds). Marketing's email brings 200 signups in the first second. Within moments every worker is busy, browsing visitors cannot get a free one, and the whole site returns errors.

The customer never needed the email or the resized photo before seeing the next page. Only the saved account is urgent. The fix is to write down the slow work as a list of jobs and let someone else do it a few seconds later.

2The idea: write the job down, do it laterThe idea

A queue is a line of messages between the part that asks for work and the part that does it, so the fast side never waits for the slow side.

A queue does three jobs. It makes the customer's wait short, it absorbs a spike (the line gets long for a minute and then shrinks), and it separates the two sides, so a slow or broken email provider no longer breaks signup. The price is that work now happens later, can happen twice, and needs watching.

A plain queue deletes a message once it is handled. A log (the Kafka model) keeps messages in order and lets each team read at its own pace. Each team is a consumer group with its own bookmark, so billing and analytics can both read every order, and a new team can replay history from the start. Inside a group, the work is shared out between the consumers.

3How it works, step by stepHow it works

  1. Put slow work behind a queue

    Do only what the customer must wait for (save the signup), then put a job describing the rest into a queue: a line of messages waiting to be handled. A separate worker program takes jobs off the line and does the slow work.

  2. Expect every message to arrive at least once

    Networks fail, so a queue must choose: at most once (can lose a job) or at least once (can deliver a job twice). Real systems choose at least once, and make the handler idempotent, meaning that doing it twice has the same effect as doing it once. That is what "exactly once" really means in practice.

  3. Never lose the event: use an outbox

    Saving an order and then publishing an event are two steps, and a crash between them loses the event. The outbox pattern writes the order and the event into the same database transaction, and a small relay program publishes unsent events afterwards. It may publish one twice, so consumers must ignore repeats.

  4. Retry gently, park the poison, push back

    A failed job is retried after a wait that grows each time (backoff). A job that keeps failing, such as a malformed message, moves to a dead-letter queue so it stops blocking everyone, and a person looks at it later. If jobs arrive faster than workers can finish, a bounded queue says "not now" (back-pressure) instead of growing without end.

2Lose it, repeat it, or make it safe

The three behaviours, each with the crash that hurts it most. At most once: the job was removed from the queue before the work, so when the worker dies mid-job the job is simply gone: job3 is lost. At least once: the job stays in a processing list until acknowledged, so after the crash it is redelivered; but this worker had already done the work before dying, so job3's effect happens twice. At least once with an idempotent handler (a SET NX marker per job) redelivers it and the duplicate is skipped, so every job takes effect exactly once. In real code the marker and the effect must be written in one transaction.

import sys
sys.path.insert(0, '.')
from rc import R
r = R()
effects = []                                    # the side effects that actually happened (for example, cards charged)
def run(label, take, finish, crash_when, idempotent=False):
    r.cmd('FLUSHALL'); effects.clear()
    for i in range(1, 6): r.cmd('RPUSH', 'jobs', 'job%d' % i)
    crashed = False
    while True:
        job = take()
        if job is None: break
        if idempotent and r.cmd('SET', 'done:' + job, '1', 'NX') is None: finish(job); continue   # already done: skip
        if job == 'job3' and not crashed:       # the worker dies while handling job3
            crashed = True
            if crash_when == 'after work': effects.append(job)        # ...after the side effect, before it could acknowledge
            if r.cmd('LLEN', 'processing'):     # at-least-once: after the visibility timeout the job comes back
                r.cmd('LMOVE', 'processing', 'jobs', 'LEFT', 'RIGHT')
            continue
        effects.append(job)                     # do the work
        finish(job)
    lost = sorted({'job%d' % i for i in range(1, 6)} - set(effects))
    dup = sorted({j for j in effects if effects.count(j) > 1})
    print('%-34s lost: %-6s duplicated effects: %s' % (label, lost or 'none', dup or 'none'))
# at most once: remove the job from the queue BEFORE working on it
def take_amo(): return r.cmd('LPOP', 'jobs')
run('at most once (crash before the work)', take_amo, lambda j: None, 'before work')
# at least once: move to a processing list, work, then acknowledge by removing it
def take_alo(): return r.cmd('LMOVE', 'jobs', 'processing', 'LEFT', 'RIGHT')
def ack(j): r.cmd('LREM', 'processing', 1, j)
run('at least once (crash after the work)', take_alo, ack, 'after work')
run('at least once + idempotent handler', take_alo, ack, 'after work', idempotent=True)
EOF

3The lost event, and the outbox

The dual-write bug and its fix, step by step. In the naive version the order is saved and the process dies before publishing: one order, zero events, and nothing will ever repair it. With the outbox the event row is committed in the same transaction as the order, so it cannot be lost. The relay publishes it; when it is made to crash after publishing but before marking the row, the event is published a second time after the restart. That is the price of the pattern: at-least-once publishing, so consumers must treat the event id as an idempotency key.

4A bad message: retry, then dead letter

Retries done properly. m2 fails once with a transient timeout, waits (a delay that doubles with random jitter) and succeeds on the second attempt. m3 is a poison message: it fails every time, so after the attempt limit it is moved to the dead-letter queue with its error, instead of blocking the others or retrying forever. m4 is processed normally afterwards. The DLQ must be monitored: a growing DLQ is a bug report, and its messages can be fixed and replayed.

import random, time
rng = random.Random(1)
dlq, log = [], []
def handle(msg, attempt):
    if msg.get('bad'): raise ValueError('malformed payload')               # a poison message: will never succeed
    if msg['id'] == 'm2' and attempt == 1: raise TimeoutError('downstream timed out')   # transient: works on retry
def process(msg, max_attempts=4, base=0.05):
    for attempt in range(1, max_attempts + 1):
        try:
            handle(msg, attempt); log.append('%s attempt %d: ok' % (msg['id'], attempt)); return
        except Exception as e:
            log.append('%s attempt %d: %s' % (msg['id'], attempt, e))
            if attempt == max_attempts:
                dlq.append((msg['id'], str(e))); log.append('%s -> dead-letter queue' % msg['id']); return
            delay = base * 2 ** (attempt - 1) * (0.5 + rng.random())      # exponential backoff with jitter
            log.append('   waiting %.0f ms before retry' % (delay * 1000)); time.sleep(delay)
for m in ({'id': 'm1'}, {'id': 'm2'}, {'id': 'm3', 'bad': True}, {'id': 'm4'}): process(m)
print('\n'.join(log)); print('dead-letter queue now holds:', dlq)
EOF

5A full queue: back-pressure

Back-pressure, measured. Jobs arrive at about 100 per second but are processed at 50 per second. The unbounded queue accepts everything, so its depth keeps growing (about 50 more jobs every second) and a newly arrived job would wait many seconds: latency grows and memory fills while every job is still "accepted". The bounded queue holds at most 20, so the excess is rejected immediately (the caller gets a clear busy and can retry later or degrade), and the wait for accepted jobs stays under half a second. Rejecting early is usually kinder than accepting work you cannot finish.

import queue, threading, time
def scenario(maxsize, label):
    q = queue.Queue(maxsize=maxsize); stats = {'done': 0, 'rejected': 0, 'peak': 0}
    stop = threading.Event()
    def worker():
        while not stop.is_set():
            try: q.get(timeout=0.1)
            except queue.Empty: continue
            time.sleep(0.02); stats['done'] += 1                          # service rate: 50 per second
    t = threading.Thread(target=worker); t.start()
    start = time.time()
    while time.time() - start < 3:                                        # arrival rate: 100 per second for 3 seconds
        try: q.put_nowait(1)
        except queue.Full: stats['rejected'] += 1
        stats['peak'] = max(stats['peak'], q.qsize()); time.sleep(0.01)
    wait = q.qsize() * 0.02
    stop.set(); t.join()
    print('%-22s peak depth %3d, rejected %3d, a new job would now wait about %.1f s' % (label, stats['peak'], stats['rejected'], wait))

5How it breaks in productionFailure modes

Duplicate work

A worker finishes the job but crashes before it confirms, so the queue hands the job out again, and the customer gets two emails or two charges. Fix: make handlers idempotent, for example by recording the job id before acting.

Lost events

The database save succeeds, the publish fails, and nothing downstream hears about the order. Fix: the outbox pattern, so the event is saved with the order.

Poison messages

One malformed job fails forever and is retried forever, blocking the line behind it. Fix: cap the retries, then move it to a dead-letter queue and alert someone.

Retry storms

A struggling email provider makes every job fail, and instant retries multiply the traffic. Fix: backoff with random jitter, a retry cap, and a circuit breaker (chapter 7).

Unbounded queues

A queue that grows without limit hides the problem, and a new job ends up waiting minutes. Fix: bound the queue, add workers or shed load, and alert on queue depth and age.

Out of order

Two workers handle events for the same account at once, so an update is applied before the create. Fix: route by key (the account id) so one account's events go to one worker in order.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official company lists.

A common prompt about queues: reported by candidates at large tech companies, not official.

"When would you put a queue in front of a service? What problems does it create?"

A foundation question that leads into delivery guarantees. A good answer gives benefits, costs and when not to use one.

Ask first

  • What work is on the request path, and does the user need the result immediately? If the user needs the answer to continue, a queue cannot hide the latency: it only fits work that can finish later.

How to think about it

  1. Name the three things it decouples.Time (work later), rate (absorb spikes), failure (retry while a dependency is down). Also lets you scale producers and consumers independently.
  2. Say when it fits.Sending emails, resizing images, calling flaky third parties, billing runs, fan-out to many services, any work the user does not need to wait for.
  3. Say when it does not.When the caller needs the result now, or the extra moving part and latency are not worth it for light, reliable work.
  4. List the costs.Asynchrony (the user sees accepted, not done), duplicates and ordering, a new component to run and monitor, visibility problems (where is my job?), and the possibility of an unbounded backlog.
  5. Say what to monitor.Queue depth, age of the oldest message, processing rate versus arrival rate, retry and dead-letter counts.
  6. Mention the limit.A queue smooths bursts. If the average arrival rate exceeds the processing rate, the backlog grows without bound: scale consumers or shed load.

How to say it

A model answer, about two minutes aloud

"A queue decouples producer and consumer in time, rate and failure. The request just enqueues and returns, a burst piles up in the queue instead of overwhelming the workers, and if a worker or a downstream service is down the job waits and is retried instead of failing the user. It lets me scale producers and consumers independently.

It fits work the user does not need to wait for: emails, image processing, calls to flaky third parties, billing, fan-out. It does not fit when the caller needs the result right now. The costs are asynchrony, duplicates and ordering concerns, another component to operate, and less visibility. I would monitor depth, the age of the oldest message and the retry and dead-letter counts, and remember that a queue only smooths bursts: if the average arrival rate exceeds the processing rate the backlog grows forever, so I would scale consumers or shed load."

Likely follow-ups

How do you tell the user the work finished?

Return a job id and let them poll a status endpoint, or push a notification (webhook, websocket, email) when it completes.

How do you size the consumers?

Consumers needed = arrival rate x time per job / concurrency per consumer, with headroom (the last lesson has the calculator).

What is a queue depth alert good for?

Depth rising steadily means consumers are slower than producers; age of the oldest message shows the user-visible delay.

Common slips

  • Saying a queue "makes it faster": it makes the request faster by moving the work.
  • Forgetting duplicates and retries.
  • No monitoring of depth and age.
A frequent probing question on delivery guarantees: reported by candidates, not official.

"Can a message queue guarantee exactly-once delivery? How do you process payments safely from a queue?"

A classic trap. The strong answer says no, explains why, and shows how to get the effect anyway.

Ask first

  • What is the side effect, and can it be repeated safely? Charging a card is not safe to repeat; setting a status to paid is.

How to think about it

  1. Answer the literal question.No. After a crash or timeout the broker cannot know whether the consumer finished, so it must choose between possibly losing the message (at most once) and possibly repeating it (at least once).
  2. Pick at least once for payments.Losing a payment job is usually worse than repeating one, provided repeating is safe.
  3. Make repeating safe.Give every payment request a unique idempotency key. The handler records the key and the result in the same database transaction as the effect (or a unique constraint on the key). A duplicate delivery finds the key and returns the stored result.
  4. Cover the outside world.When calling a payment provider, pass the idempotency key to them too, so a retry does not charge twice.
  5. Handle poison and ordering.Limit retries with backoff and a dead-letter queue; do not let one bad message block the queue.
  6. Say what the broker may call exactly once.Some brokers advertise exactly-once within their own transactions (read, process, write back to the same system): useful, but it does not cover external side effects.

How to say it

A model answer, about two minutes aloud

"No, not as a delivery guarantee: when a consumer crashes or times out the broker cannot know whether the work was done, so it must either risk losing the message or risk delivering it again. For payments I choose at least once, because losing a payment is worse, and make repeating it safe.

Every payment request carries a unique idempotency key. The handler stores the key and the outcome in the same database transaction as the effect, or relies on a unique constraint, so a duplicate delivery finds the key and returns the stored result instead of charging again. When I call the payment provider I pass the same key so their side is idempotent too. I add retries with backoff and a dead-letter queue so one poison message cannot block the rest. Some brokers offer exactly-once inside their own transactions, which helps for read-process-write within one system but does not cover external side effects."

Likely follow-ups

What is a visibility timeout and how do you choose it?

How long a taken message stays hidden before being redelivered; longer than the normal processing time, shorter than the delay you can tolerate after a crash.

What if the idempotency record is written but the effect fails?

Write them in the same transaction so they succeed or fail together; for external effects, record intent first and reconcile.

Why not just use a distributed transaction?

Two-phase commit across a queue and an external service is rarely available and blocks on failure; idempotency is simpler and more robust.

Common slips

  • Claiming the queue gives exactly-once.
  • Choosing at-most-once for money.
  • An idempotency key stored in a different place or time from the effect.
A frequent notification service deep dive: reported by candidates, not official.

"Design a notification service that sends 10 million emails a day with retries. What can go wrong in the queue?"

They want a pipeline with the failure modes named: ordering, retries, poison messages, back-pressure, third-party limits.

Ask first

  • Peak rate, delivery deadline, and are there per-user ordering needs? 10 million a day is about 115 per second on average, perhaps 1,000 per second at peak. Order matters only per user, if at all.
  • What does the email provider limit? Third parties rate-limit: the consumer must respect their limits.

How to think about it

  1. Size the flow.10M / 86,400 s is about 115 per second average; peak maybe 10x. With 100 ms per send and 50 concurrent senders, capacity is 500 per second: scale for peak, or let the queue smooth it.
  2. Pipeline.API receives requests and writes an outbox row or enqueues; a queue per priority (password resets before newsletters); workers call the provider; results update a status table.
  3. Ordering.Not global; per recipient if needed: partition by user id.
  4. Retries and idempotency.Retry transient errors with exponential backoff and jitter; an idempotency key per notification (and pass it to the provider) so a retry never double-sends; at-least-once delivery with deduplication.
  5. Poison and DLQ.Invalid addresses or payloads go to a dead-letter queue after a few attempts, with an alert and a tool to inspect and replay.
  6. Back-pressure and limits.Bounded queues, a rate limiter toward the provider (token bucket), and a priority scheme so a newsletter cannot delay a password reset; shed or defer low-priority work first.
  7. Monitoring.Queue depth and oldest age per priority, send rate, error rate by cause, DLQ size, end-to-end delivery latency.

How to say it

A model answer, about two minutes aloud

"Ten million a day is about 115 sends per second on average and maybe ten times that at peak, which a queue plus a pool of workers handles easily. The API writes the notification and an event in one transaction (an outbox) or enqueues it, with a queue per priority so password resets are never stuck behind newsletters. Workers call the email provider and record the result.

Failures: transient errors are retried with exponential backoff and jitter; every notification has an idempotency key, also passed to the provider, so at-least-once delivery cannot double-send; invalid messages go to a dead-letter queue after a few attempts, with an alert. Ordering is only needed per recipient, so I would partition by user id. I would bound the queues and rate limit toward the provider, shedding low-priority work first under pressure. I would monitor depth and oldest age per priority, error rates by cause, DLQ size and end-to-end latency."

Likely follow-ups

How do you handle the provider being down for an hour?

Retries back off; the queue grows (bounded, with alerts); fail over to a second provider if available; low-priority messages wait, high-priority ones switch route.

How do you prevent a newsletter from delaying password resets?

Separate queues and consumer pools per priority (or weighted consumption), and rate limit the bulk queue.

How would you track that a notification was delivered?

A status row per notification updated by the worker and by provider webhooks (delivered, bounced), with timestamps for latency metrics.

Common slips

  • One queue for everything.
  • Retrying forever without a dead-letter queue.
  • No idempotency: retries double-send.

8Remember thisRecap

The page in 6 lines

  • Do only the urgent work before replying; queue the rest as jobs for workers.
  • A queue absorbs spikes and separates fast code from slow or unreliable code.
  • Choose at least once delivery and make handlers idempotent: that is practical exactly once.
  • Save the event with the order (outbox) so a crash cannot lose it.
  • Use a log with consumer groups when many teams read the same events and may replay them.
  • Cap retries with backoff, send poison messages to a dead-letter queue, and bound the queue.

Check yourself

Why can a queue deliver a job twice?

A worker can finish and crash before confirming, so the queue gives the job to someone else. Handlers must be idempotent.

What problem does the outbox pattern solve?

Saving the data and publishing the event are two steps; the outbox saves the event in the same transaction so a crash cannot lose it.

What is a dead-letter queue for?

To park a job that keeps failing so it stops blocking the line, until a person can look at it.
