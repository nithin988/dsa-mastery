Chapter 6 of 14Night shift at ShopKart

When the team grows and things go wrong

When a bad commit reaches production you need three skills: undo it safely, find which commit caused it, and recover work you thought you had lost.

about 25 minutes4 steps4 real experiments3 interview questions

1Friday afternoon: the bad commitThe story

At 4:50 on Friday, Dana deploys the week's work. At 5:20 the pager goes off: some customers are charged totals a cent too high. ShopKart's pricing repository has sixteen commits since launch, and one of them changed how prices are rounded. Nobody knows which.

Ravi, who is not a Git person, wants it gone now. He runs git reset --hard three commits back and force-pushes. The bad change disappears, but so do two good commits that Mei pushed that morning. Mei's laptop is on a train home, and nobody can tell what was lost.

A calm team does three things in order. Revert the bad change safely, bisect to find the guilty commit in a few tests, and use the reflog to bring back the commits that were lost. Each is one command, and this chapter shows all three.

2The idea: shared history is added to, private history can be rewrittenThe idea

Once commits are shared, undo by adding a commit (revert). While commits are private, you may move the branch (reset). If you lose work either way, the reflog remembers.

Almost every Git disaster is the wrong undo for the situation: rewriting history that others already have, or deleting work that was never committed. Choose by one question: has anyone else seen these commits?

3How it works, step by stepHow it works

  1. Stop the bleeding: revert, do not rewrite

    git revert <commit> makes a new commit that undoes an old one. History keeps both, so everyone who already pulled the bad commit stays in step. It is the safe first move once something is shared.

  2. Find the guilty commit: bisect

    git bisect does a binary search through history. You mark one commit good and one bad, and Git checks out the middle for you to test. Each answer halves the candidates, so sixteen commits need only about four tests, and a test script can run them all.

  3. Undo on your own machine: reset has three strengths

    git reset moves your branch back. --soft keeps your changes staged, --mixed keeps them in your files, and --hard throws them away. Use reset only on commits you have not shared, because it rewrites history.

  4. Get lost work back: the reflog

    The reflog is your local diary of every place HEAD has been, even after a reset --hard or a deleted branch. Find the commit you want, then point your branch back at it. It only lives on your machine, and old entries expire.

5How it breaks in productionFailure modes

Reset or force-push on shared history

You remove a bad commit locally and force-push, and teammates' commits disappear or their branches break. Fix: use git revert on shared branches, and force-push only your own branch, with --force-with-lease.

reset --hard with uncommitted work

Commits can be rescued from the reflog, but edits that were never committed or staged cannot. Fix: commit or git stash before any hard reset.

The reflog is local and it expires

It lives only in your clone, so it cannot rescue work from a teammate's laptop. Old entries are removed by garbage collection after a configurable time. Fix: recover quickly, and push work to a branch.

Bisect with a flaky test

If the test passes sometimes and fails sometimes, bisect points at the wrong commit. Fix: make the test deterministic first, or run it several times per step.

Reverting a merge commit

A merge has two parents, so Git needs to know which side to keep (git revert -m 1 <merge>). Reverting a merge also makes it harder to re-merge that branch later. Fix: read the docs before you do it.

Conflicts during revert or rebase

An undo can clash with later changes to the same lines. Fix: resolve the conflict like any merge, git add, and continue, or --abort to start again.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A very common Git recovery question: reported by candidates, not official.

You accidentally ran `git reset --hard HEAD~3`. How do you get the commits back?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

git reflog to find the hash (or HEAD@{1}) of the commit before the reset, then git reset --hard <hash>.

Works for committed work only, on this clone, until reflog entries expire.

Uncommitted changes cannot be recovered.

Likely follow-ups

• How is a deleted branch recovered?

Common slips

  • Saying the commits are gone for good.
A frequent debugging question: reported by candidates, not official.

A test broke somewhere in the last 200 commits. How do you find the commit?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

git bisect: mark a known good and a known bad commit, test the middle, repeat; about 8 tests for 200 commits.

Automate with git bisect run <script> (exit 0 good, 1 bad, 125 skip).

Then read the commit with git show and git blame to understand why.

Likely follow-ups

• What if the test is flaky?

• What if some commits do not compile?

Common slips

  • Reading commits one by one.
A frequent question comparing undo commands: reported by candidates, not official.

Explain `git reset --soft`, `--mixed` and `--hard`. And how is revert different?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

All three move the branch back; they differ in what else they undo: soft keeps changes staged, mixed (default) keeps them unstaged, hard discards them.

Revert adds a new commit that undoes a previous one; history is preserved.

Reset for local commits; revert for anything already pushed.

Likely follow-ups

• Can you recover after a hard reset?

• How do you revert a merge commit?

Common slips

  • Using reset on a shared branch.

8Remember thisRecap

The page in 6 lines

  • On a shared branch, undo with git revert: it adds a commit and keeps history.
  • git reset rewrites your private history: soft keeps changes staged, mixed keeps files, hard throws changes away.
  • git bisect finds the first bad commit by binary search; a test script makes it automatic.
  • The reflog is a local diary of where HEAD has been: git reset --hard HEAD@{1} goes back one move.
  • Committed work is recoverable; uncommitted work lost to reset --hard is not.
  • Before any history rewrite ask: has anyone else seen these commits?

Check yourself

Revert or reset for a bad commit that is already on main?

Revert. It adds a new commit that undoes the change without rewriting shared history.

How many tests does bisect need for 200 commits?

About eight, because each test halves the candidates (200, 100, 50, 25, 13, 7, 4, 2, 1).

You ran git reset --hard HEAD~3 by mistake. What now?

Run git reflog, find the commit from before the reset, and git reset --hard to it. This works only for committed work.
