How a request travels

A web request is four trips in a row: find the address, connect, secure, ask. Learn to test each trip on its own and a customer who cannot load the site becomes a ten minute problem.

about 20 minutes4 steps4 real experiments3 interview questions

1Wednesday, 2:14 a.m.The story

ShopKart now has customers in four countries. At 2:14 a.m. the support inbox gets a message from Amara in Lagos: the site "just spins" on her phone, and has done for two hours. You open ShopKart on your laptop and it loads in under a second. You try again. Fine. The monitoring dashboard is green.

Your tools say the shop is up, and one customer says it is not. Both are true. Between her phone and your server a request makes four separate trips. It looks up an address (DNS), opens a connection (TCP), agrees a secret (TLS) and finally asks for the page (HTTP). Your laptop passes all four. Hers fails at one of them.

You do not guess. You walk the four trips in order, one command each. At 2:51 you find it. At 9 p.m. the team moved the shop to a new load balancer with a new address, and the old DNS answer had been set to be remembered for 24 hours. Amara's network still hands out the old address, where nobody answers.

2The idea: four trips, tested in orderThe idea

A web request is a relay of four trips: DNS finds the address, TCP opens a connection, TLS makes it private and proves who is at the other end, and HTTP asks for the page. Each trip fails in its own recognisable way, so the symptom tells you where to look.

A wrong or missing address points at DNS. "Connection refused" or a long hang points at TCP. A certificate warning points at TLS. A number such as 503 is an HTTP answer, which means the network itself worked. In the recorded request above, the address lookup alone took 0.455 s of a 0.795 s total, so the first trip is often the slowest.

3How it works, step by stepHow it works

  1. Find the address (DNS)

    Browsers need a number, not a name. A resolver (usually run by your internet provider) asks the DNS system for the address behind shopkart.example and remembers the answer for its time to live (TTL), in seconds. Until the TTL runs out it will not ask again, even if you have moved the shop.

  2. Open a connection (TCP)

    TCP opens a connection with a three step handshake: the client sends SYN, the server answers SYN-ACK, the client replies ACK. A port is a numbered door on the machine, such as 443 for secure web traffic. If nothing is behind the door you get an instant "connection refused"; if a firewall drops the packets you get silence and a timeout.

  3. Make it private and check who is there (TLS)

    TLS agrees secret keys, and the server shows a certificate: a signed ID card for its name. The client checks that the chain of signatures ends at a root it trusts, that the name matches, and that today's date is inside the validity window. If any check fails, the connection stops before a single byte of the page is sent.

  4. Ask for the page (HTTP)

    Only now does the browser send GET /product/42. The server answers with a status code: 2xx worked, 3xx go somewhere else, 4xx you asked wrongly, 5xx we failed. Reusing the same connection skips the first three trips for the next request.

3Distance costs time on every trip

Why latency matters more than bandwidth for small transfers: a new TCP connection cannot use the full speed straight away. With an initial window of 10 segments and doubling each round trip, even 1 MB needs 7 round trips plus the handshake. On a 200 ms intercontinental path that is 1.6 seconds, however fat the pipe is.

Real output · Debian GNU/Linux 13 (trixie), ordinary user

RTT  50 ms: handshake + transfer about   400 ms
RTT 200 ms: handshake + transfer about  1600 ms

RTT 200 ms: ... 1600 ms(7 + 1 handshake) x 200 ms: proximity to the user (CDNs) shortens the round trip itself
Show the command and the full explanation
python3 -c "seg=1460; size=1_000_000
print('sending 1 MB, initial window 10 segments, doubling each round trip (slow start)')
sent=0; cwnd=10; rounds=0
while sent < size:
    sent += cwnd*seg; rounds += 1; cwnd *= 2
print('round trips needed:', rounds)
for rtt in (10, 50, 200):
    print('RTT %3d ms: handshake + transfer about %5d ms' % (rtt, (rounds+1)*rtt))"

5How it breaks in productionFailure modes

Stale DNS after a move

A resolver keeps the old address until the TTL ends, so some customers reach the old server for hours. Fix: lower the TTL a day before any move, and keep the old address answering until the old TTL has passed.

A firewall that drops instead of refusing

A closed port answers at once with "refused". A firewall that silently drops packets leaves the client waiting for a timeout. An instant error means nobody is listening; a long hang means something is dropping the traffic.

An expired or mismatched certificate

After the certificate's end date every client refuses the site, and a certificate for www.shopkart.example does not cover shopkart.example unless both names are listed. Fix: automate renewal and alert weeks before the date.

Distance

Each trip needs round trips, and a round trip to the far side of the world is slow. In the recorded model one megabyte needed 7 round trips plus a handshake: 1,600 ms at 200 ms per trip, against 80 ms at 10 ms. Fix: serve from nearby with a CDN, and reuse connections.

Blaming the network for an HTTP answer

A 503 from the load balancer looks like "the network is down" but it is a healthy network delivering a bad answer. Read the status code before you blame the road.

Testing from the wrong place

Your laptop has a warm DNS cache, a good route and a different resolver from your customer. Test from outside (a phone on mobile data, or a checking service) before you say "it works for me".

6Where this is written downPrimary sources

IETF standard

The DNS specification defines each record's TTL as the time interval, in seconds, that the record may be cached before it should be discarded. That is why a changed address takes time to reach everyone.

RFC 1035: Domain Names, Implementation and Specification
IETF standard

The current TCP specification describes the three way handshake that opens a connection and the reset that answers a connection to a port where nothing is listening.

RFC 9293: Transmission Control Protocol
IETF standard

The TLS 1.3 specification describes how client and server agree on keys and how the server proves its identity with a certificate, so that traffic cannot be read or changed on the way.

RFC 8446: TLS 1.3

Summaries of the public standards; read the linked document for the exact wording.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists.

A very common operations prompt: reported by candidates, not official.

"Users say the website is down. Walk me through how you troubleshoot it from the command line."

The most common operational networking question. They want order, evidence and calm.

Ask first

  • Is it down for everyone or for some users? Since when? What changed? Scope and timing steer everything: all users and a recent deploy suggests the server; some users suggests DNS, a region or a client network.

How to think about it

  1. Say the order out loud."I walk the request path: DNS, TCP, TLS, HTTP, and stop at the first stage that fails."
  2. Name the command and the signature for each stage.getent hosts (no answer: DNS); nc -zv host 443 (refused: nothing listening; timed out: firewall or routing); openssl s_client (certificate errors); curl -sv (status code and headers; 5xx points at the server or a proxy).
  3. Compare with a working vantage point.Test from another network or machine to separate a client-side problem from a server-side one.
  4. Mitigate if users are hurting.If a recent change correlates, roll it back first; investigate afterwards.
  5. Then go to the server.ss -ltnp for the listener, process state, application and proxy logs, resource saturation (the performance triage module).

How to say it

A model answer, about two minutes aloud

"First I would find out who is affected, since when, and what changed. Then I walk the request path in order and stop at the first failure: does the name resolve with getent hosts; does the port accept connections with nc -zv, where refused means nothing is listening and timed out means a firewall or routing problem; is the certificate valid with openssl s_client; and what does curl -sv return, since a 5xx means the server or a proxy failed.

I would also test from a second network to tell a client problem from a server problem. If a deploy just went out, I would roll it back to stop the harm. Once I know the failing stage, I go to the server: check the listener with ss, the process, application and proxy logs, and resource saturation. Afterwards I would write up what happened and add a check or alert for that failure."

Likely follow-ups

It works for some users only. What next?

Compare the working and failing users: region, resolver, ISP, client version. That points at DNS caches or geo routing, a single bad backend behind the load balancer, or a partial CDN issue. Check per-backend error rates.

It is slow, not down. How do you find where?

curl -w timings split DNS, TCP, TLS and time to first byte; the biggest gap is the stage to investigate, and a large gap before the first byte points at the server.

How do you make sure you find out before customers do?

Synthetic checks from outside (DNS, TLS expiry, HTTP) and alerts on error rate and latency, so the page arrives before the complaint.

Common slips

  • Reading application logs before confirming the request even arrives.
  • Restarting things before capturing evidence.
A frequent follow-up to any DNS change: reported by candidates, not official.

"I changed a DNS record an hour ago and some users still see the old site. Why, and what do you do?"

A classic operational interview question that tests whether you understand caching, TTLs and the resolution chain.

Ask first

  • What exactly did you change, and what was the TTL on the old record? The old TTL decides the worst case: caches may serve the old answer for that long after your change.
  • Is it all users or some, and are they on different networks? Some users means different resolvers with different cache states, which points at caching rather than a broken change.

How to think about it

  1. Confirm the change is correct at the source.Ask the authoritative servers directly: dig @ns1.example-dns.com www.example.com. If they return the new value, your change is live and the problem is only caches.
  2. Explain why some users are fine and some are not.Every resolver cached the old record when it last asked. Those whose copy has expired have fetched the new value; the others will until their TTL runs out. There is no push or "propagation": the new value is available immediately, copies simply expire on their own clocks.
  3. Bound the time.Worst case is the old TTL (say 24 hours, 86,400 s) from the moment each resolver last fetched. Check with dig against a few public resolvers to see remaining TTLs.
  4. Look for other caches.Browser, operating system, application runtime (some caches DNS forever, like a long-lived JVM), a corporate proxy, and negative caching (a recent NXDOMAIN may be cached too).
  5. Prevent it next time.Lower the TTL (for example to 60 s) a day or two before a planned change, make the change, then raise the TTL again. For fast failover use health-checked DNS or a load balancer instead of waiting on TTLs.

How to say it

A model answer, about two minutes aloud

"The change is probably already correct at the authoritative servers, and I would verify that first by querying them directly with dig. What users see depends on resolver caches: each resolver keeps the old record until its TTL expires, so different users see the change at different times. It is not propagation in the sense of a push; every copy simply expires on its own schedule, at most one old TTL after it last fetched the record.

So I would check the old TTL to know the worst case, query a couple of public resolvers to see what they still hold, and consider other caches such as browsers, the operating system and long-running applications that cache DNS themselves. To speed it up there is not much to do except wait or flush resolvers I control.

To avoid it next time I lower the TTL a day before a planned change, make the switch, and raise it again afterwards. For failover that must be quick I would not rely on DNS TTLs at all."

Likely follow-ups

What is negative caching?

Resolvers also cache "this name does not exist" (NXDOMAIN) for a time set in the zone's SOA record, so a record you just created may stay invisible for a while to those who asked just before.

Why can't you put a CNAME at the root of a domain?

The root of a zone must hold SOA and NS records, and a CNAME cannot coexist with other records at the same name. Providers offer ALIAS or ANAME records that behave like a CNAME but are resolved by the DNS provider.

How does DNS-based load balancing work and what are its limits?

The name returns several addresses or different ones by location or health. Limits: clients and resolvers cache answers, so failover is bounded by TTL and some clients ignore it.

Common slips

  • Saying "DNS takes up to 48 hours to propagate" without knowing it depends on TTLs.
  • Not checking the authoritative server before blaming caches (or the other way round).
A common incident prompt: reported by candidates, not official.

"A site's certificate expired overnight and customers cannot reach it. How do you respond, and how do you prevent it?"

A real-incident style question. They want to see mitigation first, diagnosis with commands, and prevention.

Ask first

  • Is it every client or only some? Everyone seeing the same error points at the certificate itself. Some clients failing points at an incomplete chain or an old trust store.
  • Where is TLS terminated: load balancer, CDN or the application? That decides where the new certificate must be installed (and whether several places hold copies).

How to think about it

  1. Confirm the cause quickly.echo | openssl s_client -connect host:443 -servername host | openssl x509 -noout -dates shows notAfter in the past. Check every endpoint (some may have a different, older copy).
  2. Mitigate first.Issue and install a renewed certificate (with an ACME client such as certbot or the cloud provider's managed certificate), then reload the terminating service. Verify from outside with openssl s_client and with a browser.
  3. Do not disable verification as a workaround.Telling clients to ignore errors (curl -k) turns an outage into a security hole.
  4. Find why it was missed.Postmortem question: nobody owned renewal, the automation failed silently, or there was no monitoring for expiry.
  5. Prevent a repeat.Automate issuance and renewal (ACME, short-lived certificates), monitor days to expiry from outside with alerts at 30, 14 and 7 days, and keep an inventory of every certificate and where it lives.

How to say it

A model answer, about two minutes aloud

"First I would confirm it is expiry: connect with openssl s_client and read the notAfter date, and check every endpoint because a different load balancer or region may hold another copy. Then I would mitigate: obtain a renewed certificate, install it where TLS terminates, reload the service, and verify from the outside with openssl and a browser. I would not tell anyone to bypass verification.

Afterwards I would find out why nothing warned us. The fix is automation, using ACME or a managed certificate so renewal is hands-off, plus external monitoring that alerts at 30, 14 and 7 days to expiry. And I would keep a certificate inventory including internal services, since those are the ones that expire unnoticed."

Likely follow-ups

What is an incomplete chain and how do you detect it?

The server must send the intermediate certificates as well as its own; if it does not, some clients (without the intermediate cached) fail while browsers that cached it work. openssl s_client -showcerts shows what is sent.

What is SNI and why does it exist?

Server Name Indication: the client names the host in the ClientHello so a server with many sites on one IP knows which certificate to present, before any HTTP is sent.

What is certificate pinning and why is it risky?

The client accepts only a specific certificate or key. It blocks rogue CAs but breaks the app when you rotate certificates unless you plan the rotation carefully.

Common slips

  • "Just use -k" or turning off verification.
  • Renewing one server and forgetting others with their own copy.

8Remember thisRecap

The page in 6 lines

  • A request is four trips in a row: DNS, TCP, TLS, HTTP. Test them in that order.
  • DNS answers are remembered for the TTL, so a change reaches people at different times.
  • "Refused" is instant and means nobody is listening; a long hang means traffic is being dropped.
  • A certificate must match the name, be in date and chain to a trusted root, or TLS stops the connection.
  • An HTTP status code means the network worked: read it before blaming the road.
  • Distance multiplies every round trip, so move content closer and reuse connections.

Check yourself

A customer cannot load the site but you can. What is your first move?

Test from outside your own network, then walk the ladder: DNS, TCP, TLS, HTTP, one command each. The first trip that fails is the culprit.

What is the difference between "connection refused" and a timeout?

Refused is an instant reset: the machine answered but nothing listens on that port. A timeout is silence: packets are being dropped by a firewall or a bad route.

Why does a DNS change not reach everyone at once?

Resolvers remember each answer for its TTL. Lower the TTL before the change and keep the old address answering until the old TTL has passed.
