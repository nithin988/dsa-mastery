Chapter 3 of 14Night shift at ShopKart

The log has the answer

How to find one customer, one error or one slow host in a log of millions of lines, using four small tools: grep, awk, sort and uniq.

about 20 minutes4 steps4 real experiments3 interview questions

13:20 a.m., one customer in a million linesThe story

ShopKart's server writes every event to one file, app.log. By 3 a.m. it holds about 1.2 million lines. At 3:20 Amara from support forwards a message: a customer says checkout failed three times "around three o'clock". She wants to know what happened before she replies. She has ten minutes.

You open the file in an editor and it freezes. You try scrolling in less and give up after a minute. Nobody can read a million lines, and you do not need to. You need the dozen that mention this customer, and the pattern around them.

Four tools do almost all of this work: grep finds lines, awk picks columns and adds things up, sort and uniq count. By 3:29 you know all three failures were "db timeout" errors on one database host, db1, within a few minutes of each other. Not the customer's card. A real fault, and a clue for the chapters ahead.

2The idea: do not read the log, question itThe idea

A log is a stream of lines, one event per line. Instead of reading it, you filter it down to the lines that matter, pick the columns you need, and count what remains. Each step is one small command.

Commands on Linux read lines in and write lines out, so they join with pipes (|) like pieces of a pipeline. You build the answer in steps and watch the number of lines fall at each one: first the whole log, then only errors, then only one host, then a count. If a step surprises you, run the pipeline up to that step and look.

3How it works, step by stepHow it works

  1. Filter first with grep

    Each log line is one event. grep keeps only the lines that match a word or pattern, so a million lines shrink to the few you care about. Add -c to count them, -n to see line numbers, -v to keep everything except a match.

  2. Cut lines into columns with awk

    awk splits every line into columns on spaces: $1 is the first, $3 the third. It can test a column, keep the matches, and do sums while it reads. That turns a log into numbers.

  3. Count with sort, uniq and sort again

    To count how often each value appears, sort the values so equal ones sit together, count the neighbours with uniq -c, then sort the counts with sort -rn so the biggest is first. It is the most reused three-word recipe in operations.

  4. Save the recipe as a script

    When you type the same pipeline twice, put it in a file. A script can take the log name as an argument, print a usage message if you forget, and end with a proper exit code so cron or CI can tell whether it worked.

5How it breaks in productionFailure modes

A regular expression that backtracks

A badly written pattern can try so many ways to match that it uses all the CPU. This is a real outage cause, not a classroom worry. Fix: keep patterns simple, test them on large and odd input, and put time limits on matching.

Counting without sorting

uniq -c only counts lines that are next to each other. On unsorted input it gives several small counts for the same value and a wrong total. Fix: always sort before uniq.

xargs splits on spaces

A file called my notes.tmp becomes two names, my and notes.tmp, and the wrong thing gets processed or deleted. Fix: use find -print0 | xargs -0, which separates names with a zero byte instead.

The pattern is too narrow or too wide

grep error misses ERROR because matching is case sensitive, and grep timeout also matches unrelated lines. Fix: use -i for case, anchor with ^ or exact fields, and look at a few matches before trusting a count.

A pipeline that hides a failure

In a | b, the exit code is that of b only. If a fails, the script still looks fine: on the lab machine it printed 0 without pipefail and 1 with it. Fix: start scripts with set -euo pipefail.

The line is in another file

Logs rotate: yesterday's lines sit in app.log.1 or a compressed .gz file. Fix: search all the rotated files (zgrep reads compressed ones) and mind the time zone when matching times.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists from any company.

A very common Linux and scripting prompt: reported by candidates, not official.

Given a web server log, how would you find the top 5 most frequent client IPs?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5.

Explain each stage: extract the field, sort so duplicates are adjacent, count them, sort numerically descending, keep five.

Mention that for huge files sort spills to disk and that awk alone with an array can do it in one pass.

Likely follow-ups

• How would you do it with only awk?

• What if the log is 50 GB?

Common slips

  • Forgetting to sort before uniq -c.
  • Using sort without -n for the final ordering.
Often asked to check you know which tool to reach for: reported by candidates, not official.

What is the difference between `grep`, `sed` and `awk`? When do you choose each?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

grep filters lines by pattern.

sed edits streams: substitute, delete, print ranges.

awk works on fields with logic and variables: sums, group-by, conditions.

Rule of thumb: find with grep, change text with sed, compute with awk.

Likely follow-ups

• Can awk replace grep and sed? Should it?

Common slips

  • Reaching for awk or a script when one grep would do.
A frequent question about writing safe scripts: reported by candidates, not official.

What does `set -euo pipefail` do and why would you use it?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

-e: exit on the first failing command. -u: treat unset variables as errors. -o pipefail: a pipeline fails if any stage fails.

It turns silent mistakes into loud, early failures, protecting against things like rm -rf "$DIR/"* with an empty DIR.

Know the caveats: -e does not fire in if conditions or || lists, so it is a safety net not a design.

Likely follow-ups

• How do you handle a command that is allowed to fail?

• What does trap add?

Common slips

  • Claiming set -e makes scripts safe by itself.

8Remember thisRecap

The page in 6 lines

  • A log is one event per line, so filter, pick columns, then count.
  • grep keeps lines that match; -c counts, -n numbers them, -v inverts, -o prints only the match.
  • awk splits lines into columns ($1, $3) and can test, keep and total them while it reads.
  • sort | uniq -c | sort -rn counts values and puts the most common first; always sort before uniq.
  • Build pipelines step by step and check how many lines remain after each step.
  • Scripts should start with set -euo pipefail and exit with a code that says how they ended.

Check yourself

How do you find the top five most frequent values in a column?

awk '{print $N}' file | sort | uniq -c | sort -rn | head -5.

Why must you sort before uniq?

uniq only collapses lines that are next to each other; sorting puts equal lines side by side.

What does pipefail change?

Without it a pipeline's exit code is that of the last command only; with it, a failure in any step makes the whole pipeline fail.
