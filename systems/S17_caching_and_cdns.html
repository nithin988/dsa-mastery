Caching and CDNs

Caching is the cheapest way to make a system faster and the most common source of confusing bugs. This module uses a real Redis, a real memcached and real HTTP headers. You will measure what a cache saves, watch it serve stale data, make it fail with a stampede, fix it, run out of memory and see what is evicted, and learn to size, choose and explain a caching plan the way interviewers expect.

7 lessons2 labs2 animations7 interview questionsabout 9 to 11 hours

Why this matters

A real situation

Reading from memory takes microseconds; reading from a database over the network takes milliseconds; a request across an ocean takes hundreds of milliseconds. A cache keeps a copy of an answer closer to where it is needed, so most requests skip the expensive trip. A good cache can cut database load by 90 percent and response times by 10 times.

A cache is also a second copy of your data, and copies drift apart. Most caching incidents are one of a handful of things: stale data, a stampede when a hot key expires, a cache that is too small and thrashes, or a restart that sends the full load to a cold database. If you know these, you diagnose them quickly.

In interviews "add a cache" is the most overused phrase in system design. The strong answer says what is cached, where, with which pattern, how it is invalidated, how big it must be, and what happens when it fails.

After this module you can
  • Explain where caches live (browser, CDN, proxy, application, database) and measure the benefit of one with hit ratio and average latency.
  • Compare cache-aside, read-through, write-through, write-behind and refresh-ahead, and show staleness and invalidation in running code.
  • Explain eviction (LRU, LFU, TTL), configure a memory limit and see what a full cache does.
  • Reproduce and fix a stampede, cache penetration and understand hot keys and cold starts.
  • Compare Redis and memcached, use Redis data structures, and explain persistence, replication and sharding of a cache.
  • Set HTTP caching headers correctly (Cache-Control, ETag, 304, Vary) and explain how a CDN uses them, including versioned URLs and purging.
  • Size a cache with measured per-key overhead and the hit-ratio curve, and decide what should not be cached.
  • Answer caching interview questions with an approach, numbers and failure handling.

Why caching works, and where caches live

Must know
Situation

Your product page takes 400 ms because it runs six database queries. It is requested 5,000 times a second, and 95 percent of those requests ask for the same few thousand products. Computing the same answer thousands of times is the waste a cache removes.

You will learn
  • Why caches work at all (locality)
  • The levels of caching from browser to disk
  • Hit ratio and what it does to average latency
  • Your first real cache: Redis
Mental model

A cache is a small, fast store of answers you already computed or fetched, kept close to whoever asks, so that repeating the question does not repeat the work. It works because real access patterns are skewed: a small part of the data gets most of the requests (locality, the 80/20 effect). Keep that hot part in fast memory and most requests never reach the slow system.

Caches exist at every level: the browser, a CDN edge, a reverse proxy, an application cache such as Redis or memcached, the database's own buffer pool, and the CPU caches under all of it. A request stops at the first level that has the answer. The key number is the hit ratio (hits divided by hits plus misses). Average latency is hit_ratio x hit_time + (1 - hit_ratio) x miss_time, so with a 1 ms hit and a 50 ms miss, a 95 percent hit ratio gives about 3.5 ms, but 50 percent gives 25.5 ms. The last few percent of hit ratio are worth a great deal.

A cache is not free: it can serve stale data, it has a size limit, it has to be filled and kept consistent, and it is one more component that can fail. Every lesson in this module is about getting the benefit while controlling those costs.

Everyday analogy: Keeping the books you use every day on your desk instead of walking to the library each time. The desk is small, so you keep only what you use often, and you must remember to replace a book when a new edition comes out.

The picture
How it works, step by step
  1. A request arrives at the applicationIt needs some data: a user profile, a product page, the result of an expensive query.
  2. Look in the cache firstThe application asks the cache for the answer using a key (for example user:7). A cache lookup is a single in-memory operation: well under a millisecond.
  3. Hit: return it immediatelyIf the key is present and has not expired, that is a hit. The slow system is never touched.
  4. Miss: go to the source and remember the answerIf the key is absent (never stored, expired or evicted) that is a miss: the application reads the database, then stores the result in the cache with an expiry time, then returns it.
  5. The next requests are hitsUntil the entry expires, changes or is evicted, every repeat is served from memory. The first request pays, the following thousands are free.
  6. Measure the hit ratioHits and misses are counted by the cache itself. A falling hit ratio is an early warning: the working set grew, TTLs are too short, or someone changed the key format.

# A minimal Redis client (the Redis wire protocol is simple text), so the experiments need nothing but python3.
import socket
class R:
    def __init__(self, port=6391):
        self.s = socket.create_connection(('127.0.0.1', port)); self.f = self.s.makefile('rb')
    def cmd(self, *a):
        out = b'*%d\r\n' % len(a)
        for x in a:
            x = str(x).encode(); out += b'$%d\r\n%s\r\n' % (len(x), x)
        self.s.sendall(out); return self._read()
    def _read(self):
        line = self.f.readline().rstrip(b'\r\n'); t, val = line[:1], line[1:]
        if t == b'+': return val.decode()
        if t == b'-': raise Exception(val.decode())
        if t == b':': return int(val)
        if t == b'$':
            n = int(val)
            return None if n < 0 else self.f.read(n + 2)[:-2].decode()
        if t == b'*': return [self._read() for _ in range(int(val))]
def stat(r, name):
    return int([l for l in r.cmd('INFO').split('\r\n') if l.startswith(name + ':')][0].split(':')[1])
EOF

import sys, time
sys.path.insert(0, '.')
from rc import R, stat
r = R()
def slow_lookup(key):
    time.sleep(0.05)                       # pretend this is a database query that takes 50 ms
    return 'value-for-' + key
def cached_lookup(key):
    v = r.cmd('GET', key)
    if v is None:                          # miss: do the slow thing once, remember the answer
        v = slow_lookup(key)
        r.cmd('SET', key, v, 'EX', 60)
    return v

without = (time.perf_counter() - t) * 1000
t = time.perf_counter()
for _ in range(20): cached_lookup('item:1')

print('Redis counted: %d hits, %d miss, hit ratio %d%%' % (hits, misses, 100 * hits / (hits + misses)))

Interview in practice

"The product page is slow and the database is at 90 percent CPU. Would you add a cache, and what do you need to know first?"

The question: A realistic starting question. A weak answer says "yes, add Redis". A strong one asks what to measure, decides what to cache, and names the costs.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What exactly is slow, and what is the read to write ratio? A cache pays off for data that is read much more often than it changes.
  • How skewed are the requests? Do a few items get most of the traffic? Skew decides the hit ratio you can reach with a small cache.
  • How stale may the data be? Seconds of staleness for a product page are usually fine; for an account balance they are not.
  • Is the slowness really in repeated reads? Is it queries, missing indexes, or something else? Fix an obvious missing index first; caching a badly written query hides the problem.
2. Think it through (the reasoning, step by step)
  1. Measure before caching. Find the expensive, repeated reads: slow query log, request counts per key or per query. Cache what is both expensive and frequently repeated.
  2. Choose the level. Static content: CDN and browser. A rendered page that is the same for everyone: reverse proxy or CDN. Computed data and database results: an application cache such as Redis. Pick the level closest to the user that is still correct.
  3. Choose the pattern and the expiry. Cache-aside with a TTL fits most read-heavy data: simple, tolerant of cache failure. The TTL bounds how stale an answer can get.
  4. Estimate the benefit with the formula. If the page is 400 ms on a miss and 5 ms on a hit, a 90 percent hit ratio gives about 45 ms average; and the database sees one tenth of the reads. The skew tells you whether 90 percent is realistic.
  5. Name the costs and the failure behaviour. Staleness, memory, an extra system to run, and cold starts: what happens when the cache is empty or down. The database must survive a cold cache, or the cache must be warmed and protected (later lessons).
  6. Define how you will know it works. Track hit ratio, evictions, latency percentiles and database load before and after.
3. A strong answer, said out loud

"Before adding a cache I would measure: which queries are expensive and repeated, how skewed the traffic is, and how stale the data may be. If product data is read a hundred times for every write and a few products get most of the traffic, a cache is a good fit.

I would use cache-aside in an application cache like Redis: check the cache by product key, on a miss read the database and store the result with a TTL of a minute or so, which bounds staleness. Where the page is the same for everyone I would also let a CDN or reverse proxy cache it. With a 5 ms hit and a 400 ms miss, a 90 percent hit ratio gives an average around 45 ms and cuts database reads to a tenth.

The costs are stale data within the TTL, memory, one more component, and what happens on a cold or failed cache, so I would make sure the database can survive a cold start, monitor hit ratio and evictions, and invalidate or shorten the TTL for data that must be fresher."

4. Follow-ups you should expect
How do you decide the TTL?

From how stale the business can tolerate, and how expensive a miss is. Short TTLs mean fresher data but more misses; long TTLs mean the opposite. Often different data gets different TTLs.

What if the hit ratio is only 40 percent?

Find out why: the working set may be larger than the cache, the key may include something unique per request, or the TTL is too short. A low hit ratio can mean the cache costs more than it saves.

Where would you not use a cache?

Data that must always be exactly current, data that is rarely read twice, and as a patch for a missing index or an inefficient query.

Common slips
  • Adding a cache without measuring what is repeated and expensive.
  • Ignoring staleness and the cold-start problem.
  • Caching something with a unique key per request: the hit ratio is zero.
Quick check

Answer in your head first, then open it.

What does a cache rely on to be effective?

Skewed access patterns (locality): a small hot set gets most of the requests.

With a 1 ms hit, 50 ms miss and a 90 percent hit ratio, what is the average latency?

About 5.9 ms (0.9 x 1 + 0.1 x 50).

Name three levels where caching happens.

Browser, CDN edge, reverse proxy, application cache (Redis or memcached), the database's buffer pool.

Traps to avoid (3)
  • Caching to hide a slow query that an index would fix.
  • Treating the cache as a source of truth: it can be emptied or lost at any time.
  • Forgetting that a cold or failed cache sends the full load straight to the database.

Caching patterns: cache-aside, write-through, write-behind and friends

Must know
Situation

Reads are cached. Now someone updates the product price. How does the cache find out? Different patterns answer that question differently, and each trades speed, simplicity and consistency.

You will learn
  • Cache-aside, read-through, write-through, write-behind and refresh-ahead
  • How staleness arises and the invalidation rule that fixes most of it
  • Race conditions between a cache and a database
Mental model

Cache-aside (lazy loading): the application reads the cache, on a miss reads the database and fills the cache. The cache is just a store; the application owns the logic. Simple and robust: if the cache dies, the application still works (slowly). Read-through is the same idea with the cache layer itself loading from the database on a miss. For writes: write-through writes to the cache and the database together, so reads after a write see the new value, at the cost of write latency and caching data nobody may read. Write-behind (write-back) writes to the cache and saves to the database later in batches: fast writes, but data can be lost if the cache dies before it flushes. Refresh-ahead reloads hot entries shortly before they expire to avoid a slow miss.

With cache-aside the classic problem is staleness: the database changes and the cache still holds the old value until it expires. The usual cure is invalidate on write: after updating the database, delete the cache entry, so the next read reloads the fresh value. Deleting is safer than updating the cache, because two concurrent updates could otherwise leave an older value in the cache. Even so, a read that started before the write can store an old value after the delete (a small race), which is why every entry also gets a TTL as a safety net.

Everyday analogy: Cache-aside is checking the shelf first and fetching from the warehouse when it is bare. Write-through is updating the shelf label and the warehouse record at once. Write-behind is updating the shelf now and doing the paperwork at the end of the day: quicker, but a fire in between loses the paperwork.

How it works, step by step
  1. Reads with cache-asideGet from the cache; if missing, read the database, store the value with a TTL, return it. The cache only ever holds what someone asked for.
  2. Writes: update the database firstThe database is the source of truth, so it must be updated first and must succeed.
  3. Then invalidate the cache entryDelete the key (do not try to write the new value into the cache). The next read misses, reloads the new value and caches it.
  4. Or write throughUpdate the database and the cache together when you know the data will be read soon and you want reads to be consistent immediately. Both writes must succeed or fail together, or they diverge.
  5. Or write behindAcknowledge the write after storing it in the cache, and persist it asynchronously in batches. Use only where losing the last few writes is acceptable, or the cache itself is durable.
  6. Always keep a TTLEven with invalidation, bugs and races leave stale entries; a TTL guarantees they disappear eventually.

Interview in practice

"How do you keep a cache and a database consistent?"

The question: One of the most common caching questions. The honest answer is that you cannot make them perfectly consistent for free, so you choose how stale is acceptable and how to bound it.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How stale can this data be, and what happens if a user sees an old value? A profile picture can be minutes stale; a stock count at checkout cannot.
  • Read to write ratio, and how often is the same key written? Rarely-written data suits invalidation; constantly changing data may not suit caching at all.
  • Is there one writer path or many (several services update the same table)? Every writer must invalidate, which is easy to forget; a central write path is much safer.
2. Think it through (the reasoning, step by step)
  1. State the baseline. Cache-aside with a TTL and delete-on-write. The database is the source of truth; the cache is a disposable copy.
  2. Explain the order of operations. Write to the database, then delete the cache key. If you delete first, a concurrent read can reload the old value before the write lands and keep it for a whole TTL.
  3. Name the remaining race. A reader that missed before the write can still store its old value after your delete. This is rare and bounded by the TTL, which is why you always set one.
  4. Offer stronger options and their prices. Write-through gives fresh reads but ties writes to cache availability. Versioned keys (user:7:v12) avoid races. Event-driven invalidation publishes a change event that all caches consume (CDC), at the cost of infrastructure. For must-be-correct data, skip the cache or read from the primary database.
  5. Say what you monitor. Hit ratio, and sampled comparisons between cache and database to detect divergence.
3. A strong answer, said out loud

"I treat the database as the source of truth and the cache as a disposable copy. For reads I use cache-aside with a TTL. For writes I update the database first and then delete the cache key, so the next read reloads the fresh value. The order matters: if I deleted first, a concurrent read could reload the old value and keep it for the whole TTL.

There is still a small race, where a reader that missed before the write stores its old value after my delete, so every entry has a TTL that bounds staleness. If the business cannot tolerate that for some data, I would use write-through, versioned keys, or event-driven invalidation from a change stream, or I would not cache it and read from the primary instead. And I would monitor the hit ratio and compare samples of cache and database to catch divergence."

4. Follow-ups you should expect
Why delete rather than update the cache on a write?

Two concurrent writers can update the database in one order and the cache in the other, leaving the cache with the older value. Deleting lets the next read load whatever is currently in the database.

What is write-behind and when is it acceptable?

The cache acknowledges the write and the database is updated later in batches. It makes writes fast and cheap but can lose the last writes if the cache fails; it fits counters, metrics or view counts, not orders or payments.

What happens if the cache delete fails after the database write?

The cache keeps a stale value until the TTL. Retry the delete (from a queue if necessary), keep TTLs short for important data, and treat the TTL as the guaranteed bound.

Common slips
  • Updating the cache before the database.
  • Saying the cache and database are always consistent.
  • No TTL: one missed invalidation then lives forever.
Quick check

Answer in your head first, then open it.

What is the rule for keeping a cache-aside cache fresh when data changes?

Update the database first, then delete the cache entry, and keep a TTL as a safety net.

Why is write-behind dangerous?

The cache acknowledges writes before they reach the database, so data can be lost if the cache fails before flushing.

Why delete the cache key instead of overwriting it on a write?

Concurrent writers could leave an older value in the cache; deleting forces the next read to load the current database value.

Traps to avoid (3)
  • Invalidating before the database write completes: a concurrent read refills the cache with the old value.
  • Several services writing the same table, only one of which invalidates the cache.
  • No TTL on cached entries: any missed invalidation becomes permanent staleness.

Memory limits and eviction: what a full cache throws away

Must know
Situation

Memory is finite. After a week the cache is full. What does it do when a new key arrives: refuse, or delete something? And which something? The answer decides your hit ratio and, sometimes, your outage.

You will learn
  • Expiry versus eviction
  • LRU, LFU and random eviction
  • What Redis does at its memory limit, with real output
  • Sizing a cache
Mental model

Entries leave a cache for two reasons. Expiry removes an entry whose TTL ran out (it is stale by definition). Eviction removes a still-valid entry because memory is full. The eviction policy chooses the victim. LRU (least recently used) throws out what has not been touched for longest, on the bet that recent use predicts future use. LFU (least frequently used) throws out what is used least often, which protects steadily popular items from being pushed out by a one-time scan. Random is surprisingly acceptable and very cheap. noeviction refuses new writes with an error when memory is full: right for a database-like use of Redis, dangerous for a cache.

In Redis, maxmemory sets the limit and maxmemory-policy the behaviour (allkeys-lru, allkeys-lfu, volatile-lru which only evicts keys that have a TTL, noeviction...). Redis approximates LRU by sampling a few keys rather than tracking exact order, which keeps it fast. Sizing: a cache needs enough memory for the hot working set, not for all the data: with skewed traffic the first few percent of the data buy most of the hit ratio, then returns diminish. Remember per-key overhead: a 100-byte value costs noticeably more than 100 bytes in memory.

Everyday analogy: A desk with room for ten books. When an eleventh arrives you put one back: the one you have not touched for longest (LRU), or the one you use least overall (LFU). The rule decides whether a one-off reference book can push out your daily dictionary.

How it works, step by step
  1. Memory reaches the limitRedis counts bytes used against maxmemory. Below the limit nothing is evicted.
  2. A new write arrivesBefore storing it, Redis checks whether the new key would exceed the limit.
  3. The policy picks victimsallkeys-lru samples a handful of keys (default five) and removes the one used least recently, repeating until enough memory is free.

"Your Redis cache's hit ratio has dropped from 95 percent to 60 percent and evictions are climbing. What do you do?"

The question: A production-flavoured question. They are looking for a method: diagnose the cause from numbers, then choose the fix.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What changed around the time it dropped? A deploy changing key formats or TTLs, a new feature, a traffic spike, a bigger data set: correlation points at the cause.
  • What do memory, evicted_keys and expired_keys show? Rising evictions with memory at the limit means the working set no longer fits.
2. Think it through (the reasoning, step by step)
  1. Read the numbers first. INFO stats (hits, misses, evicted_keys, expired_keys) and INFO memory (used versus max). Evictions climbing with memory at the limit: capacity. No evictions but many misses: TTLs too short or keys not repeating.
  2. Separate the causes. (1) Working set grew: more distinct hot keys than fit. (2) A new access pattern, such as a scan or a crawler touching each key once, pushing hot keys out (cache pollution). (3) Key explosion: someone put a unique value (timestamp, request ID) in the key, so nothing is ever reused. (4) TTLs shortened. (5) A restart emptied the cache and it is simply cold.
  3. Choose the fix to match. Capacity: add memory or shard across nodes, and cache smaller values (compress, store only needed fields). Pollution: use LFU, or bypass the cache for scans. Key explosion: fix the key. TTL: restore. Cold start: warm the cache or protect the database.
  4. Check the policy. allkeys-lru or allkeys-lfu for a pure cache; volatile-* only if some keys must never be evicted; never noeviction for a cache.
  5. Protect the database meanwhile. A falling hit ratio sends extra load to it: rate limit, queue, or serve stale data if needed.
3. A strong answer, said out loud

"I would start with the numbers: the hit and miss counters, evictions and memory usage. If evictions are climbing and memory is at its limit, the working set no longer fits, either because the data grew or because something is polluting the cache, such as a job that reads every key once. If there are no evictions but lots of misses, I would suspect a key format change that makes keys unique, or TTLs that were shortened, or a restart that left the cache cold.

The fix follows the cause: add memory or shard the cache and store smaller values for capacity, switch to an LFU policy or bypass the cache for scans for pollution, fix the key or restore the TTL otherwise, and warm the cache after restarts. 4. Follow-ups you should expect
LRU versus LFU: when is each better?

LRU adapts quickly when popularity shifts but a one-off scan can flush it. LFU protects steadily popular items from scans but adapts slowly to new trends; Redis's LFU decays counters over time to soften that.

What is cache pollution?

Data that is read once and never again (for example a full table export) taking space and pushing out hot entries. Avoid by bypassing the cache for such reads or using admission policies.

How would you decide how much memory the cache needs?

Measure the hit ratio at different sizes (or use access logs to simulate), look for the knee of the curve where more memory gives little more hit ratio, and add headroom for key overhead and growth.

Common slips
  • Using noeviction for a cache.
  • Adding memory without checking why the hit ratio fell.
  • Forgetting per-key memory overhead when sizing.
Quick check

Answer in your head first, then open it.

What is the difference between expiry and eviction?

Expiry removes an entry whose TTL has run out; eviction removes a still-valid entry because memory is full.

What does noeviction do when memory is full?

It refuses new writes with an error and keeps existing data.

A scan touches many keys once; LRU would treat them as recent and evict hot keys, while LFU keeps frequently used keys.

The hard problems: stampedes, penetration, hot keys, cold starts

Must know
Situation

The cache works well for weeks. Then a popular key expires and the database collapses; or someone asks for a million product IDs that do not exist; or one celebrity key melts a single cache node. Caches fail in specific, predictable ways.

You will learn
  • Cache stampede (thundering herd) and its fixes
  • Cache penetration and negative caching
  • Hot keys and cold starts
Mental model

Stampede (thundering herd): a very popular entry expires; for the next few hundred milliseconds every request misses and every request recomputes the same expensive answer, so the database receives a thousand identical queries at once. Fixes: let one request rebuild while the others wait or serve the old value (a lock with SET key NX PX, or request coalescing), add jitter to TTLs so keys do not all expire together, and refresh ahead of expiry for hot keys.

Penetration: requests for keys that do not exist anywhere (typos, scanners, attackers) always miss the cache and always hit the database. Fix with negative caching (store "not found" for a short time) and, for floods, a Bloom filter or input validation in front. Hot keys: one key receives so much traffic that the single cache node holding it is overloaded even though the cluster is idle; replicate the hot key, add a short-lived local cache in each app server, or split it into several keys. Cold start: an empty cache (after a restart or deploy) sends full load to the database; warm it, restart nodes gradually, and protect the database with limits.

Everyday analogy: A bakery whose popular loaf sells out at exactly 8:00: a hundred customers ask at once and the baker is overwhelmed. Better to have one person start the new batch while the others wait or take yesterday's loaf, and to stagger the sell-by times.

The picture
How it works, step by step
  1. A hot entry expiresAll servers see the miss within the same few milliseconds because they were all hitting the same key.
  2. Each one recomputesWithout coordination, every request runs the expensive query: the database load jumps by the number of waiting requests.
  3. Coordinate with a lockThe first request sets a lock key with SET key NX PX; Redis guarantees only one caller wins. The winner rebuilds the entry and releases the lock.
  4. The others wait briefly or serve staleThey poll the cache for a few tens of milliseconds, or return the previous value kept alongside (stale-while-revalidate).
  5. Negative caching for the absentIf the database also has nothing, store a short-lived "none" marker so repeated lookups stop reaching the database.
  6. Spread the load in timeAdd random jitter to TTLs (for example 300 plus or minus 30 seconds) so entries written together do not expire together.

. ~/cache/rig.sh; redisup; cd ~/cache; cat > stampede.py <<'EOF'
import sys, threading, time
sys.path.insert(0, '.')
from rc import R
calls = [0]; guard = threading.Lock()
def expensive():
    with guard: calls[0] += 1
    time.sleep(0.3)                                  # an expensive query: 300 ms
    return 'page'
def naive(r):
    if r.cmd('GET', 'page') is None:
        r.cmd('SET', 'page', expensive(), 'EX', 60)
def guarded(r):
    if r.cmd('GET', 'page') is not None: return
    if r.cmd('SET', 'page:lock', '1', 'NX', 'PX', 5000):         # only ONE caller wins the lock
        r.cmd('SET', 'page', expensive(), 'EX', 60); r.cmd('DEL', 'page:lock')
    else:                                                        # everybody else waits for the winner
        for _ in range(100):
            time.sleep(0.02)
            if r.cmd('GET', 'page') is not None: return
def run(fn):
    R().cmd('FLUSHALL'); calls[0] = 0
    ts = [threading.Thread(target=fn, args=(R(),)) for _ in range(40)]
    t = time.perf_counter(); [x.start() for x in ts]; [x.join() for x in ts]
    return calls[0], (time.perf_counter() - t) * 1000
for name, fn in (('no protection', naive), ('with a lock', guarded)):
    n, ms = run(fn)
    print('%-14s 40 simultaneous requests -> %2d expensive database calls, finished in %4.0f ms' % (name, n, ms))
EOF

"A stampede is what happens when a very popular cache entry expires or is evicted: many concurrent requests all miss at once and each recomputes the same value from the database, so the database gets a burst of identical expensive queries just when traffic is highest, and may slow down or fail.

To prevent it I would make only one request rebuild the entry. 4. Follow-ups you should expect
What is stale-while-revalidate?

Serving the old value past its expiry while a background request fetches a new one: users never wait for a rebuild, at the cost of slightly older data.

What if the lock holder crashes?

The lock has an expiry (PX), so after that time another request can take it; choose it longer than a normal rebuild and shorter than your tolerance for a stall.

How does a Bloom filter help penetration?

It answers "definitely not present" cheaply for IDs that cannot exist, so invalid lookups are rejected before they reach the cache or the database; it may say "maybe present" wrongly but never the reverse.

Common slips
  • Only describing the problem without a concrete fix.
  • A lock without an expiry: one crash blocks the key forever.
  • Forgetting cold starts and missing keys, which are cousins of the same problem.

It sets the key only if it does not exist, with a 5 second expiry: exactly one caller wins, so it works as a self-expiring lock.

What is negative caching?

Caching the fact that something does not exist, for a short time, so repeated lookups of missing keys stop hitting the database.

So entries created together do not all expire together, which would send a burst of misses to the database.

  • A lock without an expiry: if the holder crashes the key is stuck.
  • A long negative-cache TTL: a record created a moment later stays invisible.
  • Fixing stampedes only for one key: after a restart every key is a stampede, so protect the database as a whole.

Redis, memcached and distributed caches

Must know
Situation

One cache server holds a few gigabytes and handles maybe a hundred thousand operations a second. Your data and traffic are bigger. What is the difference between Redis and memcached, and how do you spread a cache over many machines?

You will learn
  • What Redis offers beyond a key-value map
  • Memcached: the simplest possible cache
  • Persistence and replication in Redis
  • Distributing a cache: client-side sharding and consistent hashing
Mental model

memcached is a plain, very fast, multi-threaded in-memory key-value cache: strings with a TTL, LRU eviction, no persistence, no data structures. Redis is an in-memory data structure server: strings, lists, hashes, sets, sorted sets (leaderboards), counters, streams, pub/sub, atomic operations and scripts, optional persistence (RDB snapshots and an append-only file) and replication. The extra power is why Redis is also used for queues, rate limiters, sessions and leaderboards, and why it needs more care: with persistence and rich types it can be a database, with the responsibilities of one. Redis executes commands on one thread, so each command is atomic.

To go beyond one machine you shard: split the keys over several nodes. The simplest way is client-side sharding: the client hashes the key and picks a node; with consistent hashing adding or removing a node moves only about 1/N of the keys instead of almost all (as shown in the load balancing module). Redis Cluster does this server-side with 16,384 hash slots spread across nodes, plus replicas for failover. Replication gives read capacity and survival of a node loss, but replicas can lag, so a read from a replica may be slightly stale. Treat a cache node's death as normal: the cluster loses that share of the data and the database absorbs the misses.

Everyday analogy: memcached is a coat-check counter: hand over a coat, get a ticket, nothing more. Redis is a whole cloakroom attendant who also sorts hats, keeps a running tally, and can write the log to a ledger.

How it works, step by step
  1. Pick by what you storePlain cached blobs with TTLs and maximum simplicity: memcached or Redis. Anything with structure or atomicity (counters, queues, sorted sets, locks): Redis.
  2. Persistence is optional, and a trade-offRDB takes periodic snapshots (fast restart, may lose the last minutes); AOF logs every write (less loss, more disk work). A pure cache usually needs neither.
  3. Replicate for survival and read capacityA replica copies the primary's data. If the primary dies, a replica is promoted. Replication is asynchronous, so a promoted replica may miss the latest writes.
  4. Shard for size and write throughputHash each key to a node. Consistent hashing or hash slots limit data movement when nodes join or leave.
  5. Plan for lossWhen a node dies its keys miss until reloaded; the database must absorb that. Avoid putting everything on a few huge nodes: lose one and a large share of the cache goes cold.

"Redis or memcached? And how would you design a distributed cache for a service with 50,000 requests per second?"

The question: Two questions in one. First a comparison, then a design with numbers.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What will be stored: plain values, or structures and counters? How large, how many keys? Sizes and structure decide the product and the node count.
  • What happens if a cache node is lost? If the database cannot take the misses, you need replicas and gradual warm-up.
2. Think it through (the reasoning, step by step)
  1. Compare briefly. memcached: simplest, multi-threaded, pure LRU cache, no persistence or types. Redis: data structures, atomic operations, persistence and replication, single-threaded per instance. For a plain read cache either works; Redis is the default choice because of flexibility.
  2. Estimate load. 50,000 requests per second with a 90 percent hit ratio means 45,000 cache reads per second and 5,000 database reads per second. One Redis node can do on the order of 100,000 simple operations a second, so one node is enough for throughput; memory and availability decide the rest.
  3. Estimate memory. Hot set of 20 million entries at 1 KB with about 100 bytes of overhead is about 22 GB. That fits on a large node but is risky as a single failure domain: shard across several nodes, for example four of 8 GB each with replicas.
  4. Place the data. Consistent hashing or hash slots (Redis Cluster) over the nodes so that adding capacity moves only a fraction of the keys.
  5. Handle failure. Each shard has a replica for failover. Losing a shard sends about 1/N of reads to the database: size the database for that, warm the replica, and protect with rate limits.
  6. Handle hot keys and stampedes. Local in-process caches for the hottest keys, locks for rebuilds, jittered TTLs.
3. A strong answer, said out loud

"For a plain read cache either would work, but I would choose Redis because it also gives atomic operations, structures and optional persistence and replication; memcached is simpler and multi-threaded and fine if all I need is key-value with LRU.

With 50,000 requests per second and a 90 percent hit ratio, the cache serves 45,000 reads per second and the database 5,000. One node can handle that throughput, so I size for memory and failure: say 20 million hot entries at about 1 KB plus overhead is roughly 22 GB, so I would shard over four or more nodes using Redis Cluster hash slots or client-side consistent hashing, each with a replica. Losing one shard means about a quarter of reads fall through to the database, so the database must be able to absorb that, or I add more, smaller shards. For hot keys I would add a small local cache in each application server, and protect rebuilds with locks and jittered TTLs."

4. Follow-ups you should expect
How does Redis Cluster distribute keys?

It divides keys into 16,384 hash slots (CRC16(key) mod 16384) and assigns ranges of slots to nodes; moving a slot between nodes rebalances the data. Clients learn the map and talk to the right node.

Why is Redis fast with one thread?

Everything is in memory, commands are simple and short, there are no locks to contend for, and an event loop handles many connections; the cost is that one slow command (for example KEYS * on a big data set) blocks everyone.

Should you use Redis as your primary database?

It can be, with persistence and replication configured, if the data fits in memory and you accept its durability trade-offs. For a pure cache, treat it as disposable.

Common slips
  • Choosing Redis for everything without saying why.
  • Sizing only by throughput and forgetting memory and failure domains.
  • Running slow commands like KEYS * in production.
Quick check

Only about 1/N of the keys move to the new node; with plain modulo hashing almost every key would change node and the cache would go cold.

What happens to reads when one of four cache shards dies?

About a quarter of the keys miss and fall through to the database until they are reloaded or a replica takes over.

Traps to avoid (3)
  • Using KEYS * or other O(N) commands in production: Redis is single-threaded, so everything waits.
  • Persistence settings left at defaults without checking what they actually guarantee.
  • Treating a replica as always current: asynchronous replication can lag.

HTTP caching and CDNs: caching at the edge of the internet

Must know
Situation

Your server is in Frankfurt and your users are in Singapore. Every image and script crosses the planet. Meanwhile your server answers the same request for the same logo millions of times. Caching in HTTP and at a CDN solves both.

You will learn
  • Cache-Control, ETag, Last-Modified and 304
  • Fresh versus stale, and revalidation
  • Shared versus private caches, Vary
  • Versioned URLs and CDN purging
Mental model

HTTP has caching built in, controlled by response headers. Cache-Control: max-age=N says the response is fresh for N seconds: caches serve it without asking. public allows shared caches (CDNs, proxies) to keep it, private only the browser, no-store forbids storing, no-cache allows storing but demands revalidation each time. When a stored response is stale, the cache revalidates: it sends If-None-Match: <ETag> (or If-Modified-Since), and if nothing changed the origin answers 304 Not Modified with no body, so only a few bytes travel. Vary: Accept-Encoding tells caches that the response differs by that request header, so they must store a variant per value.

A CDN is a network of shared cache servers (edges) near users. The first request near an edge is a miss and goes to the origin; later ones are hits served close to the user, cutting latency and origin load. The hard part is change: you cannot recall copies in browsers. The standard answer is versioned (fingerprinted) URLs: app.7f3a9c.js can be cached for a year with immutable because a new build gets a new name; only the HTML page that references it must stay short-lived. For things that must change now, CDNs offer purge/invalidation APIs, used sparingly.

Everyday analogy: Local branch libraries: a popular book is stocked at every branch (edge), so most readers never travel to the central archive (origin). A new edition gets a new title (versioned URL), so nobody can accidentally keep reading the old one.

The picture
How it works, step by step
  1. First request: nothing is cachedThe browser asks the CDN edge; the edge misses and asks the origin; the origin answers with the content and caching headers.
  2. The response travels back, leaving copiesThe edge stores it (if public and allowed) and the browser stores it. Both now know how long it is fresh.
  3. Fresh: served without askingWithin max-age the browser reuses its copy with no network at all; other users near the same edge are served by the edge without touching the origin.
  4. Stale: revalidateAfter expiry the cache sends a conditional request with the ETag. If unchanged, a 304 renews the copy for free; if changed, the full new response arrives.
  5. Change safely with new namesDeploy app.8b21d4.js instead of editing app.7f3a9c.js; update the short-lived HTML to point at it. No purge needed.
  6. Purge only when you mustFor urgent fixes use the CDN's purge API for specific paths or tags; purging everything sends the full load to the origin.

"How would you design caching for a news website with global readers and breaking news that must update within a minute?"

The question: They want to see you combine CDN, HTTP headers, application caches and invalidation, and handle the "breaking news" exception without caching everything for an hour.

1. Clarify first (what to ask, and why it matters)

  • How fast must an edit appear, and is it acceptable for different users to see different versions briefly? A minute of staleness is the budget here.
  • Which parts are personalised (login, recommendations)? Personalised parts must not be cached in shared caches.
2. Think it through (the reasoning, step by step)
  1. Split the page by how it changes. Static assets (CSS, JS, images): fingerprinted URLs, max-age of a year, immutable. Article HTML: shared and short-lived. Personalised fragments: loaded separately and not cached publicly (private or no-store).

  5. Protect the origin. Origin shielding (a regional tier between the edges and the origin) so a purge or cold edges do not send every edge's request to the origin; request collapsing so simultaneous misses become one fetch.

3. A strong answer, said out loud

"I would split the page by how it changes. Static assets get fingerprinted file names and a year of caching as immutable. Personalised parts, like the logged-in user's name or recommendations, are loaded separately with private or no-store so they never enter a shared cache.

4. Follow-ups you should expect
What is the difference between max-age and s-maxage?

max-age applies to every cache including the browser; s-maxage applies only to shared caches such as CDNs and overrides max-age for them, so you can keep browsers short and the CDN longer or the reverse.

What does no-cache mean versus no-store?

no-cache lets caches store the response but requires revalidation before each reuse; no-store forbids storing it at all (use for sensitive data).

How can a CDN cache an API response that varies by user?

Do not, unless the cache key includes the identifying value (careful: low hit ratio and privacy risk). Cache the shared parts, or use short-lived signed URLs for per-user content.

  • Putting one long TTL on HTML and being unable to ship a fix.
  • Caching personalised responses in a shared cache: one user sees another's data.
  • Purging the whole CDN as a routine action.

Sizing, choosing what to cache, and proving it works

Must know
Situation

You know the mechanisms. The final skill is applying them to a real system: what to cache, where, how much memory, how to measure, and how to explain the whole plan.

You will learn
  • The measured cost of a key in Redis
  • How hit ratio grows with cache size (diminishing returns)
  • A decision guide: what to cache where
  • Measuring the effect
Mental model

Sizing a cache has three inputs: the number of hot keys, the size of each value and the per-key overhead of the cache. Overhead is real: Redis spends roughly 50 to 100 bytes on bookkeeping for every key on top of the key name and the value, so ten million small keys can cost far more memory than their raw size. The hit ratio grows quickly at first and then flattens: with skewed traffic caching the hottest 5 percent of keys may give a 60 percent hit ratio, 20 percent gives 80 percent, and getting from 95 to 99 percent can cost many times more memory than getting from 0 to 95.

Choosing what to cache: cache what is expensive to compute or fetch, read much more often than it changes, and identical for many requests. Do not cache data that must always be exactly current, data that is rarely read twice, or unique-per-request results. Prove the effect with numbers: database queries per second, p50 and p99 latency, hit ratio and evictions, before and after. A cache you cannot measure is a guess.

Everyday analogy: Stocking a corner shop: you cannot hold every product, so you stock what sells fast and spoils slowly, make room by clearing what nobody buys, and count sales to see whether the shelf space is paying for itself.

How it works, step by step
  1. Find the candidatesProfile reads: which queries or calls are slow and repeated? Rank by (frequency x cost).
  2. Check each against the rulesRead-heavy? Tolerates the staleness you can bound? Same answer for many requests? If not, skip or cache a shared part only.
  3. Pick the level and the patternCDN or proxy for shared pages, application cache for computed data, cache-aside with TTL and delete-on-write by default.
  4. Size it with real overheadHot keys x (value + key name + overhead), plus headroom; measure per-key overhead on your own data.
  5. Protect the databaseLocks and jitter for stampedes, negative caching for missing keys, rate limits as a backstop, a plan for cold starts.
  6. Measure and iterateCompare database load and latency percentiles before and after; watch hit ratio and evictions continuously.

import random

reqs = rng.choices(range(N), weights, k=200000)

    c, hits = OrderedDict(), 0

The on-call engineer pastes a cache's INFO output: slow pages, a busy database. Before anyone restarts anything, work out the hit ratio, how full the memory is, whether keys are being evicted and how much the cache is protecting the database.

Interview corner

Caching answers are judged on specifics: what is cached, where, how it is kept correct, how big it is and what happens when it fails. Use the pattern: measure, choose the level and pattern, size it, protect the database, plan failure, verify. The worked scenarios in each lesson are the models to practise with.

Add caching to a slow product page. Walk me through it.
Shape of a strong answer
  • Measure first: slow queries, repeat rate, skew across products.
  • Split by volatility: static assets on a CDN with fingerprinted URLs; assembled product data in Redis with cache-aside, TTL and delete-on-write; stock at checkout never cached; personalisation separate and private.
  • Protect the database: jittered TTLs, a lock for rebuilds, negative caching, rate limits as a backstop.
  • Size from hot set times measured per-key memory; verify with before and after database load, p50 and p99, hit ratio and evictions.
Follow-ups to expect
  • How do you know prices are not stale?
  • What if the page is slow even on a hit?
Common mistakes
  • Starting with Redis before measuring.
  • Caching data that must be exact.

Company angle: Reported by candidates as a common follow-up after any read-heavy design at large companies; not official.

Explain cache-aside, write-through and write-behind and when you would use each.
Shape of a strong answer
  • Cache-aside: the application reads the cache, on a miss reads the database and fills the cache; writes update the database and delete the entry. Default for read-heavy data; tolerates cache loss.
  • Write-through: writes go to cache and database together; reads are always fresh but writes are slower and cache fills with unread data.
  • Write-behind: write to cache and flush later; very fast writes, but a crash can lose data: only for data you can afford to lose or rebuild.
Follow-ups to expect
  • Why delete rather than update on write?
  • What race can cache-aside have?
Common mistakes
  • Naming patterns without trade-offs.
What is a cache stampede and how do you prevent it?
Shape of a strong answer
  • A hot key expires and many concurrent requests all miss and recompute the same value, hammering the database.
  • Fix: let one request rebuild (a lock with SET NX PX, or request coalescing), serve stale while revalidating, jitter TTLs, refresh hot keys ahead of expiry.
  • Related: cold start after restart, penetration by missing keys, hot keys on one node.
Follow-ups to expect
  • What if the lock holder crashes?
  • How do you test it?
Common mistakes
  • Only describing the problem.
How do you keep a cache consistent with the database?
Shape of a strong answer
  • You cannot make it perfectly consistent cheaply, so you bound staleness: TTLs as a safety net, delete on write, and for strict needs read from the primary.
  • On update, delete (not set) the key after the database commit; accept a small race window; for stronger needs publish change events that invalidate caches.
  • Decide per data type how stale is acceptable; never cache values that must be exact.
Follow-ups to expect
  • What if the delete fails?
  • How do you detect divergence?
Common mistakes
  • Promising strong consistency with a cache.
Redis or memcached? How would you scale a cache beyond one node?
Shape of a strong answer
  • Memcached: simple multi-threaded LRU cache. Redis: structures, atomic operations, persistence and replication; the default choice when you may need more than key-value.
  • Shard with consistent hashing or Redis Cluster hash slots; replicate each shard for failover; accept that losing a shard sends about 1/N of reads to the database.
  • Size for memory and failure domains, not only throughput.
Follow-ups to expect
  • How does Redis Cluster place keys?
  • What about hot keys?
Common mistakes
  • Sizing only by operations per second.
How do CDNs and HTTP caching work, and how do you update content safely?
Shape of a strong answer
  • Cache-Control sets freshness; ETag and If-None-Match allow cheap revalidation (304); Vary splits variants; CDN edges serve copies near users and shield the origin.
  • Fingerprinted file names with a year of caching mean updates need no purge; HTML stays short-lived with stale-while-revalidate.
  • Purge by URL or tag for urgent changes; use an origin shield and request collapsing so purges do not flood the origin.
Follow-ups to expect
  • max-age versus s-maxage?
  • How do you cache personalised pages?
Common mistakes
  • A long TTL on unversioned URLs.
  • Caching personal data in a shared cache.

Company angle: Google-style: candidates commonly report latency and global-distribution follow-ups here; reported by candidates, not official.

The hit ratio dropped from 95 percent to 60 percent overnight. What do you check?
Shape of a strong answer
  • Memory and evictions first (INFO): a full cache evicts hot keys; then recent deploys that changed key names or TTLs, a traffic shift to new content, a restart that emptied the cache, and a policy change.
  • Compare misses by key pattern; look for a new feature creating unique keys.
  • Fix by sizing, shortening TTLs of low-value data or fixing the key design; protect the database meanwhile.
Follow-ups to expect
  • Which metric would have warned you?
  • What is a bad cache key?
Common mistakes
  • Restarting the cache, which makes it worse.

Company angle: Amazon-style: expect "how would you have detected this before customers noticed?"; reported by candidates, not official.

Self-test

Answer in your head first, then open the question.

What is a cache hit ratio?

Hits divided by hits plus misses.

Why does a 95 percent hit ratio beat a 90 percent one by so much?

Misses fall from 10 percent to 5 percent: the database sees half the load and average latency drops sharply.

What does cache-aside do on a read miss?

Reads the database, stores the result in the cache and returns it.

Why delete the cache entry on write instead of updating it?

Avoids racing writers leaving an old value in the cache; the next read refills it.

What is write-behind's main risk?

Data in the cache but not yet flushed can be lost on a crash.

What does LRU evict?

The least recently used entry.

What happens to writes when Redis uses noeviction and is full?

They are rejected with an out-of-memory error.

What is a cache stampede?

Many concurrent misses on a just-expired hot key all recompute the value and overload the database.

What does SET key v NX PX 5000 give you?

A self-expiring lock: only one caller sets it.

What is negative caching?

Caching that something does not exist, for a short time.

Name two Redis capabilities beyond key-value strings.

Lists, hashes, sets, sorted sets, atomic counters, persistence, replication, pub/sub.

What does a 304 response mean?

Not modified: the client's copy is valid; no body is sent.

Why use fingerprinted file names?

So files can be cached for a year safely; a change gets a new name.

Which data should you not cache?

Data that must be exactly current, such as balances or checkout stock, and per-request unique results.
