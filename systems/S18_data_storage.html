Relational databases: SQL, indexes and transactions

Almost every system keeps its most important data in a relational database, and most production incidents involve one. This module runs a real PostgreSQL under your own user. You will load half a million rows, make a query slow and fast with an index, reproduce a lost update and a deadlock, kill the server and watch it recover from its log, measure bloat, count queries, and learn to answer database questions in interviews with reasoning, not slogans.

6 lessons2 labs0 animations7 interview questionsabout 9 to 11 hours

Why this matters

A real situation

The database is where correctness lives: money, orders, bookings, accounts. It is also usually the hardest component to scale, so every other part of a design (caches, queues, replicas) exists partly to protect it. Understanding what it guarantees, and what it quietly does not, is the foundation for every later module.

Most database problems are not exotic: a missing index, a transaction held open, a read-modify-write race, an N+1 query, too many connections. Engineers who can read a query plan and ask the database what it is doing fix these in minutes instead of days.

In interviews a database appears in nearly every design. The weak answer says "use a SQL database". The strong answer says what the schema is, which indexes the queries need, what isolation the invariants require, how connections are managed, and where one machine stops being enough.

After this module you can
  • Explain tables, keys, constraints, transactions and ACID with a concrete example, and run them on a real database.
  • Read EXPLAIN and EXPLAIN ANALYZE, add the right index (including composite order) and state what it costs.
  • Reproduce and fix lost updates, understand isolation levels, row locks and deadlocks, and book the last seat safely.
  • Explain MVCC, the write-ahead log, crash recovery, bloat and vacuum.
  • Design a schema: normalise first, denormalise deliberately, and avoid N+1 queries and deep offset pagination.
  • Explain connections, pooling, pg_stat_activity, locks and timeouts, and diagnose a hung production database.
  • Answer relational database interview questions with an approach and numbers.

Why a database: tables, SQL and the ACID guarantees

Must know
Situation

Your orders live in a pile of files. Two processes write at once and corrupt a file; a crash halfway through a payment loses money; finding "all paid orders from Germany last week" means reading everything. A database solves exactly these problems, and almost every system design includes one.

You will learn
  • Tables, rows, keys and relationships
  • What a transaction is, and what ACID promises
  • Your own real PostgreSQL, running in a minute
  • Constraints: the database refusing bad data
Mental model

A relational database stores data in tables of rows and columns. Each row has a primary key that identifies it; a foreign key in one table refers to a key in another (an order refers to its customer). You describe what you want in SQL (select, insert, update, delete, join) and the database decides how to get it, including which indexes to use. The database also enforces constraints (not null, unique, foreign key, check), so a bug in one application cannot silently store nonsense.

A transaction groups several statements into one unit. ACID names what the database promises: Atomicity (all of the statements take effect, or none do), Consistency (constraints hold before and after), Isolation (concurrent transactions do not see each other's half-finished work, to a degree you choose) and Durability (once committed, the data survives a crash, because it is written to a log on disk first). Almost every design question about money, bookings or inventory leans on these four words.

Everyday analogy: A bank's back office with rules: every transfer is written in a ledger, a transfer is either fully recorded or not at all, two clerks never see each other's half-written entry, and an entry stays even if the lights go out. The database is that office, run by a very fast clerk.

The picture
How it works, step by step
  1. Design tables around thingsCustomers and orders are separate tables; each order stores only the customer's id, not a copy of the customer.
  2. Declare the rulesPrimary keys, not null, and a foreign key from orders to customers: the database now rejects an order for a customer that does not exist.
  3. Ask questions in SQLA join combines rows from several tables; group by aggregates; where filters. You never say which loop to run.
  4. Group changes into a transactionbegin; ... commit; makes several statements succeed or fail together; rollback undoes them.
  5. The database logs before it changesCommitted work is written to a write-ahead log first, so a crash cannot lose it (the next lessons show this).

Atomicity and constraints, for real 
. ~/pg/rig.sh; pgup
q -c "create table accounts(id int primary key, owner text, balance int check (balance >= 0)); insert into accounts values (1,'ana',100),(2,'ben',20);"
echo "--- a transfer that fails halfway, inside a transaction:"
q -c "begin; update accounts set balance = balance - 150 where id = 1; update accounts set balance = balance + 150 where id = 2; commit;" 2>&1 | head -3
echo "--- balances afterwards (nothing moved):"
q -At -c "select owner, balance from accounts order by id"
echo "--- a valid transfer:"
q -c "begin; update accounts set balance = balance - 30 where id = 1; update accounts set balance = balance + 30 where id = 2; commit;"
q -At -c "select owner, balance from accounts order by id"
echo "--- an order for a customer that does not exist:"
q -c "insert into orders(customer_id, status, amount, created_at) values (999999, 'new', 10, now())" 2>&1 | head -2
pgdown

Atomicity and constraints in action. The first transfer tries to move 150 from an account that holds 100: the check (balance >= 0) constraint rejects the first update, the transaction is aborted, and the second update never takes effect: no money moved. The valid transfer commits both updates together. The last statement tries to insert an order for a customer that does not exist, and the foreign key refuses it. The database protected the data even though the application did nothing special.

Interview in practice

"Explain ACID with an example. Why does it matter?"

The question: A warm-up that opens many database discussions. They want precise definitions tied to a concrete example, not four memorised words.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • Is it okay if I use a bank transfer? Yes: it is the classic example because partial failure and concurrency both matter.
2. Think it through (the reasoning, step by step)
  1. Define each letter with the transfer. Atomicity: debit and credit both happen or neither. Consistency: constraints (no negative balance, totals preserved) hold after commit. Isolation: another transaction never sees the money gone from one account and not yet in the other. Durability: after the commit is acknowledged, a crash does not undo it.
  2. Say how it is implemented, briefly. Atomicity and durability come from a write-ahead log: changes are recorded in the log and flushed to disk at commit; recovery replays or undoes. Isolation comes from locks or multi-version concurrency control. Consistency comes from constraints and the application's own rules.
  3. Say why it matters for design. Without transactions every failure window needs custom repair code. With them, one commit is the point of no return. When data is spread across several databases you lose this for free, which is why distributed transactions, sagas and idempotency exist later in the course.
  4. Add the honest caveat. Isolation has levels: the default in most systems is weaker than "serializable", so you must know which anomalies remain (the next lessons demonstrate them).
3. A strong answer, said out loud

"ACID describes what a transaction guarantees. Take a transfer of 30 from Ana to Ben. Atomicity: the debit and the credit happen together or not at all, so a crash between them cannot lose money. Consistency: the rules, such as no negative balance, hold after the transaction. Isolation: another transaction never sees the money missing from Ana and not yet in Ben. Durability: once the commit is acknowledged, a crash will not undo it, because the change is in the write-ahead log on disk.

It matters because it moves failure handling into the database: one commit is the point of no return. Two caveats: isolation comes in levels and the common default allows some anomalies, and once data lives in several databases you no longer get this for free, which is where sagas and idempotency come in."

4. Follow-ups you should expect
How does a database achieve durability?

It appends the change to a write-ahead log and flushes the log to disk before acknowledging the commit; data pages are written later and recovered from the log after a crash.

Is ACID the same as the consistency in CAP?

No. ACID consistency means constraints hold; CAP consistency means all replicas agree (linearizability). Same word, different meaning.

Do NoSQL databases have transactions?

Some do (single-document or multi-document), many give atomicity only per record. Check each system rather than assume.

Common slips
  • Reciting the four words without an example.
  • Confusing the C in ACID with the C in CAP.
  • Claiming transactions work across separate databases automatically.
Quick check

Answer in your head first, then open it.

What does atomicity guarantee?

All statements in the transaction take effect, or none do.

What is a foreign key for?

It makes the database refuse a row that refers to a row that does not exist.

Why does PostgreSQL write to a log before the data files?

So a committed change can be recovered after a crash: durability.

Traps to avoid (3)
  • Running statements outside a transaction and assuming they are grouped: each runs on its own unless you begin.
  • Turning off fsync or durability settings in production to "go faster".
  • Enforcing rules only in the application: the next application (or script) will bypass them.

Indexes and query plans: why one query takes 8 ms and another takes 8 s

Must know
Situation

The orders table has half a million rows and "show this customer's orders" suddenly takes a visible fraction of a second. At ten times the data it will take seconds. The cure is almost always an index, and the skill is knowing how to see that, choose the right one, and know what it costs.

You will learn
  • How a B-tree index finds one row among millions
  • Reading EXPLAIN and EXPLAIN ANALYZE
  • Composite indexes and column order
  • What indexes cost on writes and in space
Mental model

Without an index the database must read the whole table to find matching rows (a sequential scan). An index is a separate, sorted structure (in PostgreSQL by default a B-tree) that maps column values to row locations, so a lookup reads three or four pages instead of all of them. EXPLAIN shows the plan the planner chose (which scans, joins and sorts); EXPLAIN ANALYZE also runs the query and shows the actual rows and time. The planner chooses using statistics about the data, so stale statistics (run analyze) lead to bad plans.

A composite index on (a, b) is sorted by a, then by b within each a: it helps filters on a, or on a and b, but not on b alone, and it can return rows already sorted by b for a fixed a. Put equality columns first and the range or sort column last. Indexes are not free: every insert, update of an indexed column and delete must also update every index, and indexes take disk space. They help reads at a cost to writes, so index what real queries need, not every column.

Everyday analogy: The index at the back of a textbook: finding every mention of a word takes seconds, but whoever writes the book must maintain the index with every edit, and a book with an index for every possible word would be mostly index.

The picture
How it works, step by step
  1. Find the slow queryStart from a real query (from the slow query log or a profile), not from guesses about which columns to index.
  2. Ask for the planEXPLAIN ANALYZE shows Seq Scan (reads everything) or Index Scan (uses an index), the rows examined and the time.
  3. Check the estimatesIf the planner's estimated rows differ wildly from the actual rows, run ANALYZE or investigate skew.
  4. Create the index that matches the queryEquality columns first, then the range or sort column. create index ... on orders(customer_id).
  5. Verify, then count the costRe-run EXPLAIN ANALYZE. Then measure insert speed and index size: every index must be maintained.

Composite indexes and the cost on writes 
. ~/pg/rig.sh; pgup
q -c "create index orders_status_created_idx on orders(status, created_at)"
echo "--- filter on both columns (equality first, range second): uses the index"
q -At -c "explain (costs off) select id from orders where status = 'paid' and created_at > now() - interval '2 days'"
echo "--- filter on the second column only: the index cannot help much"
q -At -c "explain (costs off) select id from orders where created_at > now() - interval '2 days'"
echo "--- newest 5 paid orders: the index returns them already sorted"
q -At -c "explain (costs off) select id from orders where status = 'paid' order by created_at desc limit 5"
pgdown

Column order matters. The index on (status, created_at) is sorted by status, then by date within each status. A filter on status and a date range jumps to one status and reads a slice. A filter on only the date cannot use that ordering, so PostgreSQL falls back to a different plan. And "newest five paid orders" needs no sorting at all: the index already stores paid orders in date order, so the first five entries from the end are the answer.

Interview in practice

"This query is slow. How do you find out why, and what do you do?"

The question: The most common database question in interviews and on call. They want a method, not a guess.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • How slow, how often, and how big is the table? A 2 s query run once a day is different from a 50 ms query run 5,000 times a second.
  • Is it slow always, or only sometimes? Always slow suggests a missing index; sometimes slow suggests locks, a bad plan after a statistics change, or load.
2. Think it through (the reasoning, step by step)
  1. Get the actual query and its plan. EXPLAIN (ANALYZE, BUFFERS) on the real query with real parameter values. Look for a Seq Scan on a big table, a large gap between estimated and actual rows, a Sort spilling to disk, or nested loops over many rows.
  2. Diagnose from the plan. Seq Scan with many rows removed means a missing or unusable index. Wrong estimates mean stale statistics (ANALYZE) or correlated columns. A Sort over a huge set means an index could deliver the order.
  3. Choose the index to fit the query. Equality columns first, then range or sort; consider a covering index (include) if the query reads few columns; check functions in the WHERE clause (lower(email)) need a matching expression index.
  4. Weigh the cost. Each index slows writes and uses memory. Measure on a copy with production-like data; create indexes without blocking writers (create index concurrently).
  5. Verify and monitor. Re-run EXPLAIN ANALYZE, compare latency percentiles before and after, and watch that write throughput did not suffer.
3. A strong answer, said out loud

"First I get the real query with real parameters and run EXPLAIN ANALYZE. I look for a sequential scan on a large table, estimates far from actual rows, or a sort that spills. A Seq Scan with almost all rows removed means a missing or unusable index; bad estimates mean I should refresh statistics.

I design the index around the query: equality columns first, then the range or sort column, and I check things like a function applied to a column that would stop the index being used. I weigh the write cost and the space, build it concurrently so writers are not blocked, and then re-run the plan and compare latency percentiles before and after. If a single index is not enough I look at the query itself: select fewer columns, paginate with a keyset instead of a big offset, or cache the result."

4. Follow-ups you should expect
Why might the planner ignore your index?

The query uses a function or type cast on the column, the table is small, the condition matches most rows (a scan is cheaper), or statistics are stale.

What is a covering index?

An index that contains every column the query needs (include (...)), so PostgreSQL answers from the index alone without visiting the table.

What are the downsides of OFFSET pagination?

The database still reads and discards all skipped rows, so deep pages get slower; keyset pagination (where id > last_seen order by id limit n) stays fast.

Common slips
  • Adding an index without looking at the plan.
  • Indexing every column "just in case".
  • Forgetting that a function on a column prevents the plain index from being used.

Transactions and isolation: what concurrent users can see, and break

Must know
Situation

Two customers buy the last ticket at the same moment. Two admin screens edit the same balance. A report runs while data changes underneath it. Isolation decides what each transaction is allowed to see, and your code must be written for the level you actually have.

You will learn
  • Lost updates, non-repeatable reads and how to prevent them
  • Isolation levels: read committed, repeatable read, serializable
  • Row locks (FOR UPDATE) and deadlocks
  • Optimistic versus pessimistic concurrency
Mental model

When transactions run concurrently, a few things can go wrong. A lost update: both read a value, both compute from it, the second write overwrites the first. A non-repeatable read: you read a row twice in one transaction and get different values because someone committed in between. A phantom: a repeated query returns new rows. A dirty read (seeing uncommitted data) is not allowed in PostgreSQL. Isolation levels choose how much of this is prevented: PostgreSQL's default read committed sees newly committed data on every statement; repeatable read gives a stable snapshot for the whole transaction; serializable behaves as if transactions ran one after another (and may abort some with a serialization failure, which the application must retry).

Prevent lost updates by not doing read-modify-write in the application: let the database compute (set balance = balance - 30), or lock the row you read (select ... for update) so other writers wait, or use optimistic concurrency (a version column: update ... where id = 1 and version = 7, and retry if zero rows changed). Locks can create deadlocks (A waits for B while B waits for A); PostgreSQL detects them and aborts one transaction, so applications must retry, and should take locks in a consistent order.

Everyday analogy: Two people editing the same shared document: if each copies it, edits and pastes it back, one person's changes vanish. Locking the document while you edit, or checking nobody changed it since you copied it, are the two ways to stay safe.

Interview in practice

"Two users try to book the last seat at the same moment. How do you make sure only one succeeds?"

The question: A staple of design interviews (tickets, rooms, inventory). They want you to name the race and give at least two concrete fixes with trade-offs.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • One database or several? Is the inventory in a single row or many? A single primary database makes row locks and constraints enough; sharded or multi-service inventory needs more.
  • What happens on conflict: wait, fail or retry? Failing fast with a clear message is usually better for the second buyer than waiting.
2. Think it through (the reasoning, step by step)
  1. Name the race. Both read seats_left = 1, both decide to sell, both decrement: oversell. It is a read-modify-write race.
  2. Fix 1: atomic conditional update. update seats set left = left - 1 where event = 7 and left > 0, then check how many rows were updated: zero means sold out. The database serialises the two updates; no explicit lock or retry loop.
  3. Fix 2: row lock. begin; select ... for update; check; update; commit; The second transaction waits, then sees the new value. Simple but holds the lock while your code runs: keep the transaction short.
  4. Fix 3: optimistic version check or a unique constraint. For individual seats, a unique constraint on (event, seat) makes the second insert fail: the database enforces it, so it holds under any concurrency.
  5. Handle the edges. Retries after serialization failures or deadlocks; a reservation with a short expiry (hold the seat for 10 minutes) with a job to release expired holds; idempotency keys so a retried request does not book twice.
  6. Mention scale. A hot single row (the last seat of a famous concert) is serialised on its lock: that is correct but limits throughput; queue the requests or shard by event.
3. A strong answer, said out loud

"The race is read-modify-write: both requests see one seat left and both sell it. I would let the database make the decision atomically. The simplest way is a conditional update, update seats set left = left - 1 where event_id = 7 and left > 0, then check the number of rows changed: if it is zero, the seat is gone. For individual seats a unique constraint on event and seat does the same job and cannot be bypassed.

Alternatively I would take a row lock with SELECT FOR UPDATE in a short transaction. I would keep transactions short, retry on deadlock or serialization errors, hold a seat with an expiry during payment, and use an idempotency key so a retried request does not book twice. For a very hot event all buyers serialise on one row, which is correct but limits throughput, so I would queue requests or partition by event."

4. Follow-ups you should expect
What if the inventory is in a different service from the database that records the order?

You cannot use one transaction. Reserve first (with an expiry), then confirm after payment, and compensate on failure: a saga with idempotent steps (later modules).

Optimistic or pessimistic locking?

Optimistic works well when conflicts are rare (retry on the rare conflict, no waiting); pessimistic when conflicts are frequent or retries are costly.

Why not just use serializable isolation everywhere?

It is correct but aborts some transactions under contention, which you must retry, and costs throughput; use it where the invariant is complex, not by default.

Common slips
  • Checking availability in the application and then updating separately.
  • Holding a row lock during a slow external call such as payment.
  • Forgetting what happens on a retry: a double booking.

Under the hood: MVCC, the write-ahead log and vacuum

Good to know
Situation

You update one row and PostgreSQL's table gets bigger. You kill the database mid-write and your committed data is still there. A long-running report blocks nobody, yet disk usage creeps up. These are the same two mechanisms at work.

You will learn
  • MVCC: readers and writers that do not block each other
  • Dead rows, bloat and VACUUM
  • The write-ahead log and crash recovery
  • What fsync and replication have to do with durability
Mental model

PostgreSQL uses MVCC (multi-version concurrency control): an UPDATE does not overwrite a row, it writes a new version and marks the old one as deleted by this transaction. Each transaction sees the versions that were visible when its snapshot was taken, so readers do not block writers and writers do not block readers. The cost: old versions (dead tuples) stay in the table until VACUUM removes them. A table with heavy updates and no timely vacuum bloats: it grows and scans slow down. The most common cause of bloat is a long-running transaction that keeps old versions visible.

Durability comes from the write-ahead log (WAL): before a change reaches the data files, a record of it is appended to the log, and at COMMIT the log is flushed to disk. If the server crashes, PostgreSQL replays the log on startup (crash recovery) and the committed data is back. Replicas work the same way: they receive the stream of WAL records and replay it, which is why a replica may lag the primary. fsync is what forces the log to physical disk; turning it off is fast and unsafe against power loss.

Everyday analogy: A ledger written in ink: nothing is erased, a correction is a new line and the old line is struck through. Readers consult the ledger as of a date; a clerk periodically copies it to a clean book without the struck lines (vacuum). The ledger is written before the summaries, so the summaries can always be rebuilt.

The picture
How it works, step by step
  1. An update writes a new row versionThe old version is still there, marked with the id of the transaction that replaced it.
  2. Readers keep seeing what they shouldA transaction that started earlier still sees the old version; new transactions see the new one: no blocking.
  3. Dead versions accumulateWhen no running transaction can see an old version any more, it is garbage, but space is only reused after vacuum.
  4. VACUUM reclaims space for reuseAutovacuum runs in the background; VACUUM marks dead space reusable (the file does not usually shrink).
  5. The WAL makes commits durableThe log is flushed at commit; data files are written lazily; recovery replays the log.

2. Think it through (the reasoning, step by step)

A point where all dirty data pages up to a log position are flushed to the data files, so recovery only has to replay the log after it.

A crash can lose the last few commits (up to a short window) but not corrupt the database: a latency-for-durability trade.

Schema design in practice: normalisation, denormalisation and the N+1 trap

Must know
Situation

You must design the tables for an online store, and interviewers ask: "normalised or denormalised? why?" Meanwhile the real-life problem is usually not the schema itself but how the application queries it: a page that runs 200 small queries instead of one.

You will learn
  • Normalisation: one fact in one place
  • When and how to denormalise deliberately
  • Keys, constraints and data types worth getting right
  • The N+1 query problem and pagination
Mental model

Normalisation means storing each fact once: a customer's name lives in the customers table, and orders point to it. This prevents update anomalies (change the name in one place, not 40,000 order rows) and keeps data consistent. The price is joins at read time. Denormalisation deliberately copies data to avoid joins (a customer_name column on orders, a precomputed order_total, a counter), trading consistency work (you must keep the copy right) for read speed. Normalise first; denormalise a specific, measured hot read, and decide who keeps the copy correct (a trigger, the application, or a periodic job).

The most common application-level performance bug is N+1 queries: one query for a list, then one query per row for its details. With 100 rows that is 101 round trips; each is cheap in the database but expensive in network and connection overhead. Fix it with one join or a single where id in (...) query. For lists, use keyset pagination (where id > :last order by id limit 20) rather than offset, which re-reads all skipped rows. Choose types carefully: use timestamptz for times, numeric for money (never floating point), and a surrogate primary key plus a natural unique constraint where one exists.

Everyday analogy: A contact list where each person's company address is written once on the company's card and people point to it. Changing the address is one edit. A denormalised list writes the address on every person's card: faster to read one card, but now moving offices means editing hundreds of cards.

How it works, step by step
  1. List the entities and their factsCustomers, products, orders, order items: one table each, with only the facts that belong to that entity.
  2. Add keys and constraintsPrimary keys, foreign keys, not null, unique, check: let the database defend the rules.
  3. Write the real queriesThe pages and reports the system must serve: do they need joins across five tables on a hot path?
  4. Measure, then denormalise a specific hot readCopy the one column or counter that removes the join, and choose how it is kept correct.
  5. Avoid N+1 and deep offsetsOne query per page of results, not one per row; keyset pagination for long lists.

"Design the schema for an online store's orders. Normalised or denormalised?"

The question: A schema design question that also tests whether you think about queries, integrity and growth.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • What are the main reads and writes, and their rates? Browsing orders per customer is a read; placing an order is a write. Reads vastly outnumber writes in most stores.
  • Do prices change, and must an old order keep the price it was bought at? Yes in nearly every real store: the order must store the price at purchase time, which is deliberate denormalisation.
2. Think it through (the reasoning, step by step)
  1. Start normalised. customers, products, orders, order_items (order_id, product_id, quantity, unit_price). Each fact once; foreign keys and constraints enforce the relationships.
  2. Identify what must be copied. unit_price and shipping address are copied into the order at purchase time: history must not change when the catalogue changes. That is correct denormalisation: a snapshot, not a duplicate to keep in sync.
  3. Add indexes from the queries. orders(customer_id, created_at desc) for "my orders"; order_items(order_id); a unique constraint on any natural key.
  4. Denormalise measured hot reads only. If the orders list page needs the total and the item count, store total_amount on the order, written in the same transaction as the items, rather than summing every time.
  5. Plan for growth. Money as numeric or integer cents; timestamptz; soft deletes versus archiving; later partitioning orders by date or sharding by customer if one database is not enough.
3. A strong answer, said out loud

"I would start normalised: customers, products, orders and order items, each fact stored once, with primary keys, foreign keys and constraints so the database defends integrity. Then I would deliberately copy what must not change: the unit price and the shipping address are stored on the order as a snapshot, because an old order must keep what the customer actually paid even if the catalogue changes.

I would add indexes for the real queries, for example orders by customer and date, and only denormalise measured hot reads, such as storing the order total in the same transaction that writes the items, so the list page does not aggregate every time. Money goes in as numeric or integer cents, times as timestamptz. If the table outgrows one machine I would partition by date or shard by customer, which is the next module."

4. Follow-ups you should expect
When is denormalisation a bad idea?

When the copy must be kept in sync across many writers, or when the saved join is not measurably the bottleneck: you take on consistency work for no gain.

How would you store money?

As integer minor units (cents) or numeric with a fixed scale, never floating point; keep the currency alongside.

How do you avoid N+1 in an ORM?

Use eager loading or an explicit join, and log query counts per request in tests so a regression is caught.

Common slips
  • Denormalising up front without measuring.
  • Using floats for money.
  • Forgetting that old orders need a price snapshot.

Connections, pooling, locks and finding what is wrong

Must know
Situation

At peak the application starts failing with "too many connections", even though the database CPU is nearly idle. Another day everything hangs because one forgotten transaction holds a lock. Knowing how connections work, and how to ask the database what it is doing, resolves most of these in minutes.

You will learn
  • Why a connection is expensive (a process each)
  • Connection pooling and its limits
  • pg_stat_activity: what is running right now
  • Finding who blocks whom, and slow query settings
Mental model

In PostgreSQL every client connection is served by its own operating system process. A connection takes time to open (authentication, process start) and memory to keep, so a database can hold a few hundred connections comfortably, not tens of thousands. Applications that open a new connection per request waste time; applications with thousands of instances each holding a pool exhaust the server. The fix is a connection pooler (PgBouncer or a built-in pool): many application connections share a small number of real ones. Size the pool to what the database can actually run in parallel (roughly a few times the CPU cores), not to the number of requests.

The database can describe itself: pg_stat_activity lists every connection, its state (active, idle, idle in transaction), the query and how long it has run. idle in transaction is dangerous: a transaction that is open but doing nothing holds locks and an old snapshot. pg_blocking_pids() shows who is blocking whom. Protect yourself with statement_timeout (kill runaway queries), lock_timeout and idle_in_transaction_session_timeout. Slow queries are found with log_min_duration_statement or the pg_stat_statements extension.

Everyday analogy: A restaurant kitchen has a limited number of cooks (CPU). Hiring a new cook for every customer who walks in is slow and wasteful; a host (the pooler) seats many customers and feeds orders to the few cooks. A customer who sits at the pass and does not leave (an idle transaction) blocks everyone behind them.

The picture
How it works, step by step
  1. Each client gets a backend processOpening one costs milliseconds and memory; the server has a hard max_connections limit.
  2. A pooler sits in betweenApplications connect to the pooler; it keeps a small set of real connections and hands them out per transaction.
  3. Look at what is runningpg_stat_activity shows state, duration and the query: the first place to look when something hangs.
  4. Find the blockerpg_blocking_pids(pid) and pg_locks show which session holds the lock others wait for.
  5. Put guard rails onTimeouts for statements, locks and idle transactions turn silent hangs into clear errors.

Interview in practice

"Production is slow and the application reports too many connections. What do you do?"

The question: An on-call style question. They want a calm, ordered diagnosis and a lasting fix, not a restart.

Pause for a minute and say how you would start, then compare with the walkthrough below.

1. Clarify first (what to ask, and why it matters)
  • Is the database CPU high or idle? Are queries slow, or are connections piling up waiting? CPU idle with many connections suggests waiting on locks or on slow clients; CPU high suggests expensive queries.
2. Think it through (the reasoning, step by step)
  1. Look at what the database is doing. select state, wait_event_type, count(*) from pg_stat_activity group by 1,2: many idle in transaction points to application bugs holding transactions open; many waiting on Lock means a blocker; many active with high CPU means heavy queries.
  2. Find the blocker or the heavy queries. pg_blocking_pids for blockers; longest-running queries by now() - query_start; slow query log or pg_stat_statements for the worst offenders.
  3. Relieve the immediate pressure carefully. Cancel the blocking query or terminate its backend (pg_cancel_backend, pg_terminate_backend) rather than restarting everything; shed load at the pooler or application.
  4. Fix the cause. Add a pooler and size pools to the database's capacity; set idle_in_transaction_session_timeout, statement_timeout, lock_timeout; fix the code that holds transactions across slow calls; add the missing index.
  5. Prevent the next one. Alert on connection count, idle in transaction age, lock waits and replication lag; load test connection limits before a launch.
3. A strong answer, said out loud

"I start by asking the database what it is doing: pg_stat_activity grouped by state and wait event. Many sessions idle in transaction usually means the application holds transactions open; many waiting on locks means a blocker that I find with pg_blocking_pids; many active sessions with high CPU means expensive queries, which I find by duration or in the slow query log.

To relieve pressure I cancel or terminate the specific blocking backend instead of restarting, and shed load at the pooler. To fix the cause I put a connection pooler in front, size it to what the database can run in parallel, set idle-in-transaction, statement and lock timeouts, and fix the code or index at fault. Then I alert on connection count, idle-in-transaction age and lock waits so the next one pages us before it becomes an outage."

4. Follow-ups you should expect
Why not just raise max_connections?

Each connection is a process with memory and scheduling overhead; more connections often make throughput worse. Pool instead.

What is the difference between session and transaction pooling?

Session pooling holds a real connection for the whole client session; transaction pooling returns it after each transaction, supporting far more clients but not session features like prepared statements or advisory locks.

What do you do when a replica lags?

Check replay load and long queries on the replica, network, and primary write volume; route lag-sensitive reads to the primary; alert on lag in seconds.

Common slips
  • Restarting the database first.
  • Raising max_connections as the only fix.
  • Having no timeouts, so one stuck session can stall everything.
