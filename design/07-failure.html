Chapter 7 of 9The ShopKart story

When things fail

The network can lose a reply, clocks disagree, and machines die half way through a job. This chapter is about designing so that none of that hurts the customer.

about 20 minutes4 steps6 real experiments3 interview questions

1Tuesday afternoon, 40 double chargesThe story

ShopKart now has queues, replicas and a cache, and most things work. Then a mobile network provider has a slow afternoon. Support starts getting emails: "You charged my card twice." By evening there are 40 of them, each for the same order, each for 50.

The cause is a single line of reasonable code. The shop calls the card network to charge the customer and waits 10 seconds. On a slow afternoon the card network did charge the card, but the reply got lost on the way back. The shop sees only a timeout, assumes failure, and tries again. The second request charges the card a second time.

The shop could not know. A timeout means "I do not know what happened", and that is the heart of distributed systems: parts of a system fail separately, and the others cannot tell a failure from slowness. The rest of this chapter is the toolkit for living with that.

2The idea: a timeout means I do not knowThe idea

In a distributed system, partial failure is normal: one part can fail while the rest keeps going, and you often cannot tell a dead machine from a slow one. So you design every step to be safe to repeat, and every decision to survive a missing answer.

Four ideas cover most of what goes wrong. Repeat safely (idempotency). Never trust clocks to order events. Agree by majority, so a split network cannot make two answers. And do not hold locks across machines: use steps that can be undone. The experiments below show each one in a few lines of code.

3How it works, step by stepHow it works

  1. Make every retry safe, and polite

    A timeout does not mean the request failed. So give each request an idempotency key, a unique id the server remembers, so a repeat returns the first result. Then retry with a growing wait and a little random jitter, and stop retrying a service that is clearly down (a circuit breaker).

  2. Order by cause, not by clock

    Clocks on different machines disagree by milliseconds or more. If you keep "the write with the later timestamp", a machine with a fast clock can make an older write win. Use logical clocks (counters that follow cause and effect) or version vectors, which also show when two writes truly conflicted.

  3. Agree by majority

    If data lives on N copies, a write that reaches W copies and a read that asks R copies always overlap when W plus R is bigger than N, so the read sees the newest write. When the network splits, you must choose: refuse some requests to stay correct (CP), or answer from both sides and merge later (AP). To pick one leader, systems like Raft need votes from a majority, so two leaders can never both win.

  4. Undo with a saga, instead of locking everyone

    A job that touches two services cannot use one database transaction. Two-phase commit asks everyone to prepare, then commit, but if the coordinator dies in between, the rows stay locked (blocked). A saga runs the steps one by one and, if one fails, runs an undo step (a compensation) for each earlier step.

1The double charge, and the fix

The double charge, with real sockets. The server charges the card and then loses the reply. The client sees no answer and, quite reasonably, retries. If each attempt is a new request, the card is charged twice. If the retry carries the same idempotency key, the server recognises it, does not charge again, and returns the stored result: one charge, and the client finally gets its answer. Nothing about the network changed; only the protocol became safe to repeat.

# A real TCP server that charges a card and then loses the FIRST reply (the connection is closed without answering).
import socket, threading, time
charges = []                                  # the effects that really happened
results = {}                                  # idempotency key -> stored result
state = {'drop_next': True}
def handle(conn):
    data = conn.recv(1024).decode().strip(); key, amount = data.split()
    if key in results:                        # a repeat of a request we already did: return the stored answer
        conn.sendall(('OK %s\n' % results[key]).encode()); conn.close(); return
    charges.append((key, int(amount)))        # do the work: charge the card
    results[key] = 'charged %s' % amount
    if state['drop_next']:                    # the reply is lost: close without answering
        state['drop_next'] = False; conn.close(); return
    conn.sendall(('OK %s\n' % results[key]).encode()); conn.close()
srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1); srv.bind(('127.0.0.1', 7301)); srv.listen(8)
def serve():
    while True:
        c, _ = srv.accept(); threading.Thread(target=handle, args=(c,)).start()
threading.Thread(target=serve, daemon=True).start()
def call(key, amount):
    s = socket.create_connection(('127.0.0.1', 7301)); s.settimeout(0.5)
    s.sendall(('%s %d\n' % (key, amount)).encode())
    try:
        r = s.recv(1024).decode().strip()
        return r or 'no answer (connection closed)'
    except socket.timeout:
        return 'timeout'
def attempt(label, keys):
    charges.clear(); results.clear(); state['drop_next'] = True
    for i, k in enumerate(keys, 1):
        print('%s attempt %d: %s' % (label, i, call(k, 50)))
        if i == 1: continue
    print('   cards actually charged: %d time(s) -> %s' % (len(charges), [c[0] for c in charges]))
attempt('naive retry (new key each time)', ['req-1', 'req-2'])
attempt('retry with the SAME idempotency key', ['pay-777', 'pay-777'])

2A fast clock wins the wrong write

Two experiments in one. First, the timestamp problem: node A's clock is 5 seconds fast, so write X, which happened first, is stamped 105, while write Y, which happened two seconds later, is stamped 102. "Last write wins" keeps X and silently discards Y: a real lost update caused only by clock skew. Second, Lamport clocks: each node counts events and, on receiving a message, jumps its counter past the sender's, so every effect has a higher number than its cause even though the nodes never share a clock.

# Three replicas with skewed clocks. Real (true) times: write X at t=100.0 on node A, write Y at t=102.0 on node B.
skew = {'A': +5.0, 'B': 0.0, 'C': -2.0}                     # seconds each node's clock is wrong by
def stamp(node, true_time): return true_time + skew[node]
x = ('X: first write',  stamp('A', 100.0))                  # stamped 105.0
y = ('Y: second write', stamp('B', 102.0))                  # stamped 102.0
print('write X happened first, at true time 100.0 on node A, stamped %.1f' % x[1])
print('write Y happened later,  at true time 102.0 on node B, stamped %.1f' % y[1])
winner = max((x, y), key=lambda w: w[1])
print('last-write-wins by timestamp keeps:', winner[0], '   <- the OLDER write won; Y was silently discarded')

# Lamport clocks: a counter that jumps past anything it has seen
class Node:
    def __init__(self, name): self.name, self.t = name, 0
    def event(self): self.t += 1; return self.t
    def send(self): return self.event()
    def receive(self, t): self.t = max(self.t, t) + 1; return self.t
a, b = Node('A'), Node('B')
e1 = a.event()                     # A does something
m = a.send()                       # A sends a message to B
e2 = b.receive(m)                  # B receives it: B's counter jumps past A's
e3 = b.event()
print('Lamport timestamps: A event=%d, A send=%d, B receive=%d, B next event=%d  (cause < effect always)' % (e1, m, e2, e3))

3How many copies must you ask?

The quorum rule, measured by simulation. With W + R ≤ N a read can miss every replica that has the new value: the stale-read column is large (a third of reads for W=1, R=1). The moment W + R > N the stale column is exactly zero, because the sets must overlap. The fault-tolerance lines show the other side of the dial: W=5, R=1 is consistent but a single failed replica stops all writes; W=3, R=3 is consistent and tolerates two failures for both.

4Electing leaders until the majority is gone

A toy Raft cluster shows the rules without the networking. The first election finds a leader with all five votes and a write commits on five nodes. After the leader crashes, the others elect a new one in a higher term and carry on. With two of five nodes down (three left) there is still a majority and writes commit. With three down (two left) no candidate can reach three votes: there is no leader, writes are refused rather than risking two sides disagreeing. The table at the end is the arithmetic to memorise: 4 nodes tolerate no more failures than 3, and 6 no more than 5, which is why clusters have odd sizes.

import random
rng = random.Random(4)
class Cluster:
    def __init__(self, n):
        self.n = n; self.alive = set(range(n)); self.term = 0; self.leader = None
        self.log, self.committed = [], 0
    def majority(self): return self.n // 2 + 1
    def election(self):
        # each living node picks a random election timeout; the earliest one becomes a candidate
        timeouts = {i: rng.randint(150, 300) for i in self.alive}
        cand = min(timeouts, key=timeouts.get)
        self.term += 1
        votes = len(self.alive)                       # every living node votes once for this term (they all grant the first request)
        if votes >= self.majority():
            self.leader = cand
            return 'term %d: node %d times out first (%d ms), gets %d of %d votes -> LEADER' % (self.term, cand, timeouts[cand], votes, self.n)
        self.leader = None
        return 'term %d: node %d asks for votes, gets only %d of %d (majority is %d) -> NO LEADER, cluster stops accepting writes' % (self.term, cand, votes, self.n, self.majority())
    def write(self, entry):
        if self.leader is None or self.leader not in self.alive: return 'write %r REFUSED: no leader' % entry
        self.log.append(entry); acks = len(self.alive)
        if acks >= self.majority():
            self.committed = len(self.log); return 'write %r COMMITTED (stored on %d of %d nodes)' % (entry, acks, self.n)
        return 'write %r NOT committed: only %d of %d nodes reachable' % (entry, acks, self.n)
c = Cluster(5)
print(c.election()); print(c.write('x=1'))
print('--- the leader (node %d) crashes' % c.leader); c.alive.discard(c.leader); print(c.election()); print(c.write('x=2'))
print('--- a second node crashes (3 of 5 left)'); c.alive.discard(max(c.alive)); print(c.election()); print(c.write('x=3'))
print('--- a third node crashes (2 of 5 left)'); c.alive.discard(max(c.alive)); print(c.election()); print(c.write('x=4'))
print()

5A retry storm, backoff and a breaker

The same outage, three client strategies (a simulation in virtual time, so it repeats exactly). With immediate retries, 200 clients hammer the dead service every 10 ms for two seconds: 40,000 requests, all wasted, all load on a service trying to start (a real server would not survive it, even though in this simulation everyone is served the instant it returns). Exponential backoff with jitter sends about 800 requests in the same window, a fiftieth of the load, but its clients are sleeping through long delays, so the last one is served at 6.5 seconds: backoff trades some extra waiting for protection (cap the delay to tune it). Adding a circuit breaker (open for half a second, then probing) sends only 80 requests during the outage and finishes at 2.5 seconds: the best of both here, because clients wait locally for a short time and come back quickly.

import random
# 200 clients each need ONE answer from a service that is down for the first 2 seconds. Time advances in 10 ms ticks.
def simulate(strategy, seed=7):
    rng = random.Random(seed)
    done, attempts, in_outage = {}, 0, 0
    state = [{'t': 0, 'n': 0} for _ in range(200)]          # per-client: next attempt time and attempts so far
    breaker = {'open_until': -1, 'fails': 0}
    for tick in range(0, 1000):                              # 10 seconds
        now = tick * 10
        for i, s in enumerate(state):
            if i in done or s['t'] > now: continue
            if strategy == 'breaker' and now < breaker['open_until']:      # open: fail fast without calling the service
                s['t'] = now + 200 + rng.randint(0, 200); continue
            attempts += 1; s['n'] += 1
            ok = now >= 2000                                  # the service recovers at 2 s
            if not ok: in_outage += 1
            if ok: done[i] = now; continue
            if strategy == 'breaker':
                breaker['fails'] += 1
                if breaker['fails'] >= 20: breaker['open_until'], breaker['fails'] = now + 500, 0
            if strategy == 'naive':   s['t'] = now + 10                                              # retry immediately, forever
            elif strategy == 'backoff': s['t'] = now + int(100 * 2 ** min(s['n'], 5) * (0.5 + rng.random()))   # exponential + jitter
            else:                     s['t'] = now + int(100 * 2 ** min(s['n'], 5) * (0.5 + rng.random()))
    finish = max(done.values()) if len(done) == 200 else None
    return attempts, in_outage, finish
print('%-22s %10s %22s %16s' % ('strategy', 'requests', 'sent while down', 'all served at'))
for name in ('naive', 'backoff', 'breaker'):
    a, o, f = simulate(name)
    print('%-22s %10d %22d %13s' % ({'naive': 'immediate retry', 'backoff': 'backoff + jitter', 'breaker': 'backoff + breaker'}[name], a, o, ('%.2f s' % (f / 1000)) if f else 'never'))

6A saga that undoes its steps

A saga with no global lock. The happy path runs three local steps in order. In the failing run the card step fails, so the saga walks backwards through the completed steps and runs each compensation: the hotel room and then the seat are released. Each compensation is a new business action, not a database rollback, so the world passes through intermediate states (a seat was briefly held for someone who then did not pay), which is why sagas lack isolation and why real systems show "pending" and use reservations that expire.

# A saga: book flight, book hotel, charge card. Each step has a compensation; failures undo completed steps in reverse.
log = []
def step(name, action, undo, fail=False):
    return dict(name=name, action=action, undo=undo, fail=fail)
def run_saga(steps):
    done = []
    for s in steps:
        if s['fail']:
            log.append('%-14s FAILED' % s['name'])
            for d in reversed(done): log.append('%-14s compensate: %s' % (d['name'], d['undo']))
            return 'saga aborted: all earlier steps compensated'
        log.append('%-14s done:       %s' % (s['name'], s['action'])); done.append(s)
    return 'saga completed'
print(run_saga([step('book flight', 'seat 14C held', 'seat released'), step('book hotel', 'room 302 held', 'room released'), step('charge card', 'authorised 480', 'authorisation voided')]))
print('\n'.join('  ' + l for l in log)); log.clear()
print()
print(run_saga([step('book flight', 'seat 14C held', 'seat released'), step('book hotel', 'room 302 held', 'room released'), step('charge card', 'authorised 480', 'authorisation voided', fail=True)]))
print('\n'.join('  ' + l for l in log))

5How it breaks in productionFailure modes

Retry storms

A service slows down, every client retries at once, and the extra load keeps it down. Fix: wait longer after each failure, add random jitter, cap the attempts, and let a circuit breaker stop calls to a service that is clearly failing.

Clock skew

Two machines disagree on the time, so "latest" is wrong, and an older write overwrites a newer one. Fix: order by version numbers or logical clocks, and treat wall clock time as a hint.

Two leaders

A network split lets two nodes both believe they lead, and each accepts writes. Fix: leadership requires a majority vote and a term number, and old leaders are fenced off.

AP overdraft

On a split network, an always-available bank account lets both sides pay out, and the cash is gone before the sides merge. Fix: for money use a CP choice (refuse without a quorum), and use AP only where a merge can repair things.

Blocked 2PC

The coordinator crashes after the prepare phase, and every bank is stuck holding locks, in doubt. Fix: avoid two-phase commit across services; use a saga with undo steps, and keep step handlers idempotent.

Key reuse mistakes

An idempotency key that is generated fresh on every retry protects nothing, and one that is shared by different orders blocks real payments. Fix: create the key once per intended action and reuse it on every retry of that action.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official company lists.

A very common payments prompt: reported by candidates at large tech companies, not official.

"A payment API call times out. What should the client do? How do you design the API?"

The most common distributed-systems interview opener. The trap is saying "retry" or "fail" without addressing the unknown outcome.

Ask first

  • Is the operation safe to repeat? Who generates the identifier? Charges are not naturally idempotent; the client should generate the key before the first attempt so every retry reuses it.

How to think about it

  1. Name the ambiguity.A timeout is not a failure. Three possibilities: request never arrived, server processed it and the reply was lost, or the server is still working. The client cannot distinguish them.
  2. Make the operation idempotent.Client sends a unique idempotency key (a UUID per intended payment) in a header. Server stores key, request fingerprint and result atomically with the effect (same transaction or unique constraint). A repeat returns the stored result.
  3. Define the client behaviour.Retry with the same key, bounded attempts, exponential backoff with jitter, and a total deadline. After exhausting retries, show "processing" and reconcile by querying the payment status by key rather than guessing.
  4. Handle edge cases on the server.Same key with a different request body is an error; the key's record expires after days; concurrent requests with the same key: the second waits or gets a conflict; do not record the key if the effect failed in a retryable way.
  5. Offer a status endpoint.GET /payments/{key} lets the client (or a reconciliation job) learn the real outcome after an unknown result.
  6. Say what it costs.Storage and lookup of keys, and discipline: every mutating endpoint that might be retried needs the same treatment.

How to say it

A model answer, about two minutes aloud

"A timeout means I do not know: the request may never have arrived, or it may have succeeded with the reply lost. So the client must not assume failure. I would make the payment endpoint idempotent: the client generates a unique idempotency key before the first attempt and sends it with every retry. The server stores the key and the result in the same transaction as the charge, so a repeat returns the stored result instead of charging again.

On the client I retry with the same key, a bounded number of times, with exponential backoff and jitter and an overall deadline; if it is still unknown I show a processing state and look up the payment by key rather than guessing. The server rejects the same key with a different body, expires keys after a few days, and handles two concurrent requests with the same key safely. A status endpoint lets reconciliation find the real outcome. The cost is storing keys and applying the same discipline to every mutating endpoint that can be retried."

Likely follow-ups

Who should generate the idempotency key?

The client, before the first attempt, so that retries reuse it; a server-generated id would be lost with the lost reply.

How long do you keep keys?

Longer than any client could plausibly retry (commonly 24 hours to a few days); then expire to bound storage.

What if the server crashes between charging and recording the key?

That is why the effect and the key must be committed atomically (one transaction); for external effects, use the provider's idempotency key as well.

Common slips

  • Answering "just retry" or "treat it as failed".
  • Generating the key on the server.
  • Storing the key outside the transaction that performs the effect.
A classic distributed systems question: reported by candidates, not official.

"Explain CAP and PACELC with an example. Would you choose CP or AP for a shopping cart? For a bank balance?"

They want you to move past the "pick two" slogan and tie the choice to the data.

Ask first

  • What does a user see when the system is wrong or unavailable, and what does it cost? Overdrawing an account costs money; a briefly stale cart costs little.

How to think about it

  1. State CAP precisely.In the presence of a network partition, a replicated system must choose between consistency (linearizable reads and writes) and availability (every request to a non-failed node gets a response). Partitions are not optional, so "CA" is not a design choice for a distributed system.
  2. Add PACELC.When there is no partition you still trade latency against consistency, for example by waiting for synchronous replicas or a quorum.
  3. Give examples.CP: a single-leader database with synchronous replicas, ZooKeeper, etcd (the minority side stops). AP: Dynamo-style stores, Cassandra with low consistency levels, DNS (answer always, reconcile later).
  4. Decide by the data.Bank balance and inventory at checkout: CP, because incorrect answers are expensive. Shopping cart, likes, session data, product catalogue reads: AP with merging, because availability matters more and conflicts are mergeable.
  5. Mention tunability.Per operation: quorum reads and writes (W + R > N) for the critical paths; weaker settings elsewhere. Most systems are not simply CP or AP.
  6. Say how AP systems reconcile.Read repair, anti-entropy, version vectors, CRDTs, or application-level merge; last-write-wins only where losing a write is acceptable.

How to say it

A model answer, about two minutes aloud

"CAP says that when the network partitions, a replicated system must choose between consistency, meaning reads and writes behave as if there is one up-to-date copy, and availability, meaning every request to a working node gets an answer. Partitions will happen, so it is really a choice between C and A during a partition. PACELC adds that even without a partition there is a trade-off between latency and consistency, for example how many replicas I wait for.

For a bank balance I would choose consistency: a single leader or a quorum, refusing on the minority side, because a wrong answer costs money. For a shopping cart I would choose availability with a merge rule, such as a union of items using version vectors or a CRDT, because being able to add to the cart matters more and conflicts are easy to merge. Most real systems let me tune this per operation with quorum settings, so I would use strong settings on the critical paths and weaker ones elsewhere."

Likely follow-ups

What is the difference between CAP consistency and ACID consistency?

CAP consistency is linearizability (all nodes agree on the latest value); ACID consistency means the database moves between states that satisfy its constraints.

What is eventual consistency?

If updates stop, all replicas converge to the same value; in the meantime reads can return older values.

What is read repair?

When a read finds replicas disagreeing it writes the newest version back to the stale ones, healing divergence lazily.

Common slips

  • "Pick two of three" as the whole answer.
  • Saying we choose CA.
  • Labelling a whole system CP or AP when it is tunable per request.
A frequent follow-up on cross-service consistency: reported by candidates, not official.

"A transfer touches two services with separate databases. How do you keep it atomic?"

The distributed transaction question. They want to hear why 2PC is avoided, how a saga works, and what you give up.

Ask first

  • Do both services support a prepare phase? Is temporary inconsistency acceptable? Independent services usually do not share a transaction manager; a few seconds of "pending" is normally fine.

How to think about it

  1. Say why not a distributed ACID transaction.2PC needs every participant to support it, holds locks across network round trips, blocks if the coordinator fails, and hurts availability and throughput.
  2. Describe the saga.A sequence of local transactions with compensations. Debit account A (local), then credit account B (local); if crediting fails, compensate by refunding A.
  3. Choose orchestration or choreography.Orchestration: a coordinator service holds the saga state and calls each step (clear, easier to monitor, a central component). Choreography: each service listens for events and emits the next (decoupled, harder to follow as it grows).
  4. Make every step safe to repeat.Idempotency keys on every step and compensation; the saga state and messages stored durably with the outbox pattern; retries with backoff; a dead-letter queue for stuck sagas with alerts.
  5. Handle isolation.Intermediate states are visible: use a pending/held status, reserve before commit, order the steps so the hardest to undo comes last, and expire reservations.
  6. Offer the simpler alternative.If both pieces of data can live in one database, use one local transaction and avoid the problem; split services only where the benefit outweighs this cost.

How to say it

A model answer, about two minutes aloud

"I would avoid a distributed ACID transaction: two-phase commit needs every participant to support it, holds locks across network calls and blocks if the coordinator dies, which hurts availability and throughput. Instead I would use a saga: debit account A in its own local transaction, then credit account B in its own; if the credit fails, run a compensation that refunds A.

I would orchestrate it from a service that stores the saga state durably, using the outbox pattern so the state and messages stay consistent. Every step and compensation carries an idempotency key and is retried with backoff, and stuck sagas go to a dead-letter queue with an alert. Because intermediate states are visible I would show a pending status and use reservations that expire. And if the two pieces of data can live in one database, a local transaction is simpler than any of this."

Likely follow-ups

Orchestration or choreography?

Orchestration for processes with many steps and clear ownership (easier to see state and debug); choreography for small, loosely coupled flows, at the risk of an implicit, hard-to-follow workflow.

What if a compensation fails?

Retry it (idempotently) until it succeeds, alert if it cannot; some steps need manual resolution, which is why steps are ordered by reversibility.

How is a saga different from a transaction?

No isolation and no automatic rollback: intermediate states are visible and undoing is a new business action.

Common slips

  • Proposing 2PC between independent microservices.
  • Compensations that are not idempotent.
  • Ignoring the intermediate states users and other services can see.

8Remember thisRecap

The page in 6 lines

  • A timeout means "I do not know": the work may or may not have happened.
  • Idempotency keys make retries safe: the server returns the first result for a repeated key.
  • Retry with growing waits, jitter and a cap, and use a circuit breaker so you stop hammering a failing service.
  • Wall clocks lie: order events with counters or version vectors, not timestamps.
  • With N copies, W plus R greater than N makes reads see the latest write; a split network forces a CP or AP choice.
  • Raft elects one leader by majority; across services prefer a saga with undo steps to two-phase commit.

Check yourself

The payment call times out. What do you do?

Retry with the same idempotency key, so a repeated request cannot charge twice.

Why not order events by timestamp across servers?

Clocks disagree, so an older write can look newer. Use logical clocks or version vectors.

Why prefer a saga to two-phase commit?

2PC holds locks and can block if the coordinator dies; a saga runs steps one by one and undoes them if a later step fails.
