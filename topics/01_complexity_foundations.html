The mindset

Algorithms are only useful if you can judge them. Before any technique, you need three habits: estimate the cost of a solution, use the constraints to decide how fast it must be, and follow a fixed routine so you never freeze on an unfamiliar problem. Nine short concepts cover this.

Ask these questions on every problem, before writing code:

  • How big can n get? → decides the target complexity.
  • What is my brute force and what does it cost? → gives a baseline and exposes the bottleneck.
  • What work is repeated or can be ruled out? → points to hashing, sorting, a window, a prefix or a heap.
  • What are the edge cases and the value ranges? → empty input, duplicates, negatives, overflow.

Reading Big-O: growth rates

🔥 Frequently asked
When to useYou must state, compare or improve the running time of any solution.
Detect it"What is the time complexity?" · "can you do better?" · two solutions to compare · input size n given in the constraints.
Intuition

Big-O answers one question: when the input doubles, how much slower does the code get? O(1) does not care, O(log n) adds one step, O(n) doubles, O(n²) quadruples, O(2ⁿ) squares. We drop constants and lower terms because for large n the fastest-growing term decides everything.

Brute force → optimised

A single loop is O(n). A loop inside a loop is usually O(n²). A loop that halves its range each step is O(log n). Counting loop levels is the fastest way to estimate.

Core idea

Count the number of basic operations as a function of n, keep the dominant term, drop constants. Sequential blocks add (take the max), nested blocks multiply.

How it works
  1. Identify what n is (array length, string length, number of nodes). With two inputs use two variables, e.g. O(n·m).
  2. Count how many times the innermost statement runs.
  3. Sequential steps add: O(n) + O(n²) = O(n²). Nested steps multiply.
  4. Drop constants and lower-order terms: 3n² + 5n + 2 → O(n²).
  5. Decide the case you are quoting: worst, average or amortised.

⏱ Complexity — This page is about the notation itself: see the table above for how fast each class grows.
Traps to avoid
  • Nested loops are not always O(n²): for i... for j in range(i, i+3) is O(n). Count the real iterations.
  • Two different inputs need two variables (O(n·m)), not O(n²).
  • O(n) time with a hidden O(n) inner call (string slice, list.index, s.contains) is really O(n²).
  • Big-O is an upper bound on growth, not an exact count. O(n) code is also "O(n²)", but always quote the tightest bound.
Variants and follow-ups
  • Big-Omega (lower bound) and Big-Theta (tight bound): interviews almost always mean tight Big-O.
  • Best, average and worst case: quicksort is O(n log n) average and O(n²) worst.
When NOT to use

Big-O hides constants. For small n or equal Big-O, constant factors, cache behaviour and library speed decide; say so when it matters.

Constraints → target complexity

🔥 Frequently asked
When to useAt the start of any problem, to decide which approaches are even allowed.
Detect itthe constraints section: "1 ≤ n ≤ 10⁵", "n ≤ 20", "values up to 10⁹".
Intuition

A judge machine does roughly 10⁸ simple operations per second. The constraint on n is a hint from the problem setter about which complexity class they expect. n = 20 is begging for 2ⁿ (subsets); n = 10⁵ rules out n² and wants n log n or n.

Brute force → optimised

Do the arithmetic first: if the brute force costs n² and n = 10⁵, that is 10¹⁰ operations (~100 s): too slow. That arithmetic is how you know you must optimise.

Core idea

Match n to the largest complexity that stays under about 10⁸ operations, then search for an algorithm in that class.

How it works
  1. Read the limit on n (and on the values).
  2. Compute the operation count for the brute force.
  3. If it is under ~10⁸, brute force is acceptable; otherwise look one class lower.
  4. Use the table below to pick the technique family.
Worked trace

constraint → complexity → typical technique

n <= 40           O(2^(n/2))      meet in the middle
n <= 100-500      O(n^3)          Floyd-Warshall, triple loops, interval DP
n <= 5,000        O(n^2)          2D DP, all pairs
n <= 1e5 - 2e5    O(n log n)      sorting, heap, binary search, segment tree
n <= 1e6 - 1e7    O(n)            hashing, two pointers, sliding window, prefix sum
n >= 1e9          O(log n)/O(1)   math, binary search on the answer, formula
⏱ Complexity — Rule of thumb only: ~10⁸ simple operations per second; recursion, hashing and I/O cost more per operation.
Traps to avoid
  • The value range matters too: values up to 10⁹ mean products overflow 32-bit, and a counting array of that size will not fit in memory.
  • Sometimes n is small but the intended answer is exponential, so do not over-optimise a 2ⁿ backtracking with n = 15.
  • If no constraints are given in an interview, ask. It is a sign of maturity, not weakness.
Variants and follow-ups
  • Multiple limits (n and m, or n and k): evaluate each term, e.g. O(n·k) with k ≤ 100 is fine at n = 10⁵.
When NOT to use

This is a heuristic for choosing an approach, never proof that an approach is correct.

Amortised analysis

🧊 Secondary
When to useAn operation is occasionally expensive but cheap on average over a sequence.
Detect it"dynamic array / ArrayList append" · "implement a queue with two stacks" · a while loop inside a for loop where the inner loop's total work is bounded.
Intuition

You pay a monthly gym fee, not per visit. A resize that copies n elements looks costly, but it only happens after n cheap appends, so spreading the cost over those appends gives O(1) each. The total work over many operations is what counts.

Brute force → optimised

Naïve reading: "append can cost O(n), so n appends cost O(n²)". The tight reading: resizes cost 1 + 2 + 4 + … + n < 2n in total, so n appends cost O(n).

Core idea

Total cost of a sequence of m operations divided by m. Use the aggregate method (add up total work) or the potential idea (cheap steps store credit for the expensive one).

How it works
  1. Find the expensive step and how often it can happen.
  2. Show each element can cause that expensive work only a bounded number of times.
  3. Total work ≤ constant × (number of elements), so the average per operation is constant.

Skeleton

dynamic array append (amortised O(1))

void add(int x) {
    if (size == data.length)
        data = Arrays.copyOf(data, 2 * data.length);   // rare O(n) copy
    data[size++] = x;                                  // common O(1) write
}
def add(self, x):
    if self.size == len(self.data):
        self.data.extend([None] * len(self.data))      # rare O(n) copy
    self.data[self.size] = x                           # common O(1) write
    self.size += 1
⏱ Complexity — Dynamic array append: O(1) amortised, O(n) worst single call. Hash table insert: O(1) amortised.
Traps to avoid
  • Amortised is not average-case: it is a guarantee over any sequence of operations, with no randomness involved.
  • A single operation can still be slow, which matters for real-time systems.
  • while inside for is not automatically O(n²). If the inner loop's pointer only moves forward overall (monotonic stack, sliding window), the total is O(n).
Variants and follow-ups
  • Queue via two stacks: each element is moved at most once, so pop is O(1) amortised.
  • Monotonic stack: each element is pushed and popped at most once.
When NOT to use

When you need a hard worst-case bound per operation (use a structure with worst-case guarantees).

Space complexity and the recursion stack

🔥 Frequently asked
When to useYou must state memory use, or you are choosing between recursion and iteration.
Detect it"in place" · "O(1) extra space" · deep recursion · memoisation tables.
Intuition

Time is how long you work; space is how much desk you need. Each recursive call that has not yet returned keeps a stack frame on the desk, so a recursion n levels deep uses O(n) space even if it allocates nothing else.

Brute force → optimised

Naïve Fibonacci recursion has O(2ⁿ) time. Adding a memo makes it O(n) time and O(n) space. Keeping only the last two values makes it O(n) time and O(1) space.

Core idea

Space = extra memory your algorithm allocates beyond the input (auxiliary space), plus recursion depth. Input size is usually not counted unless stated.

How it works
  1. Add up data structures you create (arrays, maps, copies).
  2. Add the maximum depth of the recursion stack.
  3. Take the dominant term.
  4. Ask whether the extra memory can be reused or dropped (rolling array, two variables).

memoised          time O(n)     space O(n)  (table + stack)

Skeleton

Fibonacci: time and space trade-offs

int fibNaive(int n) { return n < 2 ? n : fibNaive(n - 1) + fibNaive(n - 2); }   // O(2^n), O(n) stack

int fibMemo(int n, int[] memo) {                                                  // O(n), O(n)
    if (n < 2) return n;
    if (memo[n] != 0) return memo[n];
    return memo[n] = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
}

int fib(int n) {                                                                  // O(n), O(1)
    int a = 0, b = 1;
    for (int i = 0; i < n; i++) { int t = a + b; a = b; b = t; }
    return a;
}
def fib_naive(n):                       # O(2^n) time, O(n) stack
    return n if n < 2 else fib_naive(n - 1) + fib_naive(n - 2)

from functools import lru_cache
@lru_cache(None)
def fib_memo(n):                        # O(n) time, O(n) space
    return n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

def fib(n):                             # O(n) time, O(1) space
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
⏱ Complexity — Recursion: space = depth of the call stack (n for a linear chain, log n for a balanced halving, tree height for DFS on a tree).
Traps to avoid
  • Recursion depth counts as space: DFS on a skewed tree of 10⁵ nodes is O(n) stack and can overflow in Java or hit Python's default limit (about 1000).
  • Slicing in Python (a[1:]) or substring in Java copies, adding hidden O(n) space and time per call.
  • "In place" means O(1) extra space, not zero: a few variables are fine.
Variants and follow-ups
  • Rolling array: DP over rows only needs the previous row, O(n·m) → O(m).
  • Tail recursion is not optimised in Java or Python: convert to a loop when depth is large.
When NOT to use

When memory is plentiful and clarity matters more, a memo table is fine; just state the cost.

Recurrences and divide and conquer

🧊 Secondary
When to useA function calls itself on smaller inputs and you need its running time.
Detect it"divide and conquer" · merge sort / quicksort · binary search · tree recursion · fast power.
Intuition

Draw the recursion as a tree. Cost per level × number of levels = total. Merge sort: each level does n work and there are log n levels → n log n. Binary search: each level does 1 unit and there are log n levels → log n.

Brute force → optimised

Instead of guessing, write the recurrence: T(n) = a·T(n/b) + f(n): a sub-problems, each of size n/b, plus f(n) work to split and combine.

Core idea

Compare the work at the root f(n) with the work at the leaves n^(log_b a). Whichever dominates decides the answer; if they tie you multiply by log n.

How it works
  1. Write T(n) = a·T(n/b) + O(n^d).
  2. Compute log_b a.
  3. If d < log_b a → O(n^(log_b a)) (leaves dominate).
  4. If d == log_b a → O(n^d · log n) (every level equal).
  5. If d > log_b a → O(n^d) (root dominates).
Worked trace

recurrence cheat sheet

T(n) = T(n/2) + O(1)      O(log n)     binary search
T(n) = T(n/2) + O(n)      O(n)         quick select (average)
T(n) = 2T(n/2) + O(1)     O(n)         visit every node of a balanced tree
T(n) = 2T(n/2) + O(n)     O(n log n)   merge sort
T(n) = T(n-1) + O(1)      O(n)         linear recursion
T(n) = T(n-1) + O(n)      O(n^2)       quicksort worst case, insertion sort
T(n) = 2T(n-1) + O(1)     O(2^n)       naive Fibonacci, subsets
Skeleton

fast power: T(n) = T(n/2) + O(1) = O(log n)

double pow(double x, long n) {
    if (n == 0) return 1;
    if (n < 0) return 1 / pow(x, -n);
    double half = pow(x, n / 2);
    return n % 2 == 0 ? half * half : half * half * x;
}
def power(x, n):
    if n == 0:
        return 1.0
    if n < 0:
        return 1 / power(x, -n)
    half = power(x, n // 2)
    return half * half if n % 2 == 0 else half * half * x
⏱ Complexity — Fast power: O(log n) time and O(log n) stack. Merge sort: O(n log n) time, O(n) space.
Traps to avoid
  • Computing pow(x, n/2) twice instead of once turns O(log n) into O(n).
  • In Java negate n as long: -Integer.MIN_VALUE overflows.
  • Recurrences with unequal splits (T(n−1) + T(1)) are not solved by the master theorem: draw the tree.
Variants and follow-ups
  • Akra–Bazzi / unbalanced splits: sum the levels of the recursion tree instead.
  • Divide and conquer on arrays: max subarray, count inversions, closest pair.
When NOT to use

If sub-problems overlap heavily, use dynamic programming rather than plain divide and conquer.

From brute force to optimal

🔥 Frequently asked
When to useYou have a correct but slow solution and need a faster one.
Detect it"can you optimise it?" · nested loops · repeated scans · recomputing the same value.
Intuition

A slow solution is slow because it repeats work or looks at things it can rule out. Find the bottleneck line, ask "what do I recompute here?" and swap in a structure that remembers or orders the data.

Brute force → optimised

Always start with the obvious brute force. It proves you understand the problem, gives a correct baseline to test against, and its bottleneck shows where to improve.

Core idea

Name the bottleneck, then apply the toolbox: sort, hash, two pointers, sliding window, prefix sum, binary search, heap, memoise, precompute, greedy, bit trick.

How it works
  1. Write the brute force and its complexity.
  2. Underline the slowest part (usually a search or a recomputation).
  3. Ask: can sorting make the search faster? Can a hash map make it O(1)? Can I carry a running value instead of recomputing?
  4. State the new complexity and what you traded (time ↔ space).
  5. Check correctness on the edge cases again.
Worked trace

Two Sum: three levels of the same problem

brute force      two loops over all pairs           O(n^2) time, O(1) space
sort + 2 ptrs    sort, then move l and r inward     O(n log n) time, O(1) space (loses indices)
hash map         remember seen values, look up      O(n) time, O(n) space
Skeleton

// brute force: O(n^2)
for (int i = 0; i < n; i++)
    for (int j = i + 1; j < n; j++)
        if (a[i] + a[j] == target) return new int[]{i, j};

// hash map: O(n)
Map<Integer, Integer> seen = new HashMap<>();
for (int i = 0; i < n; i++) {
    Integer j = seen.get(target - a[i]);
    if (j != null) return new int[]{j, i};
    seen.put(a[i], i);
}
# brute force: O(n^2)
for i in range(len(a)):
    for j in range(i + 1, len(a)):
        if a[i] + a[j] == target:
            return [i, j]

# hash map: O(n)
seen = {}
for i, x in enumerate(a):
    if target - x in seen:
        return [seen[target - x], i]
    seen[x] = i
⏱ Complexity — Most optimisations trade space for time (hash map) or pay O(n log n) once to unlock faster steps (sort).
Traps to avoid
  • Jumping straight to a clever solution without stating the brute force: say it first, even in one sentence.
  • Optimising the wrong line: measure which part dominates.
  • Sorting destroys original indices; if you need them, keep pairs (value, index).
Variants and follow-ups
  • Tool for "best over all subarrays": prefix sum, sliding window, Kadane.
  • Tool for "has x been seen": hash set.
  • Tool for "smallest / largest k": heap or quick select.
  • Tool for "overlapping sub-problems": memoisation → DP.
When NOT to use

When n is tiny, the brute force is the right answer: do not over-engineer.

A repeatable problem-solving method

🔥 Frequently asked
When to useEvery problem, especially one you have not seen before.
Detect ita blank page, an unfamiliar problem, or the urge to start coding immediately.
Intuition

Interviewers grade how you think as much as the final code. A fixed routine keeps you calm, shows structure, and catches misunderstandings before they cost 20 minutes.

Core idea

Follow the same eight steps every time. Talk through each out loud.

How it works
  1. Restate the problem in your own words and confirm the input and output.
  2. Clarify constraints: size of n, value ranges, duplicates, negatives, sorted?, empty input, what to return when no answer.
  3. Examples: work a small example by hand, then an edge case.
  4. Brute force: describe it and its complexity.
  5. Optimise: find the bottleneck, name the pattern, state the new complexity.
  6. Code cleanly with meaningful names, narrating as you go.
  7. Test: dry-run your own example and the edge cases line by line.
  8. Complexity: state time and space, and mention trade-offs or follow-ups.
Worked trace

a short spoken walk-through (Two Sum)

"So given an array and a target I return the indices of two numbers adding to it.
 Can there be duplicates or negatives? Exactly one answer? Is the array sorted?"
"Example [2,7,11,15], target 9 gives [0,1]. Edge case: [3,3], target 6."
"Brute force checks every pair: O(n^2) time, O(1) space."
"The bottleneck is searching for the partner. A hash map gives O(1) lookup:
 for each x look for target-x, then store x. O(n) time, O(n) space."
[code, then dry-run [3,3]] "Complexity O(n)/O(n); if memory mattered and the array
 were sorted I would use two pointers for O(1) space."
⏱ Complexity — Not applicable: this is a process. Time-box: ~5 min understand, ~10 min approach, ~15 min code, ~5 min test.
Traps to avoid
  • Silence: narrate your thinking even when stuck; interviewers can only help if they hear it.
  • Coding before agreeing on the approach.
  • Skipping the dry run: most bugs (off-by-one, empty input) are caught here.
  • Not knowing when to stop optimising: if an interviewer says "good", move on to testing.
Variants and follow-ups
  • Stuck? Try a smaller input, draw it, solve it by hand, then generalise.
  • Still stuck? Ask what pattern family it belongs to: window, pointers, hashing, DP, graph.
  • Hint received? Say thanks and build on it; do not pretend you knew.
When NOT to use

Never skip it; scale it down for easy problems.

Edge cases, overflow and dry-running

🔥 Frequently asked
When to useBefore you say "done" on any solution.
Detect itinteger arithmetic · array indexing · loops with boundaries · "return -1 / empty if…".
Intuition

Most wrong answers are right algorithms that fail on the boundary: nothing in the input, one thing, everything the same, the biggest number. A thirty-second checklist and a line-by-line dry run catch nearly all of them.

Core idea

Run the code by hand on small inputs, tracking variables in a table, and always include the checklist cases.

How it works
  1. Empty input / n = 0.
  2. Single element, and exactly two elements.
  3. All elements equal; all distinct.
  4. Already sorted, reverse sorted.
  5. Negative numbers, zeros, very large values (overflow).
  6. Target at the first or last position, or absent.
  7. Dry-run: write each variable per iteration in a small table.

Skeleton

integer overflow in Java (Python ints do not overflow)

int mid = (lo + hi) / 2;            // BUG: lo + hi can overflow int
int mid = lo + (hi - lo) / 2;        // safe

long prod = (long) a * b;            // widen BEFORE multiplying
int safe = Math.addExact(x, y);      // throws instead of wrapping

// reverse integer: check before multiplying by 10
if (rev > Integer.MAX_VALUE / 10 || rev < Integer.MIN_VALUE / 10) return 0;
# Python ints are arbitrary precision: no overflow,
# but if the problem says 32-bit you must check manually:
if not -2**31 <= result <= 2**31 - 1:
    return 0

mid = lo + (hi - lo) // 2     # same habit; // is floor division
# note: -7 // 2 == -4 in Python but -7 / 2 == -3 in Java
⏱ Complexity — Not applicable: a correctness habit.
Traps to avoid
  • Java integer division truncates toward zero; Python // floors. They differ for negatives.
  • Math.abs(Integer.MIN_VALUE) is still negative.
  • Using <= vs < in loop bounds; check the first and last iteration by hand.
  • Mutating a collection while iterating it.
  • Returning the wrong value type for "not found" (−1 vs empty list vs null).
Variants and follow-ups
  • Also test the largest allowed n for time and the largest values for overflow.
  • Random testing: compare the optimised solution with the brute force on small random inputs.
When NOT to use

There is no case where skipping testing is wise.

Hidden costs in Java and Python

🔥 Frequently asked
When to useAny time a loop contains a library call: slicing, contains, remove(0), += on strings.
Detect itstring building in a loop · list.remove / insert(0, …) · x in list · substring inside loops.
Intuition

Complexity analysis counts the cost of every line, and library calls are lines. s += c looks like one step, but strings are immutable, so each += copies the whole string: n of them cost O(n²).

Core idea

Memorise the cost of the handful of operations you use constantly, and choose the structure whose fast operations match what your loop does.

How it works
  1. List the library calls inside your loops.
  2. Look each one up in the table below.
  3. Replace expensive ones: StringBuilder / ''.join, ArrayDeque / deque, HashSet / set, indexes instead of slices.

Skeleton

building a string in a loop

// O(n^2): copies the string every iteration
String s = "";
for (char c : chars) s += c;

// O(n): one growing buffer
StringBuilder sb = new StringBuilder();
for (char c : chars) sb.append(c);
String s2 = sb.toString();
# can be O(n^2): may copy each time
s = ""
for c in chars:
    s += c

# O(n): collect then join once
s2 = "".join(chars)
⏱ Complexity — Always quote the cost including library calls: a "loop of n with a substring" is O(n²), not O(n).
Traps to avoid
  • Stack in Java is synchronised and legacy: use ArrayDeque.
  • list.pop(0) on a Python list is O(n): use deque.popleft().
  • in on a list inside a loop is O(n²) overall; convert to a set first.
  • Passing slices to recursive calls copies each time: pass indices instead.
Variants and follow-ups
  • Immutable vs mutable: strings are immutable in both languages; convert to a char array or list to edit in place.
  • Sorting cost depends on comparator cost: sorting n strings of length k is O(n·k log n).
When NOT to use

Micro-optimising when n is small: clarity first, then fix the costly call if the complexity requires it.

Rule of thumb

before writing any code, compute n × brute-force cost. If it is over ~10⁸, you have just been told that the interviewer expects a better pattern.

Self-test

Answer in your head first, then click to reveal.

A loop runs for i in 0..n: for j in i..n. What is the complexity and why?

O(n²). The inner loop runs n−i times, so the total is n + (n−1) + … + 1 = n(n+1)/2, which is O(n²).

n = 10⁵. Can an O(n²) solution pass? What should you aim for?

No: n² = 10¹⁰ operations, about 100 seconds at 10⁸ per second. Aim for O(n log n) or O(n).

Why is appending to a dynamic array O(1) amortised even though resizing is O(n)?

Resizes happen at sizes 1, 2, 4, 8, …, so the total copy cost is less than 2n over n appends, an average of under 2 units per append.

What is the space complexity of a recursive DFS on a path-shaped tree with n nodes?

O(n): the recursion stack holds n frames at the deepest point.

Solve T(n) = 2T(n/2) + O(n).

a = 2, b = 2, d = 1, log_b a = 1 = d, so every level costs the same: O(n log n). This is merge sort.

Why can s += c in a loop be O(n²)?

Strings are immutable, so each concatenation copies the existing string; the copies total 1 + 2 + … + n.

What is the first thing to say after reading a new problem?

Restate it, then clarify constraints, inputs and edge cases before proposing any approach.

Why can mid = (lo + hi) / 2 be a bug in Java?

lo + hi can exceed Integer.MAX_VALUE and wrap negative. Use lo + (hi − lo) / 2.
