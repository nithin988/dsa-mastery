Why did my program do that?

Why the same program can behave differently on two machines, and how to see what a program is really doing: processes, system calls, memory, open files and exit codes.

about 20 minutes4 steps4 real experiments3 interview questions

112:40 a.m., the export that was emptyThe story

It is your second week at ShopKart. Finance needs a file of the day's orders every night. Your colleague Priya wrote a small script, export_orders.sh, and it works perfectly on her laptop. She set it up on the server before going home and said, "It just runs."

At 12:40 a.m. she messages from bed: the file that reached finance is empty, 0 bytes, yet the job reports success. On her laptop the same script writes thousands of rows. On the server it prints nothing at all. Nobody can say why one program behaves in two ways.

You could guess for hours. Instead you ask a better question: what did the program actually ask the machine to do? By 12:58 you have the answer. It looked for one file, did not find it, and carried on, because nobody checked the number it left behind when it failed.

2The idea: a program is a conversation with the kernelThe idea

A process is a program that is running. It has its own memory and a list of open files, it asks the kernel (the core of the operating system) for everything else through system calls, and when it ends it leaves an exit code.

This is the model behind every Linux tool in the rest of the course. Pipes connect the open files of two processes. Permissions are checked by the kernel on each system call. Containers are processes with a restricted view of the machine. Once you can see the conversation, "it works on my machine" becomes a question you can answer.

3How it works, step by stepHow it works

  1. The shell starts a process: fork, then exec

    To run a command, the shell first makes a copy of itself (fork). The copy then swaps itself for the program you asked for (exec). The new process gets its own number, the PID.

  2. Every process gets its own private memory

    A process thinks it owns all the memory. In truth the kernel gives each process its own address space, a private map to real memory, so two processes can use the same address without ever touching each other's data.

  3. A program asks the kernel for everything

    Programs cannot touch disks or networks directly. They make system calls, such as open, read and write, and the kernel does the work. When a program opens a file, the kernel answers with a small number called a file descriptor.

  4. When it ends, it leaves an exit code

    Every process finishes with a number. 0 means success and anything from 1 to 255 means failure. The parent reads it ($? in the shell), but only if someone asks. A script that never checks will carry on as if all is well.

4See it for realReal experiments

Every output below was recorded from a real run on Debian Linux as an ordinary user. Read it line by line.

Four short experiments, all ordinary commands you can type yourself. First: who starts whom. Then: what a failure looks like as a number. Then: the exact call that failed. Finally: the three files every process starts with.

1Who started this program? Parent and child

A child bash prints its own PID and its parent's. The parent PID equals the PID of the shell you typed into.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
child PID: 234, parent PID: 228
this shell is PID 228
Read it line by line
In the outputWhat it means
child PID: 234, parent PID: 228The command ran as a new process, number 234. Its parent, 228, is the shell you typed it into.
this shell is PID 228The same number again: the child really is a child of this shell.
Show the command and the full explanation
mkdir -p ~/s01 && cd ~/s01 && bash -c 'echo "child PID: $$, parent PID: $PPID"'; echo "this shell is PID $$"

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

2How a program says it failed: the exit code

The child ends with status 3 and wait hands it to the shell as $?. By convention 0 is success and anything else is failure.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
exit status: 3
Read it line by line
In the outputWhat it means
exit status: 3The command ended with code 3. The shell keeps the last code in $?. Zero would have meant success; anything else means something went wrong.
Show the command and the full explanation
bash -c 'exit 3'; echo "exit status: $?"

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

3The exact call that failed: a missing file

A failing call shows the error name: ENOENT means "no such file or directory". This is how you find the exact path a program wanted.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
openat(AT_FDCWD, "nothere.txt", O_RDONLY) = -1 ENOENT (No such file or directory)
cat: nothere.txt: No such file or directory
+++ exited with 1 +++
Read it line by line
In the outputWhat it means
openat(AT_FDCWD, "nothere.txt", O_RDONLY) = -1 ENOENTThe program asked the kernel to open nothere.txt. The kernel answered -1 with the reason ENOENT, which means no such file.
cat: nothere.txt: No such file or directoryThe program turns that answer into a message for you.
+++ exited with 1 +++And it leaves exit code 1 behind. A script that ignores this number is how an empty export reaches finance.
Show the command and the full explanation
strace -e trace=openat cat nothere.txt 2>&1 | tail -3

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

4Every process starts with three open files

Every process lists its descriptors in /proc/PID/fd. 0, 1 and 2 are already open. In your terminal they point at something like /dev/pts/0; here the output is captured, so they are pipes.

Real output · Debian GNU/Linux 13 (trixie), ordinary user
fd 0 -> pipe:[17755]
fd 1 -> pipe:[17756]
fd 2 -> pipe:[17756]
Read it line by line
In the outputWhat it means
fd 0 ->Descriptor 0 is standard input: where the program reads from.
fd 1 ->Descriptor 1 is standard output: where it prints.
fd 2 ->Descriptor 2 is standard error: where it reports problems. Here 1 and 2 point to the same place (the same pipe number), but they are separate descriptors.
Show the command and the full explanation
for n in 0 1 2; do echo "fd $n -> $(readlink /proc/$$/fd/$n)"; done

The same code runs on any Debian or Ubuntu machine as an ordinary user; nothing needs root.

5How it breaks in productionFailure modes

Ignoring the exit code

A script keeps going after a command fails, so a failed step is hidden behind a later step that succeeds. Fix: turn on set -e (stop on error) or check $?, and make the script itself exit with a non-zero code on failure.

The working directory is different

A relative path like orders.csv means "in the folder I was started from". A scheduled job often starts somewhere else, and the file is not there. Fix: use absolute paths or cd to a known folder first.

A different environment

The shell passes environment variables (such as PATH) to each process. A server, cron or a container has different ones from your laptop, so a command is not found or behaves differently. Fix: set what you need inside the script and print it when debugging.

Out of memory

A process asks for more memory than the machine has, and the kernel's OOM killer ends it, usually with exit code 137 (128 plus signal 9). Fix: find what grew, and set a memory limit and an alert before it happens.

Too many open files

Each process may hold only so many file descriptors, and sockets count too. On the lab machine the limit is 10240; many systems default to 1024 (an assumption, check yours with ulimit -n). Fix: close files you no longer need and raise the limit deliberately.

Zombies

When a process ends, its exit code waits to be collected by its parent. If the parent never does, the finished process lingers as a zombie. Fix: make the parent wait for its children, or restart the parent.

7In the interviewTop-company questions

Say your answer aloud first, then compare with the model answer. These are the shapes of question candidates report, not official lists from any company.

A very common Linux and systems prompt: reported by candidates, not official.

What happens when you type `ls` in a shell and press Enter?

Reported by candidates as a common opening question at large tech companies; not official.

How to say it

A model answer, about two minutes aloud

The shell parses the line, finds ls on the PATH, and calls fork to create a child.

The child calls exec to replace itself with /usr/bin/ls; the shell calls wait and sleeps.

ls makes system calls (open the directory, read entries, write to stdout), exits with status 0, and the shell wakes and shows the prompt.

Likely follow-ups

• Why is cd different?

• What changes when you add &?

• What does a pipe add to this picture?

Common slips

  • Saying the shell "contains" ls.
  • Forgetting fork and exec are separate steps.
Often asked as a follow-up to the question above: reported by candidates, not official.

What is a system call? Give examples and explain why they exist.

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

The controlled way a user-mode program asks the kernel to do privileged work: open, read, write, fork, execve, mmap.

They exist so the kernel can enforce permissions and share hardware safely.

strace shows them for any program.

Likely follow-ups

• What is the cost of a system call?

• What is the difference between a library call and a system call?

Common slips

  • Calling printf a system call (it uses write).
A frequent question for operations and SRE roles: reported by candidates, not official.

What is a file descriptor? What does "everything is a file" mean?

A common interview question on this topic.

How to say it

A model answer, about two minutes aloud

A small integer the kernel returns for an open resource; later calls refer to it.

0, 1, 2 are stdin, stdout, stderr; files, pipes, sockets and devices all use the same read/write/close.

Redirection is the shell rewiring a descriptor before starting the program.

Likely follow-ups

• What happens if you delete a file that a process has open?

• What does "Too many open files" mean and how do you debug it?

Common slips

  • Thinking a descriptor is a file name.

8Remember thisRecap

The page in 6 lines

  • A process is a running program: its own memory, its own open files, an exit code at the end.
  • The shell starts a command by fork (copy itself) then exec (become the new program).
  • Programs never touch hardware: they make system calls and the kernel answers.
  • Every process starts with three open files: 0 input, 1 output, 2 errors.
  • Exit code 0 is success and anything else is failure; a script must check it or pass it on.
  • When behaviour differs between machines, compare the environment, the working directory and the exact failing call.

Check yourself

What is the difference between a program and a process?

A program is a file on disk. A process is that program running, with its own memory, open files and PID.

What does exit code 0 mean, and how do you read it in the shell?

It means success. Any other number means failure. The shell stores the last code in $?.

What does ENOENT in an strace line tell you?

The kernel could not find the file or folder the program asked for: 'no such file or directory'.
